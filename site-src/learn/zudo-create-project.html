Install the ZudoJS command-line tool

So far you have installed single ZudoJS packages by hand. A real project needs a dozen of them, a server, a folder layout and scripts. The ZudoJS CLI (command-line interface) sets all of that up with one command.

It is published on npm as zudojs-cli, and the command it gives you is called zudojs. The -g flag installs it globally, so the command works in any folder:

$ npm install -g zudojs-cli added 12 packages in 3m $ zudojs --version 2.0.1

The install time depends on your connection. Your version can be higher than 2.0.1.

On macOS and Linux, a global install can fail with a permission error, depending on how Node.js was installed. Don't fix it with sudo. Skip the global install and put npx in front instead: npx zudojs-cli --version prints the same version, and npx zudojs-cli create … works for every command in this lesson. There is no npm package called zudo or zudojs. The CLI is zudojs-cli, and every framework package is named @zudojs/something.

Create the project

Go to the folder where you keep your projects, not inside ts-tasks, and run:

$ zudojs create task-api --package-manager npm --capabilities "" ◇ Project structure created ◇ Backend project generated (33 files) added 71 packages, and audited 72 packages in 2m 16 packages are looking for funding run `npm fund` for details 2 moderate severity vulnerabilities To address all issues (including breaking changes), run: npm audit fix --force Run `npm audit` for details. npm warn install-scripts 1 package has install scripts not yet covered by allowScripts: npm warn install-scripts esbuild@0.28.2 (postinstall: node install.js) npm warn install-scripts npm warn install-scripts Run `npm install-scripts ls` to review, or `npm install-scripts approve ` to allow. │ ◆ Dependencies installed ◇ Project validated ◇ Git repository initialized │ ◇ Next steps ──╮ │ │ │ cd task-api │ │ npm run dev │ │ │ ├───────────────╯ │ └ Project created successfully.

What the options mean:

  • task-api is the name of the project and of the folder it creates.
  • --package-manager npm uses npm, which you already have. The CLI's default is pnpm, a faster alternative you would have to install first.
  • --capabilities "" starts with no optional extras. You will add them one at a time as the course needs them, with zudojs add.
Windows PowerShell 5 does not pass an empty "" on to programs. Leave --capabilities "" out. When the CLI asks which capabilities to add, press Enter without selecting any.

If you leave the options out, the CLI asks you each question in turn instead. The flags simply answer them in advance. The next section shows the questions.

Two things in that output are worth understanding, and neither is a problem:

  • The esbuild warning is the same one you met in Why TypeScript exists. It is harmless.
  • "2 moderate severity vulnerabilities" comes from npm audit, which checks installed packages against a list of known security issues. Run npm audit and you will see both are in Vitest, the test runner, which only runs on your own computer while you develop. Do not run npm audit fix --force: as the message says, it makes breaking changes, and here it would jump Vitest two major versions.

Here it ran in a practice folder, with --no-install and --no-git so it only writes files. After typing my-api and pressing Enter for every question, the terminal shows:

Pressing Enter everywhere chose pnpm, which is why this project has one more file and says pnpm run dev. For this course, pick npm with the arrow keys, or use the flags from the previous section. You can delete the practice my-api folder. If you press Ctrl + C during the questions, the CLI prints Operation cancelled. and creates nothing.

Start the server

$ cd task-api $ npm run dev > task-api@0.1.0 dev > tsx watch src/server.ts { timestamp: '2026-09-23T12:22:33.727Z', level: 'info', message: '2026-09-23T12:22:33.727Z [INFO] [app-service] app service initialized', logger: 'app-service', metadata: {} } … Listening on port 3000

npm run dev runs the dev script from package.json: tsx watch src/server.ts. That is tsx from Why TypeScript exists, plus watch, which restarts the server every time you save a file.

The blocks before the last line are log entries, one per step as the application starts. Each has a time, a level (info) and which part of the app wrote it. The last line means it is ready: a backend is now listening on your computer, on port 3000. A port is a numbered door on your computer. Each program that listens for network requests uses a different one.

Leave it running. Open your web browser and go to http://localhost:3000/health. localhost means "this computer". You will see:

{"status":"ok","timestamp":"2026-09-23T12:22:38.526Z"}

You can do the same from a second terminal window. curl sends a request and prints the answer. -i also prints the status line and headers:

$ curl -i http://localhost:3000/health HTTP/1.1 200 OK content-type: application/json content-length: 54 Date: Wed, 23 Sep 2026 12:22:38 GMT Connection: keep-alive Keep-Alive: timeout=5 {"status":"ok","timestamp":"2026-09-23T12:22:38.526Z"} $ curl -i http://localhost:3000/tasks HTTP/1.1 404 Not Found content-type: application/json content-length: 21 Date: Wed, 23 Sep 2026 12:22:40 GMT Connection: keep-alive Keep-Alive: timeout=5 {"error":"Not Found"}

This is the pattern from Your first Zudo code, now real: a status code (200, 404) and a JSON body. /tasks does not exist yet, so the server answers 404. Building it is the next part of the course.

On Windows PowerShell, type curl.exe instead of curl. Plain curl there is a different command with different output.

The times and dates you see will be your own.

To stop the server, click into its terminal and press Ctrl + C.

What the CLI generated

Open the task-api folder in your editor. These are the files that matter today:

PathWhat it is
package.jsonThe project's name, its 12 @zudojs dependencies, and its scripts: dev, build, start, typecheck, test.
tsconfig.jsonTypeScript settings, like the one you wrote in Why TypeScript exists, with strict on.
src/server.tsStarts the application, then the HTTP server. Right now it only knows /health; every other path gets 404.
src/app.tsBuilds the runtime: the part of ZudoJS that starts and stops every piece of your app in the right order. It wires in a logger, a dependency container and an event bus. Later lessons explain each one.
src/modules/app.module.tsThe first module, a self-contained piece of the app that the runtime starts and stops. Those were the "app module initialized" log entries.
src/controllers/health.controller.tsThe code that answers /health. A controller turns a request into a response.
src/services/, src/repositories/, src/validators/, …Folders for each kind of code, most of them empty for now. Your TaskService from Your first Zudo code will go in services/, and its schema in validators/.
tests/app.test.tsOne placeholder test, so npm test works from day one.
.env.exampleThe settings the app reads from the environment, such as PORT. Never put real passwords in files you share.
.zudojs/manifest.jsonWhat the CLI knows about the project, so later commands like zudojs generate put files in the right place. Don't edit it by hand.

Here is the health controller. It is an ordinary class, like the ones you wrote in Classes in TypeScript:

export class HealthController { check() { return { status: "ok", timestamp: new Date().toISOString() }; } }

And here is the part of src/server.ts that decides which code answers which request. It is shortened; open the file to see all of it:

const server = createHttpServer({ adapter: createNodeHttpAdapter({ host: process.env["HOST"] ?? "0.0.0.0", port: resolvePort(), }), handler: (request: HttpRequestContext) => { if (request.path === "/health") { if (runtime.state !== "running") { return createResponseContext({ status: 503 }).json({ status: "unavailable" }); } return new HealthController().check(); } return createResponseContext({ status: 404 }).json({ error: "Not Found" }); }, });

Every request reaches handler. If the path is /health and the app is running, the controller answers. Otherwise the server sends a 404 with a JSON body. The next part of the course replaces that if with a proper router that serves /tasks.

generate with --dry-run tells you what it would write, and writes nothing. It is a safe way to learn where each kind of file belongs:

$ zudojs generate service task --dry-run Detected architecture: monolith Dry run: 4 files would be generated (nothing written): - src/services/task/task.service.ts - src/services/task/index.ts - src/services/task/commands/index.ts - src/services/task/queries/index.ts $ zudojs generate controller task --dry-run Detected architecture: monolith Dry run: 2 files would be generated (nothing written): - src/controllers/task.controller.ts - src/controllers/index.ts

The CLI read .zudojs/manifest.json, saw a monolith, and chose the folders to match. In a modular monolith the same command would place the files inside a module. Without --dry-run, it writes the new file and adds an export line for it to the folder's index.ts.

Generated files are a starting point, so run npm run typecheck after zudojs generate. With zudojs-cli 2.0.1, a generated controller fails the type check in a new project (Type 'unknown' is not assignable to type 'LogValue'), and command and query import @zudojs/cqrs, which a project created without the CQRS capability does not have. This has been reported. Fix what tsc reports, or write those files by hand as the course does.

add installs a feature's package right away. You will run this one for real in the data part of the course; this is what it prints:

$ zudojs add database Adding feature: database Packages: @zudojs/database Updated package.json Installing dependencies with npm... added 3 packages, and audited 75 packages in 12s … Feature "database" added successfully. Import from "@zudojs/database" in your modules.

It added @zudojs/database to package.json and recorded "database" in the project's features. It does not write any database code for you: that is your job, with the package's help.

Build and run for production

npm run dev is for your own computer: tsx compiles TypeScript on the fly and restarts on every save. A production server should not do that work. There, you compile once to plain JavaScript, and Node.js runs the result. That step is called the build:

$ npm run build > task-api@0.1.0 build > tsc

No output means no errors. build is plain tsc: this project's tsconfig.json has "outDir": "dist" and "rootDir": "src", so every src/ file now has a JavaScript twin in dist/, such as dist/server.js for src/server.ts. zudojs build does the same through the CLI:

$ zudojs build Building project at: ~/task-api > task-api@0.1.0 build > tsc Build completed successfully.

Now start the compiled app. The start script is node dist/server.js: no tsx, no watching. NODE_ENV=production is the usual way to tell a Node.js app it runs in production:

$ NODE_ENV=production npm start > task-api@0.1.0 start > node dist/server.js { timestamp: '2026-09-23T14:11:40.929Z', level: 'info', message: '2026-09-23T14:11:40.929Z [INFO] [app-service] app service initialized', logger: 'app-service', metadata: {} } … { timestamp: '2026-09-23T14:11:40.947Z', level: 'info', message: '2026-09-23T14:11:40.947Z [INFO] [task-api] Runtime is ready. runtimeId=rt_6525263a41ad4464bcc4df9ae8edccf7 environment=production', logger: 'task-api', metadata: { runtimeId: 'rt_6525263a41ad4464bcc4df9ae8edccf7', environment: 'production' } } Listening on port 3000

The runtime noticed environment=production. curl http://localhost:3000/health answers exactly as before. Now press Ctrl + C and read what the app prints on its way out:

^C{ timestamp: '2026-09-23T14:11:41.499Z', level: 'info', message: '2026-09-23T14:11:41.499Z [INFO] [task-api] Initiating graceful shutdown. timeoutMs=30000', logger: 'task-api', metadata: { timeoutMs: 30000 } } { timestamp: '2026-09-23T14:11:41.500Z', level: 'info', message: '2026-09-23T14:11:41.500Z [INFO] [task-api] app module stopped', logger: 'task-api', metadata: {} } … { timestamp: '2026-09-23T14:11:41.503Z', level: 'info', message: '2026-09-23T14:11:41.503Z [INFO] [task-api] Graceful shutdown complete.', logger: 'task-api', metadata: {} } { timestamp: '2026-09-23T14:11:41.503Z', level: 'info', message: '2026-09-23T14:11:41.503Z [INFO] [task-api] Runtime stopped. runtimeId=rt_6525263a41ad4464bcc4df9ae8edccf7', logger: 'task-api', metadata: { runtimeId: 'rt_6525263a41ad4464bcc4df9ae8edccf7' } }

This is the graceful shutdown the BookStore never had (the honest review listed it). The server stopped taking requests, then the runtime stopped every module in reverse order, with a 30-second limit in case something hangs. A hosting platform sends SIGTERM instead of Ctrl + C when it replaces your app, and src/server.ts handles both the same way.

Each log entry shows the time and level twice: once as fields, and again inside message. That repetition comes from the logger package in this version, not from your code. Later lessons show how to configure logging. On Windows PowerShell, set the variable first with $env:NODE_ENV = "production", then run npm start.

The generated .gitignore already lists dist/: build output is made from the source, so it never belongs in git. The deployment lesson runs exactly these two steps, npm run build and npm start, inside a Docker image.

Practice

With npm run dev running, open src/controllers/health.controller.ts and add a service: "task-api" property to the object it returns. Save the file. Watch the terminal restart the server, then reload http://localhost:3000/health.

export class HealthController { check() { return { status: "ok", service: "task-api", timestamp: new Date().toISOString() }; } }

The browser now shows {"status":"ok","service":"task-api","timestamp":"…"}. You changed a running backend without restarting it by hand, because tsx watch did it for you.

Without writing anything, find out where zudojs generate would put a repository called task.

$ zudojs generate repository task --dry-run Detected architecture: monolith Dry run: 2 files would be generated (nothing written): - src/repositories/task.repository.ts - src/repositories/index.ts

It would create src/repositories/task.repository.ts and add an export to src/repositories/index.ts. --dry-run wrote nothing.

You changed src/controllers/health.controller.ts, then ran npm start. The old answer comes back. Why, and what is the fix?

npm start runs the compiled dist/server.js, which was built before your change. Run npm run build again, then npm start. While you are developing, use npm run dev instead: it runs the TypeScript in src/ directly and restarts on every save.

Recap

  • npm install -g zudojs-cli gives you the zudojs command. npx zudojs-cli works without a global install.
  • zudojs create task-api --package-manager npm creates a project with a server, a runtime and scripts, installs its packages and sets up git.
  • npm run dev starts the server and restarts it when you save. /health answers 200; everything else is 404 for now.
  • Run zudojs create with no options to answer its questions interactively instead of passing flags.
  • npm run typecheck, npm test and zudojs doctor keep the project healthy.
  • The CLI has seven commands: create, dev, build, generate, add, doctor and info. generate --dry-run shows what would be written.
  • For production, npm run build compiles src/ into dist/, and NODE_ENV=production npm start runs it with plain Node.js. Ctrl + C or SIGTERM shuts it down gracefully.
