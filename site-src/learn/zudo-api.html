One piece of logic, many doors

In the Task API, "create a task" lives inside an HTTP route. In the RPC lesson you wrote it a second time as an RPC procedure. A nightly import job would need it a third time. Three copies drift apart: one of them forgets the title check, another returns a different error.

@zudojs/api fixes that with an operation: one named piece of logic with a declared input, a declared output and a handler. An executor runs operations, a registry finds them by name, and interceptors wrap every call with shared rules such as logging or sign-in checks.

A transport is the door a call comes through: an HTTP request, an RPC frame, a queue job. Each transport only translates. The rules live in the operation.

In your Task API folder, add the package. This lesson also uses @zudojs/queue; the other packages come from the RPC lesson. Every example is a .ts file that you run with npx tsx file.ts.

Define an operation

defineOperation(options) takes a name, an optional input and output schema from @zudojs/schema, and a handler(input, context). It checks the definition at once, so a bad name or timeout fails when the program starts, not on the first request.

import { APIConflictError, defineOperation } from "@zudojs/api"; import { schema } from "@zudojs/schema"; import type { Infer } from "@zudojs/schema"; const NewTaskSchema = schema.object({ title: schema.string().trim().min(3).max(100) }); const TaskSchema = schema.object({ id: schema.number(), title: schema.string(), done: schema.boolean() }); export type NewTask = Infer; export type Task = Infer; const tasks = new Map(); export const createTask = defineOperation({ name: "tasks.create", input: NewTaskSchema, output: TaskSchema, metadata: { description: "Create a task", tags: ["Tasks"] }, handler: async (input) => { if ([...tasks.values()].some((task) => task.title === input.title)) { throw new APIConflictError(`A task called "${input.title}" already exists.`); } const task: Task = { id: tasks.size + 1, title: input.title, done: false }; tasks.set(task.id, task); return task; }, });

The two type parameters, <NewTask, Task>, come from the schemas with Infer, which you met in your first Zudo code. So the types and the runtime checks describe the same data. APIConflictError is a ready-made error with status 409.

Now run it with an executor. createAPIContext(requestId, state) makes the context: the small object that travels with one call. You will look at it closely soon.

import { APIExecutor, APIValidationError, createAPIContext } from "@zudojs/api"; import { createTask } from "./tasks.js"; const executor = new APIExecutor(); const context = createAPIContext("req-1", {}); console.log(await executor.execute(createTask, { title: " Buy milk " }, context)); const invalid = await executor.execute(createTask, { title: "no" }, context); if (!invalid.ok && invalid.error instanceof APIValidationError) { console.log(invalid.error.statusCode, invalid.error.message, invalid.error.issues); } const twice = await executor.execute(createTask, { title: "Buy milk" }, context); if (!twice.ok) console.log(twice.error.statusCode, twice.error.code, "-", twice.error.message); { ok: true, data: { id: 1, title: 'Buy milk', done: false } } 422 Invalid input for operation "tasks.create". [ 'title: invalid' ] 409 ERR_API_CONFLICT - A task called "Buy milk" already exists.
  • Every call gave back a result: { ok: true, data } or { ok: false, error }. The executor never throws, so you check ok instead of writing try/catch.
  • The handler got the cleaned input: the spaces around "Buy milk" were trimmed by the schema.
  • The bad title failed with 422. The issue says where the problem is, title: invalid, but not what was sent. Schema messages often repeat the value, and that value can be a password. The executor leaves it out on purpose.
  • The handler's own APIConflictError came through unchanged, with its status and message.

Typed operations

Because createTask is an APIOperation<NewTask, Task>, TypeScript checks the input you pass to execute, and result.data has the type Task.

import { APIExecutor, createAPIContext } from "@zudojs/api"; import { createTask } from "./tasks.js"; const result = await new APIExecutor().execute(createTask, { titel: "Buy milk" }, createAPIContext("req-1", {})); if (result.ok) console.log(result.data.title); typed.ts:4:62 - error TS2561: Object literal may only specify known properties, but 'titel' does not exist in type '{ title: string; }'. Did you mean to write 'title'? 4 const result = await new APIExecutor().execute(createTask, { titel: "Buy milk" }, createAPIContext("req-1", {})); ~~~~~ Found 1 error in typed.ts:4

The typo is caught before the program runs. Transports get operations from the registry as APIOperation<unknown, unknown>: there the input really is unknown, because it comes from outside, and the schema checks it at runtime.

Errors the caller must not see

A handler can also fail by accident, for example with a database message. Such a message can contain table names, hosts or file paths. The executor turns every error that is not an API error into an APIInternalError with a fixed message, and keeps the original on cause for your logs:

import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; const exportTasks = defineOperation<{}, string>({ name: "tasks.export", handler: async () => { throw new Error('relation "tasks" does not exist (host 10.0.0.5)'); }, }); const result = await new APIExecutor().execute(exportTasks, {}, createAPIContext("req-7", {})); if (!result.ok) { console.log(result.error.name, result.error.statusCode, "expose:", result.error.expose); console.log("message:", result.error.message); console.log("for the log only:", (result.error.cause as Error).message); } APIInternalError 500 expose: false message: An unexpected internal error occurred in operation "tasks.export". for the log only: relation "tasks" does not exist (host 10.0.0.5)

expose is the flag that matters. true means "safe to show to the caller". false means "log it, send a generic message".

An APIError turns into JSON with its cause, and that includes the original message and stack. res.json(result.error) would leak the database message after all. Always pick the fields a caller may see. The publicError function below does that for every transport.

The API context

The context carries four things through one call: a request id, an optional AbortSignal for cancelling, a state object you choose, and typed slots. A slot is read and written through a key made with createContextKey<T>(name), so TypeScript knows the type of each value. Five keys are built in, such as UserIdContextKey. A request id often comes from an x-request-id header, which the client writes. createAPIContext throws a TypeError on an unsafe id. normalizeRequestId keeps a safe id and replaces anything else with a fresh UUID:

import { createAPIContext, createContextKey, normalizeRequestId, UserIdContextKey } from "@zudojs/api"; console.log(normalizeRequestId("web-42")); console.log(normalizeRequestId("x\nFAKE LOG LINE: admin signed in")); const PlanKey = createContextKey<"free" | "pro">("plan"); const context = createAPIContext("web-42", { locale: "en" }); context.set(UserIdContextKey, "ada"); context.set(PlanKey, "pro"); console.log(context.get(UserIdContextKey), context.get(PlanKey), context.state.locale); web-42 266de21a-0e98-4d5f-af95-48b24dc287b2 ada pro en

The id with a line break was replaced. Written into a log file as it was, it would have added a fake line to your logs. That trick is called log injection. context.set(PlanKey, "gold") would not compile, because the key says the value is "free" | "pro".

Interceptors: rules for every transport

An interceptor is an object with an intercept(call, next) method. It works like the middleware you know: do something, await next(), do something after. call holds the operation, the input and the context. An interceptor may also answer early, without calling next(), by returning apiFailure(error). This file is the heart of the Task API. It registers the operation, builds one executor with two interceptors, and has the publicError function that every transport uses:

import { APIAuthenticationError, APIExecutor, APIOperationRegistry, APIValidationError, apiFailure, UserIdContextKey } from "@zudojs/api"; import type { APIError, APIInterceptor } from "@zudojs/api"; import { createTask } from "./tasks.js"; const log: APIInterceptor = { async intercept(call, next) { const result = await next(); console.log(`[log] ${call.context.requestId} ${call.operation.name} -> ${result.ok ? "ok" : result.error.code}`); return result; }, }; const requireUser: APIInterceptor = { async intercept(call, next) { if (call.context.get(UserIdContextKey) === undefined) { return apiFailure(new APIAuthenticationError("Sign in first.")); } return next(); }, }; export const registry = new APIOperationRegistry(); registry.register(createTask); registry.freeze(); export const executor = new APIExecutor({ interceptors: [log, requireUser] }); export function publicError(error: APIError): { code: string; message: string; issues?: readonly string[] } { const issues = error instanceof APIValidationError ? { issues: error.issues } : {}; return { code: error.code, message: error.expose ? error.message : "An internal error occurred.", ...issues }; }
  • The first interceptor in the list is the outermost, so log also sees the answers of requireUser.
  • registry.freeze() locks the registry, so nobody can add or replace an operation while requests run. get(name), require(name), getAll() and findByTag(tag) read it.
  • publicError keeps only code, issues and, when expose is true, message.
In @zudojs/api 1.1.1 the executor checks the input before the interceptors run. An interceptor may replace call.input before next(), and the handler then gets the new value without any schema check. If an interceptor changes the input, it must produce valid data itself.

One operation, three transports

Now the payoff. Each transport below does the same four steps: find the operation, build a context from what it verified, call the executor, and turn the result into its own kind of answer.

HTTP

One route, POST /api/:operation, serves every operation in the registry. The user comes from a bearer token. The users map stands in for the session or JWT check from the authentication lesson. At the end, the file calls its own server four times:

import { randomBytes } from "node:crypto"; import { createAPIContext, normalizeRequestId, UserIdContextKey } from "@zudojs/api"; import { createHttpServer, createNodeHttpAdapter, createResponseContext, createRouter } from "@zudojs/http"; import type { HttpRequestContext } from "@zudojs/http"; import { executor, publicError, registry } from "./app.js"; const token = randomBytes(32).toString("hex"); const users = new Map([[token, "ada"]]); const router = createRouter(); router.post("/api/:operation", async (ctx) => { const operation = registry.get(ctx.params.operation ?? ""); if (!operation) return createResponseContext().setStatus(404).json({ ok: false, error: { code: "NOT_FOUND" } }); let input: unknown; try { input = JSON.parse(new TextDecoder().decode(ctx.request.body as Uint8Array)); } catch { return createResponseContext().setStatus(400).json({ ok: false, error: { code: "BAD_JSON" } }); } const context = createAPIContext(normalizeRequestId(ctx.request.getHeader("x-request-id")), {}, ctx.signal); const userId = users.get(ctx.request.getHeader("authorization")?.replace(/^Bearer /, "") ?? ""); if (userId) context.set(UserIdContextKey, userId); const result = await executor.execute(operation, input, context); if (result.ok) return createResponseContext().json({ ok: true, data: result.data }); return createResponseContext().setStatus(result.error.statusCode).json({ ok: false, error: publicError(result.error) }); }); const server = await createHttpServer({ adapter: createNodeHttpAdapter({ host: "127.0.0.1", port: 0 }), handler: async (request: HttpRequestContext) => (await router.dispatch(request)).response, }).start(); const calls: [string, string, unknown][] = [ ["/tasks.create", token, { title: "Buy milk" }], ["/tasks.create", "guessed-token", { title: "Buy milk" }], ["/tasks.create", "guessed-token", { title: 42 }], ["/tasks.delete", token, {}], ]; for (const [path, bearer, body] of calls) { const response = await fetch(`http://127.0.0.1:${server.address?.port}/api${path}`, { method: "POST", headers: { "content-type": "application/json", "x-request-id": "web-1", authorization: `Bearer ${bearer}` }, body: JSON.stringify(body), }); console.log(response.status, JSON.stringify(await response.json())); } await server.stop(); [log] web-1 tasks.create -> ok 200 {"ok":true,"data":{"id":1,"title":"Buy milk","done":false}} [log] web-1 tasks.create -> ERR_API_AUTHENTICATION 401 {"ok":false,"error":{"code":"ERR_API_AUTHENTICATION","message":"Sign in first."}} 422 {"ok":false,"error":{"code":"ERR_API_VALIDATION","message":"Invalid input for operation \"tasks.create\".","issues":["title: invalid"]}} 404 {"ok":false,"error":{"code":"NOT_FOUND"}}

The route has no task logic at all, and ctx.signal goes into the context, so a client that hangs up cancels the call. The guessed token got 401 from the requireUser interceptor. The third call also had a guessed token, yet it got 422, and [log] printed nothing. Validation ran first and the interceptors never ran. So a logging interceptor never sees invalid calls, and an unknown caller learns the shape of your input. When that matters, refuse unknown callers in the transport, before you call the executor.

RPC

The RPC transport registers one procedure per operation. The user comes from call.auth, the identity your RPC server verified, never from frame metadata, which the caller writes. The frame's id is written by the caller too, so it goes through normalizeRequestId. A failure becomes an RPCError with the same code:

import { createAPIContext, normalizeRequestId, UserIdContextKey } from "@zudojs/api"; import { createRPCProcedure, RPCClient, RPCError, RPCServer, isRPCError } from "@zudojs/rpc"; import { executor, publicError, registry } from "./app.js"; const rpc = new RPCServer(); for (const operation of registry.getAll()) { rpc.register(createRPCProcedure(operation.name, async (input: unknown, call) => { const context = createAPIContext(normalizeRequestId(call.request.id), {}, call.signal); if (typeof call.auth?.userId === "string") context.set(UserIdContextKey, call.auth.userId); const result = await executor.execute(operation, input, context); if (result.ok) return result.data; const { code, message } = publicError(result.error); throw new RPCError(message, { code, statusCode: result.error.statusCode, expose: true }); })); } const client = new RPCClient({ send: (request) => rpc.handle(request, { auth: { userId: "ada" } }) }); console.log(await client.call("tasks.create", { title: "Walk the dog" })); try { await client.call("tasks.create", { title: "Walk the dog" }); } catch (error) { if (isRPCError(error)) console.log(error.code, "-", error.message); } [log] a7dd43d5-ef69-4e92-ae1d-c33864d7c8af tasks.create -> ok { id: 1, title: 'Walk the dog', done: false } [log] 4a790a2b-1ab8-4d8d-8c8b-d961451f44de tasks.create -> ERR_API_CONFLICT ERR_API_CONFLICT - A task called "Walk the dog" already exists.

Queue

A background job has no HTTP request and no token. Only your own code adds jobs, after it has checked who the user is, so the job carries that user id. The job fails when the operation fails, and the queue's retry and dead-letter rules take over:

import { createAPIContext, UserIdContextKey } from "@zudojs/api"; import { createInMemoryQueue, createInMemoryQueueEventEmitter, createQueueName } from "@zudojs/queue"; import { executor, publicError, registry } from "./app.js"; const queue = createInMemoryQueue<{ input: unknown; userId: string }>(createQueueName("operations"), { eventEmitter: createInMemoryQueueEventEmitter(), }); let jobs = 0; for (const operation of registry.getAll()) { queue.process(operation.name, async (job, jobContext) => { const context = createAPIContext(`job-${++jobs}`, {}, jobContext.signal); context.set(UserIdContextKey, job.data.userId); const result = await executor.execute(operation, job.data.input, context); if (!result.ok) throw new Error(`${result.error.code}: ${publicError(result.error).message}`); console.log("[queue] completed", job.name, result.data); return result.data; }); } queue.events?.on("job:failed", ({ job, error }) => console.log("[queue] failed", job.name, error.message)); await queue.add("tasks.create", { input: { title: "Water plants" }, userId: "ada" }, { attempts: 1 }); await queue.add("tasks.create", { input: { title: "" }, userId: "ada" }, { attempts: 1 }); await new Promise((resolve) => setTimeout(resolve, 200)); await queue.close(); [log] job-1 tasks.create -> ok [queue] completed tasks.create { id: 1, title: 'Water plants', done: false } [queue] failed tasks.create ERR_API_VALIDATION: Invalid input for operation "tasks.create".

attempts: 1 matters here: a validation error fails the same way every time, so retrying it only wastes work. Without the eventEmitter option, queue.events is a silent emitter and your listeners never run.

Ready-made bindings are coming to @zudojs/api: a fetch handler for HTTP, an RPC binding, a queue binding and a command-line runner, with the operation's HTTP route set in its metadata. The docs page already describes them, but they are not in version 1.1.1 on npm. Until then, the small transports above do the same job.

Timeouts and cancelling

Every operation has a timeout: 30 seconds by default, or the timeout you set in milliseconds. When time runs out, the caller gets ERR_API_TIMEOUT (504). But the executor only stops waiting. It does not stop the handler. The only signal a handler gets is context.signal, the caller's cancel signal, and in version 1.1.1 the timeout does not abort it. So a slow handler keeps working for a caller who already got an error. That can write a report twice, or keep the database busy for nobody.

The fix: give the handler its own deadline signal, and combine it with the caller's signal with AbortSignal.any:

import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; const REPORT_TIMEOUT = 100; const sleep = (ms: number, signal: AbortSignal) => new Promise((resolve, reject) => { const timer = setTimeout(resolve, ms); signal.addEventListener("abort", () => { clearTimeout(timer); reject(signal.reason); }, { once: true }); }); const report = defineOperation<{}, string>({ name: "tasks.report", timeout: REPORT_TIMEOUT, handler: async (_input, context) => { const deadline = AbortSignal.timeout(REPORT_TIMEOUT + 10); const signals = context.signal ? [deadline, context.signal] : [deadline]; try { await sleep(300, AbortSignal.any(signals)); } catch (reason) { console.log("[handler] stopped:", (reason as Error).name); throw reason; } return "report.csv"; }, }); const executor = new APIExecutor(); const late = await executor.execute(report, {}, createAPIContext("req-1", {})); if (!late.ok) console.log("[caller]", late.error.code); const controller = new AbortController(); setTimeout(() => controller.abort(), 50); const cancelled = await executor.execute(report, {}, createAPIContext("req-2", {}, controller.signal)); if (!cancelled.ok) console.log("[caller]", cancelled.error.code, cancelled.error.statusCode); [caller] ERR_API_TIMEOUT [handler] stopped: TimeoutError [handler] stopped: AbortError [caller] ERR_OPERATION_CANCELLED 499

First call: the caller got ERR_API_TIMEOUT at 100 ms. The handler's own deadline fired 10 ms later and it stopped, instead of working for nobody. The 10 ms gap makes sure the executor answers first, so the caller always sees a clean timeout. Second call: the caller aborted after 50 ms, like a browser tab that was closed. The result code is ERR_OPERATION_CANCELLED. Check that code, not the unusual status 499.

Practice

Write an interceptor that refuses every operation tagged "Admin" unless the verified role in the context is "admin". Store the role with your own context key. The input must never decide the role: test it with an input that claims role: "admin".

import { APIAuthorizationError, APIExecutor, apiFailure, createAPIContext, createContextKey, defineOperation } from "@zudojs/api"; import type { APIInterceptor } from "@zudojs/api"; const RoleKey = createContextKey<"user" | "admin">("role"); const adminOnly: APIInterceptor = { async intercept(call, next) { if (call.operation.metadata?.tags?.includes("Admin") && call.context.get(RoleKey) !== "admin") { return apiFailure(new APIAuthorizationError("Admins only.")); } return next(); }, }; const deleteAll = defineOperation<{ role?: string }, string>({ name: "tasks.deleteAll", metadata: { tags: ["Admin"] }, handler: async () => "all tasks deleted", }); const executor = new APIExecutor([adminOnly]); const bo = createAPIContext("req-1", {}); bo.set(RoleKey, "user"); const denied = await executor.execute(deleteAll, { role: "admin" }, bo); if (!denied.ok) console.log(denied.error.statusCode, denied.error.message); const ada = createAPIContext("req-2", {}); ada.set(RoleKey, "admin"); console.log(await executor.execute(deleteAll, {}, ada)); 403 Admins only. { ok: true, data: 'all tasks deleted' }

The role comes only from the context, which the transport fills after it verified the caller. The role in the input is ignored.

A command-line tool reports failure with an exit code. Write exitCode(result): 0 for success, 77 for status 401 or 403, 65 for 422, and 1 for anything else. Test it with results made by apiSuccess and apiFailure.

import { APIAuthenticationError, APIConflictError, APIValidationError, apiFailure, apiSuccess } from "@zudojs/api"; import type { APIResult } from "@zudojs/api"; function exitCode(result: APIResult): number { if (result.ok) return 0; const status = result.error.statusCode; if (status === 401 || status === 403) return 77; if (status === 422) return 65; return 1; } const results: APIResult[] = [ apiSuccess({ id: 1 }), apiFailure(new APIAuthenticationError("Sign in first.")), apiFailure(new APIValidationError("Invalid input.", ["title: invalid"])), apiFailure(new APIConflictError("Already exists.")), ]; console.log(results.map(exitCode)); [ 0, 77, 65, 1 ]

A script that runs your tool can now tell "fix your input" (65) from "sign in" (77) without reading any text.

Recap

  • An operation is your logic with a name, an input schema, an output schema and a handler. Define it once with defineOperation.
  • APIExecutor.execute never throws. It returns { ok: true, data } or { ok: false, error }, and hides the message of every error with expose: false. Send callers only code, issues and exposed messages.
  • The context carries a safe request id, a cancel signal and typed slots. Pass header values through normalizeRequestId.
  • Interceptors apply the same rules on every transport. In 1.1.1 they run after input validation. A transport only finds the operation, builds the context from identity it verified, and translates the result.
  • A timeout stops the waiting, not the handler. Give long handlers their own deadline signal.
