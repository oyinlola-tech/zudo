What is a microservice?

A microservice runs as its own process, is deployed on its own, and owns its own data. A folder with one feature inside one app is a module of a modular monolith, not a service.

 On a sale day the catalog gets a hundred times more reads than payments. Which microservice benefit helps here?

With separate services you can run twenty catalog servers and only two payment servers. Independent deployment is about releasing on your own schedule, which is a different benefit.

 In the modular monolith, catalog.reserve() was a function call. After you extract catalog into a service, what new problem does that call have?

A function call in one process cannot time out. A network call can be slow, fail, never answer, or be delivered twice. Most of the lesson is about making that call as reliable as the function call was.

 You are starting a new online shop and do not yet know where the business boundaries are. What does the lesson recommend?

Moving a boundary between two services is far harder than moving it between two folders. A modular monolith lets you find the right boundaries first; you extract a service when independent deployment or scaling is a measured need, not a guess.

 The orders service needs a product's price. The catalog service owns the products table. What should orders do?

A service owns its data: no other service reads its tables. Reading them directly ties both services to one table layout and bypasses catalog's rules. Ask through the API, or keep a copy fed by events.

 In Docker Compose, why does http://catalog:3000 reach the catalog service?

Docker Compose and Kubernetes give every service a DNS name. You need a registry such as Consul only at a scale where configuration plus DNS names stop working.

 After checkout, ShopFlow sends a receipt e-mail. The customer does not wait for it. Which way of talking fits best?

Use synchronous calls only when a user is waiting for the answer. A queue lets orders hand the work over and finish, and a slow mail provider cannot slow down or fail the checkout.

 In the example, inventory takes 2 seconds to answer for a lamp, and the client has timeout: 1000. Why is the timeout important?

Without a timeout, every waiting request keeps memory and a connection busy in orders. A slow dependency can then make orders itself fall over. Give every remote call a timeout.

 A POST /charges request timed out. Why is it dangerous to simply send it again?

The server may have finished the work and only the answer was lost. Retrying a read is harmless, but retrying "charge this card" could charge twice, unless you use an idempotency key.

 The client sent x-request-id: req-mug, orders passed it on, and inventory logged it. Why is this useful?

A correlation id ties together log lines from different services. It is not a security token: it proves nothing about who sent the request.

 The lesson checks an id from an incoming header before copying it into logs. What does this print? function correlationId(incoming, fallback) { return incoming && /^[\w-]{1,64}$/.test(incoming) ? incoming : fallback; } console.log(correlationId("req-mug", "gen-1")); console.log(correlationId("bad\nFAKE LOG LINE", "gen-2")); console.log(correlationId(undefined, "gen-3"));

Only letters, digits, _ and - up to 64 characters pass. The second value contains a newline and spaces, so it is replaced; otherwise an attacker could write a fake line into your logs.

 Why does HttpClient add a random jitter to each backoff wait?

Without jitter, every client retries on the same schedule and hits the recovering service in waves. A little randomness spreads the retries out.

 What does this exponential backoff schedule print? function delays(base, retries, max) { const out = []; for (let i = 0; i < retries; i++) out.push(Math.min(base * 2 ** i, max)); return out; } console.log(delays(100, 4, 300));

Each wait doubles: 100, 200, 400, 800. Math.min(…, max) caps them at 300, like maxRetryDelay in the lesson's client.

 How does an idempotency key make "charge this card" safe to retry?

The key names the operation, not the attempt. The first attempt did the work; the retry with the same key gets the saved answer, so the card is charged once.

 The first attempt charged the card but its answer was lost. What does this print? const answers = new Map(); let charges = 0; function charge(key) { const saved = answers.get(key); if (saved) return { ...saved, replayed: true }; charges += 1; const answer = { chargeId: charges }; answers.set(key, answer); return { ...answer, replayed: false }; } charge("key-1"); console.log(charge("key-1")); console.log("cards charged:", charges);

The second call finds the saved answer for key-1 and replays it with replayed: true. The charge counter is not increased again.

 In production, where should the payments service keep the saved answers for idempotency keys?

A Map is lost on restart and is not shared between instances. Saving the answer in the same transaction as the charge means you can never have a charge without its saved answer.

 A circuit breaker is open. What happens to a call?

Open means "fail fast": no more load on a service that is already struggling, and no caller waits for a timeout. After the pause the breaker goes half-open and lets one trial call through.

 A breaker opens after 2 failures in a row. What does this print? let state = "closed"; let failures = 0; function call(up) { if (state === "open") return "failing fast"; if (!up) { failures += 1; if (failures >= 2) state = "open"; return "503"; } failures = 0; return "ok"; } const results = [call(false), call(false), call(true)]; console.log(results.join(", "), "|", state);

The second failure opens the breaker. The third call fails fast even though the service is up, because the breaker does not touch the network while it is open.

 The breaker around inventory is open. Which page can safely show "stock unknown" as a fallback?

A product page can live without the stock count. Checkout cannot accept an order it cannot reserve, so there the right answer is a clear "please try again in a minute".

 A receipt job fails on all of its attempts. What happens to it in the queue?

The dead-letter list keeps failed jobs visible instead of losing them. Because a job may run more than once, its handler should be idempotent too.

 Why does the lesson tell you to avoid two-phase commit (2PC) between services?

2PC tries to lock both databases and commit them together. The outbox and saga patterns give you consistency without that coupling.

 The orders service saves the order, then publishes order.placed, and crashes between the two. How does the outbox pattern fix this?

Both rows are saved or neither is, so an order can never exist without its event. The relay then reads unpublished rows, publishes them and sets published_at.

 The relay crashes after publishing an event but before marking it published. What does the receiving service need?

The outbox gives at-least-once delivery: the unmarked event is sent again on the next run. At-least-once plus idempotent handlers is the normal, reliable combination.

 In a saga, what is a compensation?

A saga does not roll back like a database. When a step fails, it runs the compensations of the steps that already succeeded, moving forward to a consistent state like "order cancelled, stock released".

 The third step fails. What does this saga print? async function runSaga(steps) { const done = []; for (const step of steps) { try { await step.run(); done.push(step); } catch { for (const finished of done.reverse()) console.log(`undone: ${finished.name}`); return false; } } return true; } const ok = await runSaga([ { name: "create order", run: async () => {} }, { name: "reserve stock", run: async () => {} }, { name: "charge card", run: async () => { throw new Error("declined"); } }, { name: "confirm order", run: async () => {} }, ]); console.log("confirmed:", ok);

Only finished steps are undone, and in reverse order: the stock was reserved last, so it is released first. The failed step did nothing, so it has nothing to undo.

 What is the difference between an orchestrated and a choreographed saga?

Orchestration has a conductor, which is easier to follow when you start. Choreography has none: order.created → inventory reserves → stock.reserved → payments charges, and so on.
