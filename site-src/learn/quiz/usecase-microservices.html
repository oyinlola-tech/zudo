Which arrow in Oja Market should be an event rather than a synchronous RPC call?

Nobody waits for a receipt, and a mail outage must not stop sales. The other three produce answers the customer or the next step needs right now.

 The notifications team needs the customer's e-mail address. What should they do?

A service's database is private to it. Reading it from outside couples two teams to one schema, so neither can change it without breaking the other.

 The internal services have no public port. Why do they still check a service token on every RPC request?

Each service verifies who is calling. A token per service, or mutual TLS, even says which service it is, so payments can refuse anyone but orders.

 A frame's metadata carries traceparent. Why is it fine to take the trace from metadata, but not the user id?

Metadata is written by the caller, so it is untrusted. What decides access must come from something verified: the token check for the calling service, and a user id that a trusted service verified and passed in the validated input.

 Why does serviceClient rethrow a timeout or a refused connection as RPCUnavailableError?

Only exposed errors keep their code across a service boundary. "A dependency did not answer" is useful to every caller up the chain, so it is turned into an error that says so.

 Orders gives payments 1 second and users 2 seconds. What should the gateway's timeout for orders.place be?

If the gateway gives up first, the customer sees an error and retries while the first attempt may still succeed. Timeouts shrink as you go down the chain; passing a deadline down makes that automatic.

 Payments is down when Ada presses "Pay". What does Oja Market answer, and why?

202 means accepted for processing. 201 would pretend it is paid; 402 would say the card was declined, which is not true; 500 would lose a sale that can still succeed.

 Payments charged the card, then its answer was lost in a timeout. Orders retries later. What stops a second charge?

The idempotency key travels with the operation to the system with the side effect. The queue's key only prevents two jobs from waiting at the same time; it knows nothing about what payments already did.

 Where does the idempotency key for POST /orders come from?

A key made per request would differ for the second press and protect nothing. Only the client knows that two requests are the same cart. The key is scoped to the user, so one customer cannot collide with another.

 Why does orders write order.paid to an outbox table instead of publishing it right after marking the order paid?

The relay publishes committed rows until it succeeds. The cost is that a row can be published twice, so consumers must be idempotent.

 What does the serialization envelope add to the order.paid body?

With plain JSON, paidAt would arrive as a string without anyone noticing. The envelope's version also lets a consumer refuse a format it does not understand instead of misreading it.

 Orders will start publishing order.paid version 2. In which order should the teams release?

If the producer goes first, every version 2 event lands in the consumers' rejected pile until they catch up. Consumers first, producers second, and never change the meaning of an existing field.

 Notifications receives an event body that is not valid JSON. What should it do?

A broken body will be broken on every delivery. Retrying it forever blocks the events behind it; a person must look at it instead.

 The outbox relay published order 7's order.paid twice. Why does Ada still get one receipt?

Two layers: the queue refuses a second job for receipt-7 while the first exists, and the mail provider covers a duplicate that arrives after the first receipt went out.

 Notifications has no RPC procedures at all. What is the benefit?

A service that only reacts to events cannot be in anyone's critical path. The e-mail outage test proved it: orders were still answered with 201.

 The payment retry job stores traceparent in its data. What would be lost without it?

AsyncLocalStorage does not survive a queue. Every asynchronous hop (queue job, outbox row, broker message) must carry the trace context explicitly.

 Why does the gateway put the trace id in an x-trace-id response header?

A trace id is not a secret and reveals nothing about the data. It is the handle that turns "my order failed at 14:03" into one trace.

 While payments is down, each order still waits a full second for the payments timeout before it becomes pending_payment. What fixes that?

The breaker turns a slow failure into a fast one while the dependency is known to be down, and lets one trial call through to notice when it is back.

 Why does orders compute the total from its own price list instead of taking prices from the cart the client sent?

The body says what the customer wants: which products and how many. What things cost is the shop's data.

 Orders calls users for every order. What is the trade-off of keeping a copy of each customer's e-mail inside orders instead?

Removing a synchronous dependency buys availability with eventual consistency. The owner of the address is still users; orders only holds a copy it updates from user.updated.
