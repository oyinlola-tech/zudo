Which of these problems is the best fit for a frequency counter?

"Same items, any order" depends only on how often each code appears, which is exactly what a frequency table keeps. Runs and consecutive windows depend on positions, and a sorted search depends on order: those need other patterns.

 A frequency table of a string keeps each character's count. What information does it throw away?

The table is a summary without positions. That is why it answers "same letters?" in O(n), and why it cannot answer order-dependent questions such as "is a ever followed by b?". (The total length can still be recovered by adding up the counts.)

 The "find and cross off" anagram check searches the remaining letters of b for each letter of a. With both strings of length n, how does its work grow?

Each of the n searches can scan up to n letters, about n(n + 1) / 2 comparisons in the worst case, and splice adds more shifting on top. Ten times longer input means about a hundred times more work.

 Why does this module compare solutions by counting operations instead of timing them?

Timings vary between runs and machines. Counting the operation in the innermost loop gives a number that is reproducible and shows the growth rate directly.

 A developer checks anagrams by testing that the strings have the same length and that new Set(a) and new Set(b) hold the same characters. Which pair does it get wrong?

A Set keeps which values appear, not how many times. "aab" and "abb" have the same set {a, b} (and even the same length) but different counts, so they are not anagrams. Counts are the whole point.

 What goes wrong if you write counts.set(x, counts.get(x) + 1) instead of using ?? 0?

A missing key reads as undefined. ?? 0 turns "not seen yet" into a count of 0. Once a count is NaN, adding to it keeps it NaN.

 sameItems counts up for every item of a and down for every item of b. When does it return false during the second loop?

A count of 0 means every copy a had has already been matched. The final check (open === 0) catches the opposite case, where a has items left over.

 sameItems ends with return open === 0. If you replaced that line with return true, which call would give a wrong answer?

The second loop only fails when b asks for something a has run out of, so it catches "ab"/"abb" and "aab"/"abb" by itself. When a is the longer one, every item of b finds a match and the loop finishes; only the leftover open count (one b never matched) shows that a had more. Two empty strings really are anagrams.

 To find the first transfer reference that appears only once in a log, why does the solution walk the log twice?

During the first pass you cannot know yet whether a reference will appear again later. Two O(n) passes are still O(n). (Iterating the Map in insertion order would also work here, but walking the input states the intent directly.)

 Why can a list have at most one majority element (a value appearing more than n / 2 times)?

"More than half" is strict. Two values with exactly half each is a tie, and neither is a majority.

 Why does the Boyer–Moore majority vote need a second, verifying pass?

When a majority exists, the vote always ends with it. When none exists, the vote still ends with some candidate. Only counting tells the two cases apart.

 Boyer–Moore uses O(1) space; a frequency table uses O(k). Why is the frequency table still called "the pattern"?

Specialised tricks trade generality for resources. Start with the general pattern and reach for the trick only when memory really matters.

 When is an array of counters a better frequency table than a Map?

With a fixed alphabet the array has a constant size, no hashing and no hash worst case, and joining it gives a signature string. For open-ended values such as ids, a Map is the right table.

 Two usernames get the signature counts.join(",") from a 36-slot counter array. When are their signatures equal?

Equal signatures mean equal counts for every character, which is the definition of an anagram. That is why a Map from signature to names finds impersonators with one lookup.

 There are 200,000 protected usernames. Why build a signature index instead of calling sameItems against each on every sign-up?

Precomputing an index is the lookup pattern from Hash maps and sets, applied to a key you compute from counts. The price is memory for the index and keeping it up to date.

 The signature function throws on a character outside the alphabet instead of skipping it. Why?

A counter that ignores unknown characters changes the question it answers. Decide the valid alphabet at the boundary and refuse anything else loudly.

 You count 1,000,000 order ids and every id is different. How big is the frequency table?

The extra space is O(k), where k is the number of distinct values. For unique ids k = n. For letters, k is small however long the text is.

 A customer's name is stored as "josé" in one system and "josé" in another. Both print as josé. What should a counter do before counting?

Unicode allows the same visible text in composed and decomposed forms. Without normalisation they are different strings and different keys, so counts and anagram checks disagree.

 Why is a Map safer than a plain object for counting values that come from users?

A Map has no inherited keys and stores any key literally. (It does not normalise anything: "Ada" and "ada" are still different keys.)

 Which question can a single frequency table NOT answer?

"Within 10 minutes" depends on positions in time, which a whole-list table has thrown away. A sliding window, which counts only the items inside a moving range, fits that question.

 The transfers live in PostgreSQL. What is the best way to find references that appear exactly once?

It is the same pattern, run next to the data, so millions of rows never travel over the network. The database builds its own counting table or sorts internally.

 The test compares sameItems with a sort-based version on 5,000 random word pairs, and prints how many pairs were anagrams. Why print that number?

A random test is only as good as the cases it happens to generate. Using a three-letter alphabet makes anagrams common, and the printed count shows it.
