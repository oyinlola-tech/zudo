In this lesson, what is a "contract" between two pieces of code?

Bugs like "payment of ₦undefined" happen when the publisher and the listener each have their own idea of the payload. Writing the contract as one type lets the compiler check both sides.

 Why did placeOrder("u-ada", "prd_pro-monthly") compile when the parameters were (productId: string, userId: string)?

Structural typing only sees "string". A brand (Brand<string, "ProductId">) gives each kind of id a different type that exists only at compile time.

 Branded ids exist only for the compiler. What does this print? import type { Brand } from "@zudojs/constants"; type OrderId = Brand; const id = "ord_000000000001" as OrderId; console.log(typeof id, id.length, JSON.stringify({ id }));

The __brand property is a fiction for the type checker. At runtime the id is the same string, so brands cost nothing and serialise normally.

 Why store money as a branded whole number of kobo instead of a number of naira?

Whole kobo are exact integers. The brand adds a second guarantee: an amount only exists if it went through the checked kobo() function.

 What does this print? const naira = 1.1 * 3; const kobo = 110 * 3; console.log(naira, naira === 3.3, kobo, kobo === 330);

1.1 has no exact binary representation, so the product is slightly off and a payment of exactly 3.3 does not match. Integer kobo have no such problem.

 In the lesson, where is value as ProductId allowed to appear?

An as is a promise the compiler cannot verify. Keeping the only one behind a check turns the type ProductId into "a value that was checked", everywhere else in the code.

 What does this kobo() helper return or throw? import type { Brand } from "@zudojs/constants"; type Kobo = Brand; function kobo(amount: number): Kobo { if (!Number.isSafeInteger(amount) || amount < 0) throw new RangeError(`Not an amount in kobo: ${amount}`); return amount as Kobo; } for (const value of [500_000, 3.3, -100, 0]) { try { console.log("ok", kobo(value)); } catch (error) { console.log((error as Error).message); } }

Only whole, non-negative safe integers pass. Zero is a valid amount (a free plan); a fraction or a negative number is refused where it enters.

 Why model an order as PendingOrder | PaidOrder | CancelledOrder instead of one interface with optional paidAt? and reason? fields?

With optional fields every combination is allowed, including "paid without paidAt". A discriminated union lists only the legal states, and status tells TypeScript which one you have.

 In RecordPayment, why does markPaid(order, …) compile only after if (order.status !== "pending") throw …?

Narrowing is how the runtime check and the type meet: the if proves the state, and the compiler remembers the proof for the rest of the block.

 A new status reaches label at runtime through data the compiler never saw. What happens? type Status = "pending" | "paid" | "cancelled"; function assertNever(value: never): never { throw new Error(`Unhandled status: ${JSON.stringify(value)}`); } function label(status: Status): string { switch (status) { case "pending": return "Waiting"; case "paid": return "Paid"; case "cancelled": return "Cancelled"; default: return assertNever(status); } } const fromDatabase = JSON.parse('["paid", "refunded"]') as Status[]; for (const status of fromDatabase) { try { console.log(label(status)); } catch (error) { console.log((error as Error).message); } }

assertNever gives you a compile error while a state is unhandled in your types, and a loud runtime error if an unexpected value slips in anyway, here through an unchecked as on parsed JSON.

 What does const badge: Record<Order["status"], string> = { … } give you when a new status is added?

A Record over a union of literals is a lookup table the compiler checks for completeness, a lighter alternative to a switch with assertNever.

 Why is type PlaceOrderBody = Infer<typeof PlaceOrderBody> better than writing the DTO interface by hand?

A hand-written interface and a schema are two sources of truth that drift apart. With Infer, changing the schema changes the type, and every use is re-checked.

 The DTO has productId: string, the command request has productId: ProductId. What happens between them?

The route is the boundary. A schema checks the shape; a parse function checks the meaning and produces the branded type the rest of the module relies on.

 What does as const satisfies Record<BillingErrorCode, number> on the status table do?

An annotation would widen the values to number; satisfies checks without widening, and as const keeps the literals.

 What does this print? type Code = "PRODUCT_NOT_FOUND" | "AMOUNT_MISMATCH"; const STATUS = { PRODUCT_NOT_FOUND: 404, AMOUNT_MISMATCH: 422 } as const satisfies Record; function status(code: Code): 404 | 422 { return STATUS[code]; } console.log(status("AMOUNT_MISMATCH"), Object.keys(STATUS).length, Object.isFrozen(STATUS));

 Why are BillingCommands and the payload types written as type aliases rather than interfaces?

An object type alias is assignable to Record<string, unknown>; an interface is not, since it could be extended with more properties later. It is a small rule that saves a confusing error.

 The raw @zudojs/cqrs bus takes the result type as a type argument. What does this print? import { createCommandBus } from "@zudojs/cqrs"; import type { CommandOf } from "@zudojs/cqrs"; type PlaceOrder = CommandOf<"PlaceOrder", { productId: string }>; const bus = createCommandBus(); bus.register("PlaceOrder", (command) => ({ orderId: `ord_for_${command.productId}` })); const claimed = await bus.execute({ type: "PlaceOrder", productId: "prd_pro-monthly" }); console.log(typeof claimed, claimed);

 What does the lesson's Handlers<BillingCommands> mapped type turn into a compile error that the raw bus only reports at runtime?

A mapped type over the command map has one required key per command. Leave one out, or return the wrong result, and the handler table does not compile.

A bus whose names are runtime strings (so wildcards and plugins work) cannot know every payload. A thin layer over a type-level map restores the connection without giving up the runtime features.

 Why do the handlers depend on OrderRepository (an interface) instead of MemoryOrders or a PostgreSQL class?

A port says what the handler needs, not how it is done. The token for the port is what ties a concrete implementation to it at one place.

 What does this print? import { createContainer, createToken } from "@zudojs/container"; interface Clock { now(): string; } const CLOCK = createToken("Clock"); const container = createContainer(); container.registerValue(CLOCK, { now: () => "2026-09-24T09:00:00.000Z" }); const clock = container.resolve(CLOCK); console.log(clock.now().slice(0, 10), container.has(createToken("Clock")));

 What does registerFactory(TOKEN, (orders, clock) => …, [ORDERS, CLOCK]) check at compile time?

Whether each token is registered is still a runtime question. registerClass with an inject option is not checked against the constructor, which is why the lesson uses factories.

 What is the composition root in the billing module?

One place builds everything. Swapping the clock for the real one, or the memory stores for PostgreSQL, changes only this function.

 The provider sends the same "charge.success" webhook twice. What does RecordPayment do the second time, and why?

Providers retry until they get a success. Answering a genuine retry with an error would make them retry forever; a different payment for the same paid order is still refused with 409.

 Why does GetOrder answer ORDER_NOT_FOUND (404) when Bola asks for Ada's order, instead of 403?

For resources identified by id, "not found" for anything the caller may not see avoids leaking existence. The rule is enforced in the query handler, where the user id is known.

 The routes return ApiResult<T>, a union of { ok: true; status: 200 | 201; body: T } and { ok: false; status: number; body: { error } }. What does that prevent?

A union of the two response shapes lets the compiler check each branch of a route, and ok lets callers narrow to the right one.

 In the lesson's failure() helper, which errors are sent to the client with their own message?

Expected failures (bad input, not found, conflicts) are meant for the client. Anything else is a bug whose message may contain internals, so the client gets a generic message and your logs get the details.

 What happens to a // @ts-expect-error type test when a refactor accidentally makes the line below it compile?

That is what makes it a test: it passes while the error exists and fails when it stops existing.

 Which statement about types at runtime is true?

Compile-time and runtime checks cover different ground. Every boundary with the outside world needs a runtime check that produces the typed value.

 order.paid events are stored and replayed by another service. You need to rename total to amount. What is the safe way?

The compiler only sees the code of this build. Stored events and other services are outside it, so a contract that leaves your process must evolve compatibly.

 In a code review of a typed module, where is an as acceptable?

Every as is a claim the compiler accepts without proof. Keeping them few and next to their proof is what keeps the rest of the types honest.
