Which database does @zudojs/database support?

The package is built on Prisma and supports PostgreSQL only. PGlite is PostgreSQL itself, running inside Node.js, which is why the lesson can use it for learning.

 ZudoJS talks to a PrismaClientLike object. What does it need from that object?

Anything that has those five methods works. That is the adapter pattern: a small object that makes one thing (PGlite, or a real Prisma client) look like what ZudoJS expects.

 In the lesson's whereToSql, values become $1, $2… parameters, but field names are checked against an allow-list instead. Why?

Parameters can only stand for values. A column name is part of the SQL text itself, so it must come from a fixed list of names you trust. Anything else is refused.

 The PGlite adapter turns PostgreSQL error 23505 into the Prisma code P2002. What does 23505 mean?

23505 is a unique violation. ZudoJS understands the Prisma code P2002 and turns it into a 409 Conflict. A missing row becomes P2025, which ZudoJS turns into 404.

 Where should a connection string like postgres://app:pa55@db:5432/tasks come from?

It contains a password, so it is a secret: read it from the environment, never write it in code. Checking it at start-up makes a missing setting fail loudly at once, not at the first request.

 Your start-up check finds that DATABASE_URL does not start with postgres://. Which error message is best?

The message should name the setting and the problem, but never show the value. Error messages end up in logs, and the value contains a password.

 What is a repository?

A repository keeps all the queries for one table in one place. Routes and services call methods like findByTitle and never see SQL.

 When is keyset (cursor) pagination the better choice?

Keyset pagination asks for "the rows after the last one I saw". It stays fast on huge tables and does not skip or repeat rows when new ones are added. Offset pagination is the one for page numbers.

A query through the ordinary tasks repository runs outside the transaction, so it would not be rolled back. The tx-bound copy makes every query part of it.

Serialization failures and deadlocks are safe to retry: running the whole callback again usually succeeds. A validation error would fail the same way every time, so it is not retried.
