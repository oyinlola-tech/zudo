What makes an application a monolith?

A monolith is about deployment and runtime: one unit. It can be, and should be, well structured inside. "Hard to change" describes a badly structured codebase of any architecture.

 ShopFlow has three developers and eight weeks. Why is a monolith the right first architecture?

Early on, the biggest risk is building the wrong thing, and boundaries drawn too early are drawn wrong. A monolith keeps every change cheap. It can be given hard boundaries later, and parts extracted when a real reason appears.

 Stock and orders live in two separate systems. What does this print? const stock = new Map([["RICE-5KG", 3]]); const orders = []; function checkout(sku, quantity, crashAfterStock) { stock.set(sku, stock.get(sku) - quantity); if (crashAfterStock) throw new Error("orders system unreachable"); orders.push({ sku, quantity }); } try { checkout("RICE-5KG", 2, true); } catch (error) { console.log("checkout failed:", error.message); } console.log("rice in stock:", stock.get("RICE-5KG"), "orders:", orders.length);

The first change happened and the second did not, and nothing undid the first. Two bags are gone with no order. One database transaction makes both changes happen together or not at all.

 Which rule does the ShopFlow monolith follow?

These are the layers from Backend architecture. Note the last option: that restriction is not enforced in the monolith, and its absence is what the modular monolith adds.

 What is the job of app.ts (createShop)?

The composition root is the one place that knows how the parts fit. Tests use it too, so they exercise the real wiring, and swapping the payment provider changes one argument.

 What does SELECT … FOR UPDATE do in checkout?

The stock check and the stock update must not be interleaved with another checkout's. The row lock makes the second checkout wait, then read the updated stock. Plain reads without FOR UPDATE are not blocked.

 Why does lockForUpdate lock the product rows ORDER BY sku?

A deadlock needs two transactions each waiting for a lock the other holds: A holds rice and wants oil, B holds oil and wants rice. With one global order, both try rice first, so one simply waits for the other.

 Why is the card charged outside the transaction that reserves the stock?

Transactions must be short. The flow is reserve (short transaction), charge (no transaction), settle (short transaction). A slow provider then slows one customer, not every customer buying rice.

 The card is declined after the stock was reserved. What does checkout do?

The reservation already committed, so it is undone by a second transaction, not by a rollback. Keeping the cancelled order (instead of deleting it) preserves the history of what happened.

 Checkout passes order-<id> as the payment reference. What does that protect against?

The reference is the idempotency key from the adapters lesson. The order id is unique and known before the charge, which makes it a natural key.

 The lesson wraps the database so every transaction throws just before COMMIT. What does the test prove?

Simulating the failure at the worst moment is how you test atomicity. Every write inside the transaction is rolled back, so the database looks as if checkout never started.

 Five checkouts for one bag of rice each run at the same time; three bags are in stock. What must happen?

With the lock, each checkout sees the stock the previous one left. The CHECK (stock >= 0) constraint is a second guard if the code were ever wrong.

 The oversell example runs on PGlite, which executes one transaction at a time. Does the result carry over to a PostgreSQL server with a connection pool?

PGlite happens to serialize, which hides the lock. A server needs the lock to get the same safety. That is why the code uses FOR UPDATE even though PGlite would pass without it; tests against a real server would catch its absence.

 Ada, a customer, sends PUT /products/RICE-5KG with her valid token. Why does she get 403?

401 would mean "we don't know who you are". 403 means "we know, and you may not". The role is put into the token by the server at login, from the database, never from the request.

 How does the monolith make sure nobody can sign up as an admin?

Anything in the request body is chosen by the client. Security-relevant fields such as roles must be set by the server.

 Why does checkout publish order.paid instead of calling the notifications service directly?

The in-process bus decouples the two parts inside one program. It is not durable, though: if the process dies right after the payment, the notification is lost. The outbox pattern fixes that when it matters.

 The orders repository's history query joins the products table. Why is that a strain as the shop grows?

In one database, reaching into another area's table is easy, and that is the problem: dependencies appear silently. The modular monolith makes orders ask the catalog through its public API, or store the product name it needs at checkout time.

 GET /notifications runs its SQL in the route. What is wrong with that?

One shortcut is harmless; a hundred are a big ball of mud. A "who uses what" check, like the one in the lesson, makes such shortcuts visible before they multiply.

 On sale days the product pages get 100 times more traffic than checkout. What is the monolith's limitation here?

A monolith scales horizontally fine (run many copies behind a load balancer); it just cannot scale one part alone. Usually a cache or read replica solves read-heavy load long before a separate service is justified.

 ShopFlow runs as three copies behind a load balancer. Which part of this lesson's code must change first?

Anything kept in one process's memory that another copy needs breaks with several copies. The database is already shared, so the transaction and the constraints keep working.

 Three copies each open a connection pool of 10. The database allows 25 connections. What happens under load?

Pools are per process. The total is copies × pool size, and it must stay under the database's limit, with room for migrations and admin tools.

 Why must schema migrations in a monolith be done in backward-compatible steps?

Add a column, deploy code that writes both, backfill, switch reads, then remove the old column in a later deploy. One shared schema means one careless migration can break every area at once.

 A new image-resizing feature leaks memory until the process crashes. What is affected in the monolith?

Shared process, shared fate. This is one of the two strains only separate processes fix; the other is scaling parts independently. Code boundaries alone, as in a modular monolith, do not help here.

 Which strain does the modular monolith fix, while keeping one deployment?

Boundaries in the code and the data are an internal matter, so they can be enforced inside one program. Independent failure, scaling and release need separate processes.

 How does checkout stay consistent in each architecture?

As long as the data is in one database, a transaction covers it, even with a schema per module. Once each service owns a separate database, no single transaction reaches across, and patterns replace it.

 Three developers, 200 orders a day, weekly releases. The team lead wants to split ShopFlow into six services "to be ready for scale". What is the best answer?

Architecture should answer measured problems. Keep boundaries clean inside the monolith (which makes a later split mechanical) and revisit when a concrete reason appears.

What does it print? let stock = 2; let queue = Promise.resolve(); const withLock = (work) => (queue = queue.then(work, work)); async function buy(name) { return withLock(async () => { const seen = stock; await new Promise((resolve) => setTimeout(resolve, 5)); if (seen < 1) return `${name}: sold out`; stock = seen - 1; return `${name}: bought`; }); } console.log(await Promise.all(["Ada", "Bola", "Chidi"].map(buy))); console.log("stock:", stock);

What does this print? const valid = (items) => items.length > 0 && items.every((item) => Number.isInteger(item.quantity) && item.quantity >= 1); console.log(valid([{ sku: "RICE-5KG", quantity: 2 }])); console.log(valid([{ sku: "RICE-5KG", quantity: 0.5 }])); console.log(valid([])); console.log(valid([{ sku: "OIL-1L", quantity: "3" }]));
