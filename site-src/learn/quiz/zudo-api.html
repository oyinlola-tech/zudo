"Create a task" exists as an HTTP route, an RPC procedure and a queue job, each written separately. What is the problem the lesson points out?

Logic written three times is changed three times, and sooner or later one copy is missed. An operation holds the rules once; each transport only translates.

 In @zudojs/api, what is a transport's job?

A transport is the door a call comes through. It finds the operation, builds a context from what it verified, calls the executor, and translates the result. The rules live in the operation.

 What does this print? import { defineOperation } from "@zudojs/api"; try { defineOperation({ name: "Create Task!", handler: async () => null }); console.log("defined"); } catch (error) { console.log(error.name); }

defineOperation checks the definition at once, so a bad name fails when the program starts, not on the first request. Names use letters, digits and signs like ., as in tasks.create.

 What does this print? import { defineOperation } from "@zudojs/api"; try { defineOperation({ name: "tasks.report", timeout: 0, handler: async () => null }); console.log("no timeout"); } catch (error) { console.log(error.name); }

Every operation has a timeout, and it cannot be switched off with 0. A bad timeout is refused when the operation is defined.

 What does this print? import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; import { schema } from "@zudojs/schema"; const createTask = defineOperation({ name: "tasks.create", input: schema.object({ title: schema.string().trim().min(3) }), handler: async (input) => ({ id: 1, title: input.title, done: false }), }); const result = await new APIExecutor().execute(createTask, { title: " Buy milk " }, createAPIContext("req-1", {})); console.log(result);

The executor wraps every answer in a result: { ok: true, data }. The handler got the cleaned input, so the spaces around the title were trimmed by the schema.

 How do you find out whether executor.execute(...) failed?

Every call gives back a result. With ok you cannot forget the failure case: TypeScript only lets you read data after checking ok.

 What does this print? import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; import { schema } from "@zudojs/schema"; const createTask = defineOperation({ name: "tasks.create", input: schema.object({ title: schema.string().trim().min(3) }), handler: async (input) => input, }); const result = await new APIExecutor().execute(createTask, { title: "no" }, createAPIContext("req-1", {})); console.log(result.ok, result.error.statusCode, result.error.issues);

A bad input fails with 422. The issue says where the problem is (title) but not what was sent. The executor leaves the value out on purpose.

 Why do the executor's validation issues say only title: invalid and not the value that was sent?

An error message goes back to the caller and often into logs. Repeating the input there can leak a password typed into the wrong field. The path alone is enough to fix the request.

 What does expose: false on an API error mean?

expose is the flag that matters when you build a response. true means "safe to show to the caller"; false means "log it, send something generic".

 What does an API context carry through one call?

createAPIContext(requestId, state, signal) makes it. Typed slots are read and written with keys made by createContextKey, such as the built-in UserIdContextKey.

 What is log injection, and how does the lesson prevent it?

The x-request-id header is written by the client. Passed through normalizeRequestId, a safe id is kept and anything else becomes a fresh UUID.

 What does this print? import { createAPIContext } from "@zudojs/api"; try { createAPIContext("x\nFAKE LOG LINE", {}); console.log("created"); } catch (error) { console.log(error.name); }

createAPIContext refuses an unsafe id with a TypeError. That is why a transport passes header values through normalizeRequestId first.

 What is an interceptor in @zudojs/api?

It works like middleware. call holds the operation, the input and the context. It can also answer early without calling next(), by returning apiFailure(error).

 What does this print? import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; const steps = []; const log = { async intercept(call, next) { steps.push("log in"); const result = await next(); steps.push("log out"); return result; }, }; const auth = { async intercept(call, next) { steps.push("auth"); return next(); }, }; const op = defineOperation({ name: "tasks.list", handler: async () => { steps.push("handler"); return []; } }); await new APIExecutor({ interceptors: [log, auth] }).execute(op, {}, createAPIContext("r1", {})); console.log(steps.join(" > "));

The first interceptor in the list is the outermost. That is why a logging interceptor placed first also sees the answers of the interceptors after it.

 What does this print? import { APIAuthenticationError, APIExecutor, apiFailure, createAPIContext, defineOperation, UserIdContextKey } from "@zudojs/api"; let handlerRuns = 0; const requireUser = { async intercept(call, next) { if (call.context.get(UserIdContextKey) === undefined) { return apiFailure(new APIAuthenticationError("Sign in first.")); } return next(); }, }; const op = defineOperation({ name: "tasks.list", handler: async () => { handlerRuns += 1; return []; } }); const executor = new APIExecutor({ interceptors: [requireUser] }); const anonymous = await executor.execute(op, {}, createAPIContext("r1", {})); const signedIn = createAPIContext("r2", {}); signedIn.set(UserIdContextKey, "ada"); const ada = await executor.execute(op, {}, signedIn); console.log(anonymous.error.statusCode, ada.ok, handlerRuns);

 What does this print? import { APIOperationRegistry, defineOperation } from "@zudojs/api"; const registry = new APIOperationRegistry(); registry.register(defineOperation({ name: "tasks.create", metadata: { tags: ["Tasks"] }, handler: async () => null })); registry.freeze(); try { registry.register(defineOperation({ name: "tasks.evil", handler: async () => null })); } catch (error) { console.log("refused"); } console.log(registry.get("tasks.evil"), registry.findByTag("Tasks").map((op) => op.name));

 In the HTTP transport, where does the user id in the context come from?

Only identity the transport verified goes into the context. A user id in the body is written by the caller and proves nothing.

 A caller with a guessed token posts an invalid title to the HTTP binding. Why does it get 401 and not the 422 with the validation issues?

Because the interceptors come first, an unknown caller never learns what a valid input looks like. Only a signed-in user's invalid call gets the 422 with its issues.

 In registerApiRpcProcedures, where must the state function take the user id from?

Metadata, the frame's id and the payload are all written by the caller. Only call.auth, filled in by the transport's auth option after a check, says who the caller really is.

 The queue transport adds jobs with { attempts: 1 }. Why?

Retries help with errors that can go away, like a restarting service. An invalid input stays invalid. After the failure, the queue's dead-letter rules take over.

 A background job has no HTTP request and no token. Why may the queue binding's state take the user id from job.metadata.userId?

The trust comes from who writes the metadata. Jobs are added by your code after it verified the user. Never let a client choose a job's metadata: whoever writes userId there acts as that user.

 An operation's timeout runs out while its handler is still working. What does the executor do?

JavaScript cannot stop a running function from outside, so the executor aborts the signal with the same APITimeoutError the caller got. Pass context.signal to fetch or database calls, or check it in a loop.

 What does this print? import { APIExecutor, createAPIContext, defineOperation } from "@zudojs/api"; const sleep = (ms, signal) => new Promise((resolve, reject) => { const timer = setTimeout(resolve, ms); signal.addEventListener("abort", () => { clearTimeout(timer); reject(signal.reason); }, { once: true }); }); const report = defineOperation({ name: "tasks.report", timeout: 50, handler: async (_input, context) => { try { await sleep(300, context.signal); } catch (reason) { console.log("[handler] stopped:", reason.name); throw reason; } return "report.csv"; }, }); const result = await new APIExecutor().execute(report, {}, createAPIContext("req-1", {})); console.log("[caller]", result.ok, result.error.code, result.error.statusCode);

 A caller aborts the call, like a browser tab that was closed. Which should your code check?

The lesson advises checking the code, not the unusual status 499. Codes are meant for programs; messages are meant for people and can change.

The input is written by the caller. The context is filled by the transport after it verified the caller. Decisions about who may do what use the context only.
