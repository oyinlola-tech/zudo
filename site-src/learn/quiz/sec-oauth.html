A budgeting app asks for your bank password so it can read your transactions. Which problem does OAuth solve here?

With the password, the app can do everything you can, forever, and a breach of the app is a breach of your bank. A scoped token limits the damage and can be revoked on its own.

 What does OpenID Connect add to OAuth 2.0?

OAuth answers "what may this app do?". OIDC answers "who just logged in?" with a standard, verifiable token and standard claims such as sub and email.

 In "Budget App reads Ada's transactions from the bank's API", which role is the bank's API?

Ada is the resource owner, Budget App is the client, the bank's log-in service is the authorization server, and the API that serves the data and checks tokens is the resource server.

 Why can't a single-page app or a mobile app keep a client secret?

These are public clients. PKCE is what protects their codes, which is why it is required for them, and recommended for confidential clients too.

 Why does the flow send a short-lived code through the browser instead of the access token itself?

The front channel (the browser) is exposed; the back channel (server to server) is not. The code is the minimum that must cross the front channel, and it is single-use and quick to expire.

 What exactly is sent where in PKCE S256?

The hash can travel through the browser because it cannot be reversed. At the exchange, the server hashes the verifier and compares it with the challenge stored with the code.

 Why should servers refuse code_challenge_method=plain?

PKCE's protection comes from the hash. Without it, a leaked URL gives an attacker both the code's challenge and the secret it was meant to hide. The OAuth 2.1 draft requires S256.

 What attack does the state parameter stop?

The state ties the callback to a log-in this browser started. An attacker's callback carries the attacker's state, which does not match the victim's stored one.

 Where should the client keep the expected state (and the PKCE verifier and nonce) between the two steps?

If the expected value also comes from the browser, an attacker who can set cookies controls both sides of the comparison. Server-side storage keeps the expected value out of their reach.

 What does the OIDC nonce protect against?

The client sends a fresh random nonce in the authorization request, and the provider copies it into the ID token. A token from any other log-in has a different nonce.

 A client registered https://budget.example/callback. The authorization server accepts any redirect URI that starts with it. What can an attacker do?

Prefix and wildcard matching have led to real code leaks. Compare the whole string against the registered list, exactly.

 The authorization request has an unregistered redirect_uri. What should the server do?

Redirecting to an unverified URI, even with an error, turns the server into an open redirect. Only verified redirect URIs ever receive a redirect.

 An authorization code that was already exchanged is presented again. What should the authorization server do?

Codes are single-use. A second redemption means the code exists in two places, so the tokens from the first redemption may be in the wrong hands too.

 Which set of checks must a client apply to an ID token?

Each check stops a different attack: forgery, tokens from another issuer, tokens for another app, old tokens, and tokens from another log-in.

 An app logs users in by calling the provider's profile endpoint with whatever access token it receives. What is the flaw?

Access tokens do not say which client they were meant for. The ID token's aud does, which is why log-in must rely on a verified ID token (or on running the code flow yourself).

 How should the client identify the local account for an OIDC user?

sub is the provider's permanent, unique id for the user; combined with iss it is unique across providers. E-mails change, get recycled, and are not always verified.

 A token has scope transactions:read and calls POST /api/transfers, which needs transactions:write. What should the resource server answer?

401 means the token is missing, invalid or expired. A valid token without the needed scope gets 403, and the header tells the client which scope it lacks.

 Why does the OAuth 2.1 draft remove the implicit flow (response_type=token)?

Single-page apps once used it because they could not do a code exchange. With PKCE they can, so the code flow replaces it everywhere.

 A client caches the provider's JWKS. An ID token arrives with a kid that is not in the cache. What should it do?

Providers rotate signing keys. Refreshing on an unknown kid handles rotation; limiting how often keeps an attacker from forcing constant refetches. A key supplied by the token itself proves nothing.

 The bank publishes its JWKS at a public URL. Why is that safe?

With RS256, the private key signs and stays with the bank; the public key (modulus n, exponent e) only verifies. Publishing it is the whole point: any client can check the bank's tokens.

 Why do providers sign ID tokens with RS256 (a public/private key pair) rather than HS256 (a shared secret)?

A shared secret gives signing power to everyone who verifies. With thousands of client apps, the provider must be the only party able to sign, which requires an asymmetric key.
