What does TypeScript check in const body: NewUser = JSON.parse(rawBody);?

Types are erased before the code runs, and any is assignable to every type. The annotation only tells the compiler what to assume. A runtime check is the only thing that looks at the actual value.

 Is const body = JSON.parse(raw) as NewUser any safer than the annotation const body: NewUser = JSON.parse(raw)?

An assertion changes only what the compiler believes. It never converts or validates (Type assertions). Both lines compile to the same JavaScript: const body = JSON.parse(raw).

 Where should an API validate a request body?

Validate once at the edge and pass the typed result inward. Checking again everywhere spreads the rules around (and they drift); checking only in the browser trusts clients you do not control.

 A handler validates the body, then saves { ...rawBody, status: "pending" }. What is wrong?

Validators that strip unknown keys return a clean copy. Using the raw input instead of that copy throws the protection away. Always continue with the parsed output.

 What does "parse, don't validate" mean?

A check that returns true leaves you holding the original, untyped value. A parser returns a new value whose type proves the checks passed, so the rest of the code cannot accidentally use unchecked data.

 A team adds phone: string to the Customer type but forgets the hand-written validator, which ends in return input as Customer. What happens?

The type and the checks are separate pieces of code joined by an assertion, so nothing connects them. Deriving the type from a schema (Infer, z.infer) removes the second copy that can drift.

 In the lesson's library, how does Infer<S> get the type a schema produces?

Each schema's TypeScript type carries what it produces (Schema<string>). infer T pattern-matches that parameter. Nothing runs; it is purely type-level.

 What does the return type Schema<{ [K in keyof Shape]: Infer<Shape[K]> }> of object(shape) do?

It is a mapped type: it walks the keys of the shape object and computes each field's type from its schema. That is how NewOrder gets quantity: number and priority: "normal" | "express" without anyone writing them.

 In Zod, what is the difference between schema.parse(value) and schema.safeParse(value)?

For request handling, safeParse fits better: invalid input is an expected outcome, and the discriminated union forces you to check success before reading data.

 What does z.object do with keys that are not in the schema, and how do you make them an error?

Stripping protects against mass assignment silently. Rejecting also tells a client that it misspelled a field (custmerEmail), which would otherwise be quietly ignored.

 A Zod schema turns "₦25,000.00" into 2500000 with .transform. What are z.input and z.output for the field?

Transforms make the accepted shape and the produced shape different. Use the input type for what clients send (and forms), the output type for what your code receives.

 A query string has ?inStock=false. Why is z.coerce.boolean() the wrong tool?

Coercion applies JavaScript's conversion rules, which are about truthiness, not meaning. z.stringbool() accepts "true"/"false", "yes"/"no" and similar words, and rejects anything else.

 A form sends quantity= (empty). What does z.coerce.number().int().min(0) make of it?

An empty field silently becomes a valid 0. Decide explicitly whether empty means "missing" and handle it before coercing, for example by treating "" as undefined.

 Which job needs .refine rather than .transform?

refine adds a rule (true or false, with a message) and leaves the value unchanged. transform changes the value, and its type. Cross-field rules are refinements on the object.

 What is the main reason Valibot uses separate functions combined with pipe instead of method chains?

Tree shaking removes unused modules and functions, not unused methods on a class. For a signup form on a slow phone connection, shipping five checks instead of the whole library matters.

 Which project benefits most from Valibot over Zod?

Both validate equally well. On a server, bundle size is irrelevant; in a browser bundle, Valibot's tree-shakable design keeps the download small. (Zod's zod/mini addresses the same need.)

 What is JSON Schema's main advantage over Zod and Valibot?

A JSON document can be read by any language. The price: no type inference by itself, and custom rules beyond the standard keywords need code.

 You validate with Ajv and a JSON Schema file. How do you get a TypeScript type for the validated data?

A JSON file is data, invisible to the type checker. Some bridge is needed; the generated options avoid drift, the hand-written one reintroduces it.

 With useDefaults: true, Ajv validated an order without priority. Where does priority: "normal" appear?

validate() returns a boolean and mutates the data to add defaults (and, with removeAdditional, to remove fields). Zod and Valibot return a new object and leave the input alone.

 z.toJSONSchema turns a z.object into JSON Schema with "additionalProperties": false. Why is that not exactly the same contract?

Translations are close, not identical, and code-only rules like refine and transform cannot be translated at all. Know which one your server really enforces.

 A schema says items has at most 100 entries. Why do you still need a request body size limit in the HTTP layer?

Validation happens on parsed data. Cap the raw size first (1 MB is common), then let the schema's maximums keep the parsed values reasonable.

 A transfer request { "fromAccount": "0123456789", "amountKobo": 500000 } passes validation. What must still happen before moving money?

A perfectly valid account number can belong to someone else. Authorisation is a separate check, done after validation, with the typed value.

 Why should an API return every validation issue at once, each with a path?

Reporting one problem at a time makes clients guess and retry. Paths let a form show each message next to the right input.

 Which of these is not a boundary where runtime validation pays off?

Validate where data comes from outside the type checker's view: clients, other services, queues, files, old stored data. Inside your own typed code, TypeScript already guarantees the shape.

 In property-based testing of a validator, why generate "near-miss" orders instead of only random JSON?

Random values prove the validator never crashes on garbage. Near misses exercise the actual rules: quantities around 1 and 50, e-mails with and without @, SKUs in the wrong case.

 In a ZudoJS application, which validator should request handlers use?

One schema library across the app means one way to read issues and one source for generated documentation. Schemas and validation in depth covers it.
