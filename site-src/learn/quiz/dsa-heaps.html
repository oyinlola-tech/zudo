What makes a priority queue different from an ordinary queue?

An ordinary queue is first in, first out. A priority queue returns the item with the best priority, whenever it was added. Whether it is sorted inside is an implementation detail; a heap is not.

 A priority queue is an unsorted array: adding pushes to the end, taking scans for the most urgent job. What does draining n jobs cost?

Each take scans all remaining jobs: n − 1, then n − 2, and so on, about n²/2 comparisons in total. With 10,000 jobs that was about 50 million comparisons.

 If you keep the job array sorted instead, what gets slow?

A sorted array makes the take O(1) (it is at one end), but every insert has to shift elements to open a gap. A heap makes both operations O(log n).

 Which statement is guaranteed in a valid min-heap?

The heap property only relates parents to their children. Siblings can be in any order, and the maximum can be any leaf. That weaker rule is what makes a heap cheaper to maintain than a sorted structure.

 Why must a binary heap be a complete tree?

A complete tree fills level by level from the left, which maps exactly onto consecutive array slots, and it has the smallest possible height. Both facts give O(log n) operations without any pointers.

 Why does pop move the last item into the root before sifting down?

Taking the root leaves a hole at the top. Filling it with the last item removes a slot from the end, so the shape stays complete; only the order needs repairing, which sift down does in O(log n).

The child that moves up becomes the parent of its sibling, so it must be the smaller one. Swapping with the larger child would put it above a smaller sibling and break the heap property.

 You change the priority field of a job that is already inside the heap. What happens?

The heap only restores order during push and pop. Changing a field behind its back can leave a small value deep in the tree. Remove and re-add the job (with an index map), or push a new entry and skip the stale one later.

 Heapify sifts down every node that has children. Why does it go from the last such node back to the root?

Leaves are already heaps. Processing nodes from the bottom up means every node's children are roots of valid heaps when it is sifted, so one sift down fixes its whole subtree.

 What does heapify cost for n items, and why?

Half the nodes are leaves (no work), a quarter sift at most one level, an eighth at most two, and so on. The total is less than n levels, so O(n), which is faster than n pushes at O(n log n) in the worst case.

Nodes from ⌊n / 2⌋ onwards are leaves. With 7 items, index 2 has children 5 and 6; with 10, index 4 has child 9. With a single item, −1 means the loop does not run at all: one item is already a heap.

 Which describes heap sort?

Heapify is O(n) and each of the n − 1 extractions sifts down O(log n), all inside the same array. Equal items can swap order, so it is not stable.

The sorted part grows from the back of the array. Swapping the maximum into the last free slot puts it in its final position; a min-heap would put the smallest item at the end, producing descending order.

A strict priority queue can postpone low-priority work forever. Aging, a guaranteed share of workers per priority, or a maximum wait all ensure every job eventually runs. A sequence number only orders equal priorities.

Jobs are promises to do work later. They must survive restarts and be visible to every worker. Redis sorted sets offer the same O(log n) add and take-minimum operations, but durably and shared.
