The Task API sends a reminder email while the user waits. Which set of problems does a job queue fix?

The request only writes down a job and answers at once. A worker does the work later, retries failures, and parks jobs that never succeed where a person can see them.

 A route adds a reminder job and answers straight away. Which status code fits best?

202 Accepted means "I have your request and will do it", not "it is done". The work happens after the response.

 Which of these should not become a background job?

The user needs the login answer right now, and it is fast, so it is a direct call. Slow or unreliable work that the user does not wait for belongs on a queue.

 What should a reminder job's data contain?

Queues are stored, logged and shown in dashboards, so never put secrets in a job. Whole objects may have changed by the time the job runs, so pass ids and load fresh data.

 Why not set a queue's concurrency to 1,000?

Pick a number that the slowest thing your jobs touch can handle, for example the 10 connections a mail provider allows or a database pool of 20.

 Why use exponential backoff instead of retrying at once?

The waits double after each failure (1 s, 2 s, 4 s...) up to maxDelay. Retrying at once mostly hits the same outage again.

 5,000 jobs failed at the same moment. Why does jitter matter for their retries?

Jitter adds randomness to each wait. The default "full" picks a random wait between 0 and the computed one. Leave it on in production; turn it off only for predictable examples.

 A processor sent the email and then failed while writing "sent" to the database. The job is retried. What happens, and what is the fix?

A retry runs the whole processor again. An idempotent processor is safe to run twice: it checks, for example, task.reminded before sending.

 A job runs for the first time. What is job.attempt?

job.attempt counts the tries that came before this one, so it starts at 0. Add 1 if you want to print "try 1".

 You add a job without an attempts option, and the processor throws. What happens?

attempts is the total number of tries, and the default is 1. Set it (and a backoff) for work that can fail temporarily, or set defaultJobOptions on the queue so no route forgets it.

 You need a report built every night at 2:00. What does the lesson say?

delay and scheduledAt postpone one job. Repeating work is the scheduler's job, covered in the next lesson.

 Jobs are piling up in the dead-letter queue. What is the most important thing to have in place?

Watch the count, find the cause, fix it, and replay the jobs with queue.add(dead.job.name, dead.job.data) when a bug caused the failures.

 The error is "mailbox does not exist". What is the best way to handle it in the processor?

Retries are for temporary failures. A permanent error only wastes retries. Record it so the user can fix their address, and keep throwing for errors that a retry can fix.

 A job's timeout runs out. What must the processor do?

The queue aborts the signal and counts the attempt as failed, but it cannot stop a running function by force. A processor that ignores the signal keeps running in the background and wastes a slot.

 What does a graceful shutdown of a worker do?

Jobs that are simply cut off die halfway. worker.stop() waits for the running jobs; waiting jobs stay in the queue for the next worker.

 Your platform kills a stopping process after 20 seconds. How should you set the worker's drainTimeout?

stop() waits at most drainTimeout (30 seconds by default) and then aborts the jobs still running. If the platform kills first, those jobs die without a clean stop.

 What is the main limit of createInMemoryQueue in production?

Production needs a queue backed by a shared store that survives restarts, such as Redis or PostgreSQL, behind the same Queue interface, so your processors do not change.

 A user double-clicks "remind me". The second add throws JobDuplicateError because of the deduplicationKey. What should the route answer?

The duplicate key stopped a second copy of the same job. From the user's point of view, the reminder is queued, so catch JobDuplicateError and answer 202.

 Why create the queue with autoProcess: false when you use a separate worker?

The worker gives you control: its own concurrency, start() and stop(). autoProcess: false leaves all processing to it.
