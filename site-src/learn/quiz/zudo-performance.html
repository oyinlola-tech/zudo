The task list got slow. The team suggests Redis, more servers, a bigger database and a rewrite. What should happen first?

Each guess costs days and may miss the cause entirely. A measurement tells you whether the time is CPU, I/O or queueing, and which function or query is responsible.

 During busy hours the task list is slow, and so is /health, which does no work. What does that suggest?

All routes share one event loop. A route that does nothing only slows down when the loop itself is busy, which points at CPU work in the process, not at a dependency.

 Only POST /tasks is slow. Event-loop delay is 2 ms, database CPU is 10%, and 30 requests are waiting for a pool connection. What kind of slowness is this?

Both the loop and the database are nearly idle, yet requests wait. They are queueing for a limited resource. Find out how long each connection is held before touching the pool size.

 A load test of the generated project reports 300 2xx responses, 1700 non 2xx responses. What should you conclude?

The generated project limits each client to 300 requests per minute, and a load tester is one client. Read the status counts before any latency number, and use a load-test configuration with a higher limit.

 Why run the load generator in a separate process from the server when you want real numbers?

In one process, the client's parsing and bookkeeping compete with the server for the same loop. That is acceptable for comparing two routes, not for absolute numbers.

 In a CPU profile, what is a function's self time?

Total time includes callees; self time does not. The functions with the most self time are where the CPU actually is, which makes them the place to look first.

 The profile's top entry is json http.js:4, the project's helper that builds JSON responses, not JSON.stringify itself. Why?

Native built-ins usually do not appear as separate entries, so their cost shows up in the caller. The helper is where 10,000 tasks were turned into text on every request.

 After paginating the list, the rate limiter's check tops the profile of the load test, which used RATE_LIMIT_MAX=1000000 from one client. With the production limit of 300 it drops to about 3%. What is the right conclusion?

A sliding-log limiter costs time proportional to the requests one client made in the window. In production each client stays under 300; the test made one client send everything under a limit of a million.

 Nine requests take about 15 ms and one takes 900 ms. Which number best shows what the slowest users feel?

The mean (about 100 ms here) describes nobody, and the median hides the slow tail completely. High percentiles show the tail that alerts should watch.

 Why does an N+1 query pattern often look harmless in development?

The problem is the number of round trips, which grows with the page. Count queries per request in development and tests instead of judging by feel.

 EXPLAIN ANALYZE shows Index Scan using tasks_pkey … (actual rows=50) with Filter: (owner_id = 'u-42') and Rows Removed by Filter: 24492. What does it tell you?

Compare rows read with rows returned. The filter threw away tens of thousands of other users' rows. A composite index that matches the filter and the order makes the work proportional to the page.

 Page 801 with LIMIT 50 OFFSET 40000 shows actual rows=40050 on the index scan. What is the better query for deep pages?

OFFSET makes the database produce and discard every earlier row. A keyset query starts right after the last row the client saw, so every page reads 50 rows.

 With a pool of 40, nobody waits in the pool, but the slowest query now takes 200 ms instead of 20 ms and the total time did not improve. What happened?

Past the database's capacity, more connections only make each query slower. The pool's waiting count looks healthy while the real queue hides in the database, where it also slows other services.

 Little's law says the board route needs about 102 busy connections at 400 requests a second, because it makes 51 queries per request. What is the right response?

Pool trouble is often a query problem in disguise. Fewer round trips per request shrink the number of connections needed directly.

 Why is one very popular key a problem in a shared cache such as a Redis cluster, when it is harmless in a single process?

A key lives on one node. Concentrated traffic overloads that node while others idle, and a synchronized expiry makes every server reload at once.

 A local in-process cache with a 1-second TTL sits in front of the shared cache for the launch-week board. For which data would that layer be a bad idea?

The local layer can serve a value up to one second old in each process. For a balance that decides a payment, stale is wrong; read it from the source inside the transaction.

 Why add jitter to the TTL of cache entries that are written at the same time?

Entries written together would otherwise expire together, sending a wave of misses to the database. A small, per-key offset spreads the reloads out.

 A mail provider allows 5 connections and each email takes 40 ms. You raise the worker's concurrency from 5 to 20. What happens?

By Little's law, 5 connections ÷ 0.04 s = 125 per second, whatever the concurrency. Set concurrency at the knee, where the downstream limit is reached.

 Which queue metric tells you most directly that workers are falling behind?

A deep queue that drains quickly is fine. An old job means work is waiting longer than it should, whatever the depth.

 A service keeps recentQuotes.set(requestId, quote) in a module-level Map and never deletes. What will you see in production?

The map keeps every quote reachable, keyed by something unbounded. Every in-memory structure needs a bound, such as a cache's maxEntries.

 Why assert "one query per page" and "a page is at most 8 KB" instead of "responds within 50 ms" in unit tests?

Time-based assertions flake on a busy machine and pass on a fast one. A new query per item or a missing limit changes the count every time.

 A middleware parses every response body and writes it into a log line. What is its cost, compared to one that logs status, size and duration?

Parsing and serializing the body again multiplies the work of producing it. Log facts about the response, not the response.

 createTimingMiddleware() adds a Server-Timing header. What is the concern on a public API?

Timing information can leak facts, such as whether a record was already cached. Send it to internal clients, or sample it.
