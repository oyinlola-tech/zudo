What is the scope of a name?

Scope is where a name exists. Outside its scope, using the name throws a ReferenceError. It is about where, not about the type or the memory.

 What does this print? function makeTitle() { const prefix = "Task:"; return `${prefix} Buy milk`; } console.log(makeTitle()); try { console.log(prefix); } catch (error) { console.log(error.name); }

prefix only exists inside makeTitle. Reading it outside throws a ReferenceError ("I do not know this name"), not undefined.

 Why is it a good thing that a variable inside a function cannot be used outside it?

Each function keeps its own names. Two functions can both have a prefix variable and never clash. That is what makes large programs manageable.

 A name is declared with let inside the body of an if. What kind of scope does it have?

let and const inside { } have block scope: they exist only inside that block. Module scope is for names at the top level of a file.

 You declare const appName = "Tasks"; at the top level of app.js. Where can it be used?

Top-level names have module scope. All code in that file sees them. Other files cannot, unless the file exports them. People often loosely call this "global", but it is not truly global.

 Which of these lives in the truly global scope?

The global scope holds what JavaScript provides, such as console, Math and JSON. You can reach it anywhere, also through globalThis. Your own top-level names are module scope.

 What does this print? const appName = "Tasks"; function count(tasks) { let openCount = 0; for (const task of tasks) { if (!task.done) { const note = "open"; openCount += 1; } } return openCount; } console.log(count([{ done: false }, { done: true }])); console.log(typeof openCount, typeof note, typeof appName);

openCount belongs to the function and note to the if block, so outside they are unknown. typeof is the one place where an unknown name does not throw: it gives "undefined".

 What does this print? if (true) { var a = "var"; let b = "let"; } console.log(typeof a, typeof b);

var ignores blocks: it belongs to the whole function (or module), so a leaks out of the if. let stays inside its block, so b is unknown outside.

 What does this print? for (var i = 0; i < 3; i++) { setTimeout(() => console.log("var:", i), 0); }

The functions run after the loop has finished. With var there is only one i for the whole loop, and by then it is 3. All three functions read that same variable.

 The same loop, but with let. What does this print? for (let j = 0; j < 3; j++) { setTimeout(() => console.log("let:", j), 0); }

With let, every turn of the loop gets its own j. Each function remembers its own copy through a closure, so they print 0, 1 and 2.

 JavaScript uses lexical scope. What decides which outer variables a function can see?

"Lexical" means "about the written text". A function sees the scopes around the place it is written, not the scopes of whoever calls it.

 What does this print? const label = "module"; function show() { return label; } function caller() { const label = "caller"; return show(); } console.log(caller());

show is written at the top level, so it looks up label in the module scope. The label inside caller is invisible to it, even though caller is the one calling it.

 Code inside a function uses the name limit. In which order does JavaScript look for it?

Scopes sit inside each other like boxes. The lookup starts in the innermost box and moves outwards to the module and global scope. The first match wins.

 What does this print? let count = 10; function reset() { let count = 0; count += 1; return count; } console.log(reset(), count);

The inner let count shadows the outer one: it is a new variable that hides the outer name. Changing it does not touch the outer count, which stays 10.

 You notice two variables called user, one in a function and one in a block inside it. What does the lesson advise?

Shadowing works, but a reader easily mixes up which user is meant. Give them different names.

 What is a closure?

A function carries its surrounding scope with it. Even after the outer function has returned, the inner function can still read and change the outer variables. Function plus remembered variables = closure.

 What does this print? function makeCounter() { let count = 0; return () => { count += 1; return count; }; } const nextTaskId = makeCounter(); const nextUserId = makeCounter(); console.log(nextTaskId(), nextTaskId(), nextUserId(), nextTaskId());

Each call to makeCounter creates a new count. nextTaskId and nextUserId each keep their own, so the user counter starts again at 1.

 What does this print? let mode = "normal"; const describe = () => `mode is ${mode}`; mode = "maintenance"; console.log(describe());

A closure keeps a link to the variable, not a snapshot of its value. When describe runs, it reads the current value of mode.

 What does this print? function createStore() { const items = []; return { add(item) { items.push(item); return items.length; }, }; } const store = createStore(); store.add("milk"); console.log(store.add("bread"), store.items);

items is a variable inside createStore, not a property of the returned object. Only add can reach it through the closure, so store.items is undefined. That is private state.

 In the lesson's task store, list() returns tasks.map((t) => ({ ...t })) instead of tasks. Why?

Returning the real array (or the real task objects) would let any caller change private data, for example rename a task. Copies keep the store the only place where tasks change.

 Why is it useful that the task store keeps nextId inside a closure instead of on the returned object?

Only the store's own functions can reach nextId. Outside code cannot reset or change it, so every id stays unique.

 What does this print? console.log(double(4)); function double(n) { return n * 2; }

A function declaration is hoisted ready to call, so you can call it above the line where it is written. This is the only hoisting the lesson says to rely on.

 What does this print? console.log(oldStyle); var oldStyle = "set"; console.log(oldStyle);

A var is created before the code runs and holds undefined until its line runs. It does not fail, which hides the mistake.

 What does this print? try { console.log(limit); } catch (error) { console.log(`${error.name}: ${error.message}`); } const limit = 10;

limit exists (it was hoisted), but its line has not run yet. Using it in this temporal dead zone throws "Cannot access … before initialization". "is not defined" would mean the name does not exist at all.

 What does this print? try { console.log(triple(2)); } catch (error) { console.log(error.name); } const triple = (n) => n * 3;

An arrow function stored in a const follows the const rule, not the function declaration rule. Before its line it is in the temporal dead zone, so calling it throws a ReferenceError.

 Why does the lesson call the temporal dead zone helpful?

var quietly gives undefined, and the bug shows up somewhere else later. let and const throw right where the mistake is.

 What is the difference between "x is not defined" and "Cannot access 'x' before initialization"?

Both are ReferenceErrors. "is not defined" means the name is unknown in every surrounding scope. "before initialization" means you used a let, const or class in its temporal dead zone.

 Why do two calls of the same function never share their local variables?

Every call creates a new execution context: which function runs, its own locals and parameters, and where to return to. So each call has fresh variables.

 a calls b, and b calls c. What does this print? const log = []; function c() { log.push("c"); return "done"; } function b() { log.push("b start"); const result = c(); log.push("b end"); return result; } function a() { log.push("a start"); const result = b(); log.push("a end"); return result; } console.log(a(), log.join(", "));

Calling a function pushes it on the call stack, and the caller waits. c finishes first, then b carries on, then a. The last function called is the first to return.

 While validate runs inside save, which runs inside handleRequest, what are save and handleRequest doing?

Only the context on top of the stack runs. The functions below are paused, waiting for the answer, and carry on from where they stopped.

 What does this print? function countDown(n) { return countDown(n - 1); } try { countDown(3); } catch (error) { console.log(error.name); }

countDown has no base case, so it calls itself thousands of times until the call stack is full. JavaScript then throws a RangeError: Maximum call stack size exceeded.

 What does a recursive function need so it does not overflow the stack?

A base case, such as if (n === 0) return "lift off";, ends the recursion. try/catch only catches the crash, it does not fix it.

 What does this print? function markDone(task) { task.done = true; } function replace(task) { task = { title: "Other", done: false }; } const task = { title: "Buy milk", done: false }; markDone(task); replace(task); console.log(task.title, task.done);

markDone follows the reference to the object on the heap and changes it. replace only points its own parameter at a new object; the variable outside still points at the old one.

 Where do objects, arrays and functions live, and what does a variable hold?

Objects live on the heap. A variable only holds a reference, which is why two variables can point at the same object.

 A server keeps a module-level array cache and pushes every response into it, never removing anything. What happens over time?

The garbage collector only removes objects nobody can reach. A module-level array stays reachable, so it is a memory leak. Use a cache with a size limit and expiry, like @zudojs/cache.

 A stack trace lists several at … lines. How should you read it?

The top of the stack is where it failed. Lines starting with node:internal are Node.js itself, so skip them. The cause is often a step or two further down, in a caller.

 The trace says TypeError: Cannot read properties of undefined (reading 'city') at return user.address.city;. What does it mean?

The message names the property that was being read (city) from something that was undefined. So the value before .city, user.address, is missing.

 The lesson suggests a safer way to read a city when data may be missing. What does this print? const users = [ { id: 1, address: { city: "London" } }, { id: 2 }, ]; function cityOf(id) { const user = users.find((u) => u.id === id); return user?.address?.city ?? "unknown"; } console.log(cityOf(1), cityOf(2), cityOf(3));

?. stops and gives undefined when the value before it is missing, instead of throwing. ?? then replaces undefined with "unknown". For id 3, user itself is undefined, and ?. handles that too.

 What does this print? const level = "module"; function outer() { const level = "outer"; function inner() { return level; } return inner; } const fn = outer(); console.log(fn()); console.log(level);

inner is written inside outer, so it finds outer's level first, and keeps it through its closure even after outer returned. The module's level never changed.

Write limit(fn, max). It returns a new function that calls fn at most max times; after that it returns "limit reached". Use a closure to count. The program should print welcome ada, welcome ada, then limit reached, each on its own line.

 function limit(fn, max) { // your code here } const login = limit((user) => `welcome ${user}`, 2); console.log(login("ada")); console.log(login("ada")); console.log(login("ada")); function limit(fn, max) { let calls = 0; return (...args) => { if (calls >= max) return "limit reached"; calls += 1; return fn(...args); }; } const login = limit((user) => `welcome ${user}`, 2); console.log(login("ada")); console.log(login("ada")); console.log(login("ada")); welcome ada welcome ada limit reached

A calls variable in the closure remembers how many times the function ran. Check it before calling fn. This is the idea behind rate limiting login routes.

This sumTo overflows the stack because it has no base case. Add one, so it returns 0 for n of 0 or less. The program should print 10 and then 0.

 function sumTo(n) { return n + sumTo(n - 1); } try { console.log(sumTo(4)); console.log(sumTo(-2)); } catch (error) { console.log(error.name); } function sumTo(n) { if (n <= 0) return 0; return n + sumTo(n - 1); } try { console.log(sumTo(4)); console.log(sumTo(-2)); } catch (error) { console.log(error.name); } 10 0

if (n <= 0) return 0; stops the recursion. Using <= instead of === also stops it for negative numbers.

This loop saves three functions, but they all print 3. Change the loop so each function remembers its own number. The program should print 0 1 2.

Write once(fn). It returns a function that calls fn the first time and remembers the result; every later call returns that saved result without calling fn again. The program should print setup, then ready ready.

 function once(fn) { // your code here } const init = once(() => { console.log("setup"); return "ready"; }); const first = init(); const second = init(); console.log(first, second); function once(fn) { let called = false; let result; return () => { if (!called) { called = true; result = fn(); } return result; }; } const init = once(() => { console.log("setup"); return "ready"; }); const first = init(); const second = init(); console.log(first, second); setup ready ready

Two closure variables do the job: called remembers whether fn ran, result keeps its answer. Both stay private between calls.

Write a recursive factorial(n): factorial(n) is n * factorial(n - 1), and factorial(1) (and anything below 1) is 1. The program should print 120 1.

 function factorial(n) { // your code here } console.log(factorial(5), factorial(0)); function factorial(n) { if (n <= 1) return 1; return n * factorial(n - 1); } console.log(factorial(5), factorial(0)); 120 1

The base case if (n <= 1) return 1; stops the recursion. Without it, the calls go on into negative numbers until the stack overflows.
