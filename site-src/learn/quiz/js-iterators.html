Which statement describes an iterable correctly?

The iterable is the thing you can walk; it hands out iterators through [Symbol.iterator](). The object with next() is the iterator, one walk with its own position. length has nothing to do with the protocol: a Set has no length and is iterable.

 What does this print? const it = ["ORD-1", "ORD-2"][Symbol.iterator](); it.next(); it.next(); const last = it.next(); console.log(last.value, last.done);

Two calls used up both items. The third call reports the end: done is true and value is undefined. The last real item came with done: false, not with done: true.

 An array iterator has already returned { value: undefined, done: true }. What does another next() call return?

A finished iterator stays finished. To start again you ask the iterable for a new iterator. That is why iterators are called one-shot.

 Why does the protocol separate the iterable (the array) from the iterator (one walk)?

If the position lived on the array, a nested loop over the same array would move the outer loop's position. With one iterator per walk, the two loops are independent.

 What does this print? const stock = { rice: 12, oil: 0 }; try { for (const item of stock) console.log(item); } catch (error) { console.log(error.name); } for (const [sku, qty] of Object.entries(stock)) console.log(sku, qty);

A plain object has no Symbol.iterator method, so for...of throws a TypeError ("stock is not iterable") before the body runs. Object.entries returns an array of pairs, which is iterable.

 What does this print? const prices = [500, 700]; const seen = []; for (const x in prices) seen.push(typeof x); for (const x of prices) seen.push(typeof x); console.log(seen.join(" "));

for...in walks property names, which are strings ("0", "1"). for...of uses the iteration protocol and gives the items, here numbers.

 How many times is next() called? The code counts. let calls = 0; const skus = { [Symbol.iterator]() { const inner = ["A", "B", "C", "D"][Symbol.iterator](); return { next() { calls++; return inner.next(); } }; }, }; const [first, second] = skus; console.log(first, second, calls);

Array destructuring pulls only as many items as it has names for, so next() runs twice. Spread would read until done, which is five calls here.

 A paginator fetches a page only when its buffer is empty. Which line fetches every page?

Spread reads until the iterator reports done, so it pulls every item and therefore every page. The others stop early and call return().

 What does this print? const tag = "🛍x"; console.log(tag.length, [...tag].length);

length counts 16-bit code units, and the emoji needs two of them. The string's iterator walks code points, so spreading gives two characters.

 What does this print? const stock = new Map([["rice", 12], ["salt", 40]]); const counts = stock.values(); const total = [...counts].reduce((a, b) => a + b, 0); console.log(total, Math.max(...counts));

stock.values() is an iterator. The first spread used it up, so the second spread passes no arguments to Math.max, which returns -Infinity. Call stock.values() again for a fresh walk.

 What does this print? const it = new Set(["a", "b"]).values(); console.log(it[Symbol.iterator]() === it);

Built-in iterators are iterable too: their [Symbol.iterator]() returns the iterator itself. That is what allows for (const x of set.values()), and also why such a value can only be walked once.

What does it print? function seats(count) { let n = 1; const iterator = { next: () => (n <= count ? { value: n++, done: false } : { value: undefined, done: true }), }; return { [Symbol.iterator]: () => iterator }; } const row = seats(3); console.log([...row], [...row]);

 How do you make the seats iterable from the previous question reusable?

Each call to [Symbol.iterator]() must return a new iterator with its own position. That is how arrays, maps and sets behave.

 Using the lesson's range convention (end excluded), what does this print? function range(start, end, step = 1) { return { [Symbol.iterator]() { let current = start; return { next() { const inside = step > 0 ? current < end : current > end; if (!inside) return { value: undefined, done: true }; const value = current; current += step; return { value, done: false }; }, }; }, }; } console.log([...range(10, 0, -4)]);

With a negative step the test becomes current > end. 10, 6 and 2 are above 0; the next value, -2, is not, so the walk ends.

 Why does the lesson's range throw for step === 0 when it is created, instead of inside next()?

Validate arguments where they come in. An error at range(1, 10, 0) points at the caller's mistake; an endless loop somewhere later points at nothing.

 In which case does for...of not call the iterator's return() method?

return() is for early exits. When the iterator itself reports done: true, it already knows it is finished, so it should release its resources at that point.

 What does this print? const rows = { [Symbol.iterator]() { let i = 0; return { next: () => ({ value: i++, done: false }), return() { console.log("closed"); return { done: true }; }, }; }, }; try { for (const row of rows) { if (row === 1) throw new Error("bad row"); } } catch (error) { console.log(error.message); }

When the body throws, for...of calls return() on the way out, before the error reaches the catch, just like a finally block would run.

 You walk a database cursor with while and cursor.next(), and break after the first match. What is the risk?

Only protocol consumers such as for...of and destructuring call return() automatically. When you drive next() by hand, cleanup is your responsibility (a try/finally with it.return?.()).

 What happens with [...invoiceNumbers("INV")], where the iterator never returns done: true?

Spread reads until done, and an infinite iterator never says done. With infinite sequences, the consumer must stop: break, destructuring, take or find.

 How many times does the map callback run? let runs = 0; const result = [3, 8, 1, 9, 12, 4] .values() .map((n) => { runs++; return n * 2; }) .filter((n) => n > 10) .take(2) .toArray(); console.log(result, runs);

Iterator helpers pull one item at a time through the chain. 3 and 1 fail the filter, 8 and 9 pass, and after the second pass take(2) stops asking. So map saw 3, 8, 1 and 9: four runs.

 The same chain, written with array methods. How many times does the map callback run? let runs = 0; const result = [3, 8, 1, 9, 12, 4] .map((n) => { runs++; return n * 2; }) .filter((n) => n > 10) .slice(0, 2); console.log(result, runs);

Array methods are eager: map builds a complete new array of six items before filter starts. The result is the same, the amount of work is not.

 Why does { next() { … } }, a hand-written iterator object, not have a .map method, while [1, 2].values() does?

Methods come through the prototype chain. Iterator.from(obj) wraps a plain iterator in one that inherits from Iterator.prototype, and a class can extends Iterator.

 What does this print? const big = [450000, 980000, 30000].values().filter((k) => k > 100000); console.log(big.toArray().length, big.toArray().length);

A helper chain is an iterator, so it is one-shot. The first toArray() used it up. Keep the array from the first call if you need the results twice.

 You have 20 products already in an array and need to show them filtered and sorted in three places on a page. What fits best?

Laziness pays off for large, expensive, streaming or infinite sources, or when you stop early. For a small array used several times, an array result is simpler and reusable.

 A loop for (const item of cart) cart.push(freeGift(item)) never ends. Why?

Array iterators are live: they read the array as it is now. Loop over a copy ([...cart]) or, better, build a new array instead of changing the one you are walking.

 What does this print? const sessions = new Map([["s1", 100], ["s2", 900], ["s3", 50]]); for (const [id, expiresAt] of sessions) { if (expiresAt < 500) sessions.delete(id); } console.log(sessions.size, [...sessions.keys()]);

Deleting the current entry from a Map while walking it is well defined and safe. Every entry is still visited once, so both expired sessions are removed.

 In the lesson's paginator, when does the first request to the API happen?

Creating the paginator or its iterator costs nothing. The request happens only when a consumer actually asks for an item. A paginator nobody reads never calls the API.

 An API returns { items: [], nextCursor: "p3" } for page 2. What must the paginator's next() do?

Some APIs legitimately return empty pages in the middle. Only a missing cursor means the end. That is why next() loads pages in a while loop.

 Why does the paginator's test check the list of fetchPage calls, not just the items it returns?

A test must be able to fail when the property you care about breaks. Laziness is invisible in the results, so the test records the requests.

 What should a paginator do if the server returns the same cursor it was just given?

A repeated cursor is a server bug that turns into an infinite loop and a large bill. Refusing it loudly makes the bug visible.

 What is different about an async iterator?

The async protocol mirrors the sync one, with promises. for await...of waits for each next() result before running the body, so pages are still fetched one at a time.

 Why does the lesson prefer cursor paging over ?offset=20&limit=10?

An offset counts positions, and positions move when data changes. A cursor from the server marks a place in the data itself.

 Why does the lesson's chunk wrapper call source.return?.() in its own return()?

A wrapper sits between the consumer and the source. If it does not pass return() on, the source never learns that nobody is reading any more. The ?. is there because return() is optional.
