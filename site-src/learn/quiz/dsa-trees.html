A menu is printed from flat category rows by calling childrenOf(id), which scans all n rows, once for the top level and once for every category. How does the work grow?

Printing is O(n), but finding children is not: each of the n + 1 calls loops over all n rows, so the comparisons are (n + 1) × n. Building a map from id to node first makes the whole walk O(n).

 Which structure is not a tree?

A tree needs one root, exactly one parent for every other node, and no loops. A and B form a loop: following parents from A never reaches the root. A single node, a wide tree and a chain are all valid trees.

 A category tree has 250 nodes. How many parent-child edges does it have?

Every node except the root has exactly one edge up to its parent, so a tree with n nodes always has n − 1 edges, whatever its shape.

 In the tree All → Electronics → Phones → Android, what are the depth of Phones and the height of Electronics? (Assume Android is a leaf and Electronics has no other deeper branch.)

Depth counts edges down from the root: All → Electronics → Phones is 2 edges. Height counts edges from a node down to its deepest leaf: Electronics → Phones → Android is 2 edges.

 Why does buildTree use a Map from id to node?

With the map, each row finds its parent node in O(1) on average, so two passes over n rows cost O(n). A Map does not sort keys, and set silently overwrites duplicates: you have to detect those yourself.

 buildTree first creates a node for every row, and only then links children to parents in a second loop. What would go wrong if it did both in one loop?

Database rows arrive in any order. If a child row comes before its parent, a single loop tries to attach it to a node that does not exist yet. Creating all nodes first removes that ordering assumption.

A path from a node up to the root has distinct nodes, so its length is at most the number of categories. Anything longer revisits a node: the data contains a loop. The check stops an infinite loop with a clear error.

 You need the total size of every folder in a directory tree. Which traversal fits?

A folder's size is the sum of its children's sizes, so the children must be finished first. Post-order does exactly that; it is what du does.

With a stack (newest first) the walk dives down one branch: depth-first. With a queue (oldest first) it finishes each level before the next: breadth-first. Everything else in the loop stays the same.

Input you do not control can be as deep as the attacker likes. A recursive walk uses one frame per level and throws a RangeError. Rejecting inputs deeper than a sensible limit, or walking with an array as a stack, removes the risk.

 What exactly does the BST invariant require?

The rule is about whole subtrees, not just direct children. A key two levels down that sits on the wrong side of its grandparent breaks the tree even if every parent-child pair looks right.

 Why does an in-order walk of a valid BST produce the keys in ascending order?

In-order is left, node, right. The BST invariant says the left subtree holds exactly the smaller keys and the right subtree the larger ones, so by induction every subtree comes out sorted, whatever the insert order or shape.

 You delete a BST node that has two children. Which key can replace it without breaking the invariant?

The successor is larger than everything on the left (it came from the right) and smaller than everything else on the right (it is the smallest there). Then you delete the successor from the right subtree; it has no left child, so that is an easy case. The largest key on the left works too.

Deleting a leaf returns null, deleting a node with one child returns that child. Returning the new subtree root and assigning it in the parent handles all cases, including the root, without tracking parent pointers.

 Order ids 1, 2, 3, …, 10,000 are inserted into a plain BST in that order. What happens?

A plain BST does nothing to keep its shape. Sorted input builds a chain leaning right, which is a linked list with extra steps: find, insert and delete all become O(n), and building it costs O(n²). Ids and timestamps are very often sorted, so this is a real risk.

 What does it mean for a family of trees to be balanced?

Balance is about height: AVL and red-black trees use different local rules, but both guarantee height O(log n), so every operation stays O(log n). Equal leaf depth is the much stricter "perfect" shape.

 Why do databases use B-trees (nodes with many keys and many children) for indexes instead of binary search trees?

Reading a page from disk costs far more than comparing keys in memory. With hundreds of keys per node, a B-tree over millions of rows is only three or four levels deep, so a lookup touches three or four pages.

 An in-memory service needs only "get the order with this id" and "add an order". Which structure is the best default in JavaScript?

Without ordered queries, a hash map gives O(1) average lookup and insert, and it is built in. A BST earns its place only when you also need keys in order, ranges or min/max with frequent changes.

 Which requirement most clearly calls for a balanced search tree rather than a Map or a sorted array?

A Map cannot answer range queries without scanning everything, and a sorted array pays O(n) per insert or delete. A balanced tree does inserts, deletes and range queries in O(log n + k).

 The lesson tests the BST by running 2,000 random operations against a sorted array. What is the array's role?

Model-based testing compares a clever implementation with a slow but obviously correct one on many operations. Checking the invariant and the contents after each step finds bugs that only appear after a specific sequence, and the fixed seed makes failures replayable.
