Why write automated tests instead of running the code and reading the output?

Every change can break something that used to work, and nobody re-checks forty endpoints by hand after each commit. Tests do it before every commit and on every pull request.

 A test checks that the task store's SQL returns only the current user's tasks from a PGlite database. What kind of test is it?

Your code working together with a real database is an integration test. It is slower than a unit test but catches SQL typos and broken constraints.

 A test sends GET /v1/tasks?limit=0 over HTTP and checks for a 400 problem details body. What kind of test is it?

It tests the whole system from the outside, the way a client uses it. End-to-end tests are the slowest, so projects write only a few of them.

 What mix of tests does the lesson recommend for most projects?

Fast unit tests catch most bugs; the slower integration and end-to-end tests prove that the parts really fit together.

Loose comparison would let a string "1" pass where the number 1 was expected, hiding real bugs.

 Why must you write await assert.rejects(promise, /db down/), with await?

assert.rejects returns a promise itself. Forgetting await lets the test pass even when the promise does not reject the way you expected.

 What does this print? import assert from "node:assert/strict"; async function loadTask(id) { if (id > 10) throw new Error("db down"); return { id }; } await assert.rejects(loadTask(99), /db down/); console.log("first passed"); try { await assert.rejects(loadTask(1), /db down/); console.log("second passed"); } catch (error) { console.log("second failed:", error.code); }

loadTask(99) rejects with a matching message, so the first check passes. loadTask(1) resolves, so rejects itself fails with an AssertionError.

 A failed deepEqual shows + done: false, and - done: true,. What do + and - mean?

The message starts with + actual - expected. Here the code returned done: false, but the test expected done: true.

 Why does the lesson put node --test into package.json as the test script?

node --test finds every test file in the project. Putting it behind npm test gives everyone the same command.

 How does a CI system know that a test failed and a pull request should be blocked?

An exit code of 0 means success; anything else is a failure. CI tools stop and mark the check red on a non-zero exit code.

 TaskList calls notify, which sends an e-mail in the real app. What does a test pass in instead?

Tests must never send real e-mail. A mock such as mock.fn() records callCount() and each call's arguments.

 What does this print? import { mock } from "node:test"; const notify = mock.fn(); notify("task.added", { id: 1 }); notify("task.added", { id: 2 }); console.log(notify.mock.callCount(), notify.mock.calls[1].arguments);

mock.calls has one entry per call, in order, and each entry's arguments is the array of arguments. calls[1] is the second call.

 What does this print? import { mock } from "node:test"; const spy = mock.method(Math, "max"); const result = Math.max(3, 7); console.log(result, spy.mock.callCount()); mock.restoreAll(); Math.max(1, 2); console.log(spy.mock.callCount());

Without a fake, mock.method is a spy: the real Math.max still runs and returns 7, and the call is recorded. After restoreAll(), the real method is back and calls are no longer recorded.

 Why does the lesson call mock.restoreAll() in afterEach?

mock.method changes a shared object, such as mailer or Math. Restoring it after each test keeps the tests independent.

 What should you mock in your tests?

A test that mocks everything only proves that the mocks work. Mock what is slow, costly or outside your control, and test your own logic for real.

Each test must pass on its own and in any order. Give every test a fresh start, for example with beforeEach.

before and after run once per suite; beforeEach and afterEach run around every single test.

 Why test a task store that runs SQL against a real database instead of a mock?

The SQL is the part most likely to be wrong. Only a real database, such as PGlite, runs it and enforces the constraints.

 In the lesson's store test, why is the schema created once in before and each test given await template.clone()?

The second test got id 1 again for "Buy milk": its database really was a fresh copy. Fast and isolated.

 What does this print? import { PGlite } from "@electric-sql/pglite"; const template = new PGlite(); await template.exec("create table tasks (id integer generated always as identity primary key, title text not null)"); const copy = await template.clone(); await copy.query("insert into tasks (title) values ($1)", ["Buy milk"]); const count = async (db) => (await db.query("select count(*)::int as n from tasks")).rows[0].n; console.log(await count(copy), await count(template)); await copy.close(); await template.close();

 Against a real PostgreSQL server, which database should your tests use?

Tests insert and delete rows. Never point them at development or production data. Recreate the tables, or wrap each test in a transaction that is rolled back.

 The HTTP test starts its server with server.listen(0, ...). Why port 0?

The test then reads the real port from server.address().port. It closes the server in after.
