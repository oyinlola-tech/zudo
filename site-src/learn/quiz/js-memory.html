 When may the garbage collector free an object?

Reachability from the roots decides. Other references (from other objects, closures, timers, listeners) keep it alive even after the creating function returns or one variable is cleared.

 Which of these is not a garbage-collection root?

Roots are the starting points: globals, module variables, the stack, and whatever the host holds for you (timers, listeners, pending promise handlers). An object reachable only from garbage is garbage too.

 An order references its customer and the customer references the order. Nothing else references either. What happens?

Mark-and-sweep starts from the roots, so a cycle that no root reaches is never marked. Only pure reference counting (which JavaScript engines do not rely on) had trouble with cycles.

 In a garbage-collected language like JavaScript, what is a memory leak?

The collector frees everything unreachable. A leak means you are still holding a path to objects you do not need, so the collector must keep them.

 Why does V8 split the heap into a young and an old generation?

Temporary objects from each request die quickly and are cleaned up cheaply. A leak shows as an old generation that keeps growing with objects that should have been temporary.

 A module-level Map stores each request's result under the request id "in case it is asked again". Why is this a leak?

A collection with no rule for shrinking grows with traffic until the process runs out of memory. Every growing collection needs a size limit, an expiry, or removal when its owner ends.

 Modules are always in strict mode. What does this print? function addToTotal(kobo) { try { runningTotal = kobo; return "created a global"; } catch (error) { return error.name; } } console.log(addToTotal(5000));

In old non-strict scripts, assigning to an undeclared variable silently created a global that lived forever. In strict mode (every module), it throws a ReferenceError instead.

 Each request calls priceFeed.addEventListener("change", onChange) on a feed that lives as long as the server, and never removes it. What leaks?

The emitter holds a reference to each listener; each closure holds its request's data. The leak costs memory and CPU time on every event.

 Node prints MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 change listeners added. What should you do first?

The warning fires when one event gets more than 10 listeners, which usually means listeners are added per request or per connection and never removed. Raise the limit only when many listeners are genuinely intended.

 A connection starts setInterval(() => ping(session), 30_000) and nobody calls clearInterval when the connection closes. What stays alive?

A pending timer is a root: the host holds its callback until it fires, and an interval fires forever. Clear it in the code that ends its owner's life.

 What does timer.unref() do in Node.js?

unref is for background housekeeping timers that should not keep a process alive. It does not free anything and is not a fix for a timer leak.

V8 keeps only variables some closure uses, but it keeps them in one shared context per scope. Any long-lived closure from that scope keeps the whole context, including rows.

 What does every production cache need so it cannot leak?

A cache grows by design, so it needs a rule for shrinking. Size limits bound memory; expiry bounds staleness and removes entries nobody reads.

 What must code always handle when it calls ref.deref() on a WeakRef?

A WeakRef does not keep its target alive, so the target can disappear at any time after the current task. Treat undefined as a cache miss and rebuild.

 Which is a correct use of FinalizationRegistry?

The specification does not promise when, or even whether, a finalization callback runs. Use it only for memory bookkeeping; essential clean-up must be explicit (close(), try/finally).

 Which process.memoryUsage() field is closest to what a container's memory limit (and an OOM kill) looks at?

rss (resident set size) is all the memory the process holds: heap, code, stacks and buffers. heapUsed is the best number for spotting a JavaScript object leak, but the limit applies to the whole process.

 A graph of heapUsed shows a sawtooth: it rises, drops sharply, rises again. The low points stay at the same level over a day. What does it show?

Rising and dropping is normal allocation and collection. A leak shows as a baseline (the low points after each collection) that keeps rising.

 What does a heap snapshot give you that process.memoryUsage() does not?

memoryUsage tells you that memory grows; a snapshot tells you what is on the heap and why it is still reachable.

 What is the most effective way to find a leak with heap snapshots?

Comparing snapshots isolates what the batch of work left behind. The retainer chain of one leaked object points at the root holding it, and so at the line to fix.

 Why should you not casually take heap snapshots on a busy production server?

Use staging, or take one instance out of the load balancer first. Node can also write a snapshot automatically near the heap limit with --heapsnapshot-near-heap-limit.

 A team's fix for a leak is "restart the service every night". What is wrong with that?

A leak grows with work done, not with time. More traffic means a crash sooner. Reproduce it, snapshot, compare, and fix the reference.
