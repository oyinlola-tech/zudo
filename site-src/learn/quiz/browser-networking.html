A front end calls the Task API with Authorization: Bearer <API key>, the key written into app.js. What is the real problem?

Anything shipped to the browser can be read in the developer tools. Browser apps prove who the user is with a login and a session (an HttpOnly cookie), not with a shared key.

 A request works with curl and from Node.js, but the same request from a page fails with a CORS error. Why?

The server answers every client the same way. Only the browser checks the Access-Control-Allow-* headers before letting page code read the response, because it acts for a user who may be logged in to many sites.

 A page is served from https://tasks.example/app. Which request is same-origin?

An origin is scheme + host + port. Only the path may differ. A subdomain, plain HTTP or another port make it a different origin.

 What does the same-origin policy not prevent?

The policy blocks reading, not sending. That is why cross-site request forgery is possible and why cookies need SameSite and state-changing routes need CSRF protection.

 Which cross-origin request is sent without a preflight?

A simple request is one an HTML form or a plain link could have sent: GET, HEAD or POST, only safe headers, and a form content type. JSON bodies, other methods and custom headers need the server's permission first.

 The API answers Access-Control-Allow-Origin: *, and the front end uses credentials: "include". What happens?

* is for public data that needs no user identity. For requests carrying cookies, the server must deliberately name each trusted origin.

 To "fix CORS", a developer makes the server copy whatever Origin header arrives into Access-Control-Allow-Origin, with credentials allowed. What have they done?

Echoing any origin grants permission to every page on the internet. Compare the origin exactly against a configured allow-list, and echo it only when it matches.

 Why does the API send Vary: Origin?

A shared cache that ignored the header could hand Access-Control-Allow-Origin: https://tasks.example to a request from a different origin, or the reverse. Vary lists the request headers that change the answer.

 Logged-in users get "Response to preflight request doesn't pass access control check" on PATCH requests only. The server runs its session check before its CORS code. What is wrong?

The preflight asks for permission; it does not carry credentials. Answer it before authentication. That is why the lesson's API calls handleCors first.

 What does HttpOnly on the session cookie protect against?

An HttpOnly cookie is invisible to document.cookie, so XSS cannot steal it. Secure handles plain HTTP, and SameSite handles cross-site requests.

 The front end on http://localhost:5173 logs in to the API on http://localhost:3000. Login succeeds, but every later request gets 401. The requests use fetch(url) with no options. What is missing?

With the default credentials: "same-origin", cookies from a cross-origin response are not stored and none are sent. The API must also allow credentials in its CORS headers.

 Why does a SameSite=Lax session cookie still work between app.tasks.example and api.tasks.example?

Origin compares scheme, host and port; site compares the registrable domain. CORS is about origins, SameSite about sites. Keeping the front end and the API on one site avoids third-party cookie problems.

 When does await fetch(url) give you the Response?

That is why there are two awaits: one for the headers, one for the body. You can check response.ok and the content type before deciding to read the body.

 A page calls fetch(url, { headers: { Cookie: "session=abc" } }). What does the browser do with that header?

If pages could set Cookie, Origin or Host, they could impersonate users and other sites. The lesson's example showed these headers disappear from the Request.

 The API sends X-Total-Count: 57 on GET /tasks. The Network tab shows it, but cross-origin page code gets null from response.headers.get("x-total-count"). Why?

CORS controls headers as well as bodies. Access-Control-Expose-Headers: X-Total-Count makes it readable. Set-Cookie can never be exposed.

 A developer "fixes" a CORS error by adding mode: "no-cors". What happens?

no-cors is for requests whose answer you do not need to read, like caching images. The fix for CORS errors is on the server (or serving both from one origin).

 Why does the lesson's client show "Could not reach the server" when CORS blocks a request?

Browsers deliberately hide why a cross-origin request failed. A developer must read the console and the Network tab; the user can only be told to try again.

 A POST /orders times out. Why is retrying it automatically risky?

After a timeout you do not know what happened on the server. Retry idempotent requests freely; retry a POST only with an idempotency key the server uses to recognise duplicates.

 A search box sends a request per pause in typing, and sometimes shows results for an older term. What is the fix?

Responses can arrive in any order. Cancelling the old request means only the latest one can update the page. A longer debounce only makes the race rarer.

 What is the simplest production setup that avoids CORS entirely?

Same-origin requests need no CORS headers and no preflights, and the default credentials setting sends the session cookie. Development servers offer a proxy setting for the same result locally.
