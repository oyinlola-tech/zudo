Why does reading orders[40000] take the same time as reading orders[0]?

Contiguous storage means one multiplication and one addition find any slot. Nothing walks past the earlier items, so indexing is O(1).

 A "recently viewed products" list adds each new product with unshift. What does each unshift cost on a list of n products?

The slots must stay contiguous from index 0, so inserting at the front moves everything. Adding at the end with push and reading the list backwards avoids the moves.

 This loop is meant to remove every cancelled order. What goes wrong? for (let i = 0; i < orders.length; i++) { if (orders[i].status === "cancelled") orders.splice(i, 1); }

splice shifts later items left, but i still increases. The skipped item is only checked if you walk backwards or rebuild the array. It is also O(n²) in moves.

 Walking the same splice loop backwards (from the last index to 0) fixes the skipped items. What is its cost for n orders when a third of them are cancelled?

Walking backwards fixes correctness, not cost. Removing near the front still moves almost everything behind it. filter or a read/write index compaction is O(n).

 You must remove all cancelled orders from 200,000 orders and nothing else holds a reference to the array. Which approach is both correct and O(n)?

filter reads each order once and writes survivors into a new array. The indexOf loop is the worst of all: each search is O(n) and each splice is O(n), repeated for every cancelled order.

 What happens when you write ids[1000000] = "ORD-1" into an empty array?

Holes are missing entries, not undefined values (0 in ids is false). Engines keep fast contiguous storage for dense arrays; very sparse ones may fall back to a dictionary. Keep arrays dense.

 A payout job empties an array of 50,000 transfers with while (transfers.length) process(transfers.shift()). What is the better way when the array does not need to shrink as you go?

shift and splice(0, 1) both move every remaining item: O(n) each, O(n²) for the loop. An index does not move anything. For a real queue that also receives new items, use a queue structure.

An engine optimisation is not a guarantee. A test on 100 items hides the growth; measure at production sizes, and design for the documented cost.

 What does currency.toUpperCase() do to const currency = "ngn"?

Strings are immutable. Every method that seems to change one returns a new string, in O(length) time. const is not the reason: a let string would not change either unless you assign the result back.

 What does line.slice(0, 20) cost, and why?

Treat string operations that produce a new string as proportional to the length they produce or scan. Engines sometimes share memory internally, but you cannot rely on it, and the result is still a new immutable string.

 Which statement-building loop has a hidden quadratic cost in V8?

V8 makes appending cheap by building a rope and copying later. Reading the partly built string (endsWith, includes, indexing) forces a flatten, a full copy, on every iteration: O(n²) overall.

 Why is parts.join("") a safe way to build a big string on every engine?

The expensive part of repeated concatenation is copying the growing result again and again. join copies each character exactly once.

 Why is "₦".length 1 but "🎉".length 2?

JavaScript strings are sequences of 16-bit code units. Characters outside the first 65,536 code points take two. [...text].length counts code points instead.

Split by code point with [...text] to keep each emoji whole. Emoji built from several code points (flags, families) need Intl.Segmenter.

The comparison only keeps two indexes. The normalization before it costs O(n) space, so the whole function is O(n) space, but the comparison step adds nothing that grows.

The sorts dominate. Counting characters with a Map brings it down to O(n), which the hash maps lesson explains.

Both contain exactly a and b and have length 3, but the counts differ. A set forgets how many times each character appears; a count does not.

% in JavaScript keeps the sign of the left operand. The empty array still needs its own check first, because k % 0 is NaN.

pop is O(1), but unshift is O(n). With two slices or three reversals the cost is O(n) whatever k is (after normalizing k below n).

 Rotating in place with three reversals (whole array, then the first k, then the rest) uses how much extra space?

Every reversal swaps items inside the same array using two indexes. The two-slice version is simpler but allocates a new array: O(n) extra space.

Typed arrays store raw numbers contiguously and are fast, but each element type has a fixed range. Float64Array or BigInt64Array fits larger amounts; choose based on the range you need.

The non-mutating methods (toSorted, toReversed, toSpliced, with) are safer but always copy. Hoist them out of loops.
