Why is the idempotency key stored with UNIQUE (user_id, idempotency_key) rather than unique on the key alone?

A key is chosen by the client. Scoping it per user means a guessed or colliding key never exposes another customer's stored result.

 The same Idempotency-Key arrives with a different card token. What does Oja answer, and why?

The stored SHA-256 fingerprint of the request is compared with the new one. Silently replaying would tell the client its new card was charged when it was not.

 What does CREATE UNIQUE INDEX one_live_payment_per_order ON payments (order_id) WHERE status <> 'declined' guarantee?

A partial unique index only covers rows that match its WHERE. It stops two keys (two devices, an app bug) from charging one order twice, while still allowing retries after a decline.

 A client sends {"orderId": 7, "card": "tok_ok", "amountKobo": 100}. What amount is charged?

Prices and totals are facts the server owns. The schema only knows orderId and card, and the service copies the order's total into the payment row.

 PayGate never answers the charge request, even after retries. Why does Oja record the payment as unknown instead of declined?

No answer is not a "no". The reconciliation job, or a client retry, asks the gateway later and settles the payment with the real outcome.

 Which status does POST /v1/payments return for a payment that is unknown?

202 is honest: accepted, not finished. The client shows "payment pending" and polls GET /v1/payments/:id, or retries with the same key, which checks with the gateway.

 The HttpClient retries only GET, HEAD and OPTIONS by default. Why is it safe for the PayGate adapter to retry POST?

Retrying a non-idempotent request is how double charges happen. The key turns the POST into an idempotent operation at the gateway; without it the retry option would be a bug.

 The adapter's key is oja-pay-<payment id>, not the client's key and not a new random value per attempt. Why?

A new key per attempt would let each attempt charge. Deriving it from our own payment id ties the key to the thing that must be charged once.

 Why does the service call the gateway between two transactions instead of inside one?

Transaction 1 records the intent ("processing"), the call happens, transaction 2 records the outcome. If we crash in between, the "processing" row tells reconciliation what to look up.

 settle runs UPDATE payments SET status = $2 … WHERE id = $1 AND status IN ('processing', 'unknown'). What happens when the reconciler settles a payment a client retry has already settled?

Making the state change conditional on the current state makes it idempotent. Several paths may report an outcome; only the first one counts.

 Why is payment.succeeded written to an outbox table in the same transaction as the status, instead of being published directly?

Publishing before the commit can announce something that is then rolled back; publishing after it can be lost in a crash. The outbox row commits atomically with the change, and a relay publishes it.

 The relay publishes an event and then marks the row published. What happens if it crashes between the two steps?

There is no way to make "publish" and "mark" one atomic step across two systems. At-least-once delivery plus idempotent consumers is the standard answer.

 Which layer stops a duplicate SMS when the worker sent it and then crashed before writing the notifications row?

The queue and the table only know what was recorded. Between sending and recording, only the receiving side can recognise the repeat, which is why the key travels with the message.

 Reconciliation finds a payment still processing after the cut-off, and PayGate has no charge with its reference. What does it do?

This is the crash between transaction 1 and the charge. Old enough and unknown to the gateway means the charge never happened. Reconciliation never charges; it only settles.

 A client retries with the same key while its payment is still unknown. What does the service do?

The retry is an occasion to learn the outcome, never to charge again. That is how the "database failed after the charge" demo recovered with one charge.

 PayGate answers 402 card_declined. How does the adapter treat it?

Retries are for failures that may pass (5xx, timeouts). A decline is the gateway's decision about this card.

 PayGate answers 401 bad_key. Why does the adapter throw instead of returning an outcome?

Mapping it to "declined" would tell customers their cards are bad while every payment fails because of us.

 Two simultaneous requests with the same key: the test accepts 409 or a replay for the loser, but exactly one fresh 201 and one charge. Why not require exactly 201 and 409?

Test the invariant (one charge, no second fresh success), not the schedule. Flaky tests teach people to ignore failures.

 What does the type argument in bus.on<Event<PaymentEvent>>("payment.succeeded", …) guarantee at runtime?

The lesson accepts it because only settle writes these events. When other code can publish, validate the payload with a schema in the handler.

 Why does Oja's API accept a card token (tok_…) and never a card number?

Data you never hold cannot leak from your logs, database or backups.

 Why must a webhook signature be checked over the raw request body, not over JSON.stringify(JSON.parse(body))?

A signature covers bytes. Verify first on the raw text, parse afterwards.

 The webhook header contains a timestamp that is part of the signed text, and the verifier rejects anything older than five minutes. What attack does that stop?

An old but genuine message still has a valid signature. Signing the timestamp and checking its age, plus remembering event ids, stops replays.

 What should a notification job contain?

Queues are stored, logged and shown in dashboards. Secrets in jobs leak there.
