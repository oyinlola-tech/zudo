How is every JavaScript number stored?

All numbers share one format, integers included. The 53 significant bits decide where integers stop being exact.

 Why is 0.1 not stored exactly?

Just as 1/3 has no finite decimal form, 1/10 has no finite binary form. The stored value is slightly above 0.1.

 What does this print? console.log(0.1, (0.1).toPrecision(20));

Printing shows the shortest decimal that maps back to the same double, 0.1. Asking for 20 significant digits reveals the stored value, a little above 0.1.

 What does this print? console.log(2 ** 53 + 1 === 2 ** 53, Number.isSafeInteger(2 ** 53), Number.isSafeInteger(2 ** 53 - 1));

Above 253 the gap between doubles is 2, so 253 + 1 rounds back to 253. That is why 253 itself is not "safe": another integer rounds to it.

 Number.isInteger(2 ** 60) is true. Why is it still wrong to trust 2 ** 60 as an exact order id?

isInteger only asks "is there a fraction?". isSafeInteger also asks "is this the only integer with this representation?".

 What does this print? const order = JSON.parse('{"id": 9007199254740993}'); console.log(order.id, String(order.id) === "9007199254740993");

JSON.parse converts every number to a double. 9007199254740993 is not representable, so it becomes its even neighbour, silently.

 What is Number.EPSILON?

It is the spacing of doubles near 1. The spacing grows with magnitude, so it is not a universal tolerance. The smallest positive number is Number.MIN_VALUE.

 Why does Math.abs(a - b) < Number.EPSILON fail to treat 1e20 + 30000 and 1e20 as nearly equal?

Scale the tolerance with the values, for example relative * Math.max(|a|, |b|).

 What does this print? console.log(0.1 + 0.2 + 0.3 === 0.6, 0.3 + 0.2 + 0.1 === 0.6);

Every addition rounds, and different orders round differently. 0.1 + 0.2 is already 0.30000000000000004, and adding 0.3 gives 0.6000000000000001; the other order happens to land on 0.6.

 What does this print? console.log(1 / 0, 0 / 0 === 0 / 0, Object.is(-0, 0), Math.max());

Dividing by zero gives Infinity; NaN is never equal to itself; Object.is distinguishes -0 from 0; and the maximum of nothing is -Infinity.

 An API receives {"quantity": 1e308} and later {"quantity": "5"}. Which check rejects both as quantities?

1e308 is a number but not a safe integer; "5" is a string, and Number.isSafeInteger does not coerce. typeof would accept 1e308, NaN and Infinity.

 A refund of −0.001 naira is shown to a customer. What does this print? const refund = -0.001; console.log(refund.toFixed(2), String(Math.round(-0.4)), Object.is(Math.round(-0.4), -0));

toFixed keeps the sign of a tiny negative, printing "-0.00". Math.round(-0.4) is negative zero; String prints it as "0", but Object.is sees it.

 What does this print? console.log(Math.round(2.5), Math.round(-2.5), (2.5).toFixed(0), (-2.5).toFixed(0));

Math.round rounds halves towards +∞, so −2.5 becomes −2. toFixed rounds halves away from zero, so it gives "−3".

 A refund of −7 kobo is split between 2 accounts with integer division. What does this print? console.log(Math.trunc(-7 / 2), Math.floor(-7 / 2), -7 % 2);

trunc drops the fraction (towards zero), floor goes down (towards −∞). % keeps the sign of the left side, which matches trunc: −7 = 2 × −3 + −1.

 Why do many accounting systems prefer round half to even?

Always rounding halves up adds a small bias every time. Half-even removes that bias on average: 2.5 → 2, 3.5 → 4.

 What does this print? console.log(Math.round(1.005 * 100), (1.005).toFixed(2));

The stored 1.005 is slightly less than 1.005, so both the product and the value toFixed rounds are just below the half. Rounding afterwards cannot fix a number that is already on the wrong side.

 What does this print? const twoDecimals = new Intl.NumberFormat("en", { minimumFractionDigits: 2, maximumFractionDigits: 2 }); console.log((1.005).toFixed(2), twoDecimals.format(1.005));

toFixed rounds the stored double (just below 1.005). Intl.NumberFormat starts from the shortest decimal for that double, "1.005", and rounds half away from zero. Two formatters, two answers: round your kobo once yourself.

 A function decides rounding by comparing 2 * remainder with the denominator, all in whole kobo. What is the advantage over Math.round(numerator / denominator)?

With integers there is no representation error, so an exact half is recognised as exactly half and the rule you chose is the rule that runs.

 An empty price field and a price with a comma arrive. What does this print? console.log(Number(""), Number("1,250"), parseFloat("1,250"), Number(null));

Number turns an empty string and null into 0, which would make a product free. parseFloat stops at the comma and reads 1. Neither is safe for money.

 Why does a safe money parser split "1250.50" at the point and build 1250 * 100 + 50 instead of computing Math.round(parseFloat("1250.50") * 100)?

"1.005" × 100 shows the problem. With the text approach, no fraction is ever stored in a double.

 A cashier types "1.005". What should a strict naira parser do?

Whatever happens to sub-kobo input must be a visible decision. Silent rounding hides typing mistakes and wrong data feeds.

 What does this print? try { console.log(10n + 1); } catch (error) { console.log(error.name); } console.log(10n > 9, 10n == 10, 10n === 10);

Arithmetic never mixes bigint and number silently. Comparisons across the types are allowed, but === also compares types, so it is false.

 What does this print? console.log(7n / 2n, -7n / 2n, 7n % 2n);

Bigint division truncates towards zero. Any other rounding must be written by hand with the remainder.

 What does this print? console.log(BigInt(9007199254740993), BigInt("9007199254740993"));

The number literal was rounded before BigInt saw it. Converting from a string keeps every digit.

 What does JSON.stringify({ total: 5n }) do?

JSON readers elsewhere might round a large integer, so JavaScript refuses by default. Use a replacer that turns bigints into strings (or JSON.rawJSON digits).

 What is the best way for an API to send a 64-bit order id in JSON?

Ids are labels, not quantities. Strings keep every digit in every language; large payment and messaging APIs do exactly this.

 What does this print? const text = '{"id": 12345678901234567890, "qty": 2}'; const data = JSON.parse(text, (key, value, context) => (key === "id" ? context.source : value)); console.log(data);

The reviver's third argument gives the original source text of a number. Returning it keeps the id as an exact string.

 A function sums kobo amounts and the total passes Number.MAX_SAFE_INTEGER. What does the lesson's sumKobo do, and why?

The rare huge-total case should be handled by code designed for it (a bigint path), not discovered later in a reconciliation report.

 Why create new Intl.NumberFormat("en-NG", { style: "currency", currency: "NGN" }) once at module level?

The same applies to every Intl object: build once, call format many times.

 What does this print? const naira = new Intl.NumberFormat("en-NG", { style: "currency", currency: "NGN" }); console.log(naira.format(1234567.5), naira.format(-2500));

The en-NG locale uses the naira sign, commas for thousands, a point for decimals, and the currency's two decimals.

 What does this print? const percent = new Intl.NumberFormat("en-NG", { style: "percent", maximumFractionDigits: 1 }); console.log(percent.format(0.075), percent.format(7.5));

Percent style multiplies by 100. Pass the fraction (0.075) for 7.5%.

 Why does formatKobo build a decimal string such as "90071992547409.93" and pass it to format, instead of passing kobo / 100?

For amounts near the safe limit, kobo / 100 is already off by a kobo before formatting. Integer division and remainder produce an exact string.

 A shop starts selling in Japanese yen as well as naira. What changes about "minor units"?

resolvedOptions().maximumFractionDigits of a currency formatter reports the decimals: 2 for NGN, 0 for JPY, 3 for KWD.

 Which is the right source for a 6-digit one-time password sent by SMS?

Math.random is predictable given enough outputs. Anything an attacker must not guess needs a secure random source.

 The pg driver returns a PostgreSQL bigint column such as amount_kobo as the string "125050". Why, and what should your code do?

The driver cannot know whether your values stay in the safe range, so it hands you the exact digits and lets you choose.

 Which is the best use of bigint in a shop's backend?

Bigints hold only integers, are slower, and do not mix with numbers. Use numbers for ordinary amounts checked with isSafeInteger, and bigints for aggregates and 64-bit values that need arithmetic.

 What happens when a calculation goes beyond Number.MAX_VALUE?

Floating-point overflow never throws. Validate results with Number.isFinite when inputs can be large.
