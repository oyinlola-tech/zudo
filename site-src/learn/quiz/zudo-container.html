What does dependency injection mean?

With dependency injection the class does not build its store or clock itself: the caller passes them in. That is why they can be shared between services and replaced in tests.

 A TaskService does new TaskStore() and new Date() inside itself. Why is it hard to test?

The service decides everything itself, so the test has no way in. Once the store and a clock are passed in, the test can pass a clock that always says the same date and check the exact output.

 What is the composition root?

Someone still has to call the constructors in the right order. Doing it in one place (in the Task API, src/container.ts) keeps the wiring out of the services themselves.

 Why can't an interface such as Clock be used directly as a container token?

TypeScript removes interfaces when it compiles. A class does exist at runtime, so it can be its own token; an interface needs a token made with createToken<Clock>("Clock").

 Why does the lesson prefer createToken<number>("MaxTasks") over a plain string token like "maxTasks"?

With a string, resolve<number>("clock") compiles even if "clock" holds a clock object. A token made with createToken<T> carries its type, so resolve returns a T.

 What does container.registerExisting(LOGGER, AppLogger) do?

registerExisting is an alias provider. If AppLogger is a singleton, both tokens give you the very same object.

 registerClass(TaskService, TaskService, { inject: [TaskStore, CLOCK] }). Which habit does the lesson recommend for inject lists?

The tokens are passed to the constructor by position, in the order you list them. A small test that resolves every service catches a wrong list before users do.

 You register a class without a scope option. What lifetime does it get?

Transient is the default. If a service must be shared (a store, a pool, an id generator), say scope: ContainerScope.SINGLETON yourself.

 A RequestContext holds data about one HTTP request (who is calling, the request id). Which lifetime fits?

Scoped means one instance per createScope(). Everything inside one request shares it, and the next request gets a fresh one. A singleton would mix different users' data.

 Why does the container refuse a singleton that depends on a scoped dependency (CaptiveDependencyError)?

A singleton lives as long as the container. If it captured one request's RequestInfo, every later request would read that first request's data: a real data leak. The rule: a dependency must live at least as long as the thing that uses it.

 Which of these registrations is allowed?

A transient object is created for the request and never outlives it, so it may use a scoped dependency. The singleton case is a CaptiveDependencyError, resolving scoped without a scope is a ScopedResolutionError, and a second registration is a DuplicateRegistrationError.

 TaskService needs Notifier, and Notifier needs TaskService. The container throws CircularDependencyError. What is a good fix?

A cycle is a design problem, not a container problem: neither class can be built first, whatever the lifetime. Break the loop by pulling the shared logic out, or by publishing an event instead of calling the other class directly.

 Which objects does await container.dispose() call dispose() on?

The container cleans up what it created and kept: its singletons (and a scope cleans up its scoped objects). Transients are not tracked, and values from registerValue were not created by the container, so it does not own them.

 Why does the container dispose singletons newest first?

A service is created after its dependencies, so newest first means "users before the things they use". The service can still flush its work through the pool, then the pool closes.

 In the Task API, when should you dispose the container?

By default the runtime does not dispose the container for you (the disposeContainerOnStop: true option changes that). Modules may still use services while they stop, so the container is disposed last.

 In a test you want the real TaskNotifier but a fake MAILER that is already registered. What should you do?

Registering the same token twice is a DuplicateRegistrationError, on purpose, so a typo cannot silently replace a real service. replace says you mean it, and singletons built on the old mailer are rebuilt.

 In the Task API schema, why write schema.enum(["low", "normal", "high"] as const)?

as const keeps the exact strings, so Infer gives "low" | "normal" | "high", which fits the store's Priority type. It is about the TypeScript type, not the runtime check.

 A route in the Task API needs the TaskService. How should it get it?

The runtime's container holds the singleton service that shares the one store. Calling new, or resolving from a brand-new container, would give the route a second store that the rest of the app never sees.
