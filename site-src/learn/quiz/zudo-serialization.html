What is serialization?

A value must become text or bytes before it goes into a queue, a cache, a file or an HTTP response. Turning the text back into a value is deserialization. Checking the shape is validation, a separate step.

 Which value can plain JSON hold without changing it?

JSON only knows strings, numbers, booleans, null, arrays and plain objects. A Date becomes a string, a Set becomes {}, and a BigInt is refused.

 What does this print? const task = { id: 1, due: new Date("2026-10-05T09:00:00Z") }; const back = JSON.parse(JSON.stringify(task)); console.log(typeof back.due, back.due);

JSON.stringify writes a Date as an ISO string, and JSON.parse has no way to know it was a date. Code that later calls back.due.getTime() crashes.

 What does this print? const task = { tags: new Set(["home", "urgent"]), notes: new Map([["2026-10-01", "called the bank"]]), }; console.log(JSON.stringify(task));

A Set and a Map keep their items in a hidden place, not in normal properties, so JSON sees empty objects. The tags and notes are silently gone, with no error.

 What does this print? const failure = { lastError: new Error("mail server is down") }; console.log(JSON.stringify(failure));

An error's message is not a normal enumerable property, so plain JSON writes {}. The message is lost.

 What does this print? try { console.log(JSON.stringify({ views: 12345678901234567890n })); } catch (error) { console.log(error.name); }

JSON refuses a BigInt with a TypeError. It will not guess, because a normal JSON number cannot hold that many digits exactly.

 A queue is created with createJsonSerializer({ preserveTypes: false }). A job's type says { remindAt: Date }, but the processor receives a string. Why does TypeScript not warn you?

TypeScript trusts the type you wrote. Plain JSON turned the date into a string at runtime, and the program runs until the first line that uses it as a Date, such as remindAt.toISOString(). The queue's default serializer keeps the Date, which is why this only happens when you switch to plain JSON.

 npm says "up to date" when you install @zudojs/serialization, because the queue and cache already use it. Why install it yourself anyway?

If you import a package, list it. Otherwise a future version of the queue could drop or change that dependency, and your code breaks without any change of yours.

With preserveTypes: true, a value that JSON cannot hold becomes a small object with a $type tag and a $value. It is still valid JSON, and the reader can rebuild a real Date.

The tags let the reader rebuild each value: a real Date, a real Set and a real bigint. Plain JSON.parse would give a string, an empty object, and an error for the BigInt.

 What does this print? import { createSerializer } from "@zudojs/serialization"; const serializer = createSerializer("json", { preserveTypes: true }); console.log(serializer.serialize({ n: 5n, tags: new Set([1, 2]) }));

A BigInt is written as its digits in a string, so no precision is lost. A Set is written as an array of its items. Both carry a $type tag.

 How does the serializer write a Uint8Array of raw bytes?

Base64 is a compact way to write bytes as text. The tag says it was a byte array, so the reader rebuilds a real Uint8Array. Plain JSON would write { "0": 137, "1": 80, … }.

 Where should you use preserveTypes: true?

The text is longer, and a service not written in JavaScript sees $type tags it does not know. For a public API, send plain JSON with dates as ISO strings, and parse them with a schema.

 What does this print? import { createSerializer } from "@zudojs/serialization"; const serializer = createSerializer("json", { preserveTypes: true }); const text = serializer.serialize({ lastError: new Error("mail server is down") }); console.log(text);

An error keeps its name and message. The stack trace is left out unless you ask for it with includeStack: true.

 Why does the serializer leave out an error's stack trace by default?

A stack trace lists your file names and code lines. Leaving it out is the safe default. Turn it on with includeStack: true only where you control who reads the data.

A value that contains itself has no end, so it cannot be written out. The serializer stops with a clear CircularReferenceError, which also says where the loop is (root.parent).

An invalid date is refused instead of being written as null (which is what plain JSON does). You find the bug where it happens, not later when a reminder never fires.

 Text arrives from another service. Which options should you set when you deserialize it?

Huge or very deeply nested text can use up memory or crash the reader. Set both limits whenever the text comes from outside.

 An attacker sends this text. By default, a tag that makes no sense is left as plain data, so one bad record does not stop your consumer. With strict: true it throws instead.

 When should a queue consumer deserialize with strict: true?

Strict mode turns a broken tag into an error. In a queue, that error fails the job, and after its retries it lands in the dead letters where you can inspect it, instead of flowing on as half-broken data.

 A reminder with taskId: -5 deserializes without any error. What is missing?

The serializer only checks that the text is safe to rebuild. It does not know your app's rules. A schema checks that taskId is a positive whole number.

 In a custom transformer for a Duration class, what does serialize need to return?

The serializer adds the $type tag from the transformer's type, so the reader knows what to rebuild. Returning the whole tagged object yourself also works, but it is not required.

 Why should a transformer's deserialize check its input before it builds the object?

deserialize is where outside text becomes your object. Throw on bad input, such as $value: -5, instead of creating a broken Duration.

 How do you add your own Duration type and keep the built-in Date, Map and Set support?

registerTransformer adds your type next to the built-in ones, which is why the date in the lesson's example still works.

 What does an envelope add to serialized text?

Like the address and stamp on a letter, the envelope tells the reader how to read the data. The reader checks it first and refuses a format or version it does not understand.

 What does this print? import { createSerializer, serializeToEnvelope } from "@zudojs/serialization"; const serializer = createSerializer("json", { preserveTypes: true }); const envelope = serializeToEnvelope({ taskId: 1 }, serializer); console.log(envelope.metadata.format, envelope.metadata.version, envelope.data);

The metadata says the format is json, version 1 of the tagging format. data is the serialized text, not the object.

 What does this print? import { createSerializer, serializeToEnvelope, unwrapEnvelope } from "@zudojs/serialization"; const serializer = createSerializer("json", { preserveTypes: true }); const envelope = serializeToEnvelope({ taskId: 1 }, serializer); try { unwrapEnvelope(envelope, "messagepack"); console.log("read it"); } catch (error) { console.log(error.message); }

The reader asked for messagepack, but the envelope says json. It is refused with a clear error instead of being misread.

 What does the envelope's version describe?

The envelope version belongs to the serializer. For changes to your data, put your own v field in the payload.

 Why put a v field in every payload from day one?

With v: 1 in every payload, the reader always knows which shape it holds and can upgrade it step by step.

 You change the reminder job from version 1 to version 2. In which order do you deploy?

If writers go first, old readers receive version 2 payloads they cannot read. Readers first means every payload that exists can always be read.

 You add a new optional field to a payload. Do you need a new version?

Only adding where you can keeps changes painless. A new version is needed when you remove or rename a field, or change its meaning.

 When can you delete the code that upgrades version 1 payloads?

Stored payloads outlive deploys. As long as a version 1 job may still sit in the queue, the reader must understand it.

 A reminder job's data holds remindAt: new Date(...). What does the processor receive with the queue's default serializer (since @zudojs/queue 1.4.0)?

The queue tags the date on the way in and rebuilds it for the processor. Only createJsonSerializer({ preserveTypes: false }) gives you plain JSON, where the date arrives as a string. Passing createJsonSerializer() explicitly documents the choice.
