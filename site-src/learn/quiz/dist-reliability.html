In the naive failure matrix, why is "queue down" worse than "database down", although both answered 500?

A failure after a side effect is the dangerous kind: the answer says "nothing happened" when something did. The customer's natural retry turns it into a duplicate.

 Before adding timeouts, retries or breakers, what does the lesson ask you to decide for each dependency?

Those three answers decide the mechanism: fail fast for critical dependencies, a fallback for optional ones, retries only for safe operations. They are business decisions, so they come first.

 A timeout wrapper uses only Promise.race with a timer and never aborts anything. What goes wrong?

Promises cannot be cancelled from outside. Giving up waiting is not stopping the work; only a signal the work listens to (or a driver's cancel call) stops it.

 Checkout calls four services in a row, each with a 2-second timeout, and the checkout page promises an answer within 2 seconds. What is the fix?

Separate timeouts add up. A deadline is shared by the whole request, so the total wait is bounded no matter how many calls it makes.

 How should you choose a dependency's timeout?

Below normal latency, the timeout fails healthy calls; far above it, it protects nothing. The slow tail, not the average, is what normal traffic actually needs.

 Which failure is worth retrying?

Only transient failures can succeed on a later attempt. Invalid input, missing records and declined cards will fail the same way every time.

 Why add jitter to exponential backoff?

Without randomness, every client computes the same waits. Jitter spreads the retries over time, turning spikes into a trickle.

 The browser, the gateway and the orders service each retry up to 3 attempts. The database is down. How many database calls can one click cause, and what is the usual fix?

Retries multiply across layers: 3 × 3 × 3. Retrying at the layer closest to the dependency, with a retry budget, keeps an outage from tripling its own load.

 A POST /orders call times out. Why must the client not simply retry it?

After a timeout the client cannot know whether the work happened. Retrying a non-idempotent write is only safe when the server can recognise the repeat.

 What does a circuit breaker add that a timeout does not?

A timeout still makes every call wait for the limit. An open breaker skips the call entirely, which protects both sides.

 Why does the lesson's breaker use a rolling window of recent results instead of "open after 3 failures in a row"?

A failure rate over recent calls describes health much better than a streak. minimumCalls stops it from judging on too few results.

 Why does the half-open breaker let exactly one probe through?

The probe asks "are you back?" gently. Only when it succeeds does full traffic return.

 A breaker around the payments API opens whenever a card is declined (402). What is wrong?

Only errors that indicate an unhealthy dependency (5xx, timeouts, refused connections, and 429) should count. Business outcomes are successes from the breaker's point of view.

 The rates API hangs and ShopFlow's single pool of outgoing calls is full of rate requests. Checkout, which needs only the healthy database, is refused. What prevents this?

Bulkheads isolate capacity, like watertight compartments in a ship. One slow dependency floods its compartment, not the whole service.

 With a full bulkhead, extra rate requests were "rejected at once" instead of waiting. Why is that good?

Waiting in line for a dependency that is not answering only spreads the outage. A quick "no" plus a fallback keeps the rest of the page fast.

 The permissions service is down. What is the right fallback for "can this user refund an order?"

Degrade features, never security. A fallback that grants access during an outage is an attacker's favourite outage.

 Why must a liveness probe not check the database?

Liveness answers "is this process stuck?", and a restart is its remedy. Readiness answers "should I get traffic?", which is where dependency checks belong.

 An instance receives SIGTERM during a deploy. What should it do first?

New traffic must stop arriving before the instance stops accepting it. Then it finishes in-flight work, drains workers, and closes dependencies last.

 In the published @zudojs/runtime, why did the lesson's /ready probe check runtime.state === "running" as well as runtime.ready?

Readiness means "my dependencies are fine and I intend to serve". The lifecycle state carries the second half, so the probe must include it.

 A worker claims a job and its process is killed. stalledAfter returns the job to the queue and another worker runs it. What must the job handler therefore be?

Crash recovery means running the job again. Store what you did (a booking reference, a payment id) and check it first, so a second run does not repeat the side effect.

 What does registering the loyalty plugin's component with critical: false change?

Optional means the application is useful without it. The component:failed event is where the alert goes, and every caller must check whether the plugin is running.

 Why validate configuration at startup, before the instance reports ready?

Failing fast is most useful when the platform can see it. Readiness is the signal the deploy system uses to continue or stop the rollout.

 A customer closes the tab while a sales report is being built. With @zudojs/http, how does the server stop the work?

Cancellation only works if the signal is passed all the way down. Each call that accepts it stops when the customer leaves.

 Why does the chaos test use a seeded random generator instead of Math.random?

Randomness finds unexpected combinations; the seed makes them repeatable. Print the seed of every random run so you can replay it.

 Which of these is an invariant for the checkout chaos test?

An invariant must hold whatever breaks. Outcomes such as 201 vary with the faults; what must never vary is the relationship between the answer and the saved state.
