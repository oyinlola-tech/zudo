Why does this course measure algorithms by counting steps instead of timing them with a clock?

performance.now() is precise, but what it measures mixes your algorithm with everything else happening on the machine. A step count isolates the algorithm, so it gives the same answer everywhere. You still confirm with a clock, carefully, at realistic sizes.

 A function does exactly 4n² + 100n + 7 steps. What is its time complexity?

Drop the lower-order terms (100n + 7) and the constant factor (4). For large n the n² term dominates everything. O(n³) is technically a true upper bound, but not the tight one you should state.

 Function A does 2n steps and function B does 50n steps. Which statement is correct?

Big O describes the shape of the growth, not the speed. Both grow linearly. The constant factor is real (B is 25 times slower) but it does not change the class. That is why Big O alone cannot pick between two algorithms of the same class.

 A report function loops over all n orders to compute the total, then loops over them again to find the largest order. What is its time complexity?

Sequential blocks add: n + n = 2n, which is O(n). Only nested loops multiply.

 For every one of n orders, a function scans all m products. How should you state its time complexity?

Nested loops multiply, and different inputs keep different letters. Calling it O(n²) hides the fact that the two sizes can be very different: 100,000 orders times 20 products is far cheaper than 100,000 times 100,000.

 What is the time complexity of this loop, where n is the starting balance? let balance = n; while (balance > 1) { balance = Math.floor(balance / 2); }

The value halves on every pass, so the loop runs about log₂ n times. A loop variable that is multiplied or divided gives a logarithm; one that goes up or down by a constant gives a linear loop.

 What does "the running time is Ω(n)" say?

Ω (omega) is a lower bound, O an upper bound, and Θ (theta) both at once: a tight bound. "Exactly n steps" would be Θ(n), and only if it held for every n from some point on.

 Which function is Θ(n) for every input of size n?

Summing visits every item exactly once, whatever the values, so it is always linear: a tight Θ(n). The search that stops early is Θ(1) in its best case and Θ(n) in its worst case, so no single Θ covers all its inputs.

 A teammate says "Big O means the worst case". What is the accurate version?

"Worst case O(n)" combines two ideas: which inputs (the worst ones) and which bound (an upper bound). You can also say "best case Θ(1)" or "worst case Ω(n)". Mixing them up leads to wrong claims such as "the best case is Ω".

 A login service looks users up with a function whose average case is fast and whose worst case is slow. Why do engineers usually plan around the worst case?

An average depends on an assumption about which inputs arrive. An attacker does not follow your assumption. Planning for the worst case (or limiting who can trigger it) keeps the service up under hostile input.

 Linear search over n orders takes (n + 1) / 2 comparisons on average when every order is equally likely. What is the average case complexity?

Dividing by a constant (2) does not change the class. Doubling the list still doubles the average work. "Halving the work once" is very different from "halving what is left at every step", which is what gives O(log n).

 A print server empties its queue like this. What is the total time for n jobs? while (jobs.length > 0) { const job = jobs.shift(); print(job); }

Removing the first array item is O(n) because the other items move. n shifts cost about n²/2 moves. The lesson on stacks and queues builds a queue that removes from the front in O(1).

 orders.filter((o) => vipIds.includes(o.customerId)) is slow with 100,000 orders and 5,000 VIPs. What is the best fix?

includes is a scan, so it runs m steps for each of n orders. A Set lookup is O(1) on average. A plain for loop or indexOf still scans.

 What is the time complexity of this function for n orders? const ids = orders.reduce((acc, order) => [...acc, order.id], []);

Spread is a loop. On the k-th order it copies k - 1 ids, so the total is 0 + 1 + … + (n - 1), about n²/2. orders.map((o) => o.id) or a push loop is O(n).

 What does "push is amortized O(1)" mean?

Amortized cost averages over a sequence of operations, not over inputs. Because the array grows by a constant factor, the expensive copies are rare enough that their total stays proportional to n.

 A custom list grows its capacity by 100 slots whenever it is full. What is the total cost of n pushes?

Growing by a constant amount gives about n / 100 copies of sizes 100, 200, 300, …, which sum to about n² / 200. Only growing by a constant factor (2, 1.5) keeps the total linear.

 What is the extra space used by this function for an array of n amounts? function sum(amounts, i = 0) { if (i === amounts.length) return 0; return amounts[i] + sum(amounts, i + 1); }

Every unfinished call keeps a stack frame. The chain is n + 1 calls deep, so the space is O(n), and a large enough n throws "Maximum call stack size exceeded". A loop does the same sum in O(1) extra space.

 Reversing an array in place by swapping from both ends uses how much extra space?

Extra (auxiliary) space counts memory beyond the input. The swaps reuse the input's own slots. The number of swaps is about time, not space.

 For a list of 8 items, an O(n²) function runs faster than an O(n log n) one. How is that possible?

Big O describes growth for large n. A simple quadratic loop with tiny constants can win for a handful of items, which is why many sort implementations use a simple quadratic sort for small pieces.

 Which way of timing two algorithms gives a trustworthy conclusion?

Warm-up lets the JIT compile, the best of several runs removes noise, and the doubling ratio reveals the growth class. Tiny inputs hide the growth, and single timings change on every run.

 You double n and the step count goes from 10,240 to 22,528 (about ×2.2). Which class fits best?

Linear gives exactly ×2 and quadratic ×4. Slightly more than ×2 is the signature of n log n: the n doubles and the log n grows by one. Exponential would square the count, not multiply it by a small number.

 Trying every combination of n coupons takes 2ⁿ steps. The checkout handles 20 coupons in a moment. What happens with 30?

Ten more coupons means ten more doublings. Exponential algorithms are only usable for small n; the course's backtracking and dynamic programming lessons show how to prune or reuse work.

 An endpoint loops over 200 orders and runs one database query per order to load its customer. In Big O it is O(n). Why is it still a production problem?

This is the "N + 1 queries" problem. The model counts every step as equal, but I/O is thousands of times slower than a comparison. Load all 200 customers in one query instead.

 Why does the lesson test the growth rate with step counters instead of timings?

A timing-based test fails when the machine is busy. An exact step count only changes when the algorithm changes, which is precisely what the test should catch.
