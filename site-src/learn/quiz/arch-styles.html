In the opening simulation, payments loses 1 response in 10 and checkout retries. Why were ten customers charged twice?

A caller cannot tell a lost request from a lost response or a slow service: all three look like a timeout. Retrying a non-idempotent operation after a lost response repeats it. In a function call inside one process, this "maybe it happened" outcome does not exist.

 Which is a genuine strength of a monolith that microservices lose?

With one database, consistency across features is a transaction. With a database per service, the same guarantee needs a saga with compensations, and the data can disagree for a while.

 What makes a monolith a "big ball of mud"?

Size and a single deploy are not the problem. Tangling is. A large monolith with enforced module boundaries stays changeable.

 In a modular monolith, the orders module needs a book's price. Which is the right way to get it?

Each module owns its data and exposes a small public API. Reaching into internals or tables couples orders to the catalog's implementation and makes a later extraction painful.

 What does a modular monolith not give you?

It is still one deployable and one process: modules ship together, and a memory leak in one affects all. It keeps transactions and simple operations, which is often the better trade.

 A system has a "book service", a "customer service" and an "order service", each wrapping one table. Every page calls all three, and most features change two of them. What is this?

Entity services are split by noun, not by business capability, so every feature crosses them. They must all be up and often deployed together.

 In the catalog, "book" means title and price; in shipping it means weight and size. What does a bounded context design do with this?

One giant shared model couples every context to every other. Separate models, connected by ids and events, let each context change on its own.

 "An order must never be confirmed without its stock being reserved" must hold at all times. Where should order placement and stock reservation live?

Strong consistency is cheap inside one database and expensive across services. Draw boundaries so the rules that must always agree stay together.

 Which operation is naturally idempotent?

Setting a value to the same thing twice has the same effect as once. Adding, charging and sending all repeat their effect, so they need an idempotency key or a record of what was handled.

 A developer generates a new random idempotency key inside the retry loop, for each attempt. What happens?

The key must identify the operation, not the attempt: made once, before the first try, and reused on every retry.

 Why add jitter to exponential backoff?

Without jitter, 1,000 clients that failed at once come back at once, every time. Randomising the wait spreads them out, as the simulation's "same moment" counts showed.

 Which failure should a client generally not retry?

A 400 will fail the same way every time: retrying only adds load. Retry failures that may go away, a few times, and only for idempotent operations.

 In the outage simulation, the breaker and the plain retries confirmed the same 30 orders. What did the breaker improve?

A breaker cannot make a dead dependency work. It limits the cost of the outage: callers fail fast, and the dependency is not hammered while it recovers.

 What happens in the breaker's half-open state?

After the pause, the breaker probes carefully. The outage log showed exactly that: half-open then open while payments was still down, half-open then closed once it recovered.

 Which message is an event?

An event is a fact in the past tense, for zero or more subscribers, and cannot be refused. The others are commands: requests to one handler, which may fail or reject them.

 What is a real cost of an event-driven design?

Loose coupling means nobody's code lists the whole process. You gain independence and pay in visibility, which traces and good event documentation recover.

 A broker promises at-least-once delivery. What must consumers do?

Redelivery after a crash between "work done" and "acknowledged" produces duplicates. Acknowledging first would turn duplicates into lost messages instead.

 What problem does the transactional outbox solve?

The event is written in the same transaction as the order, so both exist or neither does. A relay publishes it later. It can publish twice, which idempotent consumers handle.

 Right after Ada places an order, her "my orders" read model does not show it. Which fix fits CQRS best?

Read models are eventually consistent by design. Waiting for projections couples the write side to every reader again. Showing the command's own result covers the moment the user cares about.

 When is full CQRS with separate read models most worth its cost?

Separate read models pay off when reads and writes differ strongly in shape or load. For simple forms, they add projections and lag for nothing.

 Which job should an API gateway not take on?

Business rules belong in the services that own them. A gateway that accumulates rules becomes a monolith in front of your services, and every team must change it.

 Why must every service copy the incoming trace id into its outgoing calls and log lines?

Without a shared id, the logs of five services are five unrelated piles. With it, a trace tree and a log search show one request's whole journey.
