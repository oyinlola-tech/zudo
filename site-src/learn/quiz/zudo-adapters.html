Checkout reads the payment provider's SDK response directly in twenty places. What goes wrong when the business switches to another provider?

Provider-specific shapes (status: "success", amount_kobo) leak into business logic. An adapter keeps them in one class, so the rest of the app speaks its own contract and a switch touches one place.

 Checkout was written for provider A. What does it print for provider B's successful payment? function checkoutWithA(response) { if (response.status === "success") return "paid"; return `declined: ${response.gateway_response}`; } const fromB = { state: "CAPTURED", amount: { value: 20_425, currency: "NGN" }, reason: null }; console.log(checkoutWithA(fromB));

B has no status field, so the check fails and the code falls through to "declined", reading a field B does not have either. No error is thrown: the bug is silent, which makes it worse.

 In the adapter pattern, who defines the contract (the port) that adapters implement?

The contract describes what checkout needs: charge, refund, succeeded or declined. If it copied one provider's API, the next provider would have to pretend to be the first one, and the coupling would be back.

 Why is reference (the order id) part of ChargeRequest, and not only something an adapter might add?

Idempotency is a promise that checkout relies on. Putting it in the contract, and testing it in the contract suite, makes every adapter keep it: the fake by remembering references, KoboPay through the Idempotency-Key header.

 What does this idempotent charge function print? const charges = new Map(); let providerCalls = 0; async function charge(reference, amountKobo) { if (charges.has(reference)) return charges.get(reference); providerCalls += 1; const result = { id: `ch_${providerCalls}`, amountKobo }; charges.set(reference, result); return result; } const a = await charge("order-1001", 2_042_500); const b = await charge("order-1001", 2_042_500); const c = await charge("order-1002", 950_000); console.log(a.id, b.id, c.id, providerCalls);

 Which lifecycle method should check that the provider is reachable and the API key works?

initialize prepares external resources without starting work. Checking there turns a wrong key into a startup failure, instead of a failed payment for the first customer.

 What is the difference between stop() and dispose()?

A graceful shutdown does both, in order: stop taking work, wait for what is running, then release connections and timers. The lesson's KoboPay adapter waits in stop and aborts leftovers in dispose.

 KoboPay cannot refund through its API. Where should the adapter say so?

Capabilities are about the runtime: http, abortSignal, gracefulShutdown, edgeRuntime… TypeScript rejects refunds there (TS2353). Business features belong in the business contract, where checkout can read them.

 During disposeAll, one adapter's stop() throws. What happens to that adapter?

Skipping disposal would leave connections and timers with nothing holding a reference to release them. The registry disposes anyway and reports every failure once all adapters were handled.

 A charge request times out. What should checkout tell the customer?

A timeout means "no answer", not "no charge". The provider may have charged the card. "Failed" invites a second payment, and a retry with a new reference could charge twice.

 Which request is safe to retry after a timeout without any extra protection?

Reading does not change anything, so doing it twice is harmless. Charging, refunding and sending a message all have effects, and may only be retried with an idempotency key the other side honours.

 What does this print? import { AdapterTimeoutError, AdapterNotSupportedError, isAdapterError } from "@zudojs/adapters"; const timeout = new AdapterTimeoutError("kobopay", "charge", 800); const refund = new AdapterNotSupportedError("kobopay", "refund"); console.log(timeout.message, timeout.timeout, timeout.statusCode); console.log(refund.statusCode, refund.expose, isAdapterError(refund), isAdapterError(new Error("x")));

 KoboPay's DNS name does not resolve, so fetch fails before any response. Which error should the adapter throw from charge?

The request never reached the provider, so this is a connection problem, and unlike a timeout the charge certainly did not happen. AdapterNotFoundError is the registry's error for an unknown adapter name, not for a missing server.

 Why do the adapter errors keep the original problem in cause instead of in the message?

Adapter "kobopay" operation "charge" failed. is the same for every such failure, so alerts can group them. The cause, such as "KoboPay answered 503", is what an engineer needs, and stays out of customer-facing responses.

 setUpPayments receives PAYMENTS_PROVIDER=stripe-ish. Why throw at startup instead of falling back to the fake?

Defaults that hide configuration mistakes are dangerous, and with payments they lose money. Unknown or missing settings should stop the app with a clear message before it takes any traffic.

 ShopFlow moves from KoboPay to a third provider. Which files change?

Business logic depends on the contract, so it is untouched. The new adapter must pass the same contract test suite as the others before it goes live.

 What makes the lesson's contract test suite valuable when a new adapter is added?

Swappability is a claim, and the contract suite is its proof. A new adapter that charges a reference twice fails the suite before it can charge a customer twice.

 What are createMockAdapter and createMockAdapterRegistry for?

A mock adapter takes the lifecycle hooks and health you give it, so a test can make one adapter degraded or failing on purpose and check how your code reacts.

 The readiness endpoint answers 200 when payments is degraded and 503 when it is unhealthy. Why not 503 for degraded too?

Degraded is a reason to alert, not to stop serving. If all instances report not-ready at once, the load balancer has nowhere to send traffic.

 Which is the best health check for a payment adapter?

A health check must not do real work: charging, even a small amount, costs money and may trip fraud checks. A cheap, read-only call with a time limit tells you whether the provider is reachable and fast.

 The app shuts down while a charge is in flight. What does the lesson's KoboPay adapter do?

Cutting off a payment halfway creates exactly the unknown outcome you want to avoid. Waiting is safe because every call has a timeout, so stop always finishes.

 A withLogging(inner) wrapper implements PaymentAdapter by forwarding to another adapter and logging each charge. What makes this possible?

This is the decorator pattern. Timing, metrics, circuit breakers and logging can all be wrappers, and every adapter stays a plain translator.
