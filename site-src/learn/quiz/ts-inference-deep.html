What is the type of a? function same(value: T): T { return value; } const a = same("NGN");

The candidate for T is the literal "NGN". T is the whole return type, so the literal is kept, and a const does not widen it.

 What is the type of c? function boxed(value: T): { value: T } { return { value }; } const c = boxed("NGN");

When T only appears inside something (a property, an array), the inferred literal is widened to string, because the container usually holds other values later.

 Which change makes boxed("NGN") return { value: "NGN" } without the caller writing anything extra?

A constraint that mentions a primitive type tells TypeScript the exact value matters, so the literal is kept even inside the object. A const type parameter would also work.

 What is the type of b? function same(value: T): T { return value; } let b = same("NGN");

T is inferred as "NGN", but a let may be reassigned, so the variable's type is widened, exactly as for let b = "NGN".

 What does the compiler say about this call? function pair(first: T, second: T): [T, T] { return [first, second]; } const mixed = pair(150_000, "NGN");

With competing candidates and no common supertype among them, the first candidate wins and the other argument is reported. That catches "same type" arguments that are not the same type. Write pair<number | string>(…) or use two type parameters if mixing is intended.

 What is a context-sensitive argument?

TypeScript infers type parameters from the other arguments first, then checks the context-sensitive callbacks with those types. That is how (input) => … can get a type that comes from another argument.

 Why does the second call report 'input' is of type 'unknown'? declare function defineJob(job: { parse: (raw: string) => In; run: (input: In) => Out; }): void; defineJob({ parse: (raw) => ({ orderId: raw }), run: (input) => input.orderId }); defineJob({ run: (input) => input.orderId, parse: (raw) => ({ orderId: raw }) });

Context-sensitive functions in an object literal are inferred left to right. Put the property that produces a type before the one that consumes it, or annotate the consumer's parameter.

 Which of these does not give an arrow function's parameters a contextual type?

A contextual type flows into an expression from the place it is written. A later use of the variable does not flow back, so the parameters are implicitly any (TS7006).

 Why does a recursive function without a return type annotation report TS7023?

The inference is circular, so TypeScript gives up and would use any, which strict mode reports. A return type annotation breaks the circle.

 In function applyVat(order) { return order.totalKobo * 1.075; }, what type does TypeScript infer for order?

TypeScript never infers parameter types from the function body. Parameters are the boundary where you declare what the function accepts.

 What is the type of x? function exact(value: T): T { return value; } const x = exact({ currency: "NGN", methods: ["card", "transfer"] });

A const type parameter infers as if the caller had written as const: literals kept, arrays become readonly tuples, properties become read-only.

 What is the type of fromVariable? function exactList(values: T): T { return values; } const roles = ["customer", "admin"]; const fromVariable = exactList(roles);

const T only affects literals written in the call. roles was already widened to string[] when it was declared, and the call cannot bring the literals back.

 Which mistake does as const catch in const METHODS = ["GET", "POST", "GTE"] as const;?

A const assertion preserves; it has no target type to check against. Add satisfies readonly Method[] to check the values.

 What does as const change in the JavaScript that runs?

readonly exists only for the compiler. Use Object.freeze when the value must really not change at runtime.

 Which line is a compile error?

A const assertion can only be applied to literals (and enum member references): TS1355. A function call's result already has its type; there is no literal to keep.

satisfies gives the literal a contextual type. Where that type contains literal types, the literal is checked against them and kept, so method is "GET" without as const. The variable keeps its own type, not Method.

 What is the type of r.method now? const r = { method: "GET", path: "/products" } satisfies { method: string; path: string };

The contextual type for method is string, which has no literal types in it, so the literal is widened as usual.

satisfies contextually types the whole literal, including the callbacks inside it. With as const alone there would be no context and orderId would be an implicit any.

An annotation replaces the value's type with the annotated one, and that type has an index signature. The typo is only caught with satisfies, which keeps the exact keys.

 An array of routes, one of them missing its handler, ends in as RouteDef[] and compiles. Why?

An assertion rejects only conversions between types that do not overlap at all. Whether an incomplete entry is caught depends on the other entries and on literal types, so it is not a check you can rely on.

 When is an annotation better than satisfies for a value you write?

satisfies keeps details you may not want to commit to. let current: Route = routes.home must accept other routes later, and a public export's type is a promise to its users.

The mapped type gives each route either its own name or never. Indexing it with all its keys collects the values into a union, and the nevers disappear. It only works because satisfies kept each route's literal auth.
