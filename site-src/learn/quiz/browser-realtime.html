10,000 customers poll their order status every 5 seconds. Why is that a poor design?

Polling costs grow with the number of watchers times the polling rate, not with the number of changes. Pushing costs one message per change per watcher.

 What is the main difference between Server-Sent Events and WebSockets?

With SSE, the client talks back with ordinary requests if it needs to. WebSockets are a separate protocol after the upgrade, suited to frequent two-way traffic.

 What is the Last-Event-ID header for?

Every event with an id: updates the browser's last event id. On reconnect, the header lets the server resume instead of losing or repeating events, but only if the server honours it.

 An order has been delivered and the page no longer needs its EventSource. The server ends the stream. What happens if the page does nothing?

An ended stream looks like a dropped connection, so EventSource reconnects. Only close() stops it (or a server answer with an error status or a wrong content type).

 Why does the SSE server write : keep-alive every 15 seconds?

Idle connections are often closed after about a minute by infrastructure between the server and the browser. A small comment costs almost nothing and keeps the stream alive.

 Why must a WebSocket server check the Origin header during the upgrade?

Without the check, a malicious page can open a socket as the logged-in user and read and send messages: cross-site WebSocket hijacking. Compare the origin against an exact allow-list.

 How does a WebSocket connection start?

Starting as HTTP lets WebSockets use the same ports, TLS and proxies as the web, and lets the server check cookies and the origin before agreeing.

 A chat page uses a WebSocket. The user's train goes through a tunnel for 20 seconds. What must the page's code do?

Unlike EventSource, a browser WebSocket never reconnects by itself and has no message history. Reconnection and catching up are the application's job.

 A server sends a courier's location 50 times a second to a customer on a slow mobile network. What does socket.bufferedAmount tell the sender?

send never blocks, so a fast sender and a slow network fill memory. For location updates, only the newest one matters, so dropping old ones is correct.

 Why do WebSocket servers send a ping every 30 seconds or so?

TCP can take a very long time to notice a peer that disappeared. Pings detect it quickly, and they also keep idle-timeout proxies from closing healthy connections.

 The courier chat runs on two server processes behind a load balancer. The customer is connected to process A and the courier to process B. Their messages never arrive. Why, and what fixes it?

In-memory rooms work on one process only. With several, each process publishes messages to a shared bus and delivers what it receives to its local sockets.

 A site uses HTTP/1.1 and one EventSource per tab. A user opens seven tabs, and the seventh never loads its data. Why?

Long-lived streams hold connections. Serve them over HTTP/2, or share one stream between tabs (with a SharedWorker or a BroadcastChannel).

 The event stream works on a developer's machine but in production the page receives nothing for a minute, then everything at once. What is the usual cause?

SSE depends on each event being passed on immediately. Buffering reverse proxies (and gzip middleware) hold data back; nginx, for example, respects an X-Accel-Buffering: no header.

 A page runs worker.postMessage(order) and on the next line order.status = "cancelled". Which status does the worker see?

Structured clone copies the data when postMessage is called. Later changes on either side affect only that side's copy.

 What happens to an ArrayBuffer listed as a transferable in worker.postMessage({ photo }, [photo])?

Transferring avoids copying large data, at the cost of the sender losing access. Sharing memory between threads needs SharedArrayBuffer, which has extra security requirements.

 Code in a worker throws an uncaught exception. What does the page's try { await callWorker(…) } catch see?

The worker runs on another thread with its own call stack. Catch errors inside the worker and send them back in a reply, as the lesson's wrapper did, and give calls a timeout.

 Which pairing of feature and tool is best?

Pick by direction and frequency: one-way news fits SSE, two-way chat fits WebSockets, heavy local work fits a worker, and something that happens once a day fits a simple poll or a notification.

 What should a WebSocket server do with each incoming message?

A socket message is like a request body from a stranger. The lesson's server refused a location from a customer and text that was not JSON, and forwarded only fields it had checked.

 Why does each status event carry the whole new status ({"status":"packed"}) rather than an instruction like "advance one step"?

Events that describe the resulting state are idempotent. Combined with ignoring ids that were already applied, the page stays correct whatever the network does.
