Why is sending a photo base64-encoded inside a JSON body a poor choice?

Every 3 bytes become 4 characters, and a JSON parser needs the complete text. Multipart sends raw bytes that can be streamed to disk piece by piece.

 In a multipart/form-data body, what is the boundary?

The client picks a string that does not appear in the data. Each part starts after --BOUNDARY, and the body ends with --BOUNDARY--.

 Node.js can parse multipart with await request.formData(). Why does the lesson write a streaming parser instead?

For small forms, formData() is fine. For uploads of many megabytes from many users at once, only a streaming parser keeps memory flat. Production code uses a library such as busboy for this.

 Why does the parser keep back the last delimiter.length - 1 bytes of each chunk when it has not found a delimiter?

Network chunks can cut anywhere, including in the middle of \r\n--BOUNDARY. Holding back just less than a full delimiter means a split delimiter is always found once the next chunk arrives.

 The parser awaits every sink.write. What does that achieve when the disk is slower than the network?

This is backpressure: the slowest step sets the pace. Without the await, chunks would pile up in memory while the disk catches up.

 A request says Content-Length: 5000. Why does the server still count the bytes it receives?

A declared length is useful to refuse obviously huge uploads early. The only reliable limit is the one enforced while the bytes stream in.

 Which status code means "the upload is larger than the server accepts"?

413 is for a body that is too big. 415 is for a type the server does not accept, such as HTML sent as a "photo".

 Why does the server decide a file's type from its first bytes instead of the part's Content-Type or the file extension?

An attacker names an HTML file photo.jpg and labels it image/jpeg. Its first bytes are still <html>, which is not a JPEG signature.

 A file starts with a valid JPEG signature. What does that not prove?

Sniffing checks the start only. A file can have a valid header and hostile data after it. Services that display images to many people often re-encode every upload in a background job, which keeps only real image data.

 Why is an upload stored under a random id instead of its filename?

The client's name is kept only as cleaned-up metadata for display. The storage key, and the extension (from the sniffed type), are chosen by the server.

 Why does the sink write to <id>.part and rename it at the end?

A rename within one file system is atomic: readers see either no file or the complete file. It also makes cleanup of interrupted uploads easy.

 What does the wx flag in createWriteStream(path, { flags: "wx" }) do?

It guarantees an upload never overwrites an existing file, even if two random ids ever collided or a bug reused one.

 A request contains a valid photo, then an unexpected field that makes it fail. What should happen to the photo already written?

A rejected request must leave nothing behind, or the disk slowly fills with files nobody can find or delete. That is why abort also removes a finished file.

 What is the cleaned-up display name (passwd.jpg from ../../etc/passwd.jpg) used for?

It keeps the seller's friendly name without letting it touch the file system. Even cleaned, it is still client input, so it is never used to build a path.

 What makes a signed URL impossible to forge?

Anyone can read the path and the expiry in the URL. Without the secret, nobody can compute a matching signature for a changed path or a later expiry.

 Why must the expiry time be inside the signed data, not just added to the URL?

Everything that limits a permission (path, method, expiry) must be signed. Unsigned parts of the URL are just suggestions.

 Why does checkSignedUrl compare signatures with timingSafeEqual instead of ===?

A comparison whose time does not depend on where the inputs differ gives an attacker nothing to measure.

 A signed download link leaked. How can you stop it working before it expires?

A signed URL is valid as long as its signature checks out. Changing the secret invalidates every link; a per-file version invalidates just one. Short lifetimes limit the damage in the first place.

 What does the response header X-Content-Type-Options: nosniff tell the browser?

Browsers used to "sniff" and could decide that an "image" was really HTML and run it. nosniff turns that off, so the server's (sniffed and trusted) type is the only one.

 Why serve uploaded PDFs with Content-Disposition: attachment?

Documents can contain scripts and links. Downloading them, and serving user content from a separate domain, keeps them away from your site's cookies and pages.

 Two servers behind a load balancer save uploads to their own local folders. What goes wrong?

Local disks are per machine. Object storage (S3, GCS, R2, MinIO) gives every server the same bucket, and it outlives any single server.

 With a presigned PUT URL, who sends the file's bytes to the bucket?

Your servers never carry the bytes, which saves bandwidth and memory. Afterwards, the client tells your API the upload is done, and a background job checks the object before it is published.

 Where should the record "seller 7 uploaded products/7/5f0c.jpg, 48,213 bytes, SHA-256 …, pending review" live?

Metadata is what you query, join, authorise and delete by. Keeping it in the database, pointing at the object's key, lets you find every file of a product or user, for example to erase it.

 Why do many services re-encode uploaded photos before publishing them?

It is slow and can crash on hostile files, so it runs in a background job while the upload stays pending.
