Which tool should store user passwords?

Passwords need a slow, salted, memory-hard hash. SHA-256 and HMAC are fast, so leaked hashes can be guessed at billions per second. Encryption can be reversed by anyone who gets the key.

 You must store sellers' bank account numbers and read them back to pay them. Which tool fits?

You need the original value back, so it must be encryption, and authenticated encryption at that. Hashes cannot be reversed, and base64 is an encoding anyone can undo.

 A payment provider needs to prove to your server that a notification came from it. Both sides know a shared secret. What does the provider send?

An HMAC can only be made by someone with the key, and it changes if a single byte of the body changes. A plain hash can be computed by anyone, and sending the secret itself exposes it.

 Why is Math.random() wrong for password-reset tokens?

Math.random() uses a fast formula with a small internal state, meant for games and simulations. randomBytes uses the operating system's cryptographically secure generator.

 What does this print? import { randomBytes } from "node:crypto"; const token = randomBytes(16); console.log(token.length, token.toString("hex").length);

Each byte is written as two hex characters (00 to ff), so 16 bytes become 32 characters.

 What does this print? const bytes = Buffer.from([251, 255]); console.log(bytes.toString("base64"), bytes.toString("base64url"));

base64url swaps + and / for - and _, and drops the = padding, so the text can go into URLs and file names without escaping.

 What does this print? const counts = [0, 0, 0]; for (let byte = 0; byte < 256; byte++) counts[byte % 3]++; console.log(counts.join(" "));

256 = 3 × 85 + 1, so remainder 0 gets one extra byte value. Taking a random byte % 3 would make 0 slightly more likely: that is modulo bias, which randomInt avoids.

 What does this print? import { randomInt } from "node:crypto"; const rolls = new Set(); for (let i = 0; i < 1000; i++) rolls.add(randomInt(5, 6)); console.log([...rolls]);

randomInt(min, max) includes min and excludes max. With min 5 and max 6, the only possible value is 5. For a die you write randomInt(1, 7).

 Why should a UUID used as an order id not double as the secret in a "view your receipt" link?

A v4 UUID is random, but an id gets copied everywhere. Access should be granted by a separate token (32 random bytes) or by checking who is logged in, not by knowing an id.

 Why does the reset-token code store sha256(token) instead of the token?

The e-mail link holds the token; the database only holds its hash. When the link comes back, you hash it and look the hash up. Someone reading the database cannot turn a hash back into a working link.

 A fast hash (SHA-256) is fine for reset tokens but wrong for passwords. Why the difference?

The speed of the hash only matters when guessing the input is feasible. Guessing 2256 possibilities is impossible at any speed; guessing the few million common passwords takes seconds with a fast hash.

 What does this print? import { hash } from "node:crypto"; const a = hash("sha256", "Order 1042"); const b = hash("sha256", "Order 1042"); const c = hash("sha256", "order 1042"); console.log(a === b, a === c, a.length);

The same input always gives the same digest, and one changed letter gives a completely different one. A SHA-256 digest is 32 bytes, which is 64 hex characters.

 An old service checks file integrity with MD5. What is the problem?

MD5 (and SHA-1) no longer resist collisions. Use SHA-256 or SHA-512 for anything security-related.

 Why use createHmac("sha256", secret) instead of sha256(secret + message)?

HMAC was designed to be safe where naive combinations are not. Use the standard construction instead of inventing one.

 What does this print? import { createHmac } from "node:crypto"; const body = '{"event":"charge.success","amount":4500000}'; const sign = (key) => createHmac("sha256", key).update(body).digest("hex"); console.log(sign("key-one") === sign("key-one"), sign("key-one") === sign("key-two"));

An HMAC depends on both the message and the key. Without the right key you cannot produce the right value, which is exactly what makes it proof of origin.

 The provider signed raw. Your framework parsed it and you re-create the text. What does this print? const raw = '{"amount": 4500000, "event": "charge.success"}'; const recreated = JSON.stringify(JSON.parse(raw)); console.log(recreated === raw); console.log(recreated);

JSON.stringify drops the spaces, so the text differs from what was signed and the HMAC would not match. Verify the signature on the raw bytes first, then parse.

 A webhook signature is valid, but the same request arrived yesterday too. Which pair of defences handles retries and replays?

A replayed request is correctly signed, so the signature check cannot stop it. A signed timestamp limits how long a request stays valid, and a stored event id makes a repeat harmless.

 What does this print? function leakyEqual(expected, guess) { let steps = 0; for (let i = 0; i < expected.length; i++) { steps++; if (expected[i] !== guess[i]) return steps; } return steps; } console.log(leakyEqual("a91f", "b000"), leakyEqual("a91f", "a900"), leakyEqual("a91f", "a91f"));

The comparison stops at the first mismatch, so the work done reveals how many leading characters are right. That is the information a timing attack measures.

 What does this print? import { timingSafeEqual } from "node:crypto"; try { console.log(timingSafeEqual(Buffer.from("abc"), Buffer.from("abc"))); console.log(timingSafeEqual(Buffer.from("abc"), Buffer.from("abcd"))); } catch (error) { console.log(error.code); }

timingSafeEqual only compares buffers of equal length and throws otherwise. Check the lengths first and return false yourself; a signature's length is not secret.

 An attacker sends the header zz12. What does this print? const received = Buffer.from("zz12", "hex"); console.log(received.length);

Hex decoding silently stops at the first character that is not hex, which here is the very first one. The length check before timingSafeEqual turns this into a clean rejection instead of an exception.

 What is the purpose of a salt in password hashing?

The salt is random and stored next to the hash; it is not secret. Its job is uniqueness: attackers must attack each hash separately.

 What does this print? import { scryptSync } from "node:crypto"; const hashWith = (salt) => scryptSync("password123", salt, 32).toString("hex"); console.log(hashWith("salt-ada") === hashWith("salt-ada"), hashWith("salt-ada") === hashWith("salt-chidi"));

scrypt is deterministic for the same password and salt, which is what makes verification possible. A different salt gives a different hash for the same password.

 Why should a web server call the async scrypt rather than scryptSync at login?

Both compute the same result with the same cost. The difference is where the work happens: the async version leaves the event loop free.

 scryptSync(pw, salt, 64, { N: 2 ** 17, r: 8, p: 1 }) throws ERR_CRYPTO_INVALID_SCRYPT_PARAMS. Why?

Memory use is about 128 × N × r bytes. The default limit is 32 MiB, so recommended parameters require an explicit maxmem.

 Why does the stored password value include scrypt$131072$8$1$ before the salt and hash?

Verification reads the parameters from the stored value. When you raise the cost, you re-hash each password at the user's next successful login.

 What does this print? const a = "Chióma"; const b = "Chióma"; console.log(a === b, a.normalize("NFKC") === b.normalize("NFKC"));

The two strings look identical ("Chióma") but one uses a single accented character and the other a letter plus a combining accent. Normalizing before hashing makes them the same bytes, so the user can log in from any device.

 Which login error message is best?

Different messages let anyone find out which e-mail addresses have accounts. Same message, same status code, and ideally similar timing for both cases.

 What does the authentication tag in AES-256-GCM do?

GCM is authenticated encryption: decipher.final() throws when anything was altered, so you never get silently corrupted or forged plaintext.

 One bit of the ciphertext is flipped before decryption. What does this print? import { createCipheriv, createDecipheriv, randomBytes } from "node:crypto"; const key = randomBytes(32); const iv = randomBytes(12); const cipher = createCipheriv("aes-256-gcm", key, iv); const data = Buffer.concat([cipher.update("pay ₦45,000 to seller 17"), cipher.final()]); const tag = cipher.getAuthTag(); data[3] ^= 1; const decipher = createDecipheriv("aes-256-gcm", key, iv); decipher.setAuthTag(tag); const partial = decipher.update(data); try { decipher.final(); console.log("decrypted:", partial.toString()); } catch (error) { console.log("rejected:", error.message); }

The tag no longer matches, so final() throws. Note that update already returned bytes: never use them before final() has succeeded.

 The vault encrypts each bank account number with the AAD "seller:17". What attack does that stop?

The AAD is not encrypted, but it is covered by the tag. Decrypting with a different context fails, so ciphertexts are bound to their owner.

 A developer uses a fixed all-zero nonce "because the key is secret anyway". What is the consequence?

Same key and same nonce produce the same key stream. The nonce is not secret, but it must be unique per message: use 12 random bytes every time.

 Two messages were "encrypted" by XOR-ing them with the same stream. What does this print? const stream = [13, 200, 77, 5, 91]; const encrypt = (text) => [...text].map((ch, i) => ch.charCodeAt(0) ^ stream[i]); const c1 = encrypt("PAY 5"); const c2 = encrypt("PAY 9"); const known = "PAY 5"; const recovered = c2.map((byte, i) => String.fromCharCode(byte ^ c1[i] ^ known.charCodeAt(i))).join(""); console.log(recovered);

c1 XOR c2 equals p1 XOR p2 because the stream cancels out. XOR with the known p1 leaves p2. This is why a nonce may never repeat with the same key.

 A config file stores the database password as base64 "for security". What is true?

Encoding only changes how bytes are written as text. Secrets belong in environment variables or a secret manager, not in files, encoded or not.

 Where should the AES key for the payout vault come from in production?

A key in code ends up in Git; a key next to the data leaks with the data; a derived value is guessable. Load it from the environment and refuse to start if it is missing or the wrong length.

 A login code has 6 digits (1,000,000 possibilities). What makes it safe enough?

With 5 attempts, an attacker has a 5 in 1,000,000 chance. Without attempt limits, a million requests would find it. Rate limiting is what makes short codes work.

Write constantTimeEqual(a, b) for two arrays of bytes. If the lengths differ, return false. Otherwise look at every byte (no early return): combine the differences with XOR (^) and OR (|) into one number and return whether it is 0.
