Why does the pipeline run the type check and lint before the integration tests?

Put cheap, likely failures first. There is no point spending minutes on a database and migrations for a change that does not compile.

 How does a CI system decide that a step such as npm run lint failed?

Exit code 0 means success; anything else is failure. Every tool in the pipeline follows that contract, which is why a script that swallows errors (or prints them and exits 0) breaks the pipeline silently.

 In the generated project, a test passes { title: "…" } where the type requires { name: string }, yet npm run typecheck and npm test both pass. Why?

Nothing type-checks the test files. A second configuration that includes tests/, run as typecheck:tests, closes that gap.

 Which of these would a linter such as Biome report, while tsc with the generated settings accepts it?

The other three are type errors. A loose == and an unused variable are valid TypeScript but likely mistakes; that is the linter's job.

 Why is npx biome lint risky in a project that has not installed @biomejs/biome?

npx resolves a bare name on the registry when it is not installed locally. Install tools as dev dependencies so the lockfile decides exactly which code runs.

 Why does the pipeline use npm ci rather than npm install?

CI must be reproducible: the same commit installs the same versions every time. npm install may resolve newer versions and rewrite the lockfile.

 The integration tests pass on a developer's laptop and fail on a clean clone with PAYMENTS_URL is not set. What is the real problem?

A clean clone has none of your local state. That is exactly why CI starts from nothing: it finds settings, files and packages that only exist on one machine.

 The integration test file uses describe.skipIf(!process.env.DATABASE_URL). What is the trade-off?

Skipping is convenient locally and dangerous in CI. Check the test counts in the CI log, or make the CI job fail when the variable is missing.

 npm audit reports high-severity advisories in mysql2 and deepmerge-ts, pulled in by the Prisma CLI, and suggests npm audit fix --force, which downgrades Prisma a major version. What is the best first move?

Triage: is it reachable, how bad, what is the cheapest safe fix? Patched versions existed, so overrides removed the findings without a breaking downgrade. A documented, expiring exception is the fallback.

 gitleaks finds a GitHub token committed three weeks ago. What must happen first?

Once pushed, a secret must be treated as known. Rotating it makes the leaked copy useless; cleaning the history comes after, if at all.

 What does permissions: contents: read at the top of the workflow achieve?

Least privilege: if a step or a dependency is compromised, the token it can steal cannot push code or publish packages. Only the build job adds packages: write.

 The deploy jobs use concurrency: { group: deploy-production, cancel-in-progress: false }. What happens when two merges reach production deploy at the same time?

Cancelling a deploy halfway could leave a migration applied without its app. Queueing keeps each deploy whole.

 actionlint warns about run: echo "deploying ${{ github.event.head_commit.message }}". Why?

That is script injection. Put the value in env: and use "$MESSAGE": the shell then treats it as data.

 A pull request from a fork runs your workflow. Which statement is true?

Code from a fork is untrusted. The checks still run, but nothing that needs secrets or deploys does.

 Both deploy jobs refer to secrets.DEPLOY_SSH_KEY. How do they get different keys?

Environment secrets override repository secrets of the same name for jobs in that environment, and production can require an approval before its secrets are ever used.

 Which secret should the CI system not hold in this design?

Application secrets live in a file on each server, readable only by the deploy user. CI only needs to reach the server and name the release, so a compromised CI leaks less.

 GitHub masks secret values in logs. Which line still leaks?

Masking replaces the exact value. An encoding or a part of the secret is a different string and is printed in full.

 Why does the pipeline build a separate migrate image from the same Dockerfile?

The generated runtime stage keeps only production dependencies. A stage built from the same commit carries the CLI and the migration files, and runs only when asked.

 What would happen without set -euo pipefail at the top of deploy.sh if the migration step failed?

By default bash ignores failing commands and runs the next line. -e stops at the first failure, -u treats unset variables as errors, and pipefail makes a failure inside a pipe count.

 A release added a column with a default. The next release is bad and you start the previous image again. What happens to the database?

Code rolls back, the database only moves forward. That is safe as long as every migration keeps the previous release working: add, don't rename or drop, until you are sure.

 A migration that already ran in production has a wrong default. What should you do?

Applied migrations are history. Prisma stores a checksum and refuses a changed file, and an edited file would make new databases differ from production.

 Why should the deploy wait for /health (a readiness check that includes the database) rather than for "the container started"?

The bad release in the lesson started a container that crashed on a missing PAYMENTS_URL. Only a check of what users need caught it and triggered the rollback.
