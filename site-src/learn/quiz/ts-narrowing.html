In function f(amount: number | string) { if (typeof amount === "string") return; … }, what is the type of amount on the lines after the if?

A variable keeps its declared type, but at each point TypeScript tracks what it can still be. The if returns for strings, so only number reaches the following lines.

 Why does if (typeof tags === "object") return tags.length; fail to compile when tags is string | string[] | null?

JavaScript reports "object" for null. TypeScript models that, so null survives the check and you get 'tags' is possibly 'null'. Check tags !== null too, or use Array.isArray.

 Which of these is not a value the JavaScript typeof operator can return?

typeof returns one of eight strings: string, number, bigint, boolean, symbol, undefined, object and function. Arrays are "object"; use Array.isArray to recognise them.

 What does this print? function kindOf(value: string | number | string[] | null): string { if (typeof value === "object") return value === null ? "nothing" : `list of ${value.length}`; if (typeof value === "number") return `amount ${value}`; return `text ${value}`; } console.log(kindOf(null), "|", kindOf(["a", "b"]), "|", kindOf(0), "|", kindOf(""));

null and the array both pass typeof value === "object", and the inner check separates them. 0 is a number and "" a string; typeof does not care whether a value is falsy.

 What does this print? function balanceLine(balance: number | null): string { if (balance) return `₦${balance}`; return "not available"; } console.log(balanceLine(500), "|", balanceLine(0), "|", balanceLine(null));

0 is falsy, so a real balance of ₦0 goes to the "not available" branch. The code compiles because TypeScript only promises that balance is a number inside the if. Use balance !== null instead.

 For quantity: number | undefined, what is the type of quantity in the else branch of if (quantity) { … } else { … }?

A falsy number (0 or NaN) also reaches the else branch, so TypeScript cannot remove number there. The type is still number | undefined, which is the compiler reminding you that "falsy" is not "missing".

 A daily transfer limit of 0 means "this account may not transfer". What does this print? const limits: (number | undefined)[] = [0, undefined, 20000]; for (const limit of limits) { console.log(limit || 50000, limit ?? 50000); }

|| replaces every falsy value, including 0, so the blocked account suddenly gets ₦50,000. ?? only replaces null and undefined.

 Which value is truthy, and so passes if (value)?

"0" is a non-empty string, so it is truthy. The falsy values are false, 0, -0, 0n, NaN, "", null and undefined. This is why if (amount) on a string amount lets "0" through.

 What does if (to == null) return; remove from the type of to: string | null | undefined on the following lines?

Loose equality with null is true for exactly null and undefined, and TypeScript narrows accordingly. It is the one common, safe use of ==.

 to is a string and fallback is string | number. Inside if (to === fallback) { … }, what is the type of fallback?

=== can only be true when both sides are the same type, and to is a string. So equality narrows both sides to the types they have in common.

 What does this print? type Local = { accountNumber: string; bankCode: string }; type Foreign = { iban: string }; function payee(account: Local | Foreign): string { if ("iban" in account) return `IBAN ${account.iban.slice(0, 4)}`; return `NUBAN ${account.accountNumber} (${account.bankCode})`; } console.log(payee({ iban: "GB29NWBK60161331926819" })); console.log(payee({ accountNumber: "0123456789", bankCode: "058" }));

"iban" in account is true only for the foreign account. After that branch returns, only Local is left, so accountNumber and bankCode can be read without another check.

 Why can you not write value instanceof Account when Account is an interface?

instanceof checks a constructor's prototype at runtime, so it needs a class, which is a real JavaScript value. Interfaces and type aliases vanish when TypeScript compiles; check their properties instead.

 What does this print? class InsufficientFundsError extends Error {} function explain(error: unknown): string { if (error instanceof Error) return `failed: ${error.message}`; if (error instanceof InsufficientFundsError) return "top up first"; return "unknown"; } console.log(explain(new InsufficientFundsError("short by ₦500"))); console.log(explain("timeout"));

An InsufficientFundsError is also an Error, so the first check catches it and the specific branch never runs. Put the most specific class first. A thrown string is not an Error at all.

 A Money class has amount and currency properties. What is JSON.parse('{"amount": 5, "currency": "NGN"}') instanceof Money?

instanceof looks at the prototype chain, not the shape. Data from JSON is never an instance of your classes; check its properties, or build an instance from it after validating.

 You model payments as card, transfer and wallet objects. Which design narrows most reliably and gives exhaustiveness checks?

A discriminant is explicit, works on plain data from JSON, survives refactoring, and lets the compiler prove a switch covers every member. in works, but guesses from shape.

 A function with return type string ends with a switch (payment.kind) that returns in every case and has no default. Someone adds "ussd" to the union. What happens?

While every kind is covered, TypeScript knows the end of the function is unreachable. Once "ussd" is not covered, the end becomes reachable and string does not include undefined, so you get error TS2366.

 Does const { kind } = payment; if (kind === "card") { payment.last4 } compile, when payment is a discriminated union parameter that is never reassigned?

TypeScript connects a destructured const discriminant to the object it came from, as long as neither can be reassigned. With let the link could break, so it does not narrow.

 What does this print? interface Account { balance: number; frozenReason?: string; } function withdraw(account: Account | undefined, amount: number): string { if (account === undefined) return "no account"; if (account.frozenReason !== undefined) return `frozen (${account.frozenReason})`; if (amount > account.balance) return "insufficient funds"; return `new balance ${account.balance - amount}`; } console.log(withdraw({ balance: 1000 }, 1000)); console.log(withdraw({ balance: 1000, frozenReason: "KYC" }, 10)); console.log(withdraw(undefined, 10));

Each guard clause returns early, so the code below it only runs when the check failed. 1000 is not greater than 1000, so the withdrawal goes through and leaves 0.

 What does this print? let reference: string | number = "TX-7"; const first = typeof reference; reference = 7; const second = typeof reference; console.log(first, second, reference.toFixed(1));

Assigning narrows a let variable to the type of what was assigned, within its declared type. After reference = 7 it is a number, so toFixed compiles.

 Does this compile? function f(v: string | number) { const isText = typeof v === "string"; return isText ? v.toUpperCase() : v.toFixed(2); }

TypeScript (since 4.4) follows aliased conditions, as long as the condition is a const and the narrowed value is a const or an unassigned parameter.

 Why does setTimeout(() => email.toLowerCase()) fail with 'email' is possibly 'undefined' after if (email === undefined) return;, when the function later does email = undefined?

Narrowing describes a point in the code. A callback runs at another point. When the variable is not reassigned after the callback is created, TypeScript keeps the narrowing; here it is, so the compiler correctly refuses.

 What is the simplest habit that protects you from stale property narrowing like order.discount above?

A const cannot change behind your back, so narrowing on it is always true. ! would only hide the problem.

 What does the return type payment is CardPayment tell TypeScript?

A type predicate narrows in both directions: to the type on true, and to the rest of the union on false. TypeScript does not verify the body; it trusts it.

TypeScript 5.5 infers x is number for a simple arrow function whose body is a check it can read both ways, so filter uses its type-guard overload.

What does it print? function isLarge(amount: number | string): amount is number { return typeof amount === "number" && amount > 100000; } function describe(amount: number | string): string { if (isLarge(amount)) return "review"; return typeof amount === "string" ? `text ${amount}` : "a number slipped through"; } console.log(describe(500000), "|", describe("900"), "|", describe(900));

 What is the difference between a type guard (value is T) and an assertion function (asserts value is T)?

Both are ordinary runtime functions. Use a guard when you want to choose what to do with bad values, and an assertion function when bad values should stop the work.

 What does this print? function assert(condition: unknown, message: string): asserts condition { if (!condition) throw new Error(message); } function deposit(amount: number | null): number { assert(amount !== null, "amount is required"); assert(amount > 0, "amount must be positive"); return amount * 100; } for (const value of [25, null, -5]) { try { console.log(deposit(value)); } catch (error) { console.log(error instanceof Error ? error.message : "?"); } }

asserts condition narrows by the expression you pass: after the first call, amount is a number, so amount > 0 compiles. Each failed assertion throws its own message.

 const assertPositive = (n: number): asserts n => { … } compiles, but calling assertPositive(5) gives error TS2775. Why?

Control-flow analysis needs to know from the declaration alone that a call can narrow. Use a function declaration, or annotate the const with a function type that includes asserts.

 A form sends "abc" as an amount. Number("abc") gives NaN. Which check catches it?

NaN has type number, and typeof NaN is "number", so no type check can tell. Number.isFinite is false for NaN and the infinities.

 In a switch (payment.kind) that handles every kind, what does default: { const unhandled: never = payment; … } give you?

When every kind is handled, payment is never in the default branch, so the assignment is fine. A new unhandled kind is not assignable to never, and the compiler points straight at the switch.

 You wrote isNuban(value: unknown): value is string for ten-digit account numbers. Which test table is most useful?

The compiler trusts a guard's body, so tests are the only check. The values that are almost right, and the ones typeof gets wrong, are where guards break.
