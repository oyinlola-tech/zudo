In clean architecture, which import breaks the dependency rule?

Dependencies must point inward: adapters → application → domain. The domain importing an adapter points outward, so a change in HTTP formatting could now break the business rules. The composition root is allowed to import everything; that is its job.

 Who owns (declares) the OrderRepository interface, and why?

A port is written from the application's point of view. The adapter imports the port and implements it, so the import points inward even though the call goes outward at runtime. That reversal is dependency inversion. Types are erased at runtime, but the source dependency, which is what the rule is about, is real.

 Which of these is a driving (primary) adapter?

A driving adapter starts an action by calling into the application: HTTP handlers, CLIs, scheduled jobs and queue consumers. Repositories, payment gateways and clocks are driven: the application calls them.

 Why does Order.place take now: Date as an argument instead of calling new Date() itself?

A function that reads the clock gives different results on each run, so its tests cannot pin the output. The application gets the time from a Clock port, and tests give it a ManualClock, which is how the expiry test moved time forward 35 minutes instantly.

 What makes Money a value object rather than an entity?

An entity (like an order) keeps its identity while its data changes. A value object is defined by its value and is immutable: plus returns a new Money. The private constructor is how Money guarantees validity, but it is not what makes it a value object.

 What does the private constructor of Money buy you?

If the only way in is a factory that validates, every instance is valid by construction. kobo is still readable (it is readonly, not private). This is the "make invalid states unrepresentable" idea applied to a class.

 The before-code's order was { status: string } and any code could set status = "paid". What is this called, and what went wrong?

An anemic model holds data and leaves its rules to whoever touches it. The midnight job and payOrder each touched it differently. Putting the state transitions inside Order means every caller gets the same rule.

 Why do the use cases return an OrderSummary instead of the Order entity?

The use case is the only path that performs all the steps of an action. Handing out the live entity gives callers a way around it. Plain read-only data can be shown but not acted on.

 Ada asks to pay ord-3, which exists but belongs to Tunde. findOwn answers order_not_found, not forbidden. Why?

For resources that belong to someone, "not found" for both cases is a common, deliberate choice: a caller cannot probe which ids exist. HTTP does have 403; the choice is about what the answer reveals.

 Where should "the customer id comes from a verified session token" and "a customer may only pay their own order" live?

Tokens are an HTTP detail, so the adapter authenticates and passes a trusted customerId. The ownership rule must hold for every way in (web, CLI, job), so it lives in the use case, where all of them pass.

 The Catalog port promises that reserve(items) is all or nothing. Why must that promise be part of the port, not left to each caller?

Atomicity depends on the storage: a SQL transaction, a single conditional UPDATE, a lock. The port states the guarantee, every adapter must keep it, and a contract test can check it. Types cannot express it.

 In PlaceOrder, save throws after reserve succeeded. What does the catch block do, and what is it called?

Without one transaction around both steps, the use case undoes the first step by hand. It rethrows because the order really failed. Compensation is imperfect (the release can fail too), which is why a database adapter would rather use a transaction.

 save succeeded, then events.publish throws. Why is "just retry the whole PlaceOrder" a bad fix?

Retrying a whole use case that already has side effects duplicates them. Saving the events in the same transaction as the order, then publishing from that table, makes "saved but not announced" impossible.

 Why does InMemoryOrders store OrderRecords made by toRecord instead of the Order objects themselves?

A fake that stores live objects silently "saves" every mutation. Code that forgets to call save works in tests and loses data in production. The contract test's "changes count only after save" catches this.

 Where does the persistence mapper (toRecord/fromRecord) belong?

Column names like customer_id and unit_price_kobo are storage details. Putting the mapper in the domain would make the domain depend on the database schema.

 A new e-mail adapter wants totals as "₦16,500" (no kobo). Where should that formatting go?

Presentation differs per adapter: JSON, CLI and e-mail all want their own format. Keeping it out of the domain and the application means a new format never touches the rules.

 The HTTP adapter's status table is typed Record<OrderFailure["code"], number>. What happens when someone adds { code: "book_withdrawn" } to OrderFailure?

A Record over a union of keys requires every key. The compiler turns "forgot to map the new failure" into an error in the one place that must change.

 What is a contract test for a port?

The same tests run against the in-memory and the PGlite repository. If both pass, tests written against the fast fake say something true about the real database.

 Which import would the lesson's regex-based checker miss?

The pattern looks for import/export … from, side-effect imports and import("…"). require is not matched, and neither is an import built from a variable. Tools that parse the code (dependency-cruiser, eslint-plugin-boundaries) do not have these gaps.

 For which feature is full clean architecture (entity, use case, ports, mappers) most likely ceremony?

Layers pay off where there are rules to protect and technologies to swap. Opening hours are plain data with no transitions; a simple CRUD handler is clearer there, even inside a clean codebase.
