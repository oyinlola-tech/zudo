A phone sends POST /transfers and gets no response within 30 seconds. What does the phone know about the transfer?

From the client's side, a lost request, a failed request and a succeeded request with a lost response all look the same. That is why retries are necessary, and why the server must make them harmless.

 Where should a transfer endpoint get the id of the user who is sending money?

Anything in the body is chosen by the caller. The user is whoever the verified credentials say, and then the server checks that this user owns the from account.

 Ada asks to send money from account 7, which exists but belongs to Bola. Which answer leaks the least?

If "not yours" and "does not exist" give different answers, anyone can discover which account numbers exist. Answer both the same way.

 What does UPDATE accounts SET balance_kobo = balance_kobo + 1000 WHERE id = 99 do when there is no account 99?

SQL does not treat "no row matched" as an error. Check the number of changed rows (or use RETURNING), or verify the recipient exists before writing.

 Two transfers of ₦10,000 from an account holding ₦15,000 run at the same time. Each reads the balance, sees ₦15,000, and writes balance - 10000. What is the safe fix?

"Read, decide, write" leaves a gap in which another transfer can act on the same balance. A conditional update closes the gap; the constraint catches any bug that slips through. Idempotency keys solve duplicates, not two different transfers.

 A transfer debits the sender, credits the recipient and inserts a record. Why must all three run in one transaction?

Atomicity: all or nothing. Without it, a failure after the debit leaves the bank with less money than before. A transaction does not help with duplicate requests; that is the idempotency key's job.

 When should a mobile app generate the idempotency key for a transfer?

The key names one user intent. A fresh key per attempt makes every retry look new, and one key for all transfers would make the second transfer a replay of the first.

 Why are keys stored under (user_id, key) instead of just key?

A stored response may contain balances and account numbers. Scoping keys to the authenticated user means a key only ever replays that user's own responses.

 A client reuses a key from a ₦10,000 transfer for a new ₦50,000 transfer. What should the server do?

Replaying would tell the app a ₦50,000 transfer succeeded when it did not; running it would make keys meaningless. Comparing a stored fingerprint of the request catches the client bug.

 Why does the request fingerprint sort object keys before hashing?

A retry may serialize the same object with keys in another order. Without a canonical form, an honest retry would be rejected as a reused key.

 Why must the stored response be written in the same transaction as the transfer?

The work and the record of the work must agree. In one transaction, either both exist or neither does, so a retry either replays or safely redoes.

 A retry arrives while the first request with the same key is still running. What should the server answer?

The request is identical, so it is not a misuse (422). It is simply too early. A short 409 lets the first request finish; the next retry replays its result.

 A server claims a key, marks it in progress, and crashes before committing the transfer. Without a lock expiry, what happens?

The key row was committed before the crash, and nothing ever marks it complete. An expiry on the lock lets a later retry take the key over.

 Server A holds a key's lock, becomes very slow, and its lock expires. A retry takes over and completes the transfer. Then server A tries to finish. What stops a second transfer?

A lock expiry alone means two holders can believe they own the key. Tying completion to a token that changes on takeover lets only the current holder commit.

 A transfer is refused with 422 "insufficient funds". The client retries with the same key. What should it get?

Business rejections are real answers. Replaying them keeps the key's meaning simple: one intent, one outcome. Only unexpected errors release the key.

 The database is briefly unreachable and the handler throws. What should happen to the idempotency key?

An unexpected error says nothing about the request, and the transaction rolled back, so nothing happened. Replaying a stored 500 would turn a short outage into a permanent failure for that intent.

 A team stores idempotency keys in a JavaScript Map inside the server. They run three copies behind a load balancer. What goes wrong?

Keys must live where every copy sees them and where they survive restarts: the database, ideally in the same transaction as the work.

 Which responses should a transfer client retry, using the same idempotency key?

Retry what might succeed later. A 400 or 422 will fail the same way every time. Thanks to the key, retrying the others can never cause a second transfer.

 Why add random jitter to retry delays?

Without jitter, clients synchronized by one outage stay synchronized, and every retry wave hits at once. Random spreading turns a spike into a gentle slope.

 Which statement about "exactly-once delivery" is accurate?

To be sure a message arrived, a sender must be willing to send it again, so duplicates are possible. Idempotent processing makes duplicates harmless: effectively once.

 A transfer must also send an SMS. Where should the SMS be triggered?

Inside the transaction, a later rollback leaves an SMS for a transfer that never happened. After the commit, a crash loses the SMS. The outbox row exists exactly when the transfer does.
