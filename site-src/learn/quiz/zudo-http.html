createHttpServer needs an adapter and a handler. What is the job of each?

createNodeHttpAdapter uses node:http and decides the host and port. The handler is your code: it receives each request and returns the answer.

 Why do the lesson's examples use createNodeHttpAdapter({ host: "127.0.0.1", port: 0 })?

The OS picks a free port, and server.address?.port tells you which one. That is handy in examples and tests. A real server uses a fixed port such as 3000.

 Inside a route, how do you answer 400 with a JSON message, without throwing?

createResponseContext takes { status, headers, body }, or you chain setStatus, setHeader and json. The filter example in the lesson answers a bad done value exactly like this.

 What does a router give you compared to one handler for every path?

Without a router, one handler turns into a long chain of if statements. createRouter() keeps the table, and router.dispatch answers unknown paths with 404 and known paths with the wrong method with 405.

 A route is router.get("/tasks/:id", …) and the request is GET /tasks/2. What is ctx.params.id?

Route parameters are always strings, because a URL is text. Convert and check them yourself, as parseId does, or compare with String(t.id).

 A route handler receives one object, usually called ctx. Where are the request and the route parameters?

ctx.request is the request (headers, body, path), ctx.params holds values such as :id, and ctx.query holds the query string.

 The router has only GET /tasks/:id. A client sends DELETE /tasks/1. What does it get?

The path is known but the method is not, so the router answers 405 and lists ["GET"]. A path that matches no route at all gets 404.

 What type can a value in ctx.query have?

?limit=10 gives "10", a string. ?tag=a&tag=b gives ["a", "b"]. And the key may be missing, so the type is string | string[] or undefined.

 A client calls GET /tasks?done=false. Which check correctly reads the filter?

"false" is a non-empty string, so it is truthy: if (ctx.query.done) and Boolean(...) both treat it as true. Compare with the exact strings, and answer 400 for anything else.

 In a POST route, what is ctx.request.body?

The server reads the bytes for you but cannot know if they are JSON, a form or an image. Decoding with TextDecoder and parsing is your job.

 A client sends a 50 MB body to a route. What happens by default?

The body is limited to 10 MB by default, and bigger bodies get 413 Payload Too Large. A limit like this stops one client from filling the server's memory.

 Why does readJson wrap JSON.parse in try and throw badRequest(...)?

JSON.parse throws on bad input. Left uncaught, that becomes a 500, telling the client the server is broken. Catching it and throwing badRequest gives the honest answer: 400, your request is wrong.

 A client POSTs to /tasks with Content-Type: text/plain. What does the lesson's readJson do?

It checks the Content-Type header first. Anything that does not start with application/json gets 415, before any parsing.

 Why does readJson return unknown instead of any?

With unknown, TypeScript will not let you use the data until you check it, for example with NewTaskSchema.parse(...). any would switch checking off for untrusted input.

 A route throws new HttpError(415, "Send JSON"), with no third argument. What code does the client get in the JSON body?

HttpError picks its code from the status, so 415 becomes UNSUPPORTED_MEDIA_TYPE. You only pass { code: "..." } as a third argument when you want a code of your own.

 A POST /tasks creates task 7. What is the best answer?

201 says "a new resource exists now", and Location says where it lives: createResponseContext({ status: 201 }).setHeader("location", `/tasks/${task.id}`).json(task).

 A route throws new Error("Cannot read /var/data/tasks.db"). Why is it good that the client only sees {"error":"Internal Server Error"}?

Any error that is not a known HTTP error is treated as a bug. Its message is not sent; the client gets a generic 500. You log the details for yourself instead.

 A cookie set with response.cookie(...) has HttpOnly by default. What does that protect against?

HttpOnly hides the cookie from page scripts. Secure is the one about HTTPS, and SameSite=Lax is the one about other websites.

 Which default cookie setting stops other websites from making the browser send your cookie with their requests (except when the user follows a normal link)?

SameSite=Lax limits cross-site sending. HttpOnly hides the cookie from scripts, Secure keeps it to HTTPS, and Max-Age only sets how long it lives.

 A teammate wants to turn off HttpOnly and Secure on the session cookie "to make testing easier". What is the right answer?

The defaults protect users: scripts cannot read the cookie, it travels only over HTTPS, and other sites cannot send it. Convenience in testing is not a reason to weaken a real session cookie.

 In the Task API, what belongs in src/routes/tasks.routes.ts?

A route file is thin. The rules (validation, the unique title check) stay in TaskService, so they work the same no matter how the service is called.

 Why does the Task API run parseId(ctx.params.id) before calling tasks.get(...)?

Number("abc") is NaN, and a NaN id would just look like "not found". parseId checks for a positive safe whole number and answers 400: the request itself is wrong.
