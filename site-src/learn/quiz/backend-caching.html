What does it mean that a cached value is stale?

A cache holds a copy. When the original changes and the copy does not, the copy is stale. Every caching decision is about how much staleness you can accept in exchange for speed.

 Should a shop cache a customer's wallet balance and use the cached value to approve a ₦50,000 purchase?

A stale balance can approve a purchase the customer cannot pay for. You may cache a balance for display, briefly, but the decision itself happens against the real data, usually in one database statement.

 A developer caches carts under the key "cart". What happens?

A key must contain every input that changes the answer. For per-user data that includes the user id. A missing input serves one person's data to another.

 Why cache "product 999 does not exist" for a few seconds?

This is negative caching. Without it, a script requesting random ids bypasses the cache completely. Keep the TTL short, because "does not exist yet" is exactly what may change soon.

 On a price change, in which order should the code touch the database and the cache?

If you delete first, a reader can miss in between, load the old price and cache it again. Updating first and deleting after closes that gap (a small race remains, which generations handle).

 Why does the lesson invalidate by deleting the key instead of writing the new value into the cache?

Writing values from the write path duplicates the loading logic (joins, mapping, formatting), and any difference produces wrong cache entries. A delete always leads to a correct reload.

 Which two jobs does a TTL do in a cache-aside setup?

Even with careful invalidation, some write path will one day forget to delete a key. The TTL guarantees the wrong copy disappears eventually.

 Why does TtlCache take a Clock instead of calling Date.now()?

With a manual clock, "60 seconds later" is one line in a test, and the result is the same on every run. Waiting for real time makes tests slow and flaky.

 In TtlCache.get, a hit deletes the key and sets it again. Why?

Re-inserting marks the entry as most recently used. When the cache is full, entries.keys().next().value is then the least recently used key. The expiry time is kept unchanged.

 What happens to an in-process cache with no size limit on a busy server?

Expired entries in this cache are only removed when read, and even with sweeping, many unique keys can be alive at once. A size limit with LRU eviction makes memory use predictable.

 A warm-up job caches 10,000 products at once with a TTL of exactly 60 seconds. What problem does jitter solve?

Random spread (for example ±10%) turns one synchronized expiry into a steady trickle of reloads.

 A reader starts loading, a writer updates the price and deletes the key, then the reader stores the old price. Which fix does the lesson use?

The generation tells a loader that the world changed while it was working. Its result may still be returned to its own caller, but it is not stored for everyone else.

 What is a cache stampede?

It happens exactly when a hot key is empty or has just expired, which is when the database most needs the cache's protection.

 Each of ten servers uses in-process single-flight. A hot key expires in the shared cache. At most how many database reads for that key follow?

Single-flight collapses concurrent loads inside one process. Across processes, you need a shared lock (such as Redis SET … NX PX) if even ten reads are too many.

 Why must a distributed cache lock such as SET lock:product:1 <id> NX PX 5000 have an expiry?

NX sets the key only if it is absent (so one server wins); PX 5000 makes it disappear after 5 seconds no matter what happens to its owner.

 An entry is past its fresh time but still inside its stale window. What does a stale-while-revalidate cache do?

Nobody waits unless the entry is completely too old. The next request after the refresh gets the new value. HTTP has the same idea: Cache-Control: stale-while-revalidate.

 After a deploy, the cache's hit rate falls from 92% to 3%, and nothing else changed in the traffic. What is the most likely cause?

A key that contains something unique per request (a timestamp, a request id, an unnormalised query string) never repeats, so every lookup misses. Watching the hit rate is how you notice.

 The shared cache is down. What should a product page do?

For data that also lives in the database, the cache is an optimisation. Losing it must cost speed, not correctness or availability. Make sure the database can take the extra load for a while.

 Why should every call to a shared cache have a short timeout?

"Down" fails fast; "slow" holds every request hostage. A timeout turns slow into down, which fail-open code already handles.

 A search page caches results under search:${rawQueryString}. What is the risk?

Unbounded keys from raw input let an attacker, or just random tracking parameters, churn the cache. Normalise inputs (sort, drop unknown parameters, lower-case) and cache only known shapes.

 Four servers each keep an in-memory cache of prices. An admin changes a price through server 1, which deletes its own entry. What do customers on servers 2 to 4 see?

Each process only invalidates its own memory. Use a shared cache, broadcast invalidations (for example Redis pub/sub), or accept the TTL as the staleness bound.

 Why must a cache not store the result of a failed load?

A brief database hiccup would become a minute-long outage for that key. Store only successful values; the next caller retries the load.
