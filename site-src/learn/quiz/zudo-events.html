completeTask saves the task, then sends an email, updates statistics and clears the cache itself. What is the main problem?

The parts are tied together, so a change in one forces changes in the others. With events, completeTask only saves and announces; each reaction lives in its own handler.

 Which is the best name for an event?

An event says "this happened", in the past tense, as namespace.action in lowercase words joined by dots. sendWelcomeEmail is an order to do something, not an event.

 What does the code that publishes task.completed know about the handlers?

That is the point of events: the publisher does its job and announces it. Publishing to nobody is not an error.

 What is the event bus?

Publishers hand events to the bus, and the bus calls every matching handler. This bus lives in the memory of one process.

 Why are events frozen, so nobody can change them after they were created?

A frozen event is the same for every handler. If a handler needs changed data, it copies the payload first.

 A developer calls bus.on("task.completed", ...) inside a request handler. What goes wrong?

This is a listener leak. Subscribe your handlers once, when the app starts. The bus warns you when one event type collects more than 100 handlers.

 Three handlers match an event: priority 10, priority 0 and priority -10. In which order do they run?

Higher numbers run first, and the default is 0. Handlers with the same priority run in the order they subscribed. An audit log at -10 always runs last.

 Handler B only works if handler A ran first. What does the lesson suggest?

Use priorities sparingly. Two handlers that depend on each other's order are really one job, so keep them together.

 Three handlers each call a different outside API and take about 300 ms. Which dispatch mode fits best?

Parallel mode starts all handlers at once and waits for the slowest. Use sequential when order matters or handlers share something, like one database connection.

 The email handler throws because the mail server is down. The task was already saved. What does the bus do by default?

Failing the request would be wrong, because the task was saved. So the other handlers still run, and each failure is reported in result.errors and to the onError hook.

 Why should the Task API log handler failures in the bus's onError hook?

onError sees every failure once the handlers have run, even when the publisher ignores the result. Log it there with the logger.

 When is the THROW error mode a good choice?

In THROW mode the first failing handler rejects the publish and the handlers after it do not run. That is useful when any failure must stop you, like in a test.

 You write a middleware with bus.use(async (context, next) => { ... }). What must it do with next()?

next() runs the rest: other middleware, then the handlers. Returning without calling it stops the event (shortCircuited: true); forgetting to return its result hides what the handlers did.

 Why is validateEventMiddleware given priority 100 in the middleware option?

The outermost middleware runs first. A validation check belongs there, so an invalid event is rejected before any other code touches it.

 Linus tries to complete Ada's task. Where does the ownership check belong?

If the event were published, the email, statistics and cache handlers would all react to something Linus was not allowed to do. Check permissions first, then publish.

 The process crashes after the task was saved but before the email handler ran. What happens to the email?

This bus keeps events only in memory, and nothing retries them. For work that must happen, put a job on a queue (the background jobs lesson).

 Why should you publish task.completed after the database transaction commits?

Handlers react at once: an email could go out for a task that was never saved. Publish once the data is really saved.

 You run two copies of the Task API. Copy A publishes task.completed. Do handlers in copy B run?

This bus lives in the memory of one process. Another copy has its own bus and never hears about the event.
