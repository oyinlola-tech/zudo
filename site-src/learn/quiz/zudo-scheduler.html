How do a scheduler and a queue share the work in the Task API?

The scheduler starts work because of the time. The queue from the background jobs lesson makes the work reliable. Used together, the scheduler only has to add a job at the right moment.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); try { scheduler.every("5m", "refresh-stats"); console.log("scheduled"); } catch (error) { console.log(error.name); }

No job called refresh-stats was defined, so scheduling it throws at once. The lesson's rule: scheduling an id you never defined throws. The duration "5m" itself is fine.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); scheduler.define({ id: "cleanup", name: "Cleanup", handler: () => {} }); try { scheduler.define({ id: "cleanup", name: "Cleanup again", handler: () => {} }); console.log("defined twice"); } catch (error) { console.log(error.name); }

A job id names one function. Defining the same id twice is refused, so two parts of the app cannot silently replace each other's job. One job can still have several schedules.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); scheduler.define({ id: "refresh-stats", name: "Refresh", handler: () => {} }); const handle = scheduler.every("5m", "refresh-stats"); console.log(handle.state); await handle.pause(); console.log(handle.state); await handle.cancel(); console.log(handle.state);

every returns a handle, a remote control for that one schedule. It is active as soon as it is created, pause() makes it paused, and cancel() ends it for good.

 Where should the Task API call scheduler.stop()?

stop() ends the timers and deals with running jobs. Call it on shutdown next to the queue workers, so a deploy does not cut a job off halfway without warning.

 You need "once, 30 seconds from now". Which call is it?

after runs once after a delay. every would repeat every 30 seconds, at takes a Date, and the cron expression means minute 30 of every hour.

 What does this print? import { parseDuration } from "@zudojs/scheduler"; console.log(parseDuration("90s"), parseDuration("1h30m"), parseDuration("2d"));

Durations are turned into milliseconds. 90 s is 90 000 ms, 1 h 30 m is 90 minutes (5 400 000 ms), and 2 d is 48 hours (172 800 000 ms). Units can be combined, as in 1h30m.

 What does this print? import { InvalidDurationError, parseDuration } from "@zudojs/scheduler"; try { console.log(parseDuration("5")); } catch (error) { console.log(error instanceof InvalidDurationError ? "refused" : "other error"); }

A bare number is rejected, because nobody can tell whether 5 means seconds or minutes. Always write the unit: "5s" or "5m".

 What are the five fields of a cron expression, in order?

Minute comes first, which is why 0 9 * * 1-5 means "minute 0, hour 9". Getting minute and hour swapped is the most common cron mistake.

 What does 30 2 * * 1-5 mean?

Minute 30, hour 2, any day of the month, any month, day of week 1 to 5. Day of week counts 0 as Sunday, so 1-5 is Monday to Friday.

 Which expression runs at minutes 0, 15, 30 and 45 of every hour?

*/15 means "every 15th". 15 * * * * runs only at minute 15, * 15 * * * runs every minute from 15:00 to 15:59, and 0-15 runs at each of minutes 0 to 15.

 Friday 2 October 2026, 12:00 UTC. What does this print? import { CronTrigger } from "@zudojs/scheduler"; const trigger = new CronTrigger("0 9 * * 1-5", "UTC"); const next = trigger.next(new Date("2026-10-02T12:00:00Z")); console.log(next.toISOString());

09:00 on Friday has already passed at 12:00. Saturday 3 and Sunday 4 are not in 1-5, so the next run is Monday 5 October at 09:00.

 What does this print? import { CronTrigger } from "@zudojs/scheduler"; const trigger = new CronTrigger("*/15 * * * *", "UTC"); console.log(trigger.next(new Date("2026-10-02T12:00:00Z")).toISOString());

12:00 matches */15, but the next run is always strictly after the date you give. So the answer is 12:15.

 What does this print? import { CronTrigger } from "@zudojs/scheduler"; const trigger = new CronTrigger("0 */6 * * *", "UTC"); let after = new Date("2026-10-02T12:00:00Z"); const runs = []; for (let i = 0; i < 3; i++) { after = trigger.next(after); runs.push(after.toISOString().slice(11, 16)); } console.log(runs.join(" "));

*/6 in the hour field is hours 0, 6, 12 and 18, at minute 0. 12:00 is not strictly after 12:00, so the runs are 18:00, then 00:00 of the next day, then 06:00.

 What does this print? import { CronTrigger } from "@zudojs/scheduler"; const trigger = new CronTrigger("@monthly", "UTC"); console.log(trigger.next(new Date("2026-10-02T12:00:00Z")).toISOString().slice(0, 10));

@monthly is a shortcut for 0 0 1 * *: midnight on the 1st. 1 October has already passed, so the next one is 1 November.

 Both day fields are set. Starting from Friday 2 October 2026, what does this print? import { CronTrigger } from "@zudojs/scheduler"; const trigger = new CronTrigger("0 0 13 * 5", "UTC"); let after = new Date("2026-10-02T12:00:00Z"); const days = []; for (let i = 0; i < 3; i++) { after = trigger.next(after); days.push(after.toISOString().slice(0, 10)); } console.log(days.join(" "));

When both day fields are set, cron runs when either matches. So this runs on every Friday (9, 16 October) and on the 13th (a Tuesday). It does not mean "Friday the 13th".

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); scheduler.define({ id: "digest", name: "Digest", handler: () => {} }); for (const expression of ["0 9 * *", "0 0 30 2 *"]) { try { scheduler.cron(expression, "digest", { timezone: "UTC" }); console.log("ok"); } catch (error) { console.log(error.name); } }

Four fields cannot be parsed, so the first fails with CronParseError. 0 0 30 2 * is valid cron, but 30 February never comes, so the schedule is refused with InvalidScheduleError. Both fail when you write them, not at 2 a.m.

 Which time zone does the lesson recommend for cron schedules on servers, and why?

Servers move between regions, and local time has daylight-saving gaps and repeats. UTC never jumps. For users who want 09:00 their time, store their zone and compute the UTC time.

 A job is scheduled at 02:30 local time. On the night the clocks jump forward, what happens?

When clocks jump forward (say from 02:00 to 03:00), 02:30 local time never happens, so the job is skipped. When they jump back, 02:30 happens twice. UTC has neither problem.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); scheduler.define({ id: "digest", name: "Digest", handler: () => {} }); try { scheduler.cron("0 9 * * 1-5", "digest", { timezone: "Africa/Lagos" }); console.log("scheduled in Lagos time"); } catch (error) { console.log(error.name); }

The package carries no time-zone database, so named zones are refused rather than silently ignored. It supports only "UTC" or the system local zone.

 Why does the lesson pass a clock to new Scheduler({ clock }) in its examples?

The clock is where the scheduler reads the current time. A clock that always says 12:00 on 2 October makes every answer predictable, which is how you test schedules.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const now = new Date("2026-10-02T12:00:00Z"); const scheduler = new Scheduler({ clock: { now: () => new Date(now), nowMs: () => now.getTime() }, }); scheduler.define({ id: "refresh-stats", name: "Refresh", handler: () => {} }); const handle = scheduler.every("5m", "refresh-stats"); console.log(handle.nextRun().toISOString());

every("5m") first runs 5 minutes after now. The clock says 12:00, so the next run is 12:05.

 A schedule that runs every 5 minutes is paused for 15 minutes, then resumed. What happens?

Resuming computes the next run from now. A schedule paused over three fire times does not fire three times at once.

 What does this print? import { Scheduler } from "@zudojs/scheduler"; const scheduler = new Scheduler(); scheduler.define({ id: "cleanup", name: "Cleanup", handler: () => {} }); scheduler.define({ id: "stats", name: "Stats", handler: () => {} }); const cleanup = scheduler.cron("30 2 * * *", "cleanup", { timezone: "UTC" }); scheduler.every("5m", "stats"); await cleanup.cancel(); console.log(cleanup.nextRun(), scheduler.listSchedules().map((s) => s.jobId));

A cancelled schedule has no next run, and listSchedules() no longer shows it. Only the stats schedule is left.

 A job has retry: { attempts: 3 }. It throws on attempts 1 and 2 and works on attempt 3. What does onError receive?

onError hears only about what still fails after the last retry. Here the third attempt worked, so the run is recorded as completed.

 A job with timeout: 50 runs for 150 ms. What must the handler do to really stop?

JavaScript cannot kill a running function. The scheduler aborts ctx.signal and reports a SchedulerJobTimeoutError, but the handler has to look at the signal and stop its own work.

 What should the Task API's onError callback do?

A nightly job can fail every night for a month without anyone noticing. Sending failures to the logs and to an alert makes them visible. The history only holds the last 100 runs and lives in memory.

 A cleanup runs every 10 minutes but one run takes 25 minutes. Which overlap policy is usually right for it?

"skip" drops fire times while a run is still going. "allow" (the default) lets runs pile up, each one slowing the database further. "replace" would abort the long cleanup every time, so it might never finish.

 Only the newest result matters: a slow run should be aborted and a fresh one started. Which policy fits?

"replace" aborts the running one and starts fresh. "queue" would wait for the old run and then start one more.

 The scheduler keeps schedules in memory. After a restart, how does the Task API get its weekday digest back?

Recurring schedules live in your code, which is the source of truth, so nothing is lost. Only schedules that users create, such as reminders, must be stored in the database.

 A user asks "remind me on 12 October at 08:00". Where should that reminder live so it survives a restart?

A user-created reminder is data. Store it in the database and schedule it again on start. (A delayed job on a stored queue is often even simpler for one-off work.)

 The server was down at 08:00. The app restores the reminder at 12:00. What does this print? import { Scheduler } from "@zudojs/scheduler"; const now = new Date("2026-10-02T12:00:00Z"); const scheduler = new Scheduler({ clock: { now: () => new Date(now), nowMs: () => now.getTime() }, }); scheduler.define({ id: "task-reminder", name: "Reminder", handler: () => {} }); const handle = scheduler.at(new Date("2026-10-02T08:00:00Z"), "task-reminder", { misfire: "run-once", }); console.log(handle.nextRun().toISOString());

The reminder's time already passed while the server was down. With misfire: "run-once" (the default) it runs once, right away, which is 12:00 on this clock.

 Three copies of the Task API run behind a load balancer, each with its own scheduler. What happens at 09:00 without any protection?

Each scheduler is independent and only knows its own process. You need one of the fixes: run it on one instance, take a shared lock, or only enqueue and let an idempotent worker drop duplicates.

 Why is a queue deduplicationKey alone not enough to stop a second digest?

If server B fires a moment after server A's job has finished, the key no longer blocks it. An idempotent processor, backed by a unique column in the database, protects you no matter when the duplicate arrives.

 In the enqueue pattern, why is the day taken from ctx.scheduledAt rather than from new Date()?

The day must be the same for both servers so the duplicate is recognised. The time the run was due is the same on both; the real clock might already be past midnight on one of them.

 Which item belongs on the production checklist for scheduled work?

A short handler that only enqueues gives the real work the queue's retries and dead letters. The checklist also says: UTC, overlap: "skip", timeouts with ctx.signal, and stop() on shutdown.
