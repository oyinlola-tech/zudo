Sabi's access tokens are JWTs that live 15 minutes. What makes it possible to end one of them immediately at logout?

A plain JWT is valid until it expires; nothing on the server remembers it. Binding it to a session gives the server a row it can delete. One cheap lookup per request buys instant logout, "sign out everywhere" and role changes that take effect at once.

 A refresh token that was already used comes back. What does the platform do, and why?

A used refresh token should never come back. If it does, two parties have it. Ending all sessions forces both to log in again, and only the real user can. The demo showed the phone and the new laptop token dying too.

 Why does createPgRevocationStore implement revokeIfNotRevoked as a single INSERT … ON CONFLICT DO NOTHING RETURNING?

"Check, then revoke" has a gap between two awaits. The unique key makes check and write one atomic step. Without the method, @zudojs/auth falls back to the racy pair, so always implement it in a real store.

 Why does Sabi keep sessions in PostgreSQL instead of createMemorySessionStore()?

The memory store is fine for learning and single-process tests. In production, behind a load balancer, every server must see the same sessions: a database or Redis.

 A session has an idle timeout of 30 minutes and an absolute limit of 7 days. Ada uses the app every 10 minutes, day and night. When does her session end?

With only an idle timeout, a busy session (or a stolen one being used) lives forever. LEAST(now() + ttl, absolute_expires_at) in touch implements both clocks.

 Reset tokens are stored as SHA-256 hashes, while passwords use slow scrypt. Why is a fast hash acceptable for reset tokens?

Slow hashing protects low-entropy secrets from offline guessing. A random 32-byte token cannot be guessed in any number of tries, and a deterministic hash also lets you look the token up with WHERE token_hash = $1.

 Why does POST /v1/password-resets answer 202 with the same message for known and unknown e-mails?

A different answer for "no such account" is an enumeration oracle. The production concerns add the second half: the response time must not differ either, which is why the e-mail belongs on a queue.

 The reset link is https://sabi.example/reset-password#token=…. What does putting the token after # achieve?

Query strings are logged by web servers and proxies and leak through the Referer header. The fragment stays in the browser. The token still travels, but only in a POST body to your API.

 Why does a successful password reset call auth.logoutAll(user)?

Refresh tokens live 7 days, and an attacker with a session can keep refreshing. Changing the password without ending sessions leaves the attacker inside.

 confirm looks the token up before hashing the new password. What does that order protect?

An endpoint that runs expensive work before rejecting bad input can be used to burn CPU. Reject cheaply first. The conditional UPDATE afterwards still makes the token single-use if two requests race.

 Roles ride in the access token. When an admin makes Tunde a tutor, how does Tunde's access change?

Tokens cannot be edited, only replaced. Because they are session-bound, ending the sessions is how you replace them at once. The same works for demotions, which is the case that matters for security.

 Why does PUT /v1/users/:id/roles refuse an admin who tries to change their own roles?

Self-modification of privileges is a classic source of lockouts (and, the other way round, of escalation). Another admin, or a seed script on the server, handles it.

 A student registers with {"email": "…", "name": "…", "password": "…", "roles": ["admin"]}. Why does nothing happen with roles?

The client never chooses its own privileges. The schema is the allow-list, and the SQL hard-codes the default role. Incident 4 came from copying the body into the database.

 Why are Kora identities stored by (provider, provider_id) and not by e-mail?

sub is the provider's permanent id for that person. E-mail is only used once, to decide whether to link or create, and only when verified.

 Kora returns email: "ada@example.com" with email_verified: false, and no identity is linked yet. What does Sabi do?

Anyone can type any e-mail into a new provider account. Linking or creating on an unverified address hands out other people's accounts, or blocks the real owner from registering.

 Mallory registered bola@example.com with a password before Bola joined. Bola now signs in with Kora (verified e-mail). What does Sabi do, and why?

This is the pre-account takeover from incident 3. Linking alone would leave Mallory with a working password on Bola's account. Evicting whoever set an unverified password closes it; verifying e-mails at registration keeps real owners from being surprised.

 Where does Sabi keep the OAuth state and PKCE verifier between the start and the callback?

If the browser held the state itself, an attacker who controls the browser's inputs controls both sides of the comparison. On the server, it survives a callback that reaches another server, and deleting the row on use makes the callback single-use.

 The tests give @zudojs/auth-oauth a fetch that sends https://id.kora.example/… requests to the fake Kora on 127.0.0.1. Why not configure the endpoints as http://127.0.0.1:… directly?

A provider URL pointing at an internal address could turn your server into a tool for reaching internal services. The guard blocks it; the test routes the public name to the local fake instead of weakening the guard.

 In accountFor, the lookup is SELECT … FROM users WHERE email = $1 FOR UPDATE. What does FOR UPDATE prevent?

The row lock serializes the two decisions. Where the row does not exist yet, the second insert then fails on the users or identities key instead of creating a duplicate.

 Why does Sabi's error handler copy headers from the thrown error?

@zudojs/http's built-in handling sends those headers; replacing it with your own handler means taking over that job. The lockout test checks the header, so this cannot silently break.

 Logout reads the session id from the verified token's sid, not from the request body. What would go wrong with a body field?

Anything that decides whose data a request touches must come from verified credentials, not from what the client says.

 The auth service locks an e-mail after five wrong passwords. Which attack does that not stop, and what does?

A lockout counts per account, so an attacker spreading guesses across many accounts never trips it. A limit per client address, and in production shared counters across servers, covers that case.

 Bola only ever signed in with Kora, so his password_hash is NULL. What happens when someone tries POST /v1/sessions with his e-mail and any password?

A missing credential must mean "no", never "anything goes". Bola can still set a password with a reset link if he wants one.
