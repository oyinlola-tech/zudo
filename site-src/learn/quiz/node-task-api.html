The Task API supports CRUD. Which routes are those?

CRUD is the four basic things you do with records. The API maps them to POST /tasks, GET /tasks and GET /tasks/:id, PATCH /tasks/:id and DELETE /tasks/:id.

 What is a middleware in this lesson?

Middleware is how work that applies to every request (logging, headers, auth) is written once. next() runs the rest of the chain.

 What does this print? function compose(middlewares, handler) { return function run(ctx, index = 0) { if (index === middlewares.length) return handler(ctx); return middlewares[index](ctx, () => run(ctx, index + 1)); }; } const a = async (ctx, next) => { console.log("a before"); await next(); console.log("a after"); }; const b = async (ctx, next) => { console.log("b before"); await next(); console.log("b after"); }; await compose([a, b], async () => console.log("handler"))({});

Each middleware runs its "before" part, then next() runs the rest of the chain. When the handler finishes, control comes back up in reverse order, so b after comes before a after.

 What does this print? function compose(middlewares, handler) { return function run(ctx, index = 0) { if (index === middlewares.length) return handler(ctx); return middlewares[index](ctx, () => run(ctx, index + 1)); }; } const log = async (ctx, next) => { await next(); console.log("log: status", ctx.status); }; const auth = async (ctx, next) => { if (ctx.user !== "ada") { ctx.status = 401; return; } await next(); }; const app = compose([log, auth], async (ctx) => { console.log("handler ran"); ctx.status = 200; }); await app({ user: "mallory" }); await app({ user: "ada" });

For mallory, auth never calls next, so the handler never runs, but log still sees the 401 because it comes first. That is how one auth check protects every route behind it.

 Why does the logger go first in the middleware list?

Middleware runs in the order you list it. A logger placed after the auth check would never see the rejected requests, which are often the ones you want to see.

 Why should routes throw errors and let one middleware turn them into responses?

If each route writes its own error responses, one of 50 routes will eventually send a stack trace or a file path to the client. One error handler means one place to get it right.

 What does this print? class HttpError extends Error { constructor(status, message) { super(message); this.name = "HttpError"; this.status = status; } } function toResponse(error) { if (error instanceof HttpError) { return { status: error.status, body: { error: error.message } }; } return { status: 500, body: { error: "Internal Server Error" } }; } console.log(JSON.stringify(toResponse(new HttpError(404, "Task 9 not found")))); console.log(JSON.stringify(toResponse(new Error("connect ECONNREFUSED 10.0.3.7:5432")))); console.log(JSON.stringify(toResponse(new TypeError("task.title is undefined"))));

Only an HttpError, thrown on purpose with a message written for the client, is shown as it is. Anything else is a bug or an outage: the client gets a plain 500 and the details go to the server log.

 A database call fails with connect ECONNREFUSED 10.0.3.7:5432 (db password rejected). What should the client see?

That message contains an internal address and a hint about a password. Log the details where you can read them; tell the client only that something went wrong.

A function that receives its inputs is easy to test. server.js is the only file that touches process.env and the port.

 What does the Task API do when TASKS_API_KEY is missing?

A server without its secret is not safe to run, so it stops at once with a clear message. A key is never written into the code, and never printed in a log.

 How does the lesson give the server its API key on your computer?

The key is made with crypto.randomBytes(32), kept in .env, and kept out of Git. Secrets never go into code or into files you commit.

 What does this print? class TaskStore { #tasks = new Map(); #nextId = 1; create(title) { const task = { id: this.#nextId++, title, done: false }; this.#tasks.set(task.id, task); return { ...task }; } get(id) { const task = this.#tasks.get(id); return task ? { ...task } : undefined; } } const store = new TaskStore(); const task = store.create("Buy milk"); task.done = true; task.id = 99; console.log(store.get(1).done, store.get(99));

The Map is private (#tasks). As long as a new store offers the same methods, the routes do not care where the tasks live.

 Why does requireApiKey use timingSafeEqual instead of given === apiKey?

A normal comparison answers a tiny bit faster when the first characters are wrong. timingSafeEqual always takes the same time, so there is nothing to measure.

 timingSafeEqual needs two inputs of the same length. What does this print? import { createHash, timingSafeEqual } from "node:crypto"; const sha256 = (text) => createHash("sha256").update(text).digest(); try { timingSafeEqual(Buffer.from("abc"), Buffer.from("a much longer key")); } catch (error) { console.log(error.name); } console.log(sha256("abc").length, sha256("a much longer key").length); console.log(timingSafeEqual(sha256("abc"), sha256("a much longer key")));

Inputs of different lengths make timingSafeEqual throw. Hashing both sides first gives two 32-byte values, which can always be compared, and also hides how long the real key is.

 This copies how requireApiKey reads the header. What does this print? function givenKey(header) { header = header ?? ""; return header.startsWith("Bearer ") ? header.slice(7) : ""; } console.log(JSON.stringify([givenKey("Bearer abc123"), givenKey("Basic abc123"), givenKey(undefined), givenKey("bearer abc123")]));

Only a header that starts exactly with "Bearer " gives a key; slice(7) removes those 7 characters. Anything else, including a missing header, gives an empty string, which never matches the real key.

 requireApiKey(apiKey, ["/health"]) skips the key check for /health. Which mistake would be a security problem?

Forgetting a public path only makes one route stricter. Adding a path by mistake opens it to everyone. Keep the public list as short as possible.

 When is one shared API key not enough?

A shared key says "this caller is one of ours", not who they are. An API used by many people needs real user accounts, passwords and permissions.

 What do the headers X-Content-Type-Options: nosniff and Cache-Control: no-store tell a browser?

These are cheap safety headers. nosniff stops the browser treating data as a different type (such as a script), and no-store keeps private data out of caches.

 Why does PATCH /tasks/:id refuse any field except title and done?

Accept only the fields you expect. Copying whatever arrives lets a client change things it must not touch, such as ids or owners.

 This is the check PATCH runs on the body. What does it print? function checkFields(body) { for (const key of Object.keys(body ?? {})) { if (key !== "title" && key !== "done") return `400 unknown field "${key}"`; } return "ok"; } console.log(checkFields({ done: true })); console.log(checkFields({ title: "Buy milk", id: 7 })); console.log(checkFields(null));

Every key must be on the allow-list, so id is refused even next to a valid title. body ?? {} makes a null body count as "no fields".

 In the Task API, parseId throws notFound (404) for /tasks/abc, not 400. Why is that reasonable?

/tasks/abc names a task that cannot exist, so 404 describes it well. The important part is that the text is checked before it is used.

 What are SIGINT and SIGTERM?

Signals are messages the operating system sends a process. The server listens for both and shuts down gracefully.

 What does a graceful shutdown do?

server.close stops new connections and calls its function when the last one ends. Nobody gets cut off halfway through a request.

 The shutdown code has setTimeout(() => process.exit(1), 10_000).unref(). What is it for?

Normally the program ends by itself once the last connection closes. If one never closes, the timer forces an exit. Without unref, the timer alone would keep the program running for 10 seconds.

Creating and passing dependencies by hand grows with every service you add. Dependency injection, which ZudoJS provides, is the standard answer.

 Why does hand-written validation, like checkTitle and the PATCH allow-list, become a problem in a big API?

None of the checks is hard, but there are many, and consistency matters. That is why frameworks offer schema validation.
