Your code looks for tasks.ada in the cache and it is not there, so it asks the database. What is this called?

A miss means the value was not in the cache, so you do the slow work. A hit means the copy was there and you skipped the work.

 What is the main price you pay for caching?

A cached copy does not update itself. Most of the work of caching is keeping copies correct: how long they live, and removing them when the data changes.

 Which of these should you not cache?

If data must always be exact, like a bank balance or a permission check, a stale copy is a real bug or a security hole. Cache results where a short delay is acceptable.

 In @zudojs/cache, what is the difference between the CacheService and the adapter?

You always call the service (get, set, getOrSet...). The adapter decides where entries live: memory now, a shared store such as Redis later, without changing your code.

 A memory cache was created with maxEntries: 1000 and it is full. What happens when you store one more entry?

A cache is allowed to forget. When it is full, the least recently used entry makes room for the new one, and the next read of it is simply a miss.

 Why should you check found.hit instead of found.value?

An empty task list is a perfectly good cached answer. If you tested the value, you would treat it as a miss and query the database every time.

 Why does the key builder reject a key part such as "ada:tasks.list"?

The full key is prefix:namespace:key. If a key part could contain :, someone who controls part of a key could read or overwrite another user's entry.

 You cache GET /tasks under the key tasks.list, with no namespace. Ada asks first, then Linus. What happens?

The cache only knows the key. The key or namespace must include everything the answer depends on, especially the user, taken from the verified login token.

 Where should the user id for a cache namespace come from?

Anything the client can change, it can set to another user's id and read their cached data. Only the verified token tells you who is really asking.

 Why is a TTL called a safety net?

When the time is up, the entry counts as missing and the next read gets fresh data. Invalidation is the main tool; the TTL limits the damage when invalidation is missed.

 You want a settings entry that never expires. What do you write?

ttl: null means "never expires". ttl: 0 is a common mistake: it is rejected with CACHE_INVALID_TTL.

 What happens when you make a TTL much longer?

A TTL is a trade-off between speed and freshness. Data you cannot clear reliably, like another company's API answer, should live only as long as you can accept it being out of date.

 What is a cache stampede?

50 requests in the same millisecond all miss and all hit the database. getOrSet prevents it: other callers for the same key wait for the one running computation.

 You run three copies of the Task API. How far does the stampede protection of getOrSet reach?

Waiting callers are tracked in each process's memory. One query per copy is usually fine; for "exactly once across servers" you need a lock in a shared store.

 Which rule keeps cached task lists correct?

Create, update, delete and any background job that changes tasks must clear the entries they made stale. Invalidating before every read would make the cache useless.

 Why are tags often more useful than delete(key) for invalidation?

A new task changes the full list, the open list and the count. Tag them all with tasks, and a new cached view with that tag is cleared by the same code.

 You tagged Ada's entries with tasks in the namespace ada, then call invalidateByTag(["tasks"]) with no namespace. What happens?

Tags live inside a namespace. Pass the same namespace on both sides, or the stale list stays in the cache silently.

 Why do you give withLock a ttl?

A lock held by a dead process would block forever. The lease expires; while your function runs, it is renewed for you.

 What does config.failSilently: true do when the Redis cache server is down?

An outage should only make you slower. A bad key or a lock that cannot be taken still throws, because those are bugs in your code, not an outage.

 A teammate writes cache.getOrSet("report", () => buildReport(user.role)). An admin asks first, then a normal user. What is the best fix?

The answer depends on the role, but the key does not. The normal user would receive the admin report. Check permission first, so a normal user never reaches admin data, and include the role in the key.

Build stampede protection by hand. once(key, load) keeps running promises in the inFlight map: if one is already running for the key, return it; otherwise start load(), store the promise, and delete it from the map when it settles.

 const inFlight = new Map(); let queries = 0; function once(key, load) { // your code here } const slowQuery = async () => { queries += 1; await new Promise((resolve) => setTimeout(resolve, 20)); return 2; }; const answers = await Promise.all([once("ada", slowQuery), once("ada", slowQuery), once("ada", slowQuery)]); console.log(answers, "queries:", queries, "left:", inFlight.size); const inFlight = new Map(); let queries = 0; function once(key, load) { const running = inFlight.get(key); if (running) return running; const promise = load().finally(() => inFlight.delete(key)); inFlight.set(key, promise); return promise; } const slowQuery = async () => { queries += 1; await new Promise((resolve) => setTimeout(resolve, 20)); return 2; }; const answers = await Promise.all([once("ada", slowQuery), once("ada", slowQuery), once("ada", slowQuery)]); console.log(answers, "queries:", queries, "left:", inFlight.size); [ 2, 2, 2 ] queries: 1 left: 0
