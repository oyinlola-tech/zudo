In the raw node:http server, JSON.parse threw inside the async request callback. Why did the client hang instead of getting an error response?

node:http calls your function and ignores what it returns. A rejected promise from it goes nowhere: no response is written, and without an unhandledRejection handler Node ends the process. The framework wraps every request in its own try/catch.

 The raw server did { id: newId, ...JSON.parse(text) }. What went wrong when the client sent {"title":"Kindred","id":"b1","featured":true}?

Later properties in a spread win, so the client's id replaced the server's, and any extra field was stored. A strict schema that refuses unknown keys, and a record built from named fields, prevent it.

 DELETE /books/b1 is sent to a router that only has GET /books/:id. What is the correct answer?

The resource exists; the method is not supported on it. 405 with Allow tells the client exactly what would work, which 404 would hide.

 Routes GET /books/:id and GET /books/new are registered in that order. Which one handles GET /books/new in the mini router, and why?

Registration order should not decide this, or adding a route in the wrong file silently breaks another. Scoring static segments above parameters makes the result predictable.

 Why does the router wrap decodeURIComponent in try/catch?

Any input the client controls can be malformed. Turning parser exceptions into client errors keeps the status honest and the error logs free of noise.

 Middleware [logging, auth, handler] run as an onion. In what order do their "after" parts run?

Each middleware wraps everything inside it, so the innermost finishes first. The outermost starts first and finishes last, seeing the final response.

 A request-logging middleware is placed inside the error-handling middleware. What goes wrong?

The thrown error travels outward past the logger to the error handler. With the logger outside, it receives the response the error handler built, including the 4xx and 5xx ones you most need to see.

 Why does compose throw when a middleware calls next() twice?

A bug like "retry by calling next again" silently duplicates side effects. Failing loudly turns it into an error during development.

 A maintenance middleware returns a 503 without calling next(). What happens to the handler?

Answering early is how authentication, rate limits and maintenance modes work: the inner layers are skipped, the outer ones still observe the response.

 What do you gain by describing the body once with s.object({...}) instead of writing an interface and a separate parser?

Infer<typeof NewBook> is computed from the schema. Change a field in one place and both the check and every handler's type change with it.

 Why does s.object refuse keys that are not in the shape, instead of silently dropping them?

Both choices prevent mass assignment. Refusing also tells an honest client about its mistake, which silently dropping hides.

 A handler throws TypeError: Cannot read properties of undefined (reading 'priceKobo'). What should the response body contain?

Internal messages reveal field names, file paths and library versions to attackers. The request id connects a user's report to the full log entry.

 Why does HttpError carry a code such as "conflict" besides the English message?

A client that compares messages breaks when someone fixes a typo. Codes are part of the API contract; messages are for people.

 A book was saved, then the newsletter listener threw. What should the client receive?

The bus isolates listeners with Promise.allSettled. Reporting a failure for a saved book would make the client retry and create a duplicate.

 When should a reaction to book.added go to a queue or outbox instead of the in-process bus?

In-process listeners run inside the request and die with the process. Durable, retryable work belongs in a queue, published reliably with an outbox.

 Why does readBody check the size while reading the chunks instead of after reading the whole body?

A limit that is enforced after the damage is not a limit. Counting as bytes arrive lets the server refuse with 413 early.

 A client sends title=Kindred with Content-Type: text/plain to an endpoint that expects JSON. Which status fits best?

415 says "I cannot read this kind of body". 406 is about the response type the client accepts; 400 and 422 are for bodies in the right format with wrong content.

 The adapter opens a container scope per request and disposes it in finally. What does that give controllers?

The scoped controller and its scoped dependencies live exactly as long as the request. finally guarantees disposal, so a failed request cannot leak an open transaction.

 What does server.close() do to a request that is still being handled?

That is why the in-flight /report still got its 200 during the stop. closeIdleConnections() additionally drops kept-alive connections that are doing nothing, so shutdown does not wait for them.

 Why do the examples and tests listen on port 0?

Hard-coded ports fail when two test runs, or a developer's other server, already use them. server.address().port tells you the real one.

 In @zudojs/http, what is ctx.request.body for a JSON POST?

The server cannot know whether bytes are JSON, a form or an image, so it gives you the bytes (within a size limit). Your mini framework made the opposite choice and parsed JSON for every request.
