What does this print? function* steps() { console.log("validate"); yield 1; } const s = steps(); console.log("created"); s.next();

Calling a generator function only creates the generator object; the body does not start. The first next() runs it up to the first yield, which is when validate is printed.

 What does this print? function* checkout() { yield "cart ok"; return "done"; } const c = checkout(); console.log(c.next().value, c.next().done, c.next().value);

The first next() stops at yield. The second runs to return, giving { value: "done", done: true }, and we print its done. The third call on a finished generator gives { value: undefined, done: true }.

 Between two next() calls, what happens to a generator's local variables?

A paused generator keeps its whole call environment alive, like a closure does. That is what lets a generator replace the index variables of a hand-written iterator.

 What does this print? function* rates() { yield 0.075; yield 0.05; } const r = rates(); console.log([...r].length, [...r].length, [...rates()].length);

A generator object is one walk. The second spread gets a finished generator. Calling rates() again creates a new generator object that starts from the beginning.

 What does this print? function* range(start, end, step = 1) { if (step === 0) throw new RangeError("step must not be 0"); for (let n = start; n < end; n += step) yield n; } const r = range(1, 5, 0); console.log("created"); try { r.next(); } catch (error) { console.log(error.name); }

The check is part of the generator body, so it only runs on the first next(). Put argument checks in a normal wrapper function that returns the generator if you want the error where the bad call was made.

 How do you make an object that can be walked with for...of many times, using a generator?

Every for...of calls [Symbol.iterator](). If that method is a generator, each call creates a new generator object, so each walk starts fresh.

 What does this print? function* ids() { let n = 1; while (true) yield `INV-${n++}`; } console.log(ids().drop(2).take(2).toArray());

Generator objects inherit from Iterator.prototype, so they have the helpers. drop(2) skips two ids, take(2) takes the next two and stops, so the infinite loop is never run to the end.

 Why is while (true) { yield delay; … } safe inside a generator, when the same loop in a normal function would hang?

A generator only runs when asked. The infinite loop describes an unlimited sequence; take, find, destructuring or break decide how much of it is used.

 What does this print? function* double(items) { for (const x of items) { console.log("double", x); yield x * 2; } } const pipe = double([1, 2]); console.log("built"); for (const y of pipe) console.log("got", y);

Nothing runs until the loop pulls. Then each item goes all the way through the generator to the loop body before the next item is produced.

 In the lesson's first(items, count), the count is checked right after yield item, not at the top of the loop. Why?

The for...of head pulls the next item before the body runs. Returning immediately after the last wanted yield stops without that extra pull, which matters when upstream stages are expensive.

 What does this print? function* lines() { yield "RICE"; yield* ["OIL", "SALT"]; yield* "AB"; } console.log([...lines()].join(" "));

yield* hands out every value of any iterable, one at a time. An array gives its items; a string gives its characters.

 What does this print? function* a() { yield ["OIL", "SALT"]; } function* b() { yield* ["OIL", "SALT"]; } console.log([...a()].length, [...b()].length);

yield hands out one value, here the whole array. yield* delegates to the array and hands out its two items separately.

 What does this print? const tree = { name: "Shop", children: [{ name: "Food", children: [{ name: "Oils", children: [] }] }, { name: "TVs", children: [] }] }; function* names(node) { yield node.name; for (const child of node.children) yield* names(child); } console.log([...names(tree)].join(","));

Each node yields its own name, then delegates to each child in turn, which finishes its whole subtree first. That is a depth-first, pre-order walk.

 What does this print? function* rows() { yield "ORD-1"; return 1; } console.log([...rows()]);

The return value arrives with done: true, and spread (like for...of) stops at done: true without using its value.

 What does this print? function* lines(order) { for (const sku of order) yield sku; return order.length; } function* all(orders) { let total = 0; for (const order of orders) total += yield* lines(order); console.log("total", total); } console.log([...all([["RICE", "OIL"], ["SALT"]])].length);

A yield* expression evaluates to the delegate's return value, so total collects 2 + 1. The spread finishes the outer generator (printing the total) before console.log prints the length.

 What does this print? function* till() { let total = 0; while (true) total += yield total; } const t = till(); t.next(500); t.next(200); console.log(t.next(300).value);

The first next(500) only starts the body and runs to the first yield; its argument is thrown away. next(200) makes that yield evaluate to 200, and next(300) adds 300: the total yielded is 500.

 Why is the argument of the first next() call on a generator ignored?

A value sent with next(value) becomes the result of the yield the generator is paused on. Before the first call, it is paused before the body, not at a yield.

 What does this print? function* cursor() { try { yield "ORD-1"; yield "ORD-2"; } finally { console.log("closed"); } } for (const id of cursor()) { console.log(id); break; } console.log("after");

break makes for...of call the generator's return(). The generator resumes as if a return stood at the paused yield, so its finally runs before the loop is left.

 What does this print? function* g() { yield 1; yield 2; } const it = g(); it.next(); console.log(it.return(99), it.next());

return(value) finishes the generator at its paused yield and reports value with done: true. After that it stays finished.

 What does this print? function* feed() { for (const price of [100, -1, 300]) { try { yield price; } catch (error) { console.log("skip", price); } } } const f = feed(); f.next(); f.next(); console.log(f.throw(new Error("bad")).value);

throw(error) raises the error at the paused yield (the one that yielded -1). The generator's catch handles it, the loop continues, and throw() returns the next yielded value, 300.

 What happens when you call gen.throw(error) and the generator does not catch it at the paused yield?

An uncaught error travels out of the generator the same way it would out of a normal function, running finally blocks on the way. The generator is then completed.

 You call next() once on a generator that holds a lock inside try/finally, then drop the generator. What happens to the lock?

Nothing resumes a paused generator automatically. for...of and other consumers call return() for you; when you drive next() by hand, call return() in your own finally.

 Why is lines.forEach((line) => { yield line.sku; }) inside a generator a SyntaxError?

Each function has its own body, and only a function* body may contain yield. Use a for...of loop in the generator instead of a callback.

 A developer stores const allOrders = paginate(fetchPage) (a generator object) at the top of a server module and loops over it in every request handler. What happens?

A generator object is single-use state. Create one per walk, by calling the generator function inside the handler, or expose a reusable iterable with *[Symbol.iterator]().

 What does next() return on an async function* generator?

An async generator can await before it yields, so the result is only known later: next() returns a promise. for await...of awaits each one.

 What does this print? async function* pages() { for (const page of [["A", "B"], ["C"]]) { await null; console.log("fetched", page.length); yield* page; } } async function main() { for await (const item of pages()) { console.log(item); if (item === "B") break; } } main();

Async generators are lazy too. The loop stops after B, so the generator never resumes to fetch the second page.

 Why can you write for await (const chunk of fs.createReadStream("orders.csv")) in Node?

for await...of uses the async iteration protocol. Any object with a [Symbol.asyncIterator]() method works, and Node's readable streams have one.

 In the CSV export, why must a SKU like SALT,FINE be written as "SALT,FINE"?

In CSV the comma separates fields. A field containing a comma, a double quote or a newline is wrapped in quotes, and inner quotes are doubled.

 The export finds no orders at all. What should the CSV contain, according to the lesson?

A header-only file says "the export ran and found nothing". An empty file is indistinguishable from a crash, and a message in the data breaks any program that reads the CSV.

 The API throws inside paginate, three stages below exportOrders. What happens?

Generators do not hide errors. Each stage is resumed by the stage above it, so an error unwinds through all of them to the consumer, running every finally on the way.

 How does the lesson's test prove that the export streams instead of loading every page first?

The output text would be identical for an eager version. Only the request count differs, so that is what the test must assert.

Write a generator flatten(value) that yields every non-array value inside nested arrays, in order, using yield* for nested arrays.

 Why is the generator version of "all lines of all orders" so much shorter than the hand-written iterator?

A hand-written next() is called fresh each time, so all state has to be kept in variables you manage. A generator keeps its whole paused call, loops included.

 The backoff generator yields delays forever, and take(3) limits the attempts. What is the design benefit of that split?

The sequence describes the rule; the consumer decides how much of it to use. The same backoff can serve a job queue with ten attempts and a checkout with two.

 A for await...of loop walks an async generator that fetches one page per step. How are the pages fetched?

The generator only resumes when the loop asks for the next item. That keeps memory and load low; fetching several pages in parallel needs promise combinators and a concurrency limit, covered in later lessons.

 In the CSV export, only exportOrders writes to the file; orderLines and toCsv only yield. Why is that split useful?

Keeping side effects at the edges is the same advice as for pure functions: the stages are easy to test and reuse, and the one function that touches the outside world owns the try/finally.
