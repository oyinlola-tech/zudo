When is reading a framework's source the right move?

Documentation states promises; source states behaviour. Read it with a precise question, and confirm what you read with an experiment.

 Which question is best for starting to read a framework's source?

A narrow question tells you what to search for and when you are done. Broad questions lead to reading hundreds of files without an answer.

 A package's exports field lists only ".". What happens to import("@zudojs/http/dist/httpAdapter/httpAdapter.errorResponse.js")?

exports is the package's public boundary. Files outside it may exist on disk, but Node will not load them through the package name.

 The package's files field excludes dist/**/*.map. What does that mean for you when you press "Go to Definition" in your editor?

Without source maps, the declaration is where types lead. Open the neighbouring .js file, or use "Go to Source Definition", to see the code.

 What can you learn from a package's dependencies before reading any code?

@zudojs/container depends only on errors; @zudojs/http on six packages. Behaviour you see in one may be implemented in a dependency.

 What is a barrel file?

Reading a barrel first shows which areas a package covers and, through explicit re-exports, how name clashes were resolved.

 compareSegmentSpecificity is exported from @zudojs/http but not mentioned in its documentation. How should you treat it?

Barrels that re-export whole folders make helpers public by accident. Documented API is protected by semantic versioning; incidental exports may change more freely.

 Why is building on a package's internal module risky, even when you manage to load it?

Semantic versioning protects the public API only. Reading internals to understand behaviour is fine; depending on them turns every upgrade into a risk.

 Why read a function's .d.ts declaration before its implementation?

The contract narrows the reading. Knowing that registerFactory types its factory from its inject list tells you what to look for in the code.

 What does InjectedDependencies<[Token<Date>, Token<string>]> compute, given { -readonly [K in keyof Deps]: Deps[K] extends ProviderToken<infer U> ? U : never }?

A mapped type over a tuple keeps the positions; infer U extracts each token's type. The result is the factory's parameter list.

 Why does registerFactory<T, const Deps extends readonly ProviderToken[]> use the const modifier on Deps?

Without it, the list would widen to (Token<Date> | Token<string>)[], and every parameter would have the union type.

 What is a quick way to see what a complicated type from a .d.ts actually computes?

Types are erased at runtime, so they cannot be printed. The compiler, however, spells out the expected type in its error message, as it did for [Date, string].

 You saw the response body {"error":"Internal Server Error"}. What is a good way to find the code that produced it?

Messages and status texts are distinctive and rarely renamed, so they lead straight to the code that uses them. "error" matches everything.

 The source shows that HttpRouter.match sorts all routes on every call. What is the most sensible reaction?

For a few dozen routes the cost is negligible. A precise report ("sort once when a route is registered") helps everyone; editing node_modules is lost on the next install.

 In @zudojs/http, /books/:id and /books/:id(\d+) both match /books/42. Which wins?

The ranking compares segment kinds only. A constraint does not change the kind, so registration order decides. Register constrained parameters first.

 A comment in the router says the ranking "used to" be a sum, which let /:p/:q/:r/:s outrank /admin/*rest. Why are such comments valuable to a reader?

History comments are compressed bug reports. The admin bypass is a reminder that route ranking is a security property, not just a convenience.

 How does the @zudojs/http adapter decide the status code of a thrown error?

The mapper checks the shape, not the class. Your own error class with statusCode = 410 got a 410, which also lets errors from other libraries carry statuses.

 An error with statusCode: 410 and no expose is thrown. What does the client see?

Message and code are included only when the error opts in with expose: true. Details stay private by default, even for 4xx errors from custom classes.

 You resolve an unregistered class Sms whose constructor is constructor(readonly gateway = "sms.shop.ng"). What does @zudojs/container do?

Auto-registration checks token.length === 0, and Function.prototype.length stops counting at the first parameter with a default. That is convenient, and surprising if you expected an error.

 Why does @zudojs/container pass a singletonAncestor down the resolution instead of scanning the path?

Carrying the answer down avoids re-scanning the path at every step, and makes the rule explicit: once a singleton is above you, nothing scoped may be built.

 When you run npx tsc, how does npm find the program to run?

bin maps command names to files. npx uses the local install when there is one, and the #!/usr/bin/env node line makes the file executable as a Node script.
