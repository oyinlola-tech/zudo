With strict on, why is the variable in catch (error) typed unknown?

Anything can be thrown: strings, objects, null, numbers. TypeScript has no throws clause, and almost any line (including code in libraries) can throw. So the only honest type is unknown, which forces you to check before you use it.

 An old project compiles catch (error) { console.log(error.message) } without complaint. Which setting explains that?

useUnknownInCatchVariables, part of strict since TypeScript 4.4, makes catch variables unknown. Without it they are any, and every property access compiles, including ones that crash at runtime.

 Which catch clause does TypeScript accept?

A catch variable may only be annotated unknown or any (error TS1196 otherwise). A more specific annotation would be a promise nothing checks, because the try block can throw anything.

 What is wrong with catch (error) { log((error as Error).message) }?

An assertion changes the type, never the value. If null was thrown, .message throws a TypeError inside your error handler; if a string was thrown, it logs undefined. Narrow with instanceof Error or normalize instead.

 A catch handles RangeError and then ends with throw error;. Why is that last line important?

Handle only what you expect. A catch that swallows everything hides bugs, outages and data problems. Re-throwing lets a boundary (an HTTP handler, a job runner) deal with the rest.

 Why does the lesson write override readonly name = "InsufficientFundsError" instead of this.name = new.target.name?

Both work in plain Node.js. But bundlers and minifiers shorten class names, and then logs show e: …. A literal also gives the property a literal type, which is useful for narrowing.

 Which class field has the literal type "card_declined" rather than string?

A readonly property initialized with a literal keeps the literal type, because it can never change. A mutable field widens to string, and an explicit string annotation widens it too. (A static field is not on the instance at all.)

 What is the type of error.cause for an error created with new Error("failed", { cause: dbError })?

ErrorOptions declares cause?: unknown, because any value may be a cause. Narrow it like a caught value, for example with instanceof Error when walking a cause chain.

 An InsufficientFundsError with a code and a shortByKobo field is sent to a worker thread, which uses structuredClone. What arrives?

Structured cloning keeps an error's message but only the standard error types, so a custom class arrives as a plain Error. JSON.stringify does the reverse: it keeps own enumerable fields such as code and drops message. Rely on a code string at boundaries, not on instanceof.

 Why does askForNewCard(new Error("db down")) compile when the parameter type is class CardExpiredError extends Error {}?

TypeScript is structurally typed: a class with no extra members has the same shape as its parent. Add a member with its own literal type, such as readonly code = "card_expired", and a plain Error no longer fits.

 What turns CardDeclinedError | InsufficientFundsError | ProviderUnavailableError into a discriminated union that a switch can narrow?

A discriminant is a property every member has, with a different literal type in each. switch (failure.code) then narrows to the matching class, and a never default makes the check exhaustive.

 In a payments service, which failure is the best fit for a returned Result rather than a thrown error?

A declined card is part of the business: the direct caller must decide what to show or offer, and the type should force it to. Outages, missing config and bugs are unexpected; they are thrown and handled by a boundary.

 You want the caller of an async function to be forced to handle a declined card. Which return type does that?

Promise<T> has one type parameter, for the value; a rejection cannot be typed, and TypeScript has no throws clause. Put the expected failure in the resolved value instead.

 In loadRate().catch((reason) => reason.message.toUpperCase()), what is the type of reason?

TypeScript's own declarations type the .catch callback parameter as any, whatever your tsconfig says. Annotate it yourself: .catch((reason: unknown) => …).

 A function calls sendReceiptEmail(to); without await, and the rejection crashes the process later. What catches this mistake before it ships?

The compiler allows an unawaited promise as a statement. A type-aware linter reports it. A try around an unawaited call does not help: the call returns before the promise rejects.

 What does const STATUS = { … } as const satisfies Record<PaymentErrorCode, number> guarantee?

satisfies checks the object against the Record without widening its type, so a missing or extra code is a compile error, and as const keeps 402 instead of number. It cannot know about a class you forgot to add to the union; the runtime tests cover that.

 Why does the payments error system replace the message of an InternalError with a neutral sentence in the response?

An unexpected error's message was written for developers, not clients. The full error, with its cause chain, goes to the server log; the client gets a code and a safe sentence.

 Where should a service catch and normalize errors?

Boundaries are where a failure must become a response, a retry or a log line. Code in between lets errors travel, or wraps them with a cause to add meaning. A catch that neither handles nor wraps is noise.

 A test file contains // @ts-expect-error above a line. Someone changes the types and the line now compiles. What happens?

@ts-expect-error requires an error on the next line. When there is none, tsc reports "Unused '@ts-expect-error' directive". That turns "this must not compile" into a real, failing test.

 In @zudojs/errors, BaseError.code is typed ErrorCode | string. What follows from that?

ErrorCode | string is effectively string: any code is allowed, because a framework cannot know the codes your application invents. The price is weaker narrowing; your own closed union gives stronger checks inside one service.

 Which failure should be marked retryable and answered with a Retry-After header?

Only failures that may succeed later are worth retrying. A declined card or invalid input fails the same way every time, and a reused key is answered with the existing payment.

 Old tutorials put Object.setPrototypeOf(this, new.target.prototype) in every error constructor. Do you need it in a TypeScript 7 project?

With native classes (ES2015 and later), subclasses of Error get the right prototype automatically. The workaround belonged to ES5 output, which TypeScript 7 refuses (target=ES5 has been removed).
