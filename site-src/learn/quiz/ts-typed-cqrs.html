Which of these requests is a query?

A query asks for information and changes nothing, so it is safe to retry and to cache. The other three change state, so they are commands.

 Why does a command have exactly one handler, while an event can have many listeners?

"Place this order" must be done once, by the code responsible for orders, and return its result. An event only announces a fact, so any number of listeners may react, and the publisher expects no answer.

 Checkout must know the new order id to show it on the receipt. Which message fits?

Checkout needs an answer from exactly one handler, and it is asking for a change. That is a command. After it succeeds, the handler can publish order.placed so e-mail and analytics react.

 Why does the lesson's Bus take the whole handler table in its constructor instead of offering register(name, handler)?

A mapped type with one required property per request name turns "every command has a handler" into something the compiler checks. A series of register calls is just statements; nothing tracks which names are covered.

 The types guarantee a handler for every name. Why does execute still check Object.hasOwn(this.handlers, request.type) at runtime?

Types are erased. Anything that did not go through the compiler, or went around it, can send any name. Object.hasOwn also rejects names such as "toString" that plain indexing would find on the prototype.

 Why is the bus declared as Bus<S extends Specs<S>>, with type Specs<S> = { readonly [K in keyof S]: Spec }, rather than Bus<S extends Record<string, Spec>>?

The constraint says "whatever keys S has, each must be a Spec". It works for interfaces and type aliases alike, and still refuses an entry without a result.

 With "order.cancel": { input: { orderId: string; reason: string }; result: … }, what does a caller pass to execute?

RequestOf is { readonly type: K } & Readonly<input>: one flat object. K is inferred from its type field, and the other fields are checked against that request's input.

 Unlike the event bus, the command bus needs no cast to call the handler. Why?

The event bus stored listeners in a Map, whose value type cannot depend on the key. A mapped object type can: Handlers<S>[K] resolves to the handler for exactly K.

 Why is "out of stock" part of order.place's result type instead of a thrown error?

Expected business failures are data: the type lists them, and if (!result.ok) narrows to them. Bugs and outages are not expected; they throw and become a generic 500.

 What does const statusFor: Record<ErrorOf<ResultOf<ShopCommands, "order.place">>, number> guarantee?

ErrorOf pulls the error union out of the result, and Record requires a key for every member. Nothing checks that the numbers are sensible; that is what tests are for.

 Query handlers receive OrderReader = Pick<ReadonlyMap<string, OrderView>, "get" | "values">. What does this achieve?

Handing out a narrower type is a capability: code can only do what its type allows. It is a strong hint, not a proof, which is why architecture tests and reviews still matter.

 Why does a Middleware<ShopQueries> that returns cache.get(key) (typed unknown) fail to compile?

A generic function cannot invent a value of a type it knows nothing about. Middleware can pass results through, log them or throw, and a cache needs one cast that you justify (the key contains the query's type).

 The middleware type is type Middleware<S> = <K extends RequestName<S>>(request: RequestOf<S, K>, next: …) => …. Why is K on the function rather than on the type alias?

A generic function type is chosen fresh at every call. The bus calls the same audit middleware with "order.place" and then with "order.cancel", and each time next() has the matching result type.

 In abstract class Request<TResult> { declare readonly __result: TResult; }, why is the __result property there?

An unused type parameter changes nothing about a type's shape. The phantom property makes the result type part of the structure, so execute<T>(request: Request<T>) can infer T.

 What does declare readonly __result: TResult; produce in the compiled JavaScript?

A declare field tells TypeScript "this property exists" without emitting any code, so instances do not even have the key. That is why it costs nothing at runtime.

 What is a real advantage of class-based requests over the spec map?

Classes are decentralised: each module owns its requests. The price is that exhaustiveness is lost (missing handlers are runtime errors) and routing by constructor breaks for plain objects from JSON.

 A class-based bus routes by request.constructor. A PlaceOrder instance is sent through a queue as JSON and parsed on the other side. What happens?

JSON has no classes. Anything that crosses a process boundary must carry a string discriminator, which is one reason the spec-map design uses a type field.

 With @zudojs/cqrs, await bus.execute<PlaceOrder, string>(command) compiles although the handler returns an object. What is the second type argument?

The bus stores handlers by runtime string, so at the call site it cannot know which handler will answer. The result type argument is taken on trust, like as. A typed layer that derives it from your spec makes it correct by construction.

 In @zudojs/cqrs, what is the type of await commands.execute(createCommand("order.place", payload)) with no type arguments?

execute<TCommand, TResult = void> falls back to void. That hides the result rather than lying about it; to use the value you must supply (or derive) the result type.

 A @zudojs/cqrs command bus has no handler for "order.refund". When do you find out?

Handlers are registered one call at a time, at runtime, so only the bus itself knows what is registered. Check completeness at startup, or register from a typed handler table.

 A customer double-clicks "Pay", and two identical invoice.pay commands arrive. What prevents a double charge?

Types describe one call; they cannot see that two valid calls are the same intent. Idempotency is a runtime design, usually a table of processed command ids written in the same transaction as the payment.

 Why should commands return small results (an id, or a known failure) rather than the full updated order?

Separating the write result from the read model is the core of CQRS. A command that returns a full view couples every caller to the read shape and to the handler's timing.
