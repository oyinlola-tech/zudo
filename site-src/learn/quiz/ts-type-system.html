What does TypeScript check when you pass a value to a parameter of type Payment?

TypeScript is structurally typed: compatibility is decided by shape, not by name or origin. Extra members are allowed (outside of fresh literals), which is how an Order with an id and an amountKobo passed as a Payment.

 Why is TypeScript structural rather than nominal?

TypeScript had to describe JavaScript as it is written. Objects rarely declare a type at creation, so the only thing the compiler can compare is their shape.

 Two classes, PaymentId and OrderId, each have exactly one member: #value: string. Can an OrderId be passed where a PaymentId is expected?

The compiler cannot compare members it cannot see from outside, so private members make a class behave nominally. It is a real technique, with the runtime cost of an object per id.

 Inside structural typing, what is the simplest change that stops an Order being accepted as a Payment when both have id and amountKobo?

Different literal types are incompatible, so the shapes no longer match. Names and type versus interface do not matter structurally, and readonly properties do not affect assignability.

 Given interface Payment { readonly amountKobo: number } and interface Editable { amountKobo: number }, what does const e: Editable = payment; do?

This is a known hole: readonly arrays are checked in assignments, readonly properties are not. The assignment creates an alias, not a copy, so writing through it changes the original.

 A function takes options: { reason?: string; notifyCustomer?: boolean }. You pass a variable holding { notify: true }. What happens?

A type whose properties are all optional is a weak type. Assigning something that shares none of its properties is almost certainly a mistake, so TypeScript reports it, even for a variable that is not a fresh literal.

 In which of these does an excess property check run on { paymentId: "PAY-1", amountKobo: 500, reasn: "late" }?

Only a fresh literal, written where the target type is known, is checked. Variables, spread properties and parsed JSON all pass extra properties through silently.

 With type Payout = { last4: string } | { bank: string }, does const p: Payout = { last4: "4242", bank: "GTBank" } compile?

The literal is a valid { last4: string } with a property that another member knows, so it passes. Add a kind discriminant and TypeScript checks the literal against the chosen member alone.

 A sign-up handler types its body as { name: string; email: string }. An attacker sends "role": "admin" in the JSON. What stops the extra field?

Types are erased and the body comes from JSON.parse, which is never a fresh literal. Unknown keys survive unless a runtime validator strips or rejects them.

 A generic type F<T> is covariant in T when…

Covariance keeps the direction of subtyping. It is safe when T only comes out of the type: return values, readonly arrays, promises.

 Which of these types is contravariant in T?

A function that accepts a T only consumes it. A handler for any Order can serve as a handler for PaidOrder, not the reverse: the direction flips.

 Why is type Slot<T> = { get: () => T; set: (value: T) => void } invariant?

Widening a Slot<PaidOrder> to Slot<Order> would let set store an unpaid order; narrowing the other way would let get return an order without paidAt. Only exact matches are safe.

 Mutable arrays are treated as covariant, which is unsound. Why did the TypeScript team choose it?

It is a deliberate trade of soundness for convenience. The defence is to take arrays you only read as readonly T[], where covariance is sound because there is no push.

 An interface declares handle(event: ShopEvent): void, and an object whose handle only accepts PaymentCaptured compiles against it. What change makes the compiler reject that object?

Method parameters are checked bivariantly even in strict mode. Function-typed properties get the strict, contravariant check.

 Why does TypeScript keep method parameters bivariant?

If push's parameter were checked strictly, T would be in an input position and PaidOrder[] could no longer be used as Order[] anywhere. Method bivariance keeps the standard library convenient.

 Which compiler flag makes function-typed parameters contravariant instead of bivariant?

strictFunctionTypes applies to function types and function-typed properties, but not to method syntax, which stays bivariant.

 What does interface Feed<out T> { readonly latest: () => T } tell the compiler?

out means T only comes out of the type. If a member ever used T as an input, the annotation would fail with TS2636.

 Which is not a benefit of in/out annotations?

An annotation that contradicts the structure is an error (TS2636). Annotations document and check; they do not loosen the rules.

 In interface Channel<E> { readonly subscribe: (handler: (event: E) => void) => void }, in which direction does E flow through subscribe?

Each function parameter position flips the direction. E is a parameter of the handler, which is itself a parameter of subscribe, so the two flips cancel. The channel gives events out to handlers.

 Which of these costs the compiler work every time it is used with a new type argument?

Recursive object and union types are descriptions, expanded lazily. A recursive conditional or mapped type that builds a result is a computation, repeated for each input.

 In type Reachable<S, Seen = never> = S extends Seen ? never : S | Reachable<Next<S>, Seen | S>, what makes the recursion stop at a final status such as "delivered"?

A final status has an empty list of next statuses, so the recursive call receives never, which distributes over zero members and produces never. Seen handles cycles, not final states.

 Why does type Otp = `${Digit}${Digit}${Digit}${Digit}${Digit}${Digit}` fail with TS2590?

Template literal types multiply their unions: 106 strings. The better design is string plus a runtime pattern check, with a brand to record that the check passed.

 The lesson's Paths<T> is applied to { zones: { name: string }[] }. What does it produce?

Array indexes are numbers, so keyof T & string skips them; every method is a function, which extends object but yields no paths. Only length is left: a quiet wrong answer, the most dangerous kind.

 When is a type that computes its answer most likely worth keeping?

Outside data needs a runtime check anyway; one-off puzzles cost more to read than they save. Types like Awaited or an overloaded pipe earn their place by serving many callers well.

 The build's type test helper is type Assignable<From, To> = [From] extends [To] ? true : false. Why the brackets?

A naked type parameter in extends distributes: From = A | B would give true | false, which is boolean. Wrapping both sides in a one-element tuple asks the question once for the whole union.
