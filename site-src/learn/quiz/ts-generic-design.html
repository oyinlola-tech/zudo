Which signature has a type parameter that does not earn its place?

In logAll, T appears once and connects nothing; readonly unknown[] says the same thing more simply. In the others, the type parameter links an input to an output or to another argument.

 Why is function parseJson<T>(text: string): T dangerous?

A return-only type parameter cannot be inferred from anything, so it just becomes whatever the caller writes. The honest signature returns unknown, followed by a guard or a validator.

 This compiles. What does it print? function parseJson(text: string): T { return JSON.parse(text); } const account = parseJson<{ id: string; kobo: number }>('{"id": "ACC-1", "kobo": "5000"}'); console.log(typeof account.kobo, account.kobo + 100);

The JSON holds the string "5000". The type parameter only told the compiler to call it a number, so + 100 joins text. Nothing checked the data.

 In function choose<C extends string>(allowed: readonly C[], fallback: NoInfer<C>): C, what does NoInfer do?

Without NoInfer, a fallback of "GBP" would widen C to include it. With it, "GBP" is rejected because it is not one of the allowed currencies.

 This compiles (no NoInfer). What does it print? function choose(allowed: readonly C[], wanted: string, fallback: C): C { return allowed.find((c) => c === wanted) ?? fallback; } console.log(choose(["NGN", "USD"], "USD", "GBP"), choose(["NGN", "USD"], "EUR", "GBP"));

C was inferred from both arguments, so "GBP" is accepted as a fallback even though it is not allowed, and it is returned when nothing matches. NoInfer<C> on the fallback turns this into a compile error.

 Why is groupBy(items, keyOf) a better parameter order than groupBy(keyOf, items)?

Inference works best when a value reveals the type parameter and callbacks are then contextually typed from it. With the callback first, its parameter may have to be annotated by hand.

 class Emitter<Events extends Record<string, unknown>> rejects interface BankEvents { "transfer.completed": { kobo: number } }. Why?

The constraint asked for more than the class needs. It only uses keyof Events and Events[K], so Events extends object is enough and accepts interfaces.

 What is a good rule for choosing a constraint on a type parameter?

Too loose and the code cannot do its job (you cannot read item.id); too tight and good types are refused. T extends { id: Id } for a repository is the right size.

 Which declaration is invalid?

Type parameters with defaults must come after those without, just like optional function parameters. C = string before the required T is an error.

 With interface Repository<TEntity, TId = string, TCreateInput = Partial<TEntity>>, what is Repository<Account>?

Missing type arguments take their defaults, and a default may use earlier parameters: Partial<TEntity> becomes Partial<Account>. That is how @zudojs/database keeps its five-parameter contract short to use.

 What does findBy<K extends keyof T>(key: K, value: T[K]) guarantee?

K is inferred from the key, and T[K] is the type of that property. So findBy("frozen", "yes") is refused when frozen is a boolean.

 What does this print? function findBy(items: readonly T[], key: K, value: T[K]): T[] { return items.filter((item) => item[key] === value); } const accounts = [ { id: "ACC-1", owner: "Ada", frozen: false }, { id: "ACC-2", owner: "Tunde", frozen: true }, { id: "ACC-3", owner: "Eve", frozen: true }, ]; console.log(findBy(accounts, "frozen", true).map((a) => a.owner).join(","), findBy(accounts, "owner", "Ada").length);

Two accounts are frozen, and one belongs to Ada. The generic keeps the full element type, so a.owner is known on the results.

 Why does the repository's create take Omit<T, "id"> and update take Partial<Omit<T, "id">>?

Removing id from the input types makes "choose your own id" and "change an id" compile errors. Partial lets an update change only some fields.

 A patch arrived from JSON with an id the type did not allow. What does this print? const current = { id: "ACC-1", owner: "Ada", kobo: 500 }; const patch: unknown = JSON.parse('{"kobo": 900, "id": "ACC-666"}'); const next = { ...current, ...(patch as object), id: current.id }; console.log(next.id, next.kobo);

Later spreads win. Putting id last means a smuggled id in the patch is always overwritten, even when the types were bypassed at runtime.

 In the generic repository, create builds { ...input, id: this.nextId() } as T. Why is that assertion considered justified?

This is the "proof the compiler cannot follow" case. It sits in one place in shared code, where tests cover it, instead of being scattered across callers.

 Why should a generic findById return T | undefined rather than throw when nothing is found?

A lookup screen might show "no such account"; a transfer might treat it as a failure. Returning T | undefined, like Map.get, lets each caller decide, and the type forces them to.

 What is the error type of andThen(r1, fn) when r1: Result<number, "invalid-amount"> and fn returns Result<Account, "account-not-found">?

andThen returns Result<U, E | F>: the chain can fail at either step, so the error type is the union of both. The types collect the possible failures for you.

 Why is err declared as function err<const E>(error: E): Result<never, E>?

A const type parameter infers the narrowest type, like an as const at the call site. Literal error codes are what make E a useful, closed union.

 What does this print? type Result = { ok: true; value: T } | { ok: false; error: E }; function map(result: Result, fn: (value: T) => U): Result { return result.ok ? { ok: true, value: fn(result.value) } : result; } const good: Result = { ok: true, value: 250000 }; const bad: Result = { ok: false, error: "account-not-found" }; const toNaira = (kobo: number) => `₦${kobo / 100}`; console.log(map(good, toNaira), map(bad, toNaira));

map transforms the value of a success and passes a failure through untouched. The function never runs for the failed result.

 In a function returning Result<{ balance: number }, TransferError>, why may you write if (!from.ok) return from; when from is Result<Account, "account-frozen">?

After narrowing, from is { ok: false; error: "account-frozen" }. That object is a valid failed Result of any value type whose error union includes "account-frozen".

 What does the parameter messages: Record<E, string> in toResponse<T, E extends string>(result, messages) enforce?

Record<E, string> is an object type with exactly one required property per member of E. Leaving one out is a compile error at the endpoint.

 Why do transaction-history APIs often use a cursor (nextCursor) instead of page numbers?

With offsets, a new item at the top pushes everything down one position. A cursor names a specific item, so the next page starts right after it regardless of inserts.

 What does this print? interface Page { readonly items: readonly T[]; readonly nextCursor: string | null; } function paginate(all: readonly T[], limit: number, after: string | null = null): Page { const index = after === null ? -1 : all.findIndex((item) => item.id === after); const items = all.slice(index + 1, index + 1 + limit); const last = items.at(-1); return { items, nextCursor: index + 1 + limit < all.length && last ? last.id : null }; } const txs = [{ id: "T1" }, { id: "T2" }, { id: "T3" }]; const p1 = paginate(txs, 2); const p2 = paginate(txs, 2, p1.nextCursor); console.log(p1.items.length, p1.nextCursor, p2.items.map((t) => t.id), p2.nextCursor);

The first page holds T1 and T2, and its cursor is the last id, T2. The second page starts after T2, holds only T3, and there is nothing more, so its cursor is null.

 What does mapPage<T, U>(page: Page<T>, fn: (item: T) => U): Page<U> protect against?

The helper changes only the items and keeps everything else, so every endpoint that reshapes a page keeps its cursor by construction.

 What makes ApiResponse<T, E> a good envelope for every endpoint?

One discriminated union shape means one client helper can unwrap every response, and the error codes per endpoint are known at compile time.

 Why does TtlCache<K, V extends {} | null> forbid undefined as a value type?

{} is every value except null and undefined; adding | null allows null back. The constraint turns an ambiguous API into a compile error.

 What does this print? class TtlCache { private readonly entries = new Map(); constructor(private readonly ttlMs: number, private readonly now: () => number) {} async getOrLoad(key: K, load: (key: K) => Promise): Promise { const entry = this.entries.get(key); if (entry !== undefined && entry.expiresAt > this.now()) return entry.value; const value = await load(key); this.entries.set(key, { value, expiresAt: this.now() + this.ttlMs }); return value; } } let clock = 0; let calls = 0; const rates = new TtlCache(1000, () => clock); const load = async () => ++calls * 100; const a = await rates.getOrLoad("USD/NGN", load); clock = 500; const b = await rates.getOrLoad("USD/NGN", load); clock = 1500; const c = await rates.getOrLoad("USD/NGN", load); console.log(a, b, c, calls);

The first call loads and caches until time 1000. At 500 the entry is still fresh. At 1500 it has expired, so the loader runs a second time.

 What does this print? const cache = new Map<{ from: string; to: string }, number>(); cache.set({ from: "USD", to: "NGN" }, 1550); const byString = new Map(); byString.set("USD/NGN", 1550); console.log(cache.get({ from: "USD", to: "NGN" }), byString.get("USD/NGN"));

Map compares object keys by identity: the second object literal is a different object, so the lookup misses. Composite cache keys are safer as strings.

 Why does the cache take a now: () => number parameter defaulting to Date.now?

Injecting the clock makes time-based behaviour deterministic and fast to test, while production code simply uses the default.

 In emit<K extends keyof Events>(name: K, payload: Events[K]), what does Events[K] give?

K is inferred from the name you pass, and indexing the event map with it picks that event's payload type. Wrong names and wrong payloads both become compile errors.

 Why does TransferService take a Repository<Account> rather than a MemoryRepository<Account>?

Depending on the interface keeps the service independent of storage. Anything that implements Repository<Account> fits.

 A type-test file contains // @ts-expect-error above accounts.findBy("frozen", "yes"). What happens if someone loosens findBy so the line compiles?

@ts-expect-error requires an error on the next line. When the error disappears, the directive itself becomes an error, which is exactly how type-level tests catch APIs that stopped refusing bad calls.

 Why should a generic repository's runtime tests use at least two different entity types, such as one with string ids and one with number ids?

Generic code runs the same JavaScript for every type, but the values differ. Map.get("101") misses a number key 101, and only a test with numeric ids shows it.

Write andThen: if the result succeeded, call fn with its value and return what fn returns; otherwise return the failure unchanged. Then chain the two checks.
