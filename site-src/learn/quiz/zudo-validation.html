What is the trust boundary of an HTTP API?

Every value from outside is untrusted until a schema has checked it. Validate at the boundary, once, and the services behind it can rely on clean, typed data.

 Which of these does not need a schema check at the boundary of the Task API?

Route parameters, query strings, headers and bodies come from the client, so they are untrusted. A value your own code computes did not cross the boundary.

 What is the difference between parse and safeParse?

Both run the same rules. Use parse when a failure should become an error (a 400 in a route), and safeParse when you want to look at the issues yourself.

 A schema issue has a code, a path and a message. Which is meant for your program to react to?

The code is stable for programs, the message is text for people, and the path says which field it is about.

 An issue has path: ["tags", 1]. What does it point at?

A path lists the keys and indexes from the top of the value down to the field. Array indexes start at 0, so 1 is the second item.

 What does schema.safeParse(value, { abortEarly: true }) do?

Normally all issues are reported at once, which is what a form wants. When you only need to know "valid or not", abortEarly saves work.

 Where should you use schema.coerce.number() instead of schema.number()?

A JSON body has real numbers and booleans. Coercing there would accept "1" where the client should have sent 1, and hide the client's mistake.

 Why use schema.coerce.boolean() for ?done=false instead of Boolean(ctx.query.done)?

Any non-empty string is truthy. The coercing schema knows the words: "true", "1", "yes", "on" become true, "false" becomes false.

 A schema is schema.string().max(200).transform((text) => text.split(",")). What does Infer<typeof TagList> give?

The schema accepts a string, but its output type follows whatever the transform function returns: an array of strings.

 When does a .transform(fn) function run?

The transform receives a value that is already valid. For 42, which is not a string, the transform never runs and the parse fails.

 You need a rule that compares two fields of an object (reminder date not after due date). How do you write it?

A field-level rule only sees its own field. .transform() and .refine() exist as methods on every simple schema (strings, numbers, booleans, enums, coerce schemas); for objects, use the wrapper functions schema.refine(inner, check, message) and schema.transform(inner, fn).

 Should the schema check "does a task with this title already exist?" in a refine?

A schema checks the value itself, nothing else. Rules that need stored data belong in the service, which knows the store and throws the right error (409).

 Why does comparing value.remindOn <= value.dueOn as strings work for YYYY-MM-DD dates?

Year first, then month, then day, each with a fixed number of digits: comparing character by character gives the same order as comparing the dates. That is not true for DD/MM/YYYY.

 NewTaskSchema has priority: schema.default(…, "normal"). For a PATCH, the lesson uses NewTaskSchema.partial(). What does NewTaskSchema.partial().parse({ title: "Walk the dog" }) give, and why is that right?

partial() makes every field optional and applies no defaults. Defaults describe creating a task; an update must not invent values, or it would quietly reset a high priority to normal.

 An object schema gets a body with an extra key id. What is the difference between the default behaviour and .strict()?

Stripping is already safe: the extra key never reaches your code. .strict() goes further, so a client that sends a field you do not accept learns about its mistake.

 What is mass assignment?

The defence is an explicit schema that lists exactly the changeable fields (strict or stripping), and code that copies only those fields. Never write { ...task, ...body }.

 Which update code is safe?

Parse first, then copy each known field. Only the listed fields can change, and a field the client did not send keeps its stored value. The other options copy the raw body, and as StoredTask only hides the problem from TypeScript.

 Why send every task through a TaskResponse schema before it leaves the server?

Object schemas strip unknown keys, so parsing the stored object keeps only the fields you chose to publish, including after someone adds new internal fields next year.

 A stored task is missing its priority, and TaskResponse.parse(task) fails in a route. What status is right?

The client sent nothing wrong. A response that does not match its schema means the server has a bug, and the response schema caught it before the client saw bad data.

 Why run assertDepthWithinLimit and assertSizeWithinLimit before the schema?

A schema walks the whole value. The structural guards are cheap checks that refuse absurd input before any expensive work starts.

 @zudojs/validation also has a complete Zod-based schema system. What does the course advise?

The two systems do not share schemas. Mixing them means writing every rule twice.
