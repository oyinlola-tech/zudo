In a multi-tenant Task API, what is a tenant?

Acme and Globex are tenants. Each has its own users and tasks, but they all use one copy of the application and, with shared tables, one database.

 What is the most important rule of multi-tenancy?

This is tenant isolation. A bug here is not small: it shows one company's data to another company, possibly a competitor.

 The Task API uses shared tables: every row has a tenant_id column. What is the main risk of this strategy?

Shared tables are the cheapest and simplest to run, but every query must filter on tenant_id. That is why the repository adds the filter itself instead of trusting each caller.

 Which strategy gives the strongest isolation, and is usually kept for large customers because it costs the most?

A whole database per tenant has the strongest walls but the highest cost. Schema per tenant sits in between. Shared tables are the usual starting point.

 Initech did not pay, and its tenant status is suspended. What should happen when an Initech user sends a request?

manager.requireActive(id) loads the tenant and throws TenantUnavailableError when it is not active. The user logged in before the suspension, but that does not matter.

 What does this print? import { tryCreateTenantId } from "@zudojs/tenancy"; console.log(tryCreateTenantId(" ACME ")); console.log(tryCreateTenantId("acme:admin"), tryCreateTenantId("../globex"));

A tenant id is trimmed and lower-cased, then it must match ^[a-z0-9][a-z0-9_-]*$. :, . and / are not allowed, so tryCreateTenantId returns undefined for those.

 What does this print? import { createTenantId, TenantError } from "@zudojs/tenancy"; try { createTenantId("acme:admin"); console.log("created"); } catch (error) { if (error instanceof TenantError) console.log(error.name); }

createTenantId throws for an invalid id, while tryCreateTenantId returns undefined. The error is an InvalidTenantIdError, which extends TenantError.

 Why must a tenant id like acme:admin be refused?

Characters like :, / and .. have a meaning inside keys and paths. A strict pattern keeps every tenant id a plain, safe name.

 What is tenant resolution?

Every request must be tied to one tenant. Resolvers do this, each looking at a different part of the request: the session, the host name, a header or the path.

 Which list gives the lesson's trust levels correctly?

Your server created the session when the user logged in, so its tenant is trusted. A header or path is written by the client, so it is untrusted.

 Why is an x-tenant-id header sent by the client untrusted?

If your app believed the header, every Acme user could read Globex's tasks by adding one line to their request. The tenant must come from something your server created, like the session.

 In a resolver chain, the JWT resolver throws because the token is invalid. What happens?

If a broken token fell through to the next resolver, an attacker could send a bad token plus an x-tenant-id header. Stopping the chain closes that door.

 What does this print? import { assertTrustLevel, TenantError } from "@zudojs/tenancy"; for (const trust of ["trusted", "verified", "untrusted"]) { try { assertTrustLevel(trust, "verified", "test"); console.log(trust, "OK"); } catch (error) { if (error instanceof TenantError) console.log(trust, "DENY", error.statusCode); } }

assertTrustLevel refuses anything below the level you require. trusted is above verified, so it passes. untrusted throws a TenantTrustLevelError with status 403.

 A tenant check fails. What should the client receive?

An attacker probing tenant names should not learn which ones exist or are suspended. Log the reason on the server; send the client only "Forbidden".

 What does this print? import { AuthorizationError } from "@zudojs/errors"; import { TenantError } from "@zudojs/tenancy"; const error = new TenantError("No tenant for this request"); console.log(error instanceof AuthorizationError, error.statusCode);

Every tenancy error extends TenantError, which is an AuthorizationError from @zudojs/errors, so it already carries status 403.

 When is it acceptable to resolve the tenant from an x-tenant-id header?

Then the header was written by your proxy, not by the client, and you create the resolver with createHeaderResolver({ trust: "verified" }). The app must never be reachable without that proxy.

 A developer suggests choosing the tenant with ?tenant=acme. Is that safe on its own?

Validating the id only checks its format, not who may use it. Anything the client writes is untrusted; the tenant must come from the verified session or a key your server issued.

 A partner system calls your API with an API key. How should you find its tenant?

The key was created by your server and stored with its tenant. Looking up the tenant from the key is like reading it from a session.

 Why does the tenancy package keep the current tenant in an AsyncLocalStorage instead of passing it as a parameter?

Services, repositories, cache keys and log lines all need the tenant. AsyncLocalStorage gives each request's async chain its own value, so code reads it without a parameter to forget.

 Which repository method is written the safe way?

The repository reads the tenant from the context itself, so callers cannot pass a wrong one, and the id goes in as a parameter, never glued into the SQL text. Filtering later is one forgotten line away from a leak.

 Why does get(id) use where id = $1 and tenant_id = $2 and not only where id = $1?

The id alone identifies a row in the whole table, across all tenants. Adding tenant_id to the lookup means another tenant's row is simply not found.

 Acme asks for GET /tasks/2, and task 2 belongs to Globex. Which status should the API answer?

For the client, "belongs to someone else" and "does not exist" must look the same. A 403 would tell an attacker that the id exists.

 You add rename(id, title) to the repository. What must its update query contain?

Writes need the tenant filter just as much as reads. Without it, Acme could rename or delete Globex's task by guessing its id.
