What makes enum different from interfaces, type aliases and annotations?

Almost all TypeScript syntax is erased. An enum is also a value, so tsc emits code that builds an object for it.

 What does this print? enum OrderStatus { Placed, Packed, Shipped, Delivered, } console.log(OrderStatus.Placed, OrderStatus.Shipped, OrderStatus.Delivered);

Without initialisers, the first member is 0 and each next one is one higher, so Shipped is 2 and Delivered is 3.

 What does this print? enum TransferError { InsufficientFunds = 51, LimitExceeded = 61, AccountBlocked, UnknownBank = 91, Timeout, } console.log(TransferError.AccountBlocked, TransferError.Timeout);

A member without a value continues counting from the member before it: 61 + 1 = 62, and 91 + 1 = 92.

 tsc emits Status[Status["Paid"] = 1] = "Paid"; for a numeric member. What does this line do?

The inner assignment Status["Paid"] = 1 evaluates to 1, so the outer assignment is Status[1] = "Paid". That second key is the reverse mapping.

 What does this print? enum PaymentStatus { Pending, Authorized, Captured, } const stored: PaymentStatus = 1; console.log(PaymentStatus[stored], PaymentStatus.Captured);

Numeric members get a reverse mapping, so PaymentStatus[1] is the name "Authorized". PaymentStatus.Captured is the number 2.

 What does this print? enum Frequency { Daily, Weekly, Monthly, } console.log(Object.keys(Frequency).length, Object.values(Frequency).length);

The object holds both directions: three names and three numeric keys. Object.keys and Object.values both see all six entries.

 How do you list only the members of a numeric enum Frequency, as numbers?

The values are a mix of numbers (from the name keys) and names (from the reverse mapping keys). Keeping only the numbers gives exactly one entry per member.

 What does this print? enum Currency { Naira = "NGN", Dollar = "USD", } console.log(Object.keys(Currency), Currency.Naira);

String members get no reverse mapping, so the object only has the two name keys. Currency.Naira is its value, "NGN".

 What does this print? enum Status { Pending, Paid, } enum Currency { Naira = "NGN", } console.log(JSON.stringify({ status: Status.Paid, currency: Currency.Naira }));

JSON gets the member values. A numeric enum becomes an unreadable number in every API response and database row; a string enum stays readable.

 With enum Currency { Naira = "NGN" } and function format(c: Currency), why is format("NGN") a compile error?

Unlike every other TypeScript type, string enum types are matched by name. The literal "NGN" has the same value but not the same type, so you must write Currency.Naira or convert after a check.

 Which line compiles with enum PaymentStatus { Pending, Paid }?

A numeric literal that is not a member is refused, but any value of type number is accepted, because numeric enums are also used for combined bit flags. So a numeric enum parameter does not guarantee a real member.

 This compiles. What does it print? enum PaymentStatus { Pending, Paid, } function label(status: PaymentStatus): string { return PaymentStatus[status] ?? "unknown"; } const fromDatabase: number = 5; console.log(label(PaymentStatus.Paid), label(fromDatabase));

The number 5 is accepted as a PaymentStatus, and the reverse mapping has no key 5, so the lookup gives undefined and ?? supplies the fallback.

 Version 1 stored StatusV1.Refunded in the database. Version 2 inserted a member. What does this print? enum StatusV1 { Pending, Paid, Refunded, } enum StatusV2 { Pending, Paid, Disputed, Refunded, } const stored = StatusV1.Refunded; console.log(stored, StatusV2[stored]);

Numeric values come from member order. Inserting Disputed shifted Refunded to 3, so the stored 2 now means "Disputed". Pin every value explicitly, or store strings.

 You must keep a numeric enum whose values are stored in a database. What is the safe way to add a member?

Stored numbers are a contract. Explicit, never-reused values keep old rows meaning the same thing. tsc has no idea what is in your database.

 Without isolatedModules, what does tsc emit for const enum Direction { Debit = "DR" } and const d = Direction.Debit;?

That is the purpose of const enum: tsc inlines each value and deletes the declaration, leaving a comment with the member's name.

 With verbatimModuleSyntax (which implies isolatedModules), how does TypeScript 7 compile a const enum?

Under isolatedModules, code must be translatable one file at a time, and a tool translating one file cannot see an enum's values in another file. So the enum is kept as a real object, and inlining is dropped.

 Why can't tools such as tsx, bundlers and Node.js inline const enum values from another file?

Per-file translation is what makes these tools fast. To inline Direction.Debit, a tool would need the declaration from direction.ts, which it never reads.

 What happens with const enum Priority { Low, High } and Priority[0]?

A const enum is designed to have no object at runtime, so reverse lookups are forbidden, even in configurations where the object happens to be emitted.

 What happens when Node.js 24 runs node status.ts on a file with an enum, without extra flags?

Node's type stripping only deletes types; it never generates code. An enum needs generated code, so Node refuses it. --experimental-transform-types or tsx can run it.

 Does Node's type stripping accept a const enum?

Inlining would need code generation and knowledge of other files, which type stripping does neither of. Node also ignores tsconfig.json.

 What does the erasableSyntaxOnly compiler option do?

With erasableSyntaxOnly, tsc flags every construct that needs generated code (error TS1294), so code that must run under plain node is caught before it runs.

 Which of these is allowed under erasableSyntaxOnly?

An as const object is plain JavaScript plus a type-only suffix. Enums, parameter properties and namespaces with code all generate JavaScript and are rejected.

 Given const PaymentStatus = { Pending: "pending", Paid: "paid" } as const;, what is (typeof PaymentStatus)[keyof typeof PaymentStatus]?

keyof typeof PaymentStatus is the union of the names. Indexing the object's type with every name gives the union of the values, which as const kept as literals.

 What goes wrong if you leave out as const in const Role = { Admin: "admin", Customer: "customer" };?

Without as const, TypeScript assumes the properties may change later and infers string for each. The derived "union" collapses to string.

 What does this print? const Role = { Admin: "admin", Teller: "teller", Customer: "customer", } as const; type Role = (typeof Role)[keyof typeof Role]; const fromToken: string = "teller"; const valid = Object.values(Role).some((role) => role === fromToken); const mine: Role = "customer"; console.log(Object.values(Role).length, valid, mine === Role.Customer);

An as const object has no reverse mapping, so it has exactly three values. The plain string "customer" is accepted as a Role because the derived type is a structural union.

 A status arrives from JSON as a plain string. Why is a literal union type ("pending" | "paid") easier to work with than a string enum here?

A union is structural: a checked "paid" is simply a "pending" | "paid". With a string enum, you also have to turn the string into Status.Paid, usually with a lookup or an assertion.

 What does a bare literal union type such as type Currency = "NGN" | "USD" not give you?

Types are erased, so the union leaves nothing at runtime. When you need the list, write an as const array or object and derive the type from it.

 Where is a numeric enum a reasonable choice?

When the order itself carries meaning and the numbers are never stored or sent, numeric enums fit well. Values that leave the process are better as readable strings.

 What does this print? import { LoggerLevel, shouldLog } from "@zudojs/logger"; console.log(LoggerLevel.ERROR < LoggerLevel.DEBUG, shouldLog(LoggerLevel.INFO, LoggerLevel.WARN));

LoggerLevel is a numeric enum where lower means more severe (ERROR is 1, DEBUG is 4). With an INFO threshold, a WARN message is severe enough to be logged.

 Why should a published library avoid exporting a const enum?

Inlining needs the value at compile time from a declaration file, which per-file tools cannot do. TypeScript reports an error for ambient const enums under isolatedModules.

 You replace enum PaymentStatus { Pending, Paid } with an as const object with the same member names, and a type named PaymentStatus. Which existing code breaks?

Member access and the type name keep working. The reverse mapping only existed on numeric enums, so reverse lookups, and any code comparing numbers, must change; tsc points at each one.

 During the migration, old rows store numbers and new rows store strings. How should old numbers be translated?

Positions change when someone reorders the object. An explicit table keeps the meaning of every old row fixed forever.

 Why write a test that compares Object.values(PaymentStatus) with a hard-coded list of strings?

Renaming a value compiles fine and quietly breaks every stored row. A snapshot of the values catches it in CI.

 enum Frequency { Daily, Weekly, Monthly, Yearly, } const options = Object.keys(Frequency).map((key) => ({ value: key, label: key })); console.log(options.length); console.log(options[0]); enum Frequency { Daily, Weekly, Monthly, Yearly, } const options = Object.values(Frequency) .filter((value) => typeof value === "number") .map((value) => ({ value, label: Frequency[value] })); console.log(options.length); console.log(options[0]); 4 { value: 0, label: 'Daily' }

Replace the string enum with an as const object called Currency and a derived type of the same name, so that format(2500, "USD") compiles and Currency.Naira still works.
