A user says "the app is slow today". Which signal tells you where the time of one slow request went?

A trace is the story of one request, split into timed steps (spans). Metrics tell you how much and how fast over time, and logs tell you what happened in detail.

 What does createObservability(...) give you?

One object holds all three signals and the propagation that links them. The exporters are the parts that send the data somewhere, by default to the console.

 Which createObservability call follows the lesson's advice for a real service?

The lesson says: always pass redaction: {}, so secret fields such as password are hidden with the default field list. Being explicit keeps you safe whatever the default is. The service name tells the monitoring system which service sent the data.

With redaction: {}, fields with secret names like password are replaced before any exporter sees them. In this logger the metadata is called context.

 Why must you call await obs.shutdown() before the process exits?

Batching is much cheaper than one network call per record, but records wait in memory until the next batch. shutdown() sends the rest, which are often the most important last records.

The exporter works in batches, so the log record waits in memory. It is sent when shutdown() flushes the batch, after "still running" was printed.

 You want to track how many jobs are waiting in the email queue right now. Which kind of metric fits?

A counter only goes up (requests served, tasks created). The queue length goes up when jobs arrive and down when they are done, which is what a gauge is for.

 Nine requests took 12 to 40 ms and one took 900 ms. The mean is 111.7 ms. What should you alert on?

The mean of 111.7 ms describes none of the real requests. A percentile says "95% were faster than this", which matches what users experience. Alert on p95 or p99, never on the mean.

 A histogram reports p50: 23. What does that mean?

p50 is the 50th percentile, also called the median: half the values are below it. The histogram estimates it from buckets, so it is close but not exact.

 Why should you not add { userId } as a label on http.requests?

Every different set of labels is a separate series. A few values like route and status are fine. Ids belong in logs and traces, never in metric labels.

 Which label is a good idea on a tasks.created counter?

A priority has three possible values, so it makes three series at most. A title, an id or a time can take endless values, and each one would become a new series.

A real path contains an id, so every task would become a new series. The route template has one value for all tasks.

 What is a span?

A trace is made of spans, one per step. Spans nest: a span started inside another becomes its child, and all spans of one trace share one trace id.

 What does this print? import { createObservability, withSpan } from "@zudojs/observability"; const obs = createObservability({ serviceName: "task-api", redaction: {}, useConsoleExporters: false }); const count = await withSpan(obs.tracer, "db.count", async (span) => { span.setAttribute("db.table", "tasks"); return 42; }); console.log("tasks:", count); await obs.shutdown();

withSpan starts a span, runs your function, ends the span and gives back the function's result. So you can wrap a step without changing what it returns.

 Which span kind marks the span that handles an incoming request?

SERVER is for handling a request that came in. When your service calls another system, that span is a CLIENT span.

The trace id is on every log line and span of the request, so it works as a correlation id. It reveals nothing about your system, unlike a stack trace or SQL.

 What does the W3C traceparent header contain?

The caller sends its trace id and current span id, plus flags that say whether it kept (sampled) the trace. The receiver starts its spans as children of that span.

 What does this print? import { parseTraceparent } from "@zudojs/observability"; const parent = parseTraceparent("00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"); console.log(parent.traceId); console.log(parent.spanId, parent.traceFlags);

The header has four parts separated by dashes: version 00, the 32-character trace id, the 16-character span id and the flags. The flags 01 become the number 1: the caller kept the trace.

 A client sends traceparent and x-user-role: admin. The Task API joins the trace. What about the role?

Joining a trace only links spans; at worst, a client makes its request appear inside someone else's trace. A role decides what the caller may do, so it must never come from a header the client can type.

 What may an incoming traceparent header decide in your service?

The header comes from outside, so it is untrusted. Give it only as much power as it can safely have: linking spans. It must never decide what a caller may do.

 A handler throws new Error("report service unreachable"). What does the instrumented Task API send to the client?

Internal error messages can reveal how your system works. The wrapper records the error on the span and logs it, and gives the client only a safe message.

 During an incident, in which order does the lesson suggest using the three signals?

An alert on a metric (like 5xx rate or p95) tells you there is a problem. A log search finds the error and its trace id. The trace with that id shows which step failed or was slow.

 What should change about exporters before you deploy?

The console exporters are for development. In production you implement the SpanExporter, LogExporter and MetricExporter interfaces (or install a package that does) and send the data to a collector.

 With sampling, when is the "keep this trace or not" decision made?

Deciding once per trace means you never get half a trace. A parent-based sampler also follows the caller's decision from the traceparent flags.
