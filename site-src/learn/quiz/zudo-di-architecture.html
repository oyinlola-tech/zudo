What is the composition root of an application?

The composition root is where all "which class, which lifetime, which settings" decisions are made, once, at startup. Everything else receives its dependencies instead of creating them.

 In a generated Task API, app.ts resolves TaskStore from the container for the modules, while createDependencies builds new TaskService(new TaskStore(), clock) for the routes. What is the result?

Both lines are valid TypeScript and the container never sees the new TaskStore(). Two places decided how a store is made, so there are two stores. One composition root prevents exactly this.

 In a freshly generated ZudoJS project, which statement is true?

The names mislead: the file called container.ts holds a hand-written composition root (createDependencies), and the real container is created in app.ts and handed to createRuntime, empty.

 You add a PaymentGateway that is shared by an invoice service and a refund service, must be closed at shutdown, and must be replaced with a fake in tests. Where should it be built?

Shared, lifetime-managed, disposable and replaceable in tests: those are exactly the reasons to use the container. replace in tests and dispose at shutdown both come for free.

 Should a newly created Task object (id, title, createdAt) be registered in the container?

A container wires services, repositories, clocks and pools: the long-lived parts. Data flowing through the app is created by those services while they run.

 Why does the Task API create StoreModule and TasksModule with new in app.ts instead of registering them in the container?

Who owns an object's lifecycle should create it. The runtime starts and stops modules; the container creates and disposes services. The modules still get the store through constructor injection, from the one container.

 Which is not an advantage of constructor injection?

Fetching services later without listing them is the service locator pattern, which constructor injection exists to avoid.

 What does this print? interface Clock { now(): Date; } class ReportService { clock?: Clock; today(): string { return this.clock!.now().toISOString().slice(0, 10); } } const reports = new ReportService(); try { console.log(reports.today()); } catch (error) { console.log((error as Error).name); } reports.clock = { now: () => new Date("2026-09-24T09:00:00Z") }; console.log(reports.today());

Property injection creates a half-built object. The ! silenced TypeScript, so the first call fails at run time with a TypeError. Only after someone assigns the clock does the object work.

 Why does this lesson register classes with registerFactory(TaskService, (store, clock) => new TaskService(store, clock), [TaskStore, CLOCK]) instead of registerClass(TaskService, TaskService, { inject: [TaskStore, CLOCK] })?

registerClass types the class as a constructor taking any[], so a swapped inject list compiles and fails at run time. The arrow function costs one line and lets the compiler check the wiring.

 The Task API should print e-mails in development and send them over SMTP in production. Where does the if that chooses belong?

Choosing an implementation is a composition decision. A factory registration makes it once; TaskNotifier just asks for "a mailer".

 A TaskImporter must create a new ImportReport for every file it imports. What should it receive?

A single injected report would be shared by every import, the container would make it a service locator, and new inside the service hard-wires the clock. A factory function is narrow, typed and easy to fake.

 What does this print? import { createContainer, createToken } from "@zudojs/container"; class Receipt { constructor(readonly orderId: string) {} } type ReceiptFactory = (orderId: string) => Receipt; const RECEIPTS = createToken("ReceiptFactory"); class Checkout { constructor(private readonly newReceipt: ReceiptFactory) {} pay(orderId: string): Receipt { return this.newReceipt(orderId); } } const container = createContainer(); container.registerFactory(RECEIPTS, () => (orderId: string) => new Receipt(orderId)); container.registerFactory(Checkout, (newReceipt) => new Checkout(newReceipt), [RECEIPTS]); const checkout = container.resolve(Checkout); const a = checkout.pay("ord-1"); const b = checkout.pay("ord-2"); console.log(a.orderId, b.orderId, a === b);

The container resolved the factory function once, but every call of that function builds a new Receipt, with the id given at run time.

 Which class is a service locator?

A class that receives the container and pulls dependencies out of it hides what it needs. Its constructor says "I need everything".

 What does this print? import { createContainer, createToken } from "@zudojs/container"; import type { Container } from "@zudojs/container"; interface Mailer { send(text: string): void; } const MAILER = createToken("Mailer"); class Reminder { constructor(private readonly container: Container) {} run(): void { this.container.resolve(MAILER).send("2 tasks due"); } } const container = createContainer(); container.registerFactory(Reminder, () => new Reminder(container)); const reminder = container.resolve(Reminder); console.log("started"); try { reminder.run(); } catch (error) { console.log((error as Error).name); }

 What does this print? import { createContainer, createToken } from "@zudojs/container"; interface Mailer { send(text: string): void; } const MAILER = createToken("Mailer"); class Reminder { constructor(private readonly mailer: Mailer) {} run(): void { this.mailer.send("2 tasks due"); } } const container = createContainer(); container.registerFactory(Reminder, (mailer) => new Reminder(mailer), [MAILER]); try { container.resolve(Reminder); console.log("started"); } catch (error) { console.log((error as Error).name); }

 What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; const RATE = createToken("VatRate"); class Listed { constructor(readonly rate: number) {} } class Hidden { constructor(readonly rate: number) {} } const container = createContainer(); container.registerValue(RATE, 0.075); container.registerFactory(Listed, (rate) => new Listed(rate), [RATE], { scope: ContainerScope.SINGLETON }); container.registerFactory(Hidden, () => new Hidden(container.resolve(RATE)), [], { scope: ContainerScope.SINGLETON }); container.resolve(Listed); container.resolve(Hidden); container.replace(RATE, { useValue: 0.1 }); console.log(container.resolve(Listed).rate, container.resolve(Hidden).rate);

 In the Task API, which code may call container.resolve?

Resolving at the edges keeps every dependency visible to the container. Services, repositories and controllers receive what they need through constructors.

 Why can a service locator break the container's captive-dependency check?

A singleton that lists a scoped token gets a CaptiveDependencyError. The same singleton pulling the value from a scope inside its factory keeps one request's data forever, and nothing complains.

 Why should tests call the same registerServices function as the app, then replace a few tokens, instead of registering their own objects from scratch?

A test that builds its own wiring tests a second composition root. Reusing the real one means the tests check the wiring the app actually runs, and only the outside world is faked.

 CLOCK is createToken<Clock>("Clock") and Clock has now(): Date. What happens with container.replace(CLOCK, { useValue: { today: () => "2026-09-24" } })?

replace is typed from the token, exactly like registerValue. A fake with the wrong shape is a compile error, so fakes stay honest.

 What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; const RATE = createToken("VatRate"); class PriceService { constructor(readonly rate: number) {} gross(kobo: number): number { return Math.round(kobo * (1 + this.rate)); } } const container = createContainer(); container.registerValue(RATE, 0.075); container.registerFactory(PriceService, (rate) => new PriceService(rate), [RATE], { scope: ContainerScope.SINGLETON }); const early = container.resolve(PriceService); container.replace(RATE, { useValue: 0 }); const late = container.resolve(PriceService); console.log(early.gross(100000), late.gross(100000));

replace rebuilt the singleton for everyone who resolves afterwards. The reference taken before still points at the old instance with the 7.5% rate. In tests, replace first, then resolve.

 What does container.snapshot() save?

A snapshot holds registrations, not instances. Restoring evicts and disposes the cached singletons, so a store that was filled during the test comes back empty.

 What does this print? import { ContainerScope, createContainer } from "@zudojs/container"; class Cart { readonly items: string[] = []; } const container = createContainer(); container.registerClass(Cart, Cart, { scope: ContainerScope.SINGLETON }); const saved = container.snapshot(); container.resolve(Cart).items.push("Rice 5kg"); console.log(container.resolve(Cart).items.length); container.restoreSnapshot(saved); console.log(container.resolve(Cart).items.length);

The snapshot kept the registration, not the cart. restoreSnapshot evicted the cached singleton, so the next resolve built a new, empty cart.

 Two test files share one container and use replace plus restoreSnapshot. The test runner runs files in parallel. What is the risk?

A shared container is shared state. Keep a shared container inside one file, or build a fresh container per test, which is the simplest isolation.

 Why does the lesson add a verifyContainer step at startup?

Resolving every registration once, scoped ones inside a throwaway scope, moves wiring errors from "first unlucky request" to "the deploy does not start".

 What does this print? import { createContainer, createToken } from "@zudojs/container"; const RATE = createToken("VatRate"); const container = createContainer({ name: "shop", freezeRegistrations: true }); container.registerValue(RATE, 0.075); try { container.replace(RATE, { useValue: 0 }); console.log("replaced before start"); } catch (error) { console.log((error as Error).message); } console.log(container.resolve(RATE)); try { container.replace(RATE, { useValue: 0 }); console.log("replaced after start"); } catch (error) { console.log((error as Error).message); }

With freezeRegistrations: true the set is frozen when the container starts, and the first resolve starts it. Before that, registering and replacing still work, which is when the composition root does its job.

 What does this print? import { createContainer } from "@zudojs/container"; class ForgottenService {} const relaxed = createContainer(); const strict = createContainer({ resolution: { autoRegisterClasses: false } }); console.log(relaxed.resolve(ForgottenService) instanceof ForgottenService); try { strict.resolve(ForgottenService); console.log("strict: built"); } catch (error) { console.log("strict:", (error as Error).name); }

By default an unregistered class with a no-argument constructor is built on demand. With autoRegisterClasses: false it is refused, so a forgotten registration cannot hide in production.

 A database pool needs await connect(). What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; interface Pool { readonly url: string; } const POOL = createToken("Pool"); async function connect(url: string): Promise { return { url }; } const container = createContainer(); container.registerFactory(POOL, () => connect("postgres://localhost/shop") as unknown as Pool, [], { scope: ContainerScope.SINGLETON, }); try { console.log(container.resolve(POOL).url); } catch (error) { console.log((error as Error).name); } const fixed = createContainer(); fixed.registerValue(POOL, await connect("postgres://localhost/shop")); console.log(fixed.resolve(POOL).url);

The container is synchronous, so a singleton factory that returns a promise is refused with AsyncProviderError instead of caching the promise. Await the resource in the composition root, then register the finished object with registerValue.

 What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; class Resource { constructor(readonly name: string) {} dispose(): void { console.log(`closed ${this.name}`); } } const POOL = createToken("Pool"); const container = createContainer(); container.registerValue(POOL, new Resource("pool")); container.registerFactory(Resource, () => new Resource("cache"), [], { scope: ContainerScope.SINGLETON }); container.resolve(POOL); container.resolve(Resource); await container.dispose(); console.log("done");

The container disposes the singletons it created. It did not create the value given to registerValue, so it does not own it: whoever opened the pool must close it.

 In an HTTP app, where should a per-request container scope be created and disposed?

The request is the natural scope, and the middleware sees its start and end. finally makes sure the scope is disposed even when the route throws.

 What does this print? import { ContainerScope, createContainer } from "@zudojs/container"; let created = 0; class AuditLog { readonly id = ++created; dispose(): void { console.log(`flush log ${this.id}`); } } const container = createContainer(); container.registerClass(AuditLog, AuditLog, { scope: ContainerScope.SCOPED }); for (const request of ["req-1", "req-2"]) { const scope = container.createScope({ name: request }); const a = scope.resolve(AuditLog); const b = scope.resolve(AuditLog); console.log(request, a.id, a === b); await scope.dispose(); }

A scoped registration gives one instance per scope: both resolves in a request share it. Disposing the scope at the end of each request disposes that request's log, before the next request starts.

 verifyContainer resolves scoped registrations through a throwaway scope. What does this print, and why is that needed? import { ContainerScope, createContainer } from "@zudojs/container"; class RequestInfo {} const container = createContainer(); container.registerClass(RequestInfo, RequestInfo, { scope: ContainerScope.SCOPED }); try { container.resolve(RequestInfo); console.log("root: ok"); } catch (error) { console.log("root:", (error as Error).name); } const scope = container.createScope({ name: "startup-check" }); console.log("scope:", scope.resolve(RequestInfo) instanceof RequestInfo); await scope.dispose();

A scoped registration cannot be resolved at the root: that would be a false alarm in a startup check. Inside a scope it resolves normally, so request-only registrations are checked too.

 A service's constructor has grown to seven parameters. What is the best response?

Constructor injection makes the number of dependencies visible, which is its point. A long list is design feedback; hiding it behind a locator or an options bag only hides the problem.

 A route handler calls scopeOf(ctx.request).resolve(TaskCommands), where a middleware put a per-request scope on the request. Is that a service locator?

The route is edge code, the per-request part of the composition root. The problem with a locator is a service hiding its dependencies; here the dependency graph below the route is still declared in inject lists.

 In the Task API, why is verifyContainer called in server.ts and not inside createApp?

It disposes its throwaway scope with await, so it runs where awaiting is possible: right after createApp, before runtime.start() and long before the port opens.
