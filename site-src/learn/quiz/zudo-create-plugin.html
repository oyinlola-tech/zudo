ShopFlow and the invoicing service want email receipts; the bookings app does not. Why build receipts as a plugin rather than as code inside ShopFlow?

A plugin is an optional feature behind a fixed interface. The host stays unchanged, and switching the feature on or off is a registration, not a code change. It still runs with the host's full power, so it can break the host.

 The receipts plugin resolves the mailer from the container in initialize, not in install. Why?

install is where plugins offer things; initialize is where they can rely on everything that was offered. The mailer is a dependency, so its install would run first anyway, but initialize also works for services from plugins that are not dependencies.

 Why does the mailer call context.registerDisposable right after opening the connection in start, instead of closing the connection in its own dispose hook?

A dispose hook runs whenever the plugin is disposed, including after a failed or skipped start, and would have to guess what exists. Registering cleanup next to the acquisition makes rollback exact.

 Why is the plugin exported as createReceiptsPlugin() instead of a ready-made object?

A disposed plugin cannot be started again. Sharing one object between hosts or tests would also share its counters and subscriptions. A factory avoids both problems.

 The host grants allowedCapabilities: ["events"]. The receipts plugin declares ["events", "container"]. When does it fail?

The manager compares declared capabilities with the allow-list when the plugin is registered. It is a declaration check that catches mistakes, not a sandbox: a plugin can still do anything the process can.

 Receipts requires @mycompany/zudo-plugin-mailer@^2.0.0 and the host registers mailer 3.0.0. What has run when the error is thrown?

Resolution and version checks happen before the first phase, so there is nothing to roll back. The error is a PluginDependencyVersionError, a subclass of PluginDependencyError.

 A host writes manager.register(createReceiptsPlugin(), { form: "receipts@shopflow.ng" }), with form instead of from. The plugin is typed Plugin<Partial<ReceiptsOptions> | undefined>. What catches the typo?

In the published @zudojs/plugins, register(plugin, options?: unknown) accepts anything. Validating in install turns the typo into a failed start with a rollback, instead of receipts with no sender.

 Why does the receipts plugin check typeof context.container.resolve === "function" at run time?

The plugin context is deliberately minimal: plugins are expected to offer services. A plugin that consumes one depends on more than the type guarantees, so it checks and fails early with a message that says what the host must provide.

 Why is the mailer's container token Symbol.for("@mycompany/zudo-plugin-mailer:Mailer") rather than Symbol("Mailer") or createToken("Mailer")?

Symbol() and createToken() create a new, unique key per module evaluation. Symbol.for(key) is shared through the global registry, the same idea as the @zudojs/errors brand.

 Receipts lists the audit plugin under optionalDependencies. What does that do when audit is installed, and when it is not?

A present optional dependency takes part in ordering exactly like a required one; an absent one is ignored. Receipts never calls audit; audit listens for receipt.sent.

 When should one plugin talk to another through a declared dependency and a container service, and when through events?

A dependency makes the manager guarantee presence and order. An event keeps the announcer unaware of its listeners, so audit, statistics or anything else can be added without touching receipts.

 The payment.succeeded handler starts sendReceipt and tracks it in inFlight, but does not await it. Why?

The payment already succeeded; the receipt is follow-up work. Awaiting it would make every checkout as slow as the mail server. Tracking the promise lets stop wait for it at shutdown.

 What is the difference between the receipts plugin's stop and its disposal?

Finishing work needs the resources still in place, so it comes first. Releasing comes after, newest first, and also runs for plugins that never started.

 When does a plugin's context.signal abort?

The manager aborts each plugin's own signal at the start of its disposal. That is why the mailer's send takes the signal: a receipt that outlived stop fails fast instead of writing to a closed connection.

 manager.diagnostics() reports the receipts plugin healthy, yet its last three receipts bounced. Why, and what fixes it?

Only the plugin knows whether its work succeeds. A health endpoint that combines lifecycle state with each plugin's own report catches a running-but-failing plugin.

 Mailer and receipts are started; then SMS alerts, which depends on receipts, throws in start. In what order are things undone?

Rollback stops what was started in reverse dependency order, then disposes everything that holds resources in the same reverse order, including the failed plugin. The mailer's connection closes last because others depended on it.

 In the published @zudojs/plugins, what does catch (error) around manager.start receive when a plugin's start throws new Error("key rejected")?

PluginStartError is exported but the manager never throws it. The lesson's startPlugins helper finds the failed plugin in the diagnostics and wraps the error, keeping the original as cause.

 After a rolled-back start, you fix the configuration and call manager.start(context) again on the same manager. What happens?

Disposal is final by design, so a released resource can never be used again. Factories make "new plugin objects" a one-line change.

 With hookTimeout: 200, a plugin's start returns a promise that never settles. The host starts plugins before its HTTP server listens. What happens under plain Node?

An unref'd timer does not keep Node running. With no socket, timer or other work pending, Node ends the process. Holding the process open during start-up (the lesson's keepAlive interval) lets the timeout fire.

 Version 1.3.0 of your plugin adds "network" to its capabilities. Why is that a breaking change?

Capabilities are part of the contract with the host. Requiring a new one is like requiring a new peer dependency: installations that worked yesterday stop working, so it belongs in a major version.

 The receipts package lists @mycompany/zudo-plugin-mailer in peerDependencies and the receipts plugin lists it in dependencies. What does each one check?

A host could have the package installed but register a different mailer plugin, or none. The two ranges should agree, and each guards a different mistake.

 The host moves payment.succeeded from the in-process bus to a message queue that delivers at least once. What must the receipts plugin add?

"At least once" means duplicates will happen. Deduplicating by a stable key makes the handler idempotent, exactly like the payment service's reference check.

plugin:started becomes plugin.started when published. A namespace wildcard matches it; plugin:* is not a valid pattern, because a wildcard is only allowed as the last segment after a dot.
