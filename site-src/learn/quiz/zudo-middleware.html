What is middleware?

Middleware is for work that belongs to every request (headers, CORS, rate limits, timing). It receives context and next; next() runs the next middleware and, at the end, the route.

 A maintenance middleware returns a 503 response without calling next(). What is this called, and what happens to the route?

Not calling next() stops the chain there. Nothing after that middleware, including the route, runs.

 In an HttpMiddlewarePipeline, how does priority decide the order?

pipeline.use(mw, { priority: -10 }) runs before a middleware with the default 0. Lower priority means an outer layer of the onion: it starts first and finishes last.

 A middleware adds x-response-time to responses. It must also appear on 503 answers from a maintenance middleware. Where should it go?

A middleware only sees responses from the layers inside it. Put middleware that must see every response first, so even a short-circuited answer passes back through it.

 What does X-Content-Type-Options: nosniff protect against?

With nosniff, the browser must trust the Content-Type you send. Framing is X-Frame-Options, cookies over HTTPS is the Secure flag, and request floods are rate limiting.

 Which headers from createSecurityMiddleware() stop clickjacking, where an invisible frame tricks the user into clicking your buttons?

Both say "no other site may show my pages inside a frame". Without a frame, there is nothing invisible to click.

 Your development server on localhost sends HSTS. When does that cause trouble?

Browsers only accept HSTS from an HTTPS answer. A plain-HTTP dev server can send it without harm. If your dev server answers over HTTPS (a local certificate or proxy), send max-age=0 there, so browsers forget it. In production, behind HTTPS, keep the long default.

 Your CORS allow-list only contains your own web app. A script uses curl to call the API directly. What happens?

Even a browser request from another site got status 200 and the data; only the missing header made the browser hide it. CORS never replaces authentication or permissions.

 Why does createCorsMiddleware({ allowOrigin: "*", credentials: true }) throw a ConfigurationError?

credentials: true lets the browser send cookies along. With "every origin", any site could act as your logged-in users. List the exact origins instead.

 A teammate writes their own origin check: origin.startsWith("https://tasks.example.com"). What is wrong?

An attacker can register a domain that merely starts with yours. The allow-list in createCorsMiddleware compares whole origins exactly; never replace it with startsWith or a loose regular expression.

 Where should the CORS allow-list live?

The allowed origins differ per environment. Configuration holds them, and the code stays the same everywhere. The config lesson does exactly this.

 Why must a public API have a rate limit?

A rate limiter counts requests per client in a time window and answers 429 Too Many Requests when the client goes over, usually with a Retry-After header.

 The limiter allows 3 requests per 60 seconds, and its window slides. What does that prevent?

Each check forgets only requests older than windowMs, so there is no fixed moment when the counter resets and a burst can slip through.

 The Task API runs behind one load balancer, so every request seems to come from the balancer's IP. What is the safe fix?

Any client can send X-Forwarded-For and pick its own address. Only with trustProxy set to the real number of proxies does the adapter believe it.

 Why does the Task API use a gentle limit for every request plus a stricter one only for writes?

limitWrites only calls the strict middleware for methods that are not GET, HEAD or OPTIONS. A client that hit the write limit can still read its tasks.

 The Task API runs as three copies of the same process, each with the in-memory limiter set to 100 per minute. What really happens?

The counts live in the memory of one process. With several copies you need a shared store; the security lesson covers that case.

 In the Task API pipeline, why does CORS come before the rate limits?

The CORS middleware answers OPTIONS preflights by itself. Placed first, those extra browser requests never reach the limiter. Security headers go before both, so every answer gets them.

 When should you use @zudojs/middleware's createPipeline instead of HttpMiddlewarePipeline?

createPipeline works with any kind of context and reports whether the run succeeded, so one set of checks can serve a job, a CLI tool and, through a small adapter, a route. For plain HTTP middleware, stay with HttpMiddlewarePipeline, which knows about requests and responses.

 What does server.stop() do with a request that is already running?

That is a graceful shutdown: the door closes to new connections, and requests in progress get a full answer. The default wait is 30 seconds.

 What is the right order in src/server.ts when SIGTERM arrives?

Requests in progress still use the store, so the server stops first. Then the modules stop, and the container is disposed last.

 Your platform kills the process 30 seconds after SIGTERM. How should you set gracefulShutdownTimeout?

If the platform kills the process first, requests are cut off and the runtime never stops cleanly. Leave time for the runtime and the container after the server.
