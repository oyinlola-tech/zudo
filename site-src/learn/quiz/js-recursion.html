Which of these is not one of the three things every recursive function needs?

Base case, smaller step and combine step are the whole recipe. A depth counter can be useful (as a parameter), but it is not required, and a global one is shared by every call, which causes bugs.

 folderSize adds a folder's files, then calls itself for each sub-folder. It has no if. Why does it still stop?

Recursion over a tree stops where the tree stops. A leaf (no children) is the base case, handled by a loop over an empty list.

 When you write the combine step of a recursive function, what should you assume?

This "leap of faith" is the same reasoning as proof by induction. If the base case is correct and each call gets closer to it, the function is correct at any depth.

 countPeople declares let total = 1 and then adds the results of its recursive calls. While the deepest call runs, how many total variables exist?

Every call has its own execution context with its own local variables. The waiting calls keep their half-finished total until the call above them returns.

 In a recursive walk of an org chart, which call returns first?

A call cannot finish until all the calls it made have finished. The first to finish is the first one that makes no further calls, and results then flow back up the stack.

 To delete a folder, each folder must be emptied before it is removed. Which order does your recursive function need?

Post-order puts the work after the recursive calls, so all children are handled before their parent. Pre-order would try to remove a folder that still has contents.

 function preOrder(node, out = []) { out.push(node.name); for (const c of node.children) preOrder(c, out); return out; }. What role does out play?

The top-level call creates the array (by the default), and every recursive call receives the same array as an argument. The alternative is for each call to return its own list and combine them.

 In pathTo(person, target), the loop does const path = pathTo(report, target); if (path !== null) return [person.name, ...path];. What goes wrong if you write return [person.name, ...pathTo(report, target)] instead?

A search must try the next branch when one fails. Returning unconditionally ends the loop after the first report; spreading a null result into an array throws a TypeError.

 Why is if (n <= 0) usually a safer base case than if (n === 0)?

A base case must be reached from every valid input. Covering a range protects you from inputs that step past the single value you expected.

 A recursive size function calls itself for each sub-folder but forgets to add the returned value. What is the symptom?

The recursive calls run and return their answers, which are then thrown away. Silent wrong answers are the most dangerous bugs; tests with nested data catch them.

 A report count over the org chart suddenly throws RangeError: Maximum call stack size exceeded, although the company has only 40 people. What is the most likely cause?

Recursion over a tree assumes no item is its own ancestor. A cycle turns a 40-person walk into an endless one. Track visited people in a Set and report the cycle.

 Cycle detection stores visited people in a Set. Why is it right that a Set compares objects by identity here?

Storing names would wrongly flag two different employees who share a name. Identity answers the real question: have I been at this exact node before?

 ways(n) returns ways(n - 1) + ways(n - 2). For n = 40 it takes seconds. Why, and what is the fix?

ways(38) is computed twice, ways(37) three times, and so on. Caching each result makes the count linear, as the lesson's 242,785 calls versus 49 calls showed.

 Roughly how deep can a simple recursive function go in Node.js or Chrome before RangeError: Maximum call stack size exceeded?

The stack is small compared with the heap. Folder trees and menus are nowhere near the limit; chains of records and user-controlled nesting can be.

 A function ends with return total(entry.previous, sum + entry.amountKobo), a tail call. Does that protect it from stack overflow in Node.js?

You cannot rely on tail call elimination in the engines you deploy on: only JavaScriptCore, Safari's engine, implements proper tail calls. For data that can be arbitrarily deep, use a loop or an explicit stack.

 Why does rewriting a recursive walk with an array used as a stack remove the depth limit?

Recursion keeps "what is still to do" in stack frames. An explicit stack keeps the same information in a heap array, whose size is limited only by memory.

 In an explicit-stack walk, what changes if you take work from the front with shift() instead of the end with pop()?

A stack (last in, first out) goes deep first. A queue (first in, first out) finishes a whole level before the next, which answers "who reports directly to the CEO, then who reports to them".

 Comment rows arrive from the database in any order, each with an id and a parentId. Why does buildThread first put every row in a Map and only then attach children?

Two passes make the order of the rows irrelevant and need no recursion at all, so building the tree cannot overflow the stack however deep the thread is.

 Your API walks the JSON body of each request with an unlimited recursive function. What is the production risk?

Data from users can be as deep as they like. Any recursion over it needs a depth limit, or an explicit stack, so that bad input produces a clean validation error instead of a crash.

 balanceAfter(months) can be written recursively or with a for loop over the months. Which is usually the better choice, and why?

Recursion earns its place on data that contains smaller copies of itself. For a count of months, a loop is the natural tool.

 In deepEqual(a, b) for JSON data, what is the base case?

Objects and arrays are the branches of a JSON tree; primitives are the leaves. Leaves are compared directly, and branches compare each key by calling deepEqual again. (Identity is a useful shortcut, but not the base case that ends the walk.)

 You need the number of replies under a comment in a table of 20 million comments. What is the better design?

Loading millions of rows to count a few is wasteful. SQL databases can walk trees themselves with WITH RECURSIVE, close to the data.
