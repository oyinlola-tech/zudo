Customers forward receipts to employers, who must be able to check that a receipt really came from your shop. Employers will never hold any secret of yours. Which tool fits?

The need is public verifiability: anyone can check, only you can create. A signature separates the two abilities. HMAC needs the shared secret to check, and a plain hash has no key, so anyone could compute one for an edited receipt.

 Why is HMAC a poor choice when many outside parties must verify your messages?

HMAC is symmetric: one key both creates and checks. That is fine between parties that trust each other (your own services, a payment provider and you), but not when verifiers must not be able to forge.

 A mobile app caches the product catalogue on the phone and wants to notice if the file got corrupted on disk. What is enough?

The threat is an accident, not an attacker, so integrity without a key is enough. Choose the smallest tool that gives the promise you need; a signature would add key management for no benefit here.

 You store customers' dates of birth and must show them on the profile page. What should protect them at rest?

You must read the value back, so it needs encryption, not hashing. Base64 is encoding: anyone can decode it. A signature proves authenticity but hides nothing.

 With Ed25519, which key creates signatures and which checks them?

Only the holder of the private key can sign. The public key can be published and used by anyone to verify; node:crypto even refuses to sign with a public key object.

 Two parties run an X25519 key exchange over the internet. What does the key exchange alone not give them?

A key exchange defeats passive eavesdroppers, but it does not authenticate the public keys. An active man-in-the-middle can run one exchange with each side. TLS adds certificates and a signature over the handshake to close that gap.

 Why does the lesson pass the key-exchange result through HKDF with a label such as "shop session v1"?

A raw key-exchange output should not be used directly as a key. HKDF derives uniform keys and binds each to a purpose, so one shared secret can safely produce separate keys for separate jobs.

 TLS uses asymmetric cryptography during the handshake, then switches to AES-GCM or ChaCha20 for the data. Why not use asymmetric cryptography for everything?

This combination is hybrid encryption: each kind of cryptography does the job it is good at.

 Which of these does TLS not promise?

TLS protects data in transit and authenticates the server. What the server does with the data afterwards is up to its own security: encryption at rest, access control, and so on.

 A client connects to api.shop.example and receives a valid, CA-signed certificate for blog.example. What must it do?

A certificate proves that a key belongs to a name. A genuine certificate for another name proves nothing about this host; anyone can get a valid certificate for a domain they own.

 In development, a request to your local HTTPS server fails with DEPTH_ZERO_SELF_SIGNED_CERT. What is the right fix?

The first two accept any certificate from anyone, which removes server authentication, and they tend to leak into production. Trusting exactly your development certificate keeps every check on.

 What does "self-signed certificate" mean?

Issuer and subject are the same. Nothing outside vouches for it, so clients reject it unless they have been told to trust that exact certificate.

 A production API key was committed and pushed to a public repository an hour ago. What comes first?

Scanners find public keys within minutes, and clones already contain it. Only revoking makes the copy useless. Then investigate how it was used, then clean the history.

 Your secrets are injected as environment variables. What does a secret store (such as Vault or a cloud secret manager) add?

Environment variables are a delivery mechanism, visible to the whole process and often to crash reports. The store is where secrets are managed: who may read which one, who did, and which version is current.

 Which services should hold the private key that signs receipts?

Least privilege: each service gets only the secrets it uses. Verifying needs only the public key, which is not secret.

 A colleague wants to reuse the payment webhook HMAC secret to sign session cookies too, "to have fewer secrets". What is the problem?

Keep one key per purpose. If both must come from one master secret, derive separate keys with HKDF and different labels.

 What is the right order for rotating a signing key without breaking verification?

Verifiers must know the new public key before they see signatures made with it, and old signatures must keep verifying until they no longer matter.

 A signed token carries kid: "receipts-2026-09". How should the verifier use it?

The key id only selects among keys the verifier already trusts. Letting the message supply the key or the algorithm hands the decision to whoever wrote the message.

 Why should a verifier check the signature on the exact received bytes, before calling JSON.parse?

Verify, then parse, then act. Genuine messages keep verifying, and forged ones never reach code that trusts their content.

 What does a KMS or HSM give you that a key stored in an environment variable does not?

If your server is compromised, an attacker can use the KMS while they have access, but cannot copy the key and keep using it afterwards. That limits the damage to the time of the breach.

 In envelope encryption, what does the KMS encrypt?

Encrypting large data locally is fast, and the KMS only handles small keys. A leaked database is useless without access to the KMS to unwrap the data keys.

 Ed25519 signatures are deterministic: the same key and message always give the same signature. Why is that an advantage?

A reused or predictable nonce in ECDSA can reveal the private key. Ed25519 derives its nonce from the key and message, removing that failure mode. Deterministic does not mean forgeable: you still need the private key.
