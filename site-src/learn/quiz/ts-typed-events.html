In emit<K extends EventName<E>>(name: K, ...args: PayloadArgs<E[K]>), what decides which payload type the call accepts?

K is inferred from the string literal you pass, and E[K] looks up that one event's payload in the map. The name decides. If the caller or a listener could pick the type, it would be a claim that nothing checks.

 With new EventEmitter<ShopEvents>() from node:events, shop.on("order.created", (order) => …) compiled although the map only has "order.placed". Why?

Node's typings are deliberately open: an unknown name is allowed, and its listener parameters are any. The map helps with known names but cannot make a typo an error. A bus whose on only accepts keyof E can.

 The map has "cart.cleared": void, and emit takes ...args: PayloadArgs<E[K]> with type PayloadArgs<P> = [P] extends [void] ? [] : [payload: P]. Which call compiles?

For void the rest parameter is the empty tuple [], so the call takes no payload at all. Any second argument, even undefined, is "expected 1 arguments, but got 2".

 Why is PayloadArgs written [P] extends [void] instead of P extends void?

A conditional type on a naked type parameter runs once per union member. For a payload like { note: string } | void the naked version would give [] | [payload: { note: string }], silently making the payload optional. Wrapping both sides in a tuple switches distribution off.

 Why does this compile, although it sends a cancellation payload to the "stock.low" listeners? function forward(name: "order.cancelled" | "stock.low", payload: ShopEvents["order.cancelled" | "stock.low"]) { shop.emit(name, payload); } forward("stock.low", { orderId: "ORD-7", reason: "duplicate" });

This is the correlated-union problem. The pairing between a name and its payload exists only in your head once they are two union-typed variables. Keep them in one EventOf value instead.

 What is the best way to make forward refuse a mismatched name and payload?

Each member of EventOf ties one name to its payload, so a mismatched pair matches no member and is refused. A generic K helps literal callers, but a caller holding a union name would reopen the hole; the cast only hides it.

 The bus stores all listeners in one Map<string, Set<Stored>> and casts each listener on the way in. Why can this cast not be avoided?

Map<keyof E, Listener<E[keyof E]>> would say "any listener under any name". The honest design is a typed public API over loosely typed storage, with the single cast at the point where precise types enter it, justified because emit checks the arguments per name.

 Why does emit loop over [...set] instead of the live collection?

once listeners remove themselves while emit is running. With an array that would skip the next listener; with a live Set, a listener added during the loop would also run. Iterating over a snapshot avoids both.

 With the lesson's onPattern, what does a listener for "order.*" receive?

A wildcard listener receives several kinds of event, so it gets EventOf<E, Matching<E, "order.*">>. Checking event.name narrows event.payload to that event's type.

 A plugin subscribes with bus.onPattern(`${moduleName}.*`, …) where moduleName: string. What happens?

Types only know values known at compile time. A pattern built from a plain string could be anything, so the typed method refuses it. You must check the value at runtime and cast, or use an untyped method. This is one of the real limits of typed wildcards.

 Why does the lesson's bus refuse onPattern("*.placed", …)?

The type-level pattern language and the runtime matcher must agree. Every extra form ("any namespace", "one level only") has to be added to both, which is why a small pattern language is the practical choice.

 Why does the bus use Promise.allSettled rather than Promise.all to run async listeners?

For error isolation the publisher needs every outcome: which listeners succeeded, which failed and why. allSettled reports each result as fulfilled or rejected.

 The bus runs calls.map(async (call) => call()). What would go wrong with calls.map((call) => call())?

An async function never throws; it returns a rejected promise. The wrapper converts a synchronous throw into a rejection, so it is isolated and reported like any async failure.

 A worker reads events from a message queue and publishes them on the typed bus. What does the event map guarantee about those payloads?

Types are erased and never inspect data. The map describes what the program expects; a validator per event name checks what actually arrived.

 What does annotating the validators object as { readonly [K in EventName<E>]: (payload: unknown) => payload is E[K] } buy you?

The mapped type turns "every event needs a validator" into a compile-time rule. The validators still do the actual checking at runtime.

 Why does parseEvent check the incoming name with Object.hasOwn(validators, name) rather than name in validators?

An object literal inherits from Object.prototype. "toString" in validators is true. Names from outside the program must be checked against the object's own keys only.

 With @zudojs/events, bus.on<Event<OrderPlaced>>("stock.low", handler) compiles. What is the type argument?

A type argument that only describes what a callback will receive works like as. The package's event types are plain strings, so it cannot link names to payloads; a small typed layer that takes your map as a type parameter can.

 EventUnion<ShopEvents> from @zudojs/events fails with "Index signature for type 'string' is missing" when ShopEvents is an interface. Why?

An interface can be extended later by declaration merging, so TypeScript will not assume it has only string keys with unknown values. A type alias is closed, so it is assignable to Record<string, unknown>.

 What is the advantage of accepting { signal?: AbortSignal } in on?

AbortSignal is the platform's shared cancellation token. Tying listeners to it means cleanup happens in one place instead of keeping every unsubscribe function around.

 Checkout needs to know whether charging the card succeeded before it shows the receipt. Is an event the right tool?

An event says "this happened" and does not care who listens. When you need an answer, or a guarantee that exactly one piece of code ran, you want a command or query, the topic of the next lesson.

 You must rename totalKobo to amountKobo in the order.placed payload, and another service reads these events from a queue. What is the safe approach?

The compiler only sees code compiled with yours. Listeners in other services, and messages already sitting in the queue, still have the old shape. A new event name lets old and new consumers coexist during the change.

The directive expects an error on the next line. If there is none, tsc reports an unused directive. So the file proves that the API keeps refusing what it should.
