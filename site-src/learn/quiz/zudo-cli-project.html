Why does the lesson commit before every zudojs generate?

The CLI does not look at git at all. The commit is for you: a known starting point makes the generator's changes visible and reversible, which is how the lesson undid the accidental availability module in one line.

 zudojs generate module scheduling --dry-run listed 7 files; the real run wrote 8. What was the extra change?

The real run also registered new SchedulingModule() in src/app.ts. A dry run is a close preview, not a contract, so read git diff after the real run.

 In a modular-monolith project, what does zudojs generate service availability --module scheduling do?

The CLI maps service to module for this architecture and says so on one line. Because the exit code is 0, a script would not notice. Undo it and write the service inside the module yourself.

 Which part of that run is the clearest sign that something unexpected happened?

The mapping line and the paths are the only signals. The architecture line is correct, 8 files is normal for a module, and the exit code is 0.

 You need a service class inside the scheduling module. Which approach works with the published CLI?

controller, repository, dto and the other schematics respect --module. Editing the manifest by hand would make every later command misread the project, and --service is for microservice projects.

 What is dangerous about the file zudojs generate validator booking-date writes?

A stub that compiles and has a convincing name is easy to wire in and forget. Search for such stubs before a release and keep a test that feeds each validator bad input.

 Why does the booking store amountKobo: 50_000_000 instead of amountNaira: 500000.00?

Money in the smallest unit as an integer is exact. 0.1 + 0.2 style errors only appear with fractions, so the code keeps fractions out of every calculation.

 Where does a booking's amountKobo come from?

The client never chooses its own price. Copying the rate into the booking also keeps old bookings at the price they were made for, even if the hall's rate changes later.

 The server's clock runs in UTC. Why does AvailabilityService compute "today" with timeZone: "Africa/Lagos"?

"Today" is a local concept. The service takes it from a replaceable function, defaulting to the Lagos date, so tests can pin it to a fixed day.

 Where must "never book a hall twice for the same date" be enforced so that two simultaneous requests cannot both succeed?

Any check followed later by a write leaves a gap in which another request can pass the same check. Only the place that writes can make "check and insert" one indivisible step.

 The in-memory bookings repository refuses double bookings correctly. You run three copies of the app behind a load balancer. What happens?

Process memory is per process. The rule has to move to shared storage: a PostgreSQL table with UNIQUE (hall_id, date), whose violation becomes a ConflictError.

 The // zudojs:routes markers were deleted from a module's routes/index.ts, and you generate a new resource there. What happens?

Missing markers only produce a warning. Read the last lines of every generate, and keep a smoke test that builds the router the way server.ts does.

 Why does tests/enquiries.test.ts pass even though the enquiries routes were never registered in the app?

It is a unit test of the resource. Wiring is only tested by something that builds the router from createDependencies() and registerRoutes(), like the smoke test.

 In a freshly generated project, a repository throws new Error("connection refused") during a request. What happens?

The generated dispatch rethrows errors that are not exposed 4xx errors, and the HTTP server answers a bare 500. The client learns nothing, which is right, but neither does the operator. createDispatch(router, logger) fixes that.

 The fixed createDispatch logs unexpected errors but not NotFoundError. Why not log every error?

Logs are for the operator. Errors that the client caused and that the app answered correctly belong in metrics at most; errors the app could not handle need a log line with the method, path and message.

 In the generated src/app.ts, how does the runtime learn the environment?

So loadConfig({ NODE_ENV: "production" }) in a test gives a production config and a runtime that says test (Vitest sets NODE_ENV). Passing { NODE_ENV: options.config.nodeEnv } makes both agree.

 After you added a second constructor parameter to BookingsService, the old test still called it with one argument, yet npm run typecheck passed. Why?

Nothing type-checks the tests until you add something that does, such as tsconfig.test.json with "include": ["src/**/*", "tests/**/*"] and a typecheck:tests script.

 You have written real code in the bookings resource and moved its wiring out of the markers. A teammate runs zudojs generate resource bookings --module scheduling --force. What happens?

--force overwrites the schematic's own files and re-inserts the wiring line it cannot find. In the lesson the type checker caught the damage; a change the types cannot see would have been lost silently.

 What does the published CLI offer for deployment?

The CLI prepares; you deploy. Building and running the image, the release step and the pipeline are yours, as the deployment and CI/CD lessons show.

 Where do database migrations come from in a CLI-made project?

zudojs migrate does not exist. Migrations are npm scripts; your release process runs db:deploy before starting the new version.
