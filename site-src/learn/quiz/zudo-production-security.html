In a security review, which of these is the strongest evidence that "only logged-in users can read tasks" holds?

Reading code and docs tells you what someone intended. A test that sends the forbidden request proves what the running app does, and it keeps proving it after the review, because it fails the moment the protection disappears.

 Why does the authentication check loop over router.list() instead of a hand-written list of paths?

The typical authentication bug is a new route that nobody protected. A test that asks the router for every route covers it on the day it is added. A hand-written list only covers the routes someone remembered.

 The check also asserts that exactly two routes are public. What does that add?

Without it, anyone could mark a route public and the deny-by-default loop would simply skip it. Pinning the list forces the change through a test edit that a reviewer sees.

 Linus asks for the id of a task that belongs to Ada. Which answer is safest?

Any difference between "exists but not yours" and "does not exist" lets someone discover which ids are real. The same status and the same body reveal nothing.

 A client sends POST /tasks with {"title":"Pay rent","ownerId":"u-linus"} while logged in as Ada. What should the Task API do?

Who the caller is comes only from what the server verified. Fields in the body that claim an identity are ignored; the NewTask schema keeps only title.

 Why does the review insist on issuer and audience in the token configuration?

The signature only proves "someone with this key made it". The aud and iss claims say who it is for and who made it, and the verifier refuses a mismatch, including a token that has none.

 verifyAccessToken(pair.refreshToken, config) returns valid: false. Why is that the behaviour you want?

Refresh tokens live days, access tokens minutes. If a refresh token also opened every route, stealing one would give long-lived access to everything. Separate secrets and a type claim keep them apart.

 Which Set-Cookie line fails the cookie check from the lesson?

SameSite=None sends the cookie with requests started by any other site, which is what CSRF needs. The Task API has no cookie that other sites must send, so the check requires Lax or Strict.

 Why may requests authenticated with Authorization: Bearer … skip the CSRF token check?

CSRF works because browsers attach cookies automatically. An Authorization header is only sent when your own JavaScript adds it, and a page on another origin cannot read your token to add it.

 Linus logs in, copies his own valid CSRF token, and tricks Ada's browser into posting it together with Ada's cookies. Why does the Task API refuse it?

A CSRF token that is not tied to a session can be taken from the attacker's own account and replayed against a victim. Passing the same sessionId to issue and verify closes that gap.

 A preflight from https://evil.example gets no Access-Control-Allow-Origin header. What does that protect against?

CORS is enforced by browsers, for scripts running on other origins. Direct callers ignore it; authentication, authorization and rate limits stop them.

 The adapter has no trustProxy setting. An attacker sends six login attempts, each with a different X-Forwarded-For. What does the login limiter count?

Without trustProxy the header is just text the client wrote, so the limiter keys on the address of the actual connection. Behind your own proxy you set trustProxy to that proxy, so only its header is believed.

 https://internal.example.org/hook passes isSafeUrl. Why does the webhook route still resolve the host name?

isSafeUrl can only judge the text of the URL. Where a name points is decided by DNS, so the route checks every resolved address with isPrivateHostname, and the sender checks again at delivery time.

 A task title is <img src=x onerror="alert(1)">. Which is the right defence?

The text is harmless as data. XSS happens when output is interpreted as HTML, so encode at the place it lands, for that language. Filtering input breaks legitimate text and misses encodings.

 The SQL check ends with check("the scan does spot one", stringBuilt.test("db.query(`…${id}`)")). Why?

A "no problems found" result is only meaningful from a check that can find problems. Testing the scanner on a known bad line shows it actually works.

 Why do the path traversal and request smuggling checks write raw HTTP to a socket instead of using fetch?

A URL like /tasks/../../etc/passwd is cleaned up to /etc/passwd by the URL parser before it is sent, and fetch manages framing headers itself. To test how the server treats what a raw client or a broken proxy might send, you send those bytes yourself.

 What is a canary in this lesson's log check?

Because the test chose the values, it can search every captured line for them. Unlike key-based redaction, this also catches a secret glued into a message string.

 Why does the log check also assert that "database unavailable" appears in the captured lines?

Absence checks are easy to satisfy by accident: a broken transport, a wrong level, a mocked logger. One presence check shows the lines searched are the real ones.

 Where must the middleware that turns errors into responses go so that error responses carry the security headers?

Middleware runs like nested calls. The security middleware adds headers to whatever its next() returns. An error that escapes past it, or is only turned into a response outside it, gets no headers.

 An app uses createApplication from @zudojs/core and logs { password } on failed logins. What fixes the leak with the published package?

The core ConsoleLogger writes context as given unless a redaction hook is configured. createLogRedactor() is that hook. It is a safety net; the real fix is to never put a password in a log call.

 A ConflictError carries metadata: { field, ownerEmail }. What does serializePublicError(error, { publicMetadataKeys: ["field"] }) guarantee?

Without the option, exposed errors publish all their metadata, with only secret-looking key names redacted. The allow-list names exactly what may leave, so new keys stay private by default.

 Which finding deserves the highest severity?

Severity is impact times likelihood. Reading everyone's private data with a changed number is high impact and trivial to do. A missing framing header on a JSON body is low on both.
