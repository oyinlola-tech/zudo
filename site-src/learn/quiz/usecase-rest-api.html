The old Oja API paged products with ?page=2&limit=20 (SQL OFFSET 20). A partner saw a product on page 1 again on page 2. What is the most likely cause?

An offset counts rows from the start. When a new row sorts in before the ones already shown, everything shifts by one, and the last row of page 1 becomes the first row of page 2. Keyset pagination ("after id 57") is anchored to a row, not a position, so it cannot repeat.

 Why does the Oja API model logging in as POST /v1/tokens?

Thinking in resources turns the verb "log in" into a noun: a token is created. POST is not more secret than GET over HTTPS, but a password must never go into a URL, where it ends up in logs; that is a second reason to use a body.

 Why is cancelling POST /v1/orders/{id}/cancel rather than PATCH /v1/orders/{id} with {"status": "cancelled"}?

Cancelling is a state transition with a side effect (stock goes back). A small action resource exposes exactly that transition. A status PATCH invites {"status": "placed"} or "shipped", and every one needs a rule.

 Bola asks for GET /v1/orders/1, which is Ada's order. Why does the API answer 404 instead of 403?

An attacker who changes the id in the URL learns nothing: existing and missing orders look the same. The SQL WHERE id = $1 AND user_id = $2 finds no row in both cases, so the code does not even need a separate check.

 In POST /v1/orders, "not enough stock" is 409 and "product 99 does not exist" is 422. What is the idea behind the split?

A client can react differently: after a 409 it can show "sold out, try later" or reduce the quantity; after a 422 it has a bug or stale data. Syntax and schema errors are 400, before any business rule runs.

 Ada's phone sends POST /v1/orders/7/cancel, loses the response, and sends it again. The order is already cancelled. What should the second request return, and why?

The client wanted the order cancelled, and it is. Returning the current state makes retries safe. The conditional UPDATE … WHERE status = 'placed' guarantees the stock is only returned by the request that actually changed the status.

 Which change can Oja ship in /v1 without breaking an old mobile app that nobody updated?

Additive changes keep old clients working, because they ignore fields they do not know. Renames, type changes and removals break them and need /v2. This is also why responses allow additional properties in the OpenAPI document.

 Why does order_lines store its own price_kobo instead of joining to products.price_kobo when showing an order?

The product's price is current data; the order line's price is a historical fact. Copying it at the moment of sale is the correct model, not a denormalisation shortcut.

 A teammate replaces the UNIQUE constraint on users.email with code: "SELECT the e-mail; if no row, INSERT". Tests still pass. What breaks?

There is a gap between the read and the write. Only the database can close it: a UNIQUE constraint, used with ON CONFLICT DO NOTHING, makes one insert win and turns the other into a clean 409.

 Oja's requireUser reads the user's role from the database on every request instead of trusting a roles claim in the JWT. What does that buy?

A claim in a token is fixed until the token expires. Reading the role fresh makes changes take effect at once. Revoking the token itself before it expires needs sessions, which the next lesson adds.

 Why does login run verifyPassword against a decoy hash when the e-mail is unknown?

Password hashing is deliberately slow. Skipping it for unknown e-mails makes those answers measurably faster, which leaks exactly what the identical error message was meant to hide.

 Why does Oja's error handler build the body from error.code and error.message instead of sending serializePublicError(error)?

The lesson's example put a warehouse name and a supplier cost into a DomainError's metadata; serializePublicError passed them on. Building the body from named fields is an allow-list for errors, just like output schemas are for data.

 Why does products.list ask the database for limit + 1 rows?

The extra row is only looked at, never returned. count(*) on every page request gets slower as the table grows; one extra row costs nothing.

 What does signing the cursor with cursorSecret protect against?

A signature proves integrity, not secrecy: the payload is plain base64url JSON anyone can read. A changed payload with an old signature is rejected with 400, and allowedFields rejects unexpected keys.

 The contract test did not report an extra cost_kobo field in a product response. Why, and what protects against that leak instead?

Response schemas are deliberately open to additions. A contract test catches wrong types, missing fields and undocumented statuses. Leaks are stopped where data leaves the database: named columns, never SELECT *, and allow-list parsing.

 Why does createRouter get a notFoundHandler and a methodNotAllowedHandler?

One error envelope means one error-handling path in every client. The router's own answers must be brought into line too. The 405 also sets the Allow header.

 A request fails because the database is down. What should the client receive?

Internal details help attackers and confuse users. The request id connects the customer's report to the log line that holds the real cause.

 The test suite runs on PGlite. Which kind of bug can it miss that a real PostgreSQL server with a connection pool would expose?

PGlite is real PostgreSQL, so SQL and constraints behave the same. But with a single connection, two "simultaneous" orders run one after the other, which hides races. Run the concurrency tests against a real server in CI.

 A phone sends POST /v1/orders, the connection drops before the response, and the app retries. What happens with this lesson's API, and what fixes it?

A transaction makes one order all-or-nothing; it cannot know that two requests are the same intent. Only a key chosen by the client, once per intent, can. The payments use case builds this.

 listMine loads 50 order ids, then calls load for each (two queries each). How many queries is that, and what is the pattern called?

One query for the ids plus two per order. The fix is to fetch all orders and then all their lines with WHERE order_id = ANY($1) in two queries, and group them in code.

 Why does ProductQuery cap limit at 50?

Every input that controls work needs an upper bound. The cap also appears in the OpenAPI document, so clients know it before they hit the 400.

 ProductPatch is NewProduct.omit(["sku"]).partial().strict(). An admin sends {"sku": "new-sku", "stock": 5}. What happens?

Stripping would hide the admin's mistake: they would believe the SKU changed. .strict() turns an unknown field into a clear error. For responses, stripping is right; for update requests, strictness is kinder.

 currentUser(ctx) throws "requireUser is missing on this route" when no user is in the state. Why not return undefined and let the route decide?

Security code should fail closed. A missing check that silently passes is the classic way an admin route becomes public.

 An order has three lines. Lines 1 and 2 take their stock, line 3 finds too little. With withTransaction, what is the final state?

The error leaves the callback, so withTransaction rolls back everything done inside it. The client gets 409 and the stock is exactly as before, which the "rolls back every line" test checks.
