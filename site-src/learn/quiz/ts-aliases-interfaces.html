Four functions each write { amount: number } inline in their signatures. A currency field is later added to the objects. Why does nothing fail to compile?

With one named Money type used everywhere, adding currency to it makes every place that builds money without a currency fail to compile, which is exactly where decisions must be made.

 Which of these can only be named with type, not with interface?

An interface can only describe an object type. Unions, tuples, primitives and computed types need a type alias.

 Given type Naira = number and type Kobo = number, what happens when you pass a Kobo value to a parameter of type Naira?

An alias is a name, not a new type. To make units truly distinct you need branded types; until then, use one unit everywhere and name variables clearly (feeKobo).

 Which declaration is valid?

An interface can extend several parents, and they may be interfaces or aliases of object types. A type alias combines with & instead of extends, and nothing can extend a union.

 interface Account { id: string } and interface Legacy extends Account { id: number }. Where is the error reported?

extends checks that the child is compatible with the parent right at the declaration, and explains which property clashes.

 What is the type of id in type Legacy = Account & { id: number }, where Account has id: string?

string & number is empty. The intersection is accepted, and the problem only appears later, when someone tries to create a value. That is the practical reason to prefer extends for object hierarchies.

 You really do need a legacy account whose id is a number. How should you declare it?

Omit removes the old id first, so the new one does not conflict. The first option is TS2430, the second silently makes id never, and any throws away checking.

 A module declares interface Transfer { from: string; to: string } and, much further down, interface Transfer { reference: string }. What happens?

That is declaration merging. It is silent where it happens; the error shows up wherever a Transfer without a reference is written.

 What happens if a module declares type Fee = { amount: number } twice?

Type aliases never merge. A duplicate name is reported where it is written, which is often what you want.

 What is module augmentation for?

declare module "./events.js" { interface TransferEvent { riskScore?: number } } reopens that module's scope, and the interface merges with the original. Plugin systems rely on this.

 Why should a plugin's augmentation add riskScore?: number rather than riskScore: number?

Merging changes the type for everybody. Only the plugin sets the score, so only the plugin should be able to assume it is there.

 Why can two files that both declare interface Account merge in an old-style project, but not in the course's setup?

Merging only happens within a scope. With "type": "module" and module: "NodeNext", each file is a module, so accidental cross-file merging cannot happen.

 Which type correctly describes a chart of accounts where each account can contain sub-accounts?

The self-reference goes through an array, so a leaf account simply has an empty list. The first option requires infinitely many nested accounts, the third refers to itself directly (an error), and the fourth throws away checking.

 In totalBalance(account) = account.children.reduce((sum, c) => sum + totalBalance(c), account.balance), what is the base case?

The data shape provides the base case. Leaves have children: [], and the recursion stops there.

 Why is type Json = string | number | boolean | null | Json[] | { [key: string]: Json } a better type for parsed JSON than any?

Like every type, it is erased, so it does not validate. But unlike any, it does not switch checking off: you must narrow before calling string or array methods.

 A value typed with an interface is refused by a function that takes Record<string, string>, although every property is a string. Why?

The error is TS2345, "Index signature for type 'string' is missing in type …". Spreading into a fresh object or giving the function a more specific parameter type fixes it.

 interface Customer { name: string; phone: string } and type Contact = { name: string; phone: string }. Can a Customer be passed where a Contact is expected?

Whether a type was declared with type or interface does not change compatibility between plain object shapes. (The index-signature rule is the exception.)

 Which signature lets the SMS function serve both customers and staff?

Ask for the smallest type the function needs. The intersection would require a value that is both a customer and a staff member at once.

 Which choice follows the convention "interface for object shapes, type for everything else"?

Object shapes (especially ones others extend or augment) as interfaces; unions, tuples and function types as aliases. The first option is not valid syntax.

 Why should a request context type that plugins add fields to be an interface?

A plugin can reopen the module and add fields to an interface. A type alias cannot be reopened; a second declaration is a duplicate-identifier error.

 ZudoJS's conventions ask for interface names without an I prefix (EventBus, not IEventBus). What is a good reason?

If IEventBus later becomes a type alias or a class, every import would need renaming. A domain name stays correct.

 A Customer with kycLevel: 1 | 2 | 3 is loaded from a database row. What guarantees that kycLevel is really 1, 2 or 3?

Types are erased. A row with kycLevel = 7 becomes a "Customer" with 7 unless code checks it when it enters the program.
