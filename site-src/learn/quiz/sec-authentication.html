Why does a stored password hash include the algorithm and its cost parameters, as in $argon2id$v=19$m=19456,t=2,p=1$salt$hash?

Verification reads the parameters from the stored value, so old and new hashes live side by side. Comparing them with the current parameters tells you which ones to rehash at the next log-in.

 When can a server upgrade a user's old password hash to Argon2id with new costs?

A hash cannot be turned back into the password, so the new hash must be computed from the password itself. A successful log-in is the natural moment; accounts that never log in again can be forced to reset later.

 Why cap passwords at, say, 1,024 bytes before hashing?

A cap far above any real passphrase costs honest users nothing and bounds the work one request can cause. Check it in bytes, before hashing.

 What does Argon2id's memory cost (for example 19 MiB per hash) defend against?

Memory-hardness makes each guess need real memory, which is what attackers' hardware lacks. The same memory is a capacity limit on your servers, so plan concurrent log-ins accordingly.

 Which password policy follows current NIST guidance?

Composition rules and forced changes push people to predictable patterns. Length and refusing known-breached passwords do far more for security.

 Why does the sessions table store SHA-256 of the session token instead of the token?

Whoever has a live token is logged in. Storing only the hash means a database leak does not leak live sessions.

 Passwords need a slow hash, but session tokens are hashed with fast SHA-256. Why is that fine?

Slow hashing protects low-entropy secrets that humans choose. A long random token has so much entropy that even billions of guesses per second get nowhere.

 A session has a 30-minute idle timeout but no absolute timeout. What is the risk?

The idle clock moves forward on every use. An absolute limit that never moves ends every session eventually, however active.

 What is session fixation, and what prevents it?

If log-in upgrades the existing session in place, whoever knew its token before is now logged in too. A fresh token on every privilege change breaks that link.

 Which statement about an HS256 JWT is true?

The header and payload are only base64url-encoded. Never put secrets or private data in a JWT.

 A verifier reads alg from the token's header and uses that algorithm to check the signature. What is the attack?

The token must not choose how it is verified. The server fixes the allowed algorithm(s) and rejects everything else.

 What is the kid header for, and what must the verifier check about it?

During rotation, new tokens use the new key while old ones are still accepted. An attacker-supplied kid must never reach a file path, a database query or an object's prototype.

 Two services share a signing key. Why must each check the aud (audience) claim?

The audience says who the token is for. Without the check, a token leaked from the less protected service works everywhere the key is shared.

 Why do JWT verifiers allow a small leeway (for example 30 seconds) on exp and nbf?

Clock skew between machines is normal. A small leeway avoids spurious failures without meaningfully extending a token's life.

 A web shop's browser app talks only to its own backend. A user reports their laptop stolen. Which design lets you cut the thief off immediately with the least extra machinery?

Revocation is a row deletion with sessions. A stateless JWT stays valid until it expires unless you add a denylist, which brings back the lookup that JWTs were meant to avoid.

 With refresh-token rotation, an already-used refresh token is presented again. What should the server do?

A used token coming back means two parties hold copies, and the server cannot tell which is the thief. Revoking the family is the only safe answer; the real user just logs in again.

 Why is an HttpOnly cookie a better home for a session token than localStorage?

XSS still lets an attacker act within the page while it is open, but it cannot copy an HttpOnly session token away for later use.

 What does naming a cookie __Host-session guarantee?

The prefix closes the route where a compromised or careless subdomain plants a session cookie for the main site, one way to carry out session fixation.

 What is the problem with "lock the account for one hour after 5 wrong passwords"?

A hard lock turns your defence into a denial-of-service tool. Progressive delays, per-IP limits and second factors slow guessers without letting them lock out customers.

 Credential stuffing tries one leaked password per account across 50,000 accounts. Which defence does the most against it?

Each account sees only one attempt, so per-account counting never triggers. Limits per source slow the attack, and a second factor makes a correct leaked password insufficient.
