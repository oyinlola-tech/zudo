Two requests each read Ada's balance (₦50,000) into JavaScript, subtract their amount, and write the result back with update … set balance = $1. What is this bug called?

Read-modify-write in the application is the classic lost update. Each statement is correct; the gap between the read and the write is not protected.

 Which statement debits safely even when many sessions run it on the same row at once, in the default isolation level?

The new value is computed from the current row, and the check is part of the where. A second session waits for the row lock and re-checks the condition against the committed new balance. The unconditional version checks nothing: it overdraws the account unless a check constraint refuses it with an error instead of a clean "not enough money".

 A transfer debits Ada, then the credit to Tunde fails. Which ACID property makes sure Ada's debit is undone?

Atomicity means all or nothing: when any statement in the transaction fails and it rolls back, every change in it is undone.

 What does durability mean in PostgreSQL?

PostgreSQL confirms a commit only after its WAL records are safely on disk. After a crash, replaying the WAL restores every committed change.

 You wrap the naive read-then-write transfer in begin … commit on a real server, at the default isolation level. Is the lost update fixed?

The lesson's lost-update.js shows it: ₦30,000 appeared in read committed although both sessions used transactions. You need relative conditional writes, row locks, a version check, or a stricter level with retries.

 Can a PostgreSQL transaction see another transaction's uncommitted changes (a dirty read)?

MVCC gives every statement a snapshot of committed data only. PostgreSQL has no mode that exposes uncommitted rows.

 In read committed, a transaction reads Ada's balance, another session commits a debit, and the transaction reads again. What does the second read return?

That is a non-repeatable read. Repeatable read would keep the first snapshot for the whole transaction and return the same value twice.

 A report counts transfers over ₦10,000, then sums them, in two statements. Meanwhile another session inserts a large transfer. The count and the sum disagree. Which anomaly is this, and which level prevents it?

A phantom is a new row appearing in a repeated query with the same condition. Repeatable read gives the whole transaction one snapshot, so both statements describe the same moment.

 Two transactions each check that the family total is at least ₦40,000, then each withdraws ₦40,000 from a different wallet. Both commit in repeatable read, and the total goes negative. Why did repeatable read not stop it?

Repeatable read detects two transactions updating the same row. Write skew needs serializable, which tracks read/write dependencies, or explicit locks on every row the decision depends on.

 A repeatable read or serializable transaction fails with SQLSTATE 40001. What should the application do?

A serialization failure means "you lost a race, nothing you did was kept". Retrying the whole transaction makes it read fresh data and decide again.

 Session A runs select … from accounts where id = 1 for update and keeps its transaction open. What happens when session B runs a plain select balance_kobo from accounts where id = 1?

Row locks block other writers and other lockers (for update, update, delete), never plain readers. That is the benefit of MVCC.

 When do you need select … for update instead of a single conditional update?

Locking first turns a multi-step check into a safe one: every read after the lock sees current data, and nobody else can change those rows in between.

 Several workers poll a payout_jobs table. Which query lets each worker take a different job without waiting for the others?

Without a lock, two workers take the same job. With a plain for update, they queue behind each other on the first job. nowait makes them fail. skip locked moves past rows another worker holds.

 Transfer A (Ada → Tunde) and transfer B (Tunde → Ada) run at the same time and one fails with 40P01. What caused it?

A deadlock is a cycle in the "waits for" relation. PostgreSQL detects it after deadlock_timeout and aborts one transaction so the other can finish.

 What is the standard way to prevent that deadlock?

If every transaction takes its locks in the same global order, no cycle can form: whoever gets the first lock goes ahead, the other waits while holding nothing. Retrying on 40P01 is still wise for the cases you did not foresee.

 A support agent opens a customer's settings form, edits for five minutes, and saves. How should you stop them overwriting a change made in the meantime?

No database lock or transaction can span five minutes of user think time. A version check detects the conflict at save time, and the application can show the newer data.

 Over HTTP, how is a version conflict usually expressed?

ETags are the HTTP form of the version column. 412 (or 409) tells the client to reload and try again with fresh data.

 A retry helper catches 40001. Which code should run again on each attempt?

The failed attempt decided on data that has since changed. Only rerunning the reads lets the next attempt decide correctly. It also means the function must not have outside side effects, such as sending an SMS.

 A mobile app's transfer request times out, and the app sends it again. Can the server simply run the transfer a second time?

A database retry after 40001 is safe because nothing was committed. A client retry after a timeout is different: the outcome is unknown. Idempotency keys (API engineering course) solve that.

 Why should you never call a payment provider's HTTP API inside a database transaction?

External calls can take seconds or hang. Meanwhile row locks block other transfers and the connection is unavailable. Record intent in the database, commit, call the provider, then record the result in a second transaction.

 In pg_stat_activity you find a session that has been idle in transaction for 40 minutes. Why is that a problem?

A forgotten open transaction pins old snapshots and locks. idle_in_transaction_session_timeout ends such sessions automatically.

 With the pg pool, why must begin, the queries and commit all go through one client from pool.connect()?

If begin runs on connection 1 and the update on connection 2, the update runs outside the transaction and commits immediately. Take one client, use it for the whole transaction, and release it in finally.
