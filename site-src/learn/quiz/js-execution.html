 In which order does an engine like V8 process your code?

The scanner produces tokens, the parser builds an AST, the bytecode generator produces bytecode for the interpreter, and hot functions are compiled to optimized machine code while the program runs.

 What does the scanner (lexer) produce from total = price * qty; // line total?

Scanning groups characters into the words of the language and throws away whitespace and comments. Building structure from the tokens is the parser's job.

 In the syntax tree for price - 500 * qty, where is the multiplication?

Higher-precedence operations sit deeper in the tree and are evaluated first. The subtraction's right operand is the whole product 500 * qty.

 Why does V8 start by interpreting bytecode instead of compiling everything to optimized machine code immediately?

Optimizing everything up front would make startup slow, and the optimizer would not yet know what types the code really sees. So the engine interprets first and optimizes the hot functions.

 What does "just-in-time" compilation mean?

A JIT compiler works during execution, using the type feedback the interpreter gathered. Ahead-of-time compilers work before the program runs.

 A hot function optimized for integers is suddenly called with a string. What happens?

Deoptimization only affects speed, never results. The optimized code's assumption no longer holds, so the engine falls back to bytecode and may re-optimize later with wider assumptions.

 Which habit helps hot code stay optimized, and is also simply correct?

Parse a form's "950000" into a number when it arrives. Inner functions then see one type, which the JIT likes, and you avoid bugs such as "950000" + 2 giving "9500002".

 What is a hidden class (V8's "map")?

Objects created the same way share a hidden class, so the engine can read a property with one memory access, remembered by an inline cache.

Same properties, same order, set in one place, means one shape. Adding or deleting properties later creates new shapes.

Pre-parsing is cheaper than a full parse but still checks the syntax, which is why an error anywhere stops the file.

 A function creates an order object and returns it. When the function returns, what happens?

Frames live on the stack and disappear on return. Objects live on the heap; the returned reference keeps the order alive.

 Which of these is provided by the host (browser or Node.js), not by the JavaScript engine itself?

The language defines Promise, Map and JSON. Timers, I/O and the event loop come from the host that embeds the engine.

 Who decides which callback runs next when the call stack is empty?

The engine runs a function until the stack is empty, then its microtasks. Which task comes next (a timer, a request, a click) is the host's decision.

 Why must the pricing-rule engine not run staff formulas with new Function("return " + rule)?

Parsing into a tree you control, with a whitelist of names and operators, guarantees only arithmetic can run. Generating code from that tree is then safe.

 Where does the rule engine check that a formula only uses allowed names?

Checking as early as possible means the later stages can trust their input. It also reports the problem with a position when the rule is saved.

 How does the recursive descent parser make * bind more tightly than +?

Each precedence level is its own grammar rule, and lower levels call higher ones. Precedence falls out of the structure, with no special cases.

 Why is the compiled rule faster than the tree-walking interpreter when run over 300,000 cart lines?

An interpreter repeats the same decisions on every evaluation. Compiling does them once, which is the same trade a JIT makes for hot functions.
