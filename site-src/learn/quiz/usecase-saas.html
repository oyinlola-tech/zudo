In InvoiceHub, what is the tenant?

A tenant is one customer of the shared application, and InvoiceHub's customers are businesses. Users are global and can belong to several organizations, so they cannot be the tenant.

 Ada owns Ada's Bakery and is a viewer at Kola Motors. Where should her role be stored?

A role only means something together with an organization. The user row and the token have one role for all organizations, and a cookie is written by the client. The membership row is the only place where "owner of the bakery, viewer at Kola Motors" fits.

 Both organizations want their first invoice to be INV-0001. Which constraint is right?

Numbers are unique per organization, so the pair is unique. A global unique (number) would refuse Kola Motors' first invoice. Checking in code first has a race: two requests can both see "free" and both insert.

 Why does invoices use foreign key (org_id, customer_id) references customers (org_id, id) instead of customer_id references customers (id)?

With the plain key, Kola Motors could bill the bakery's customer 1: that id exists. With the composite key the pair (kola-motors, 1) must exist, and it does not. The rule lives in the database, so no future code change can break it.

 Why does customers declare unique (org_id, id) although id is already its primary key?

PostgreSQL only accepts a foreign key whose target columns have a unique constraint or primary key as a group. The pair is trivially unique because id is, but it has to be declared.

 InvoiceHub turned on row-level security, yet the seed code and db.query(...) outside inTenant still see every organization's rows. Why?

Table owners and superusers bypass policies. That is why inTenant switches to the ordinary role app_user, and why only migrations and seeds should ever run as the owner.

 A new route calls inTenant(db, "", …) by mistake: the organization id is empty. What does select * from invoices return inside it?

current_setting('app.org_id', true) returns an empty value instead of throwing, and no row has an empty org_id. The mistake fails closed: the client sees an empty list, not somebody else's data.

 Why does inTenant use set local role and set_config(..., true) inside a transaction, instead of a plain set once per connection?

With a connection pool, the next request that borrows the connection could be another tenant. A session-level setting would still say the previous organization. local scope ends at commit or rollback, so every transaction starts clean.

 A mobile developer asks to send the chosen organization in an x-tenant-id header on every request, "to save a database lookup". What is the problem?

Validating the format only proves the value looks like a tenant id. It says nothing about whether this user may use that organization. InvoiceHub takes the organization from a record the server wrote after checking the membership.

 Why does InvoiceHub give every user roles: [] in the auth service, instead of putting their role in the login token?

"Owner" in a token does not say owner of what. And a demoted accountant would keep the old role for the token's whole lifetime. Reading the role from the membership row on every request fixes both.

 The membership is checked at login. Why does loadMembership check it again on every request?

Tokens live for 15 minutes and sessions longer. The failure demo removed Bisi and promoted Tunde between two requests, and both changes applied at once, because the role is read from the database each time.

 Kola asks for GET /invoices/1, which belongs to Ada's Bakery. Which answer is best?

A 403 confirms that invoice 1 exists, which leaks information about another customer. For the attacker, "not yours" and "does not exist" must look the same.

 At login, a user names an organization they do not belong to. What should InvoiceHub answer when the organization exists, compared with when it does not?

Different answers would turn the login form into a way to discover which businesses use InvoiceHub. Ending the session means the refused login leaves nothing behind.

 The engine has a global rule { effect: "deny", resource: "*", action: "*", condition: not(tenantIsolation("orgId", "orgId")) }. What happens when a route calls engine.can(actor, "invoice:create") with no resource?

Missing data means no. That is why every InvoiceHub check passes a resource, even for "create" and "list": { orgId: currentOrg().id }, the organization's collection.

 Where must metadata.orgId in the permission check come from?

The deny rule compares the resource's organization with the request's organization. If the request's side came from the client or from the resource itself, the comparison would prove nothing.

 Why does InvoiceRepository.list() take no orgId parameter?

A parameter can be filled from the wrong place, such as the query string. The context is set once, by the middleware, from a trusted source. Outside a context the repository throws TenantContextMissingError.

 Why does InvoiceHub use namespace: orgId with @zudojs/cache instead of a key from tenantKey(tenantId, "dashboard.totals")?

The cache uses : to separate prefix, namespace and key, so it refuses it inside a key part. A tenant id is a valid namespace, because both allow only letters, digits, - and _.

 The founders want "bulk reminders" for about 10% of organizations. Which evaluation context is right?

The percentage rule buckets by userId first, then tenantId, then sessionId. With the user in the context, members of one organization land in different buckets and disagree. For an organization feature, leave the user out.

 Why does POST /reminders/bulk answer 404 for an organization outside the beta, rather than 403?

Unreleased features often carry names you have not announced. The route still checks invoice:send after the flag: a flag is not a permission.

 InvoiceHub sets notFoundResponse on the tenancy middleware so that an unknown, a suspended and a "no longer a member" organization all answer 404 Organization not found. What does that protect?

Different messages ("Tenant not found" from the middleware, "Organization not found" from loadMembership) would let anyone with a token probe the state of other organizations. The owner of a suspended organization learns why by e-mail, not from a 404.

 A nightly job must e-mail every organization's overdue invoices. Which design keeps isolation?

Inside tenantContext.run the job uses the same two walls as a request. One big owner query puts every organization's rows in one loop, where one bug (or one log line) mixes them up.

 The isolation test starts with expect(ids.length).toBeGreaterThan(0). Why?

If a seed change left the victim without invoices, the attack loop would never run, and the suite would still be green. The guard makes that situation fail loudly.

 Why does the "never lists or counts" test load the victim's dashboard before the attacker's?

The caching leak depends on order: whoever fills the shared key first decides what everybody sees. The test creates exactly that order, and the mutation run showed it fail when namespace was removed.

 Someone removes both the org_id filter and inTenant from InvoiceRepository.get. Kola requests the bakery's invoice 1. What happens, and why does the test still fail?

The deny rule is a third wall: the foreign invoice is loaded but refused. The answer is still wrong, because it tells the attacker that invoice 1 exists, and the suite catches it.
