Which problem is the clearest fit for two pointers from opposite ends?

Sorted data plus a question about pairs is the classic signal. The other three depend on counts, not order, and fit the frequency counter.

 In a sorted list, amounts[left] + amounts[right] is bigger than the target. Why is it safe to move right one place left?

Every other partner still in range is at least as large as amounts[left]. So amounts[right] is ruled out for good, and dropping it loses nothing.

 What invariant makes the pair-sum walk correct?

It holds at the start (the whole array) and each move keeps it true. When the pointers meet, the range holds no pair, so by the invariant none existed.

 What goes wrong if pair sum uses while (left <= right)?

A pair needs two different positions. left < right guarantees that and also handles empty and one-element lists without special cases.

 At most how many sums does the two-pointer pair search compute on 10,000 sorted payouts?

Each step moves one pointer one place towards the other, and they start n − 1 places apart. The naive version needs up to n(n − 1) / 2 = 49,995,000.

 Unsorted payouts arrive and memory is plentiful. Which pair-sum approach is usually the better choice?

Two pointers on unsorted data is simply wrong. Sorting first costs O(n log n). The Map is O(n) time; its only price is memory. Two pointers win when the data is already sorted or memory is tight.

 What happens if you run the two-pointer pair search on unsorted amounts?

The safety argument for each move relies on sorted order. Without it the function returns wrong answers with no error at all, which is the worst kind of bug.

 Amounts are sorted with amounts.sort() before the pair search. What is wrong?

Use amounts.sort((a, b) => a - b) for numbers. String order puts "100" before "25".

 Why does in-place dedupe compare ids[read] only with ids[write - 1], the last kept id?

Sorting groups equal values into runs. On unsorted data you would need a Set of seen ids (O(n) space) instead.

 Removing every repeat with splice inside one loop looks like a single pass. Why is it O(n²)?

The hidden loop is inside splice. With every id twice, 100,000 ids cause about 2.5 billion moves; the reader/writer version makes one write per kept id.

 What is the main risk of an in-place algorithm like dedupeSorted(ids)?

In-place saves memory by reusing the input. Make it obvious in the name and documentation, and prefer a copy when memory allows.

 In container with most water, the left panel is shorter than the right. Why move left and not right?

Moving the taller side is not safe: the tanks tried next would still be capped by the short side while the width shrinks, and the dropped tall panel might belong to the best tank (in [2, 10, 10] the best tank is the two 10s). Moving the shorter side discards only a panel that is provably finished.

 Container with most water uses two pointers although the heights are not sorted. What replaces sortedness in the argument?

Two pointers need a proof that each move is safe, not necessarily sorted data. Sortedness is just the most common source of such a proof.

 Which pairing of problem and pointer shape is right?

Pair sum uses opposite ends; the middle of a list uses fast and slow; merging uses one pointer per list, each advancing when its head is taken.

 Why use fast and slow pointers to find the middle of a linked list rather than computing Math.floor(n / 2)?

When the fast pointer (two steps at a time) reaches the end, the slow one (one step) has walked half as far. Both are O(n); fast/slow saves the second walk.

 To find the stop 3 from the end of a linked route in one walk, the lead pointer gets a head start. Of how many stops, and why does it work?

A fixed gap between two same-speed pointers turns "k from the end" into "k behind the lead". If the head start runs out of stops, the route has fewer than k stops.

 Why does the middle loop test fast !== null && fast.next !== null?

The order matters too: && stops at the first false test, so fast.next is never read when fast is null.

 In Floyd's cycle detection, why must the fast pointer eventually land on the slow one if there is a loop?

Once both are in the loop, the distance from fast to slow (going forward) decreases by 1 per move. A gap that shrinks by exactly 1 must reach 0, within one lap.

 When would you pick a Set of visited accounts over Floyd's method for a forwarding loop?

Both find the loop in O(n) time. Floyd's needs O(1) space. For a modest number of accounts, the simpler code is usually the better engineering choice.

 An account forwards money to itself. What does Floyd's method do?

After one move, slow and fast are both at the account again, so they meet; the second phase then starts both at the same account and returns it immediately.

 Where does the two-pointer walk show up inside databases?

Merge joins, external merge sorts and reconciliations of two sorted files all walk two sorted inputs once each, just like merging two sorted arrays.

 A developer's two-pointer loop has a branch where neither pointer moves. What happens?

Termination comes from the pointers getting closer on every step. Every branch must move at least one pointer.

 A random test only checks that refundPair returns non-null exactly when the brute force finds a pair. Which bug would it miss?

"Found or not" agrees, yet the positions are useless. The lesson's test also checks that each returned pair has i < j and really adds up to the target.
