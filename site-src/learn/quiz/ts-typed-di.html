In the opening example, Tunde was charged for Ada's rice although every type was correct. What was the real bug?

Types describe shapes, not how long objects live or who shares them. The cart was correct as a type and wrong as a lifetime. Scopes give each request its own instance.

 What is the composition root?

Services only declare what they need in their constructors. The composition root (hand-written or a container) is the only code that knows the concrete classes and how they fit together.

 Why can't container.resolve(Clock) work when Clock is an interface?

TypeScript reports "'Clock' only refers to a type, but is being used as a value here." A container needs a key that exists at runtime: a string, a symbol, a class or a token object.

 What is wrong with using plain strings such as "clock" as tokens?

The string exists at runtime but says nothing about the type registered under it. A token object carries its type (through a phantom type parameter) and is unique by identity.

 What does declare readonly __type: T do in class Token<T>?

Without a property that uses T, every Token<X> has the same shape and TypeScript could not tell them apart. The declare field exists only for the type checker.

 A file creates new Token<Clock>("Clock") instead of importing the exported CLOCK. What happens when it resolves it?

Token identity is the key; the name is only for messages. The type is identical, so the compiler cannot help. Export each token from exactly one module and import it everywhere.

 Why is register declared with <T, const D extends readonly Token<unknown>[]>?

Without const, [CART, CLOCK] would be inferred as an array of a union, and TypesOf could not map position 0 to Cart and position 1 to Clock.

 What is TypesOf<[Token<Cart>, Token<Clock>, Token<Logger>]>?

A mapped type over a tuple maps each position separately. The conditional type with infer U pulls the type out of each token, keeping the order, so the result can be a factory's parameter list.

 The lesson's registerClass(token, lifetime, deps, type) types type as new (...deps: TypesOf<D>) => T. Which mistake does that catch?

The constructor's real parameter list is compared with the types of the tokens, position by position. Whether those tokens are registered, and with which lifetime, is runtime information.

 Which lifetime fits a shopping cart that belongs to one HTTP request?

Scoped means one instance per scope, and a web server creates one scope per request. Every service in that request shares the cart; the next request gets a new one.

 Which lifetime fits a database connection pool?

A pool exists precisely to share a few connections across all requests. Creating one per request (or per resolve) would open connections until the database refused them.

 Why must a container refuse a singleton that depends on a scoped service?

This is a captive dependency: a longer-lived object captures a shorter-lived one. With a scoped cart or current user it becomes a data leak between customers.

 DailyReport (singleton) needs CheckoutService (transient), which needs Cart (scoped). Is Cart captive?

What matters is the longest-lived object above the scoped one on the path. That is why the lesson's container looks for any singleton on the path, not only the direct parent.

 How does the lesson's #resolve detect a cycle such as OrderService -> InvoiceService -> OrderService?

Resolving is a depth-first walk of the dependency graph. A token that appears twice on the current path is a cycle; naive recursion would instead overflow the stack. The path also makes the error message useful.

 Why is "nothing is registered for PaymentGateway" not a compile error in an ordinary container?

Which registrations ran can depend on conditions, loops or plugins. Only a design whose type changes with each registration (the lesson's builder) can move this error to compile time.

 A factory lists FIXED_CLOCK where SYSTEM_CLOCK was meant; both are Token<Clock>. What catches it?

Types compare shapes. Two tokens of the same type are interchangeable to the compiler, and the container happily resolves whichever you asked for. Give such tokens very different names and test the composition root.

 What is the best practical defence against the wiring errors types cannot catch?

A missing registration, a cycle or a captive dependency found at startup stops the deployment. Found at the first request, it stops a customer.

 The typed ServiceBuilder makes a missing service a compile error. What does it cost?

The builder's type grows with each add, so it must see every registration in one place and in dependency order. That fits small apps and libraries; frameworks with modules usually prefer a runtime container plus startup checks.

 In add<K extends string, T>(name: K extends keyof S ? never : K, …), what does K extends keyof S ? never : K achieve?

No string is assignable to never, so a duplicate name is refused with "not assignable to parameter of type 'never'". It is a conditional type used as a guard.

 In @zudojs/container, what lifetime does registerFactory(token, factory) use when you pass no scope?

The package defaults to ContainerScope.TRANSIENT. registerValue is always a singleton, because a value provider returns the same object anyway. Many other containers default to singleton, so check before you rely on sharing.

 container.registerClass(CHECKOUT, CheckoutService, { inject: [CLOCK, CART, LOGGER] }) has the first two tokens swapped. What happens with @zudojs/container?

registerFactory types the factory's parameters from its inject list; registerClass does not check inject against the constructor. A one-line factory, (cart, clock, log) => new CheckoutService(cart, clock, log), makes the mistake a compile error.

 Why should services receive dependencies through their constructors instead of calling container.resolve themselves?

Calling the container from inside services is the "service locator" style. Constructor parameters make dependencies explicit and typed, so a test can pass fakes directly and the composition root shows the whole graph.

 A small service has eight classes and no per-request state. Should it use a DI container?

Dependency injection is the idea (pass dependencies in); a container is a tool for doing the wiring. Fakes work just as well with hand wiring, as the Classes lesson showed.

 What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; let built = 0; const ID = createToken("Id"); const container = createContainer(); container.registerFactory(ID, () => ++built); console.log(container.resolve(ID), container.resolve(ID)); container.replace(ID, { useFactory: () => ++built }, { scope: ContainerScope.SINGLETON }); console.log(container.resolve(ID), container.resolve(ID));

Without a scope, the factory is transient and runs on every resolve (1, then 2). After replacing it with a singleton registration, it runs once (3) and the instance is reused.

 What does this print? class Token { declare readonly __type: T; constructor(readonly name: string) {} } const CLOCK = new Token<{ now(): Date }>("Clock"); const registry = new Map, string>([[CLOCK, "system clock"]]); const again = new Token<{ now(): Date }>("Clock"); console.log(registry.get(CLOCK), registry.get(again), CLOCK === again); console.log(Object.keys(CLOCK));

A Map compares object keys by identity, so a second token with the same name is a different key. The phantom __type field is declared, so it never exists at runtime.

 What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; let carts = 0; const CART = createToken<{ id: number }>("Cart"); const container = createContainer(); container.registerFactory(CART, () => ({ id: ++carts }), [], { scope: ContainerScope.SCOPED }); const ada = container.createScope(); const tunde = container.createScope(); console.log(ada.resolve(CART).id, ada.resolve(CART).id, tunde.resolve(CART).id); try { container.resolve(CART); } catch (error) { console.log((error as Error).name); }

Inside one scope the scoped cart is built once and reused; another scope gets its own. At the root there is no scope to own a scoped instance, so the container refuses instead of silently making it a singleton.

 The same audit log is registered once as a singleton and once as scoped. What does this print? import { ContainerScope, createContainer, createToken } from "@zudojs/container"; const USER = createToken<{ name: string }>("CurrentUser"); const AUDIT = createToken<{ log(action: string): string }>("AuditLog"); for (const scope of [ContainerScope.SINGLETON, ContainerScope.SCOPED]) { const container = createContainer(); container.registerFactory(USER, () => ({ name: "Ada" }), [], { scope: ContainerScope.SCOPED }); container.registerFactory(AUDIT, (user) => ({ log: (action: string) => `${user.name}: ${action}` }), [USER], { scope }); try { console.log(container.createScope().resolve(AUDIT).log("refund ORD-7")); } catch (error) { console.log((error as Error).name); } }

A singleton audit log would keep the first request's user forever, so the container refuses it even when resolved inside a scope. As a scoped service it lives exactly as long as the user it depends on.
