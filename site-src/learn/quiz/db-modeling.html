A flat order_sheet table repeats each customer's phone on every order row. Support changes Ada's phone on one of her orders only. Which problem is this?

The phone is one fact stored once per order row. Changing some copies and not others leaves the data contradicting itself. Normalising moves the phone into customers, where it is stored once.

 In the flat sheet keyed by (order_id, sku), why can't the shop record a new product that nobody has ordered yet?

That is an insertion anomaly. The product's facts depend on sku alone, but they are stored in a table whose key also needs an order. Giving products their own table removes it.

 A table order_lines (order_id, product_id, quantity, product_name) has the key (order_id, product_id). Which normal form does it break, and why?

A partial dependency on part of a composite key breaks 2NF. The fix is to drop product_name and join to products.

 products (id, name, supplier_id, supplier_phone) has the key id. What is wrong with it?

That is a transitive dependency: id → supplier_id → supplier_phone. The supplier's phone would be repeated on every one of their products, with the same update anomaly as Ada's phone. Move it into suppliers.

 Which design breaks first normal form?

phone1, phone2, phone3 is a repeating group. It also caps customers at three phones and makes "find the customer with this phone" check three columns. A customer_phones table fixes both.

 Order lines store unit_price_kobo, although products.price_kobo exists. Is this a normalisation mistake?

If the rice price goes up next month, last month's orders must keep their totals. The line's price depends on the whole line (this order, this product, at that time), so it is correctly stored there.

 A product can be in several categories and a category holds many products. Where does the relationship live?

Many-to-many needs a third table with one row per link. The composite primary key stops the same link being stored twice, and both columns can be foreign keys.

 Why does the shop use id integer generated always as identity as the primary key of products, plus unique on sku, instead of making sku the primary key?

Natural keys change more often than expected. A meaningless surrogate key never needs to change, and the unique constraint on sku still prevents duplicates.

 Which on delete rule fits the foreign key from order_lines.product_id to products?

Cascading would silently delete sales history, and set null would leave lines that cannot say what was sold. Restrict refuses the delete; the shop marks such products as discontinued instead.

 You split a table into three and want to prove the split lost nothing. What does the lesson's check do?

A lossless decomposition gives back exactly the original rows when joined. A except B lists rows only in A; empty in both directions means no row was lost and none was invented.

 An order has two lines and two payments. A report joins orders to order_lines and payments in one query and sums line_total_kobo. What goes wrong?

This is fan-out: joining two independent child tables multiplies their rows. Aggregate each child table separately (a subquery or a grouped CTE per table), then combine the results.

 The order list page is slow. When is adding a cached orders.total_kobo column the right move?

Denormalisation trades write complexity and drift risk for faster reads. Do it deliberately: measure first, try an index, then write the value in the same transaction as the lines and run a reconciliation query.

 What is a reconciliation check?

Caches derived from other rows can drift when some code path forgets to update them. A query that compares cache and source, with an alert when it returns rows, catches that drift.

 What does cycle id set is_cycle using visited add to a recursive CTE?

The clause protects the read from looping forever. It does not stop bad data being written; the code that moves categories must still refuse loops.

 What is the main trade-off of storing a category tree as an adjacency list (parent_id on each row)?

Only the moved node's parent_id changes, which makes writes simple. Reading all descendants needs with recursive. Materialised paths and closure tables flip that trade-off.

 When is it reasonable to keep data in a jsonb column instead of rows in a table?

The lesson's rule of thumb: if you will filter by it, join on it, count it or constrain it, it deserves rows. A provider's raw webhook payload, stored for auditing, is a good fit for jsonb.

 A comments (target_type, target_id) table points at orders or products. What is the main problem?

A foreign key references one table. With a type column, the database cannot enforce the link, and deleting an order leaves orphan comments. Use one nullable foreign key column per target with a check that exactly one is set, or one table per target.

 A developer proposes attributes (product_id, key, value text) "so we never need to change the schema". What does the shop lose?

Entity-attribute-value moves the schema into data, where the database cannot check it: every value is text, and "products under ₦5,000 in stock" becomes several self-joins. Add real columns with migrations, or a jsonb column for truly free-form extras.

 Which rule can a single-row check constraint enforce?

A check sees only the row being written. reserved <= on_hand is inside one row. The others span several rows or tables, so they need transactions and application code, triggers, or invariant queries in tests.

 Why does the lesson's schema test assert the SQLSTATE code (such as 23514) rather than just "an error happened"?

A test that accepts any error passes when the SQL itself is broken. Pinning the code proves the intended constraint did the refusing, and it pins the codes your HTTP error mapping depends on.

 Which type should orders.placed_at use?

timestamptz stores an absolute moment and converts correctly for any time zone. timestamp without a zone stores a wall-clock reading whose meaning depends on where it was written.

A B-tree index stays compact and cache-friendly when new keys arrive in order. Random UUIDs scatter inserts across the whole index. The next lesson looks inside B-trees.
