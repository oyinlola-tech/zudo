The gift-card feature worked in the demo. Why was that not enough?

Ada redeeming her own card worked. Five things any curious user could try all caused real incidents: injection, acting as someone else, creating money, losing money and reading other people's balances.

 What made the SQL injection in GET /giftcards?code=… possible?

When input becomes part of the SQL text, the input can change the query. With a $1 placeholder the value travels separately and is only ever compared as data.

 This is how the broken server built its query. What does it print? const code = "x' OR '1'='1"; const sql = `SELECT * FROM gift_cards WHERE code = '${code}'`; console.log(sql);

The quote in the input closes the SQL string, and OR '1'='1' is true for every row. The lookup for one card became "every card", and Ada learned Linus's unused code.

 The fixed code keeps the SQL text and the values apart. What does this print? function findCard(code) { return { text: "SELECT amount_cents FROM gift_cards WHERE code = $1", values: [code] }; } const query = findCard("x' OR '1'='1"); console.log(query.text); console.log(query.values);

The SQL text never changes, whatever the input is. The database looks for a card literally named x' OR '1'='1 and finds none. Node prints a string with single quotes inside using double quotes.

 The fixed code checks every gift code against a regular expression. Does it still need the $1 placeholder?

Defence in depth. Even without the schema, the parameterized query would have answered 404 for the injection string instead of listing every card.

 The fixed module accepts a gift code only if it matches this pattern. What does this print? const CODE = /^GIFT-[A-Z0-9-]{4,40}$/; const inputs = ["GIFT-ADA-5000", "x' OR '1'='1", "gift-ada-5000", "GIFT-AB"]; console.log(inputs.map((code) => CODE.test(code)));

Codes are upper case, start with GIFT-, and have 4 to 40 more characters. GIFT-AB has only 2. The injection string contains quotes and spaces, so it never reaches SQL.

 The broken /giftcards/redeem read userId from the request body. What is the fix?

Anything in the request can be chosen by the caller. With identity from the body, anyone could act as anyone, with no login at all. The fixed server has no route that accepts a user id for "who am I".

 GET /wallets/:userId let anyone read anyone's balance. What is this kind of bug called?

Changing a number in the URL was enough to see another user's data. The fix is /wallets/me: the wallet is found from the caller's session, never from the URL.

 Ada "sent" Linus -3000 cents. The first UPDATE added 30.00 to Ada, the second failed on the CHECK and answered 500. Which two missing things caused the damage?

Validation would have refused the negative amount with 400. A transaction would have rolled back the first write when the second failed. With neither, money was created.

 This copies the broken transfer: two separate writes, no validation, no transaction. What does it print? const wallets = { 1: 1000, 2: 1000 }; function write(userId, delta) { if (wallets[userId] + delta < 0) throw new Error("violates check constraint"); wallets[userId] += delta; } function brokenTransfer(from, to, amount) { try { write(from, -amount); write(to, amount); return 200; } catch { return 500; } } console.log(brokenTransfer(1, 2, -3000), wallets);

Taking -3000 from Ada adds 3000. The second write would make Linus negative, so the CHECK fails and the answer is 500, but the first write already happened. Ada gained 30.00 out of nothing.

 Linus sent 1000 cents to user 99, who does not exist, and got 200. What check was missing?

An UPDATE that matches no row is not an error for the database. The fix checks affectedRows after each UPDATE and throws when it is 0, which rolls back the whole transaction.

 This transfer runs inside a fake transaction that throws away the changes on error. The debit happened only on the draft. The missing receiver threw, the draft was thrown away, and Linus still has 10.00. That is what db.transaction does with ROLLBACK.

 Two redemptions of the same card arrive at the same moment. Why did the broken code pay twice?

Between reading and writing there is a gap, and another request can run in it. The fix removes the gap.

 Which statement claims a gift card safely, even under parallel requests?

One statement checks and claims the card. The second request finds redeemed_by already set, matches no row and gets 404. It is the same idea as ShopFlow's conditional stock UPDATE.

 This copies the broken "SELECT, then UPDATE" redemption. Two requests run at the same time.  The fixed module parses transfers with this schema. What does it print? import { schema } from "@zudojs/schema"; const Transfer = schema.object({ to: schema.number().int().positive(), amountCents: schema.number().int().min(1).max(100_000), }); const amounts = [-3000, 0, 12.5, 500, 100_001]; console.log(amounts.map((amountCents) => Transfer.safeParse({ to: 2, amountCents }).success));

Amounts are whole cents from 1 to 100000. Negative, zero, fractional and huge amounts are refused with 400 before any SQL runs.

 Why does the fixed transfer throw a ValidationError when to equals the caller's own id?

Business rules live in the module, next to the schema. A clear 400 is better than an operation that does nothing useful and still shows up in the audit trail.

 What is wrong with returning SELECT * results to the client?

Name the columns you want to show. The fixed card returns only amountCents and a redeemed flag.

 The fixed lookup shows a card without internal columns. What does this print? const row = { code: "GIFT-LINUS-2000", amount_cents: 2000, redeemed_by: 2 }; function publicCard(row) { return { amountCents: row.amount_cents, redeemed: row.redeemed_by !== null }; } console.log(publicCard(row));

The client learns what it needs, the amount and whether the card is used, but not who used it. That is the SQL version redeemed_by IS NOT NULL AS redeemed in JavaScript.

 Why does the fix move the rules into a wallets.ts module with no HTTP in it?

The HTTP layer only reads, authenticates and delegates. The tests call wallets.redeem and wallets.transfer directly, with a fresh database each time.

 The fixed server finds the user from the bearer token only.  After the fixed server survived the attacks, the lesson checks that "the money adds up". What does this print? const walletsStart = [1000, 1000]; const cardsTotal = 5000 + 2000; const walletsEnd = [6000, 1000]; const unusedCards = [2000]; const before = walletsStart.reduce((a, b) => a + b, 0) + cardsTotal; const after = walletsEnd.reduce((a, b) => a + b, 0) + unusedCards.reduce((a, b) => a + b, 0); console.log(before, after, before === after ? Wallets plus unused cards must stay the same: Ada's card moved 50.00 into her wallet, and Linus's card is still unused. With the broken code the same check would show money created.

 Why must gift-code lookups and redemptions be rate-limited?

Codes are secrets that are worth money. Limit per user and per IP, and count failed redemptions per user.

 Should wallet balances be cached?

A cached balance could be out of date and let someone spend money twice or see the wrong amount. Caching card lookups would mostly help attackers guessing codes.

 What should the request logs of the wallet service contain?

A gift code in a log is money anyone with log access can spend. The logger's redaction does not know that code is secret here, so leave it out yourself.

 Where must the ledger row for a money movement be written?

A ledger that can disagree with the balances is worse than none. Same transaction means both are saved, or neither.

 Where does the wallet.credited event get published, and what does the e-mail job carry?

Exactly like order.placed in the capstone. For no lost events, write an outbox row inside the transaction instead. Jobs are stored and logged, so keep secrets out of them.

 You count failures with a wallet.failed metric. What should its label be?

Labels should have few possible values and no personal or secret data. An error code tells you what is going wrong; user ids and codes belong nowhere near a metric.

 How do you check that your new tests really protect you?

A test that passes on broken code proves nothing. Every incident needs a test that failed on the old code and passes now.

 The race test passes with PGlite. Why should it also run against real PostgreSQL in CI?

A race needs real concurrency. The fixed code is safe either way, but only a real server proves it.
