What is ZudoJS?

ZudoJS takes over the backend jobs from the last lesson: lifecycle, dependency injection, routing, configuration, validation, errors, data access, security, testing and project structure.

 How is ZudoJS published?

Each package owns one job. You install only the ones you use, and most of them also work on their own in a project that is not a ZudoJS app.

 Your app needs validation and errors, but no queue and no tenancy. What do you install?

ZudoJS is split so you install only what you need. queue arrives when you have background jobs, tenancy when you serve several customers from one app.

 ZudoJS packages sit on "shelves". What is the rule?

Dependencies point down only. The bottom packages depend on no other ZudoJS package, and the top ones build on everything below.

 What does the shelf rule give you?

If dependencies only point down, no package can end up needing itself through others. That keeps each package independent, like the domain in the last lessons.

 Which package sits at the bottom, used by almost every other package?

Because almost every package uses @zudojs/errors, an error from any package is a BaseError with a status code and a stable code. @zudojs/types sits beside it.

 After sign-up, you want to send a welcome e-mail in the background. Which package is for that?

A queue runs background jobs, so the sign-up request can answer at once while the e-mail is sent later, with retries.

 Only admins may delete books. Which package decides who may do what?

@zudojs/auth finds out who is asking. @zudojs/permissions decides whether that user may do the action. You need both checks, but "only admins" is a permission rule.

 You must read DATABASE_URL and stop the app if it is missing. Which package?

Reading and checking settings is the job of @zudojs/config. The database package uses the setting, but config reads it and fails early when it is missing.

 You want to count requests per second on a dashboard. Which package?

Observability is about seeing inside a running app: metrics like requests per second, and traces. The logger writes what happened, line by line.

 On a request's path, which packages find out who is asking, and whether they may do it?

auth finds the user, like requireUserId did in the BookStore, and permissions decides what that user may do. schema checks the body, and errors turns failures into status codes.

 What does "one description, two uses" mean for NewBookSchema?

In the BookStore you wrote an interface and a parser separately, and they could disagree. A schema is one description that gives both the runtime check and the type.

 The example registers BookService with scope: ContainerScope.SINGLETON. What does that mean?

Singleton means one shared instance. That is why container.resolve(BOOKS) === books printed true: all code sees the same list of books.

 Why can one instanceof BaseError check read the status code of both a SchemaError and your own NotFoundError?

Every ZudoJS package builds its errors on @zudojs/errors, so they share one family. One check handles errors from any package the same way.

 Which command starts the development server and restarts it when you save a file?

zudojs dev is for working on your code. zudojs build compiles the project to JavaScript for production, and create makes a new project.

 You want a new OrderService file in the right folder of your project. Which command?

generate adds a service, controller, repository, module and more. add adds a whole feature, such as database or queue, to an existing project.

 Something is wrong with your setup, and you want the CLI to check your Node.js, packages and project. Which command?

doctor checks for problems. info only shows the CLI version and the project's ZudoJS packages.

 You are starting a new project with a small team. Which architecture should you choose?

A monolith is the default and what this course uses. Microservices add a lot of operational work, and pay off only when parts must scale or deploy on their own.

 What is a modular monolith?

It is still one program to deploy, but modules like catalog, orders and users keep clear boundaries. You get order in the code without running many services.

 When do microservices make sense?

Microservices are separate applications talking over the network, usually behind a gateway. The healthy path is monolith, then modular monolith, then microservices only where needed.
