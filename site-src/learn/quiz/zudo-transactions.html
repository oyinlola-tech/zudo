createTask calls insertTask, which calls recordActivity. What problem does @zudojs/transactions solve here?

Passing tx through every function gets awkward as the app grows. The manager remembers the current transaction for you and decides what a transaction inside another one should do.

 Does @zudojs/transactions talk to PostgreSQL itself?

The package coordinates transactions but never sends SQL itself. The adapter turns begin, commit, rollback and the savepoint methods into commands for your database.

 The adapter builds BEGIN ISOLATION LEVEL … from a fixed table like { serializable: "SERIALIZABLE", … }. Why not write the caller's string straight into the SQL?

An isolation level is part of the SQL text, not a parameter. Looking it up in a fixed table means only the four known phrases can ever be sent.

 How does a nested function know a transaction is already open, when nobody passed it one?

AsyncLocalStorage is a value that follows the async work that started inside run, and is invisible everywhere else. A plain global would be shared by all requests at once.

 Three nested functions each call manager.run with the default propagation. How many COMMITs are sent?

The inner calls are participants: no second BEGIN, no own COMMIT. The root commits everything once, at the end.

 A participant fails, and the root catches the error and carries on. What does this print? import { createInMemoryAdapter, createTransactionManager, TransactionRollbackError } from "@zudojs/transactions"; const manager = createTransactionManager({ adapter: createInMemoryAdapter() }); async function recordActivity(message) { await manager.run(async () => { if (message.length > 20) throw new Error("activity message too long"); }); } try { await manager.run(async (tx) => { try { await recordActivity("created a task called Buy milk"); } catch { console.log("caught it; rollback-only?", tx.isRollbackOnly()); } return "saved"; }); } catch (error) { console.log(error instanceof TransactionRollbackError, error.metadata.originalError); }

The participant's failure spoiled the unit of work, so the transaction became rollback-only. Catching the error does not save it: the root's commit is refused with a TransactionRollbackError, and metadata.originalError holds the reason.

 Why does the manager refuse to commit after a participant failed, even when the root caught the error?

A participant has no way to undo only its own work in the shared transaction. If part of the work should be allowed to fail on its own, use a savepoint (propagation: "nested").

 What does this print? import { createInMemoryAdapter, createTransactionManager, TransactionRollbackError } from "@zudojs/transactions"; const manager = createTransactionManager({ adapter: createInMemoryAdapter() }); async function importTasks(titles, dryRun) { return manager.run(async (tx) => { if (dryRun) tx.markRollbackOnly("dry run"); return titles.length; }); } try { console.log("imported", await importTasks(["Buy milk", "Walk the dog"], true)); } catch (error) { if (error instanceof TransactionRollbackError) console.log("thrown away:", error.metadata.originalError); } console.log("imported", await importTasks(["Buy milk", "Walk the dog"], false));

tx.markRollbackOnly(reason) lets you do all the work and then throw it away: the commit is refused and the reason travels in metadata.originalError. The real import commits normally.

 What is a savepoint?

Rolling back to a savepoint undoes only the work after it. The outer transaction stays healthy and can still commit.

"mandatory" joins an open transaction and throws when there is none. It guards a function that must never write outside a transaction.

 A transaction is open. Which propagation rule pauses it and opens a separate one?

requires_new pauses the open transaction and opens a second one. That needs a second connection, so it only works with a pool, not with PGlite. nested uses a savepoint in the same transaction.

 What does propagation: "never" do?

"never" is the opposite of "mandatory": the code must not run inside a transaction. With none open, it simply runs without one.

 The code sends a "task created" email inside the transaction, and then the transaction rolls back. What went wrong, and what is the fix?

A database rollback cannot unsend an email. Anything that leaves your database (emails, messages, cache updates) must wait until the commit really happened.

 What does this print? import { createInMemoryAdapter, createTransactionManager } from "@zudojs/transactions"; const manager = createTransactionManager({ adapter: createInMemoryAdapter() }); async function createTask(title, fail) { await manager.run(async (tx) => { tx.afterCommit(async () => console.log(`email: ${title}`)); tx.afterRollback(async () => console.log(`rolled back: ${title}`)); console.log(`inserted ${title}`); if (fail) throw new Error("duplicate title"); }); } await createTask("Buy milk", false); await createTask("Buy milk", true).catch(() => console.log("failed"));

afterCommit callbacks run only after a successful commit and are thrown away on a rollback; afterRollback callbacks run only after a rollback. Both run before run returns (or throws) to your code.

 Where in the callback should you register tx.afterRollback(...)?

When a line throws, the rest of the callback is skipped. Register hooks first, then do the work.

 Which errors are worth retrying the whole transaction for?

Serialization failures and deadlocks come from timing between transactions, so a new attempt usually works. Bad input fails the same way every time, and a duplicate stays a duplicate.

Finish delays(attempts, base): the list of pauses before each retry with exponential backoff. The first pause is base, and each next one is twice the one before.

Pause number i is base * 2 ** i. Waiting longer after each failure gives a busy database some breathing room.

 A transaction with retry sends an email inside its callback, and it commits on the third attempt. How many emails go out?

Retries replay the whole callback. Put side effects in afterCommit, which runs once, after the attempt that committed.

 What does the timeout option of manager.run guarantee?

A timed-out transaction is never committed. To stop a slow query inside PostgreSQL itself, also set PostgreSQL's statement_timeout.

 Why put a time limit on a transaction at all?

While a transaction is open, the rows it changed stay locked. Other transactions that need them wait, so one slow transaction can hold up many requests.

 In a real server with a connection pool, why can't every query just use pg.query like the PGlite examples?

PGlite is one connection, so every query lands in the open transaction. With a pool, a query on a different connection would run outside it. The lesson uses withTransaction from @zudojs/database for that case.

onEvent only observes: it tells you what happened, such as how many transactions roll back, without changing the outcome.
