In merge sort, which of the three divide-and-conquer steps does the real work?

Merge sort divides trivially by cutting at the middle. All the comparisons happen while merging. Quick sort is the opposite: its partition (divide) does the work and its combine step is empty.

 Quick sort's combine step does nothing. Why is nothing needed?

The partition puts the pivot in its final position and separates smaller from larger items. Sorting each side in place finishes the job; there is nothing to merge.

 You find the largest of n order totals by divide and conquer (largest of each half, then compare the two). How many comparisons does it make?

Every order except the winner must lose exactly one comparison, so any method needs n − 1. Dividing only pays when it lets you skip work or when the combine step does something clever.

 Why do the divide-and-conquer functions in the lesson pass lo and hi indexes instead of items.slice(0, mid)?

A slice is a new array, built by copying. In binary search that turns O(log n) into O(n). Merge sort can afford slices only because it already does O(n) work per level.

 What is a recursion tree used for?

Each node carries the work done by one call, excluding its children. Summing each level and then the levels gives the total. For merge sort each level sums to n and there are log₂ n levels.

 Merge sort runs on 4,096 items. How many levels of merging are there, and how many items are merged on each level?

4,096 = 212, so halving reaches single items after 12 levels. On every level the merges together cover all 4,096 items once. That is 12 × 4,096 = n log₂ n.

 What does bottom-up merge sort (merge runs of width 1, then 2, 4, 8, …) gain over the recursive version?

It does the same merges as the recursion tree, just from the leaves upwards. It still needs a buffer for merging, and it makes about the same number of comparisons.

After merging runs of width 8, one run of 16 would cover all 10 items, so the loop stops once width reaches 16. The last runs on a level can be shorter than the width: the length does not need to be a power of two.

 While counting inversions during a merge, the item at right[j] is smaller than left[i] and is taken. How many inversions does that add?

The left half is sorted, so if right[j] is smaller than left[i], it is smaller than all of left[i..]. Each of those came earlier in the input and is larger: one inversion each.

 Quickselect uses the same partition as quick sort. Why is it O(n) on average while quick sort is O(n log n)?

Quick sort must sort both sides, so every level of its recursion tree does n work. Quickselect's recursion is a single path whose ranges shrink geometrically, and a geometric series is bounded by a constant times its first term.

 Why is n + n/2 + n/4 + n/8 + … less than 2n however many terms you add?

n/2 + n/4 + n/8 + … approaches n but never reaches it. This geometric sum is why quickselect is O(n) and why the "root wins" case of the master theorem costs O(f(n)).

 The quickselect in the lesson starts with const a = [...input]. What would go wrong without the copy?

Partitioning swaps items around. The copy costs O(n) memory and time, which does not change quickselect's O(n) complexity, and it keeps the function free of side effects. If memory is tight, reorder in place and document it clearly.

 A quickselect always uses the last item of the range as the pivot. What is its cost on an array that is already sorted, when you ask for the smallest item (k = 0)?

The last item is the largest, so each partition removes only that one item and continues with n − 1, n − 2, … items: about n²/2 comparisons. A random pivot avoids depending on the input order.

 Merge sort follows T(n) = 2T(n/2) + n. Which master theorem case is it, and why?

Compare f(n) with nlogb a = nlog₂ 2 = n. They grow alike, so each of the log n levels contributes n: Θ(n log n).

 An algorithm multiplies two n-digit numbers by splitting each in half and computing four half-size products, then adding them in O(n): T(n) = 4T(n/2) + n. What is its cost?

nlog₂ 4 = n², which grows faster than f(n) = n, so the leaves win: Θ(n²). Karatsuba's trick of needing only three products gives nlog₂ 3 ≈ n1.585.

 Quickselect's average case is T(n) = T(n/2) + n. What does the master theorem give, and which part of the tree dominates?

With a = 1 there is one leaf, and the work per level halves as you go down: n + n/2 + … < 2n. The root's own work decides the total.

 What does this print? function T(n) { if (n <= 1) return 1; return 2 * T(n / 2) + 1; } console.log(T(8), T(16), T(1024));

T(n) = 2T(n/2) + 1 is the divide-and-conquer maximum: 2n − 1 nodes in its recursion tree, each costing 1. The leaves win (nlog₂ 2 = n beats f(n) = 1), so it is Θ(n).

 For a recurrence where the leaves dominate, which change makes the biggest difference to the cost?

When leaves win, f(n) does not appear in the answer at all. Karatsuba reduced a from 4 to 3 and the exponent from 2 to about 1.585. When the root wins, it is the other way round: make f(n) cheaper.

 "Ways to pay ₦n with ₦50 and ₦100 notes" splits into ways(n − 50) + ways(n − 100). Solving the two parts independently takes exponential time. Why, and what is the fix?

Divide and conquer assumes independent parts, like the two halves of merge sort. When parts share sub-subproblems, solve each distinct subproblem once and store it: that is dynamic programming.

 A monitoring system must report p95 latency over billions of requests from 50 servers every minute. Why is quickselect not the right tool?

Quickselect is exact but needs the full data set. Sketches trade a small, known error for tiny memory and the ability to combine summaries from many servers.

 Real merge sort and quick sort implementations stop dividing at around 16 to 64 items and finish those pieces with insertion sort. Why?

Big O describes growth for large n. For 20 items, an O(n²) algorithm with a tiny constant beats an O(n log n) one with call overhead. Hybrid algorithms use each where it is best.

 Which property of a divide-and-conquer algorithm makes it easy to run on several cores or machines?

The two halves of merge sort share nothing until the merge, so they can be sorted in parallel. That is the idea behind map-reduce and parallel query engines, and it only pays when the combine step is cheap.
