ShopFlow grows in three stages. Which one do you build first, and why?

Start simple. In stage 3 the single checkout transaction becomes a saga across services, which is the price of microservices. You pay it only when there is a real reason.

 In stage 1, users, catalog and orders share the database connection, cache, event bus and queue. What else do they share?

Modules share infrastructure and nothing else. Orders never reads the catalog's code; things that should happen after a sale listen for an order.placed event.

 Why does ShopFlow store prices as whole cents in an INT column?

Whole cents add up exactly. You divide by 100 only when you show a price.

 What does this print? console.log(0.1 + 0.2 === 0.3); console.log(10 + 20 === 30); console.log(((1200 * 2) / 100).toFixed(2));

0.1 + 0.2 is 0.30000000000000004. Cents are whole numbers, so they add exactly. Two mugs at 1200 cents cost 2400 cents, shown as 24.00.

 The products table has CHECK (stock >= 0). What is it for, if the checkout code already checks the stock?

Defence in depth. The database refuses the write with an error, so a bug cannot silently sell stock that does not exist.

 Why does the sessions table store only a hash of the session token?

The token goes to the client once. On each request the server hashes the token it receives and looks up the hash, together with an expiry date.

 Ada registers with { "email": …, "password": …, "role": "admin" }. What does ShopFlow do with role?

If the body could set role, anyone could make themselves an admin. The role comes from the database, never from the request. Her later attempt to create a product got 403.

 The Credentials schema parses a registration body. What does this print? import { schema } from "@zudojs/schema"; const Credentials = schema.object({ email: schema.string().trim().toLowerCase().email(), password: schema.string().min(12).max(128), }); console.log(Credentials.parse({ email: " Ada@Example.com ", password: "long-s3cret-pass", role: "admin" }));

The e-mail is trimmed and lower-cased, so Ada@Example.com and ada@example.com are one account. The object schema keeps only the fields it knows, so role never reaches the insert.

 Why does login give the same answer, Wrong e-mail or password, for an unknown e-mail and for a wrong password?

Different answers would let anyone test a list of e-mails. For the same reason the code verifies a decoy hash when the e-mail is unknown, so both cases also take the same time.

 When the e-mail is unknown, login still runs verifyPassword against a decoyHash. Why?

Password hashing is slow on purpose. Skipping it for unknown e-mails would make those answers measurably faster, a timing leak.

 The catalog module does not check permissions. Where does ShopFlow check them?

The module does not know who is calling. The HTTP route authenticates the user from the bearer token, calls authorize(user, "product:create"), and only then calls the module.

 These are ShopFlow's roles. What does this print? import { createPermissionActor, createPermissionEngine } from "@zudojs/permissions"; const permissions = createPermissionEngine({ roles: [ { name: "customer", permissions: ["product:read", "order:create"] }, { name: "admin", permissions: ["*:*"] }, ], }); const ada = createPermissionActor("2", { roles: ["customer"] }); const boss = createPermissionActor("1", { roles: ["admin"] }); console.log(await permissions.can(ada, "order:create"), await permissions.can(ada, "product:create"), await permissions.can(boss, "product:create"));

A customer may create orders but not products. The admin's *:* matches every permission. The HTTP layer turns a false into a 403 AuthorizationError.

 Which statement takes stock safely, so two customers can never both buy the last mug?

The check and the change are one statement. PostgreSQL locks the row for the first UPDATE, and the second one sees the new stock. If there is not enough, no row matches and RETURNING returns nothing.

 A teammate replaced the conditional UPDATE with "read, then write". Two checkouts for the last mug run at the same time. What does this print? const db = { mug: 1 }; const pause = () => new Promise((resolve) => setTimeout(resolve, 5)); async function checkout(name) { const stock = db.mug; await pause(); if (stock < 1) return `${name}: sold out`; db.mug = stock - 1; return `${name}: bought`; } console.log(await Promise.all([checkout("ada"), checkout("linus")]), "left:", db.mug);

Both read 1 before either writes, so both decide there is enough. Both write 0: two mugs sold, one existed. This gap between reading and writing is a race condition; the single conditional UPDATE has no gap.

 Now the check and the change happen in one step, like the conditional UPDATE. What does this print? const db = { mug: 1 }; const pause = () => new Promise((resolve) => setTimeout(resolve, 5)); function takeStock(sku, quantity) { if (db[sku] < quantity) return false; db[sku] -= quantity; return true; } async function checkout(name) { await pause(); return takeStock("mug", 1) ? `${name}: bought` : `${name}: sold out`; } console.log(await Promise.all([checkout("ada"), checkout("linus")]), "left:", db.mug);

With no await between the check and the change, nothing can run in between. The second checkout sees 0 and gets "sold out", just as the second UPDATE sees the new stock in PostgreSQL.

 A client sends { "sku": "mug", "quantity": 1, "priceCents": 1 } to /checkout. Which price does ShopFlow charge?

The price comes from the database, never from the request, so a client cannot choose its own price. The checkout schema does not even read priceCents.

 Ada checks out a T-shirt and a mug. The T-shirt line succeeds, then the mug has no stock. What happens to the T-shirt's stock?

All lines, the order, its lines and the audit event run in one transaction. The final product list in the lesson still shows 5 T-shirts after the 409.

 Why is order.placed published after db.transaction returns, not inside it?

Side effects happen after the commit. A crash between the commit and the publish could still lose the event, which the outbox milestone fixes.

 What does this print? import { AuthenticationError, AuthorizationError, ConflictError } from "@zudojs/errors"; for (const error of [new AuthenticationError("Log in first"), new AuthorizationError("Missing permission"), new ConflictError("Not enough stock")]) { console.log(error.statusCode, error.message); }

401 means "we do not know who you are", 403 means "we know you, and you may not do this", 409 means "this conflicts with the current state". The HTTP layer maps them for you.

 What does the checkout schema say about these three bodies? import { schema } from "@zudojs/schema"; const Checkout = schema.object({ items: schema .array(schema.object({ sku: schema.string().max(40), quantity: schema.number().int().min(1).max(20) })) .min(1) .max(20), }); const bodies = [{ items: [] }, { items: [{ sku: "tee", quantity: -3 }] }, { items: [{ sku: "tee", quantity: 2 }] }]; console.log(bodies.map((body) => Checkout.safeParse(body).success));

An empty cart and a negative quantity are both refused before the database is touched (400). Limits on the array and the quantity also stop a single request from asking for millions of items.

 Why does /login have its own rate limiter?

Password hashing is slow on purpose, and login is the favourite target of guessing attacks. Milestone 1 adds a second limit per e-mail.

 The "never oversells" test fires four checkouts at the same time for a product with two left. What must it require?

With Promise.allSettled, count the fulfilled results. Remove AND stock >= $1 on purpose and watch the test fail: that is how you know it protects something.

 Why should the "never oversells" test also run against a real PostgreSQL server in CI?

A race needs things to really happen at the same time. PGlite is great for fast, isolated tests, but it is gentler than production.

 Milestone 3: GET /orders/:id for someone else's order. What should it answer, and how?

Putting the owner in the SQL means an order that is not yours is never even loaded, so one forgotten check cannot leak data. 404 instead of 403 means nobody can learn which order ids exist.

 This finds an order the way the lesson's one(userId, orderId) does. What does it print? const orders = [ { id: 1, userId: 2, totalCents: 2400 }, { id: 2, userId: 3, totalCents: 900 }, ]; function one(userId, orderId) { const order = orders.find((o) => o.id === orderId && o.userId === userId); return order ? `200 ${order.totalCents}` : "404 No order " + orderId; } console.log(one(2, 1)); console.log(one(2, 2)); console.log(one(2, 3));

Order 2 exists but belongs to user 3, and order 3 does not exist at all. Both answer the same 404, so user 2 cannot tell which ids are real.

 The milestones say "parameterized SQL only". Which query follows that rule?

With $1 the value travels separately from the SQL text, so it can never change the query. Building SQL with strings, even after a conversion, is the habit that leads to injection.

 Milestone 4 adds a support role. Which permission list fits "may read every order and cancel one, but may not touch products or roles"?

Give each role only what it needs (least privilege). A wildcard such as *:* or product:* would let support staff change prices or roles.

What does this print? async function sha256(text) { const bytes = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(text)); return [...new Uint8Array(bytes)].map((b) => b.toString(16).padStart(2, "0")).join(""); } const token = "tok-7f3a9c"; const stored = await sha256(token); console.log(stored.length, stored === token); console.log("login with token:", (await sha256(token)) === stored); console.log("login with stolen hash:", (await sha256(stored)) === stored);
