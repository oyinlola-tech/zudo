Which of these facts about a function can its TypeScript signature actually express?

A readonly T[] parameter removes every mutating method from the array's type, so the compiler checks that promise. TypeScript has no effect system: reading the clock, logging and determinism are invisible to the types and stay a matter of convention.

 Which call is referentially transparent, meaning you could replace it with its result everywhere without changing what the program does?

vatKobo(1000000) is always 75000 and does nothing else, so 75000 can replace it. The counter changes state, the charge has an effect in the world, and the delivery fee depends on a hidden input (the clock).

 A teammate wants to cache (memoise) a function's results. What must be true of the function for the cache to be safe?

A cache replaces later calls with an earlier result. That only preserves behaviour when the call could have been replaced by its result in the first place. A function that logs, or reads a price table that changes, gives wrong or missing behaviour when cached.

 Given function addGift(lines: string[]): void and function count(lines: readonly string[]): number, which call does tsc reject? const draft: string[] = ["RICE-5"]; const confirmed: readonly string[] = ["OIL-1"];

Mutable fits readonly: count only promises not to change the array. Readonly does not fit mutable: addGift could push into an array its owner was promised would stay unchanged, so TS4104 refuses it.

 Why is it a good default to type array parameters as readonly T[] when a function does not change them?

A readonly parameter accepts the widest range of callers and states a promise the compiler enforces inside the function. It changes nothing at runtime: the array is not frozen and runs at the same speed.

 With interface Line { sku: string; qty: number }, which line inside function f(lines: readonly Line[]) compiles?

readonly Line[] protects the array, not the objects inside it. qty is not readonly on Line, so changing it compiles. Mark the properties readonly too, or use a deep readonly type.

 A plain JavaScript file imports your TypeScript function that returns a readonly string[]. What stops the JavaScript code from pushing into it?

Types are erased when TypeScript becomes JavaScript. readonly stops TypeScript code that sees the type. To make the runtime refuse, freeze the array, which throws a TypeError on push in strict mode code.

 Why is function pipe(...fns: Array<(x: any) => any>) a poor type for a pipe helper?

any switches checking off at every join and leaks into whatever uses the result. Overloads link each step's output type to the next step's input type, which is what makes swapped steps a compile error.

 The lesson's pipe has overloads for one to four steps. You need six steps. What keeps full type checking?

A nested pipe is itself a function from the first input to the third output, so it is a valid single step of the outer one. The implementation signature is not callable from outside; only the overloads are.

 In which situation does an Option type fix something that T | undefined cannot?

(T | undefined) | undefined is just T | undefined, so two levels of absence collapse into one. Option<T> | undefined keeps them apart. For the other cases, T | undefined is simpler and fully checked.

 With type Maybe<T> = T | undefined, what is Maybe<Maybe<string>>?

Unions are sets, and a set containing undefined twice contains it once. The nesting vanishes, which is exactly why a two-level "maybe" needs a type with its own discriminant.

 Why does the lesson's mapResult take the function first and the result later, as mapResult(fn)(result)?

mapResult(priceLines) is a ready-made step that pipe can call with each result. "Configuration first, data last" is the same rule that made curried functions composable in Functional JavaScript.

 A cart has five lines, and each line is checked independently (known product, whole quantity above zero). Which error strategy suits the customer best?

When checks do not depend on each other, collecting all problems lets the customer fix everything in one round trip. Fail-fast suits dependent steps, such as reading a rate that can only exist after the JSON parsed. Dropping lines charges for a cart the customer did not see.

 Where does a tryCatch(run, onError) helper belong?

It converts foreign exceptions into values where they enter your code. Pure core functions return Results directly. Programming errors (broken invariants) should still throw loudly rather than become ordinary values.

 How many different values does { paid: boolean; channel: "web" | "app" | "pos" } have?

An object type is a product: 2 values of paid times 3 values of channel is 6.

 How many different values does { kind: "none" } | { kind: "some"; value: boolean } have?

A union is a sum: the none member has 1 value and the some member has 2 (one per boolean), so 1 + 2 = 3. That is Option<boolean>: "the values of boolean, plus one".

 Promotions are an ADT (a discriminated union with one interpreter). Which change is easy in this design?

With an ADT, a new operation is one more function with a switch over the kinds. A new kind requires every interpreter to handle it (the compiler lists them). Functions have the opposite trade-off: this tension is the expression problem.

 What can a promotion represented as an ADT do that a promotion represented as a function cannot?

An ADT value is plain data, so it survives JSON.stringify, can be listed and described, and validated. A function can only be called; its logic is opaque.

 What does "parse, don't validate" change about the first step of the checkout?

A boolean check leaves later steps with a plain SKU and a lookup typed Product | undefined. Returning a richer type carries the proof in the data, and every later step can rely on it.

 Why does the build give each pipeline stage its own type (PricedQuote, DiscountedQuote, TaxedQuote…) instead of one Quote with optional fields?

With one wide type, addVat would accept a quote with no discount yet and would have to check discountKobo for undefined. Stage types turn the business order into a type error.

 The lesson says the stage types are only "partly" safe. Why?

Structural typing checks what a value looks like, not where it came from. Someone can write { ...quote, discountKobo: 0 } and skip the promotion step. The next lessons show how brands make a type that only one function can produce.

@ts-expect-error requires the next line to have an error. When the line starts compiling, the directive itself becomes the error. That is what makes it a test of what must not compile.

 A function creates an empty array, pushes into it in a loop, and returns it as readonly T[]. Is it pure?

Purity is about what callers can observe. Mutating a local value that has not escaped is invisible from outside, and is often the fastest way to build a result.

The compiler cannot link "the handler for this value's kind" with "this value". One contained cast behind a well-typed signature, pinned by tests, is a reasonable price; the same cast spread through application code is not.
