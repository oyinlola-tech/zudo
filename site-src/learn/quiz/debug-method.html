You have just made a bug happen on purpose with a one-line command. According to the method, what comes next?

Observe, reproduce, isolate, hypothesize, test, fix, verify. After reproducing comes isolating: a minimal reproduction removes most of the program from suspicion before you start guessing causes.

 A developer cannot reproduce a crash, changes a line that "looks risky", deploys, and the crash has not happened for a day. What is wrong with calling it fixed?

If you cannot make the bug happen on demand, you cannot tell whether a change fixed it. "It hasn't happened again" is also what you would see if the fix did nothing. Reproduce first, then the same reproduction proves the fix.

 You change the price parser, the rounding function and the cache timeout at once, and the wrong totals disappear. What do you now know?

Changing one thing at a time is what makes an experiment tell you something. With three changes, the result cannot separate their effects, and the unneeded changes may introduce new bugs.

 A report says: "The payment page is broken, Tunde paid ₦5,000 for a ₦50,000 order at 14:10." Which part is an interpretation rather than a fact?

The amounts and the time can be checked in the database. "The payment page is broken" names a suspect. The wrong amount could come from the cart, the catalogue, a discount or a conversion; don't let the report choose where you look.

 Wrong totals started "since yesterday afternoon". What is the most useful next observation?

Bugs rarely appear out of nowhere. Something changed just before the first bad result. In the lesson it was a price import at 15:39, three minutes before the first wrong order.

A stack trace is the call stack at the moment of the error. By the time the timer fired, the function that scheduled it was long finished. Only await keeps async frames; timers, events and callback APIs do not.

Wrapping with new Error(message, { cause }) keeps both levels: the meaning (loading order 1042 failed) and the detail (the file is missing, and the relative path shows where the program looked).

 Why does throw "Insufficient funds" make debugging harder than throw new Error("Insufficient funds")?

An Error captures the call stack when it is constructed. A thrown string carries only its text. In an ES module, the uncaught output does not even name the file or the line.

 A crash deep inside a long middleware chain shows ten frames, all inside the middleware library, and none of your route code. What is the quickest way to see more?

V8 records 10 frames by default. When the interesting frames are further down, raise the limit for the debugging session.

 Production charged ₦666 for order 1042. Your reproduction script prints ₦0. What should you conclude?

A reproduction should fail the same way production does. A different wrong answer can come from a mistake in the repro itself (wrong data, missing setup) and send you after the wrong cause.

 Your local run of the import gives correct prices, but the server's import does not. Which is the right next step?

When a bug does not reproduce, the difference between the two environments is the bug. Narrow it down one difference at a time, starting with the exact input data.

 Which is not a benefit of a minimal reproduction?

A minimal repro makes the bug small enough to explain; it does not fix anything. It still fails, and that failure becomes your regression test.

 Which is the most useful hypothesis?

A useful hypothesis names one mechanism and makes predictions that could turn out false. This one predicts a sharp boundary at ₦1,000 that you can test in one line.

 Two hypotheses explain "only expensive items are charged wrongly": (A) a discount rule misfires on expensive items, (B) the imported prices are wrong. Which single observation separates them?

A predicts correct catalogue prices and a wrong total; B predicts wrong catalogue prices. Printing the imported prices kills one of them immediately. Good tests are chosen because the hypotheses disagree about their result.

 While debugging, why is console.log(order) usually better than console.log(JSON.stringify(order)) in Node.js?

console.log uses util.inspect, which shows values as they are: strings in quotes, undefined fields, Map entries. JSON is a data format, not a debugging view.

 In Chrome, you log a cart, then the code adds an item, then you expand the logged cart in the console. What do you see?

Browser consoles show logged objects live: expanding reads the current values. Log a copy (structuredClone(cart)) or specific fields when the object changes later.

 A loop processes 50,000 orders, and stock goes negative somewhere. Why is console.assert(stock >= 0, ...) a good tool here?

console.assert stays silent until its condition is false, so you get one line at the exact moment it matters, instead of 50,000 lines to scroll through. (It does not throw.)

 Which change fixes the root cause of the ₦8,500 → ₦8 import bug?

The database fix disappears at the next import. Removing one comma breaks on ₦1,250,000.00. The root cause is a parser that silently accepts text it does not understand; the fix understands every valid format and fails loudly on the rest.

 Why should you run a new regression test against the old, buggy code once?

The proof that a test guards against the bug is that it fails when the bug is present. If it passes on both versions, it tests something else.

 You have been stuck for 45 minutes. What makes the best question to a colleague, an issue tracker or an AI assistant?

Whoever answers needs the same facts you needed. A minimal repro plus your ruled-out hypotheses lets them skip what you already did. And whatever answer comes back is still a hypothesis: test it against your repro.

 Every order is being undercharged right now. What comes first?

Stop the bleeding first. A mitigation is not a fix, but it buys time to debug properly. Experimenting on live production code adds a second problem to the first.
