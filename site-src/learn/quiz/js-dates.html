What does a Date object store?

A Date is an instant. Every zone-related method has to choose a zone at the moment you call it, which is where the bugs come from.

 What does this print? console.log(new Date(Date.UTC(2026, 3, 1)).toISOString().slice(0, 10));

Months in Date.UTC and the Date constructor start at 0, so 3 is April. It is the most common date bug in JavaScript.

 What does this print? const paid = new Date("2026-03-04T09:15:00Z"); const shipped = new Date("2026-03-04T11:45:00Z"); console.log((shipped - paid) / 60000);

Subtracting dates subtracts their timestamps in milliseconds; dividing by 60,000 gives minutes.

 What does this print? const d = new Date("31/12/2026"); console.log(Number.isNaN(d.getTime()), JSON.stringify({ due: d }));

The string is not a format JavaScript understands, so the Date is invalid (timestamp NaN). Creating it does not throw, and JSON.stringify writes null silently. toISOString would throw.

 A server computes order.placedAt.getDate() to print "ordered on the 4th". Why is this fragile?

Local getters depend on the machine. Use getUTCDate for UTC, or Intl.DateTimeFormat with an explicit timeZone for a particular place.

 What does this print? const placedAt = new Date("2026-03-03T23:30:00Z"); console.log(placedAt.getUTCDate(), placedAt.getUTCHours(), placedAt.getUTCDay());

UTC getters read the instant in UTC: 3 March at 23:00, a Tuesday (getUTCDay counts Sunday as 0). They give the same answer on every machine.

 What does this print? const placedAt = new Date("2026-03-03T23:30:00Z"); const f = new Intl.DateTimeFormat("en-NG", { timeZone: "Africa/Lagos", dateStyle: "medium", timeStyle: "short" }); console.log(f.format(placedAt));

Lagos is UTC+1 all year, so 23:30 UTC is 00:30 the next day in Lagos. Naming the zone makes the result independent of the machine.

 Why should a shop store timeZone: "Europe/London" rather than offset: "+00:00" for its London branch?

An offset describes one moment. A time zone describes which offset applies when, including daylight saving time.

 British Summer Time starts on 29 March 2026. What does this print? const london = new Intl.DateTimeFormat("en-GB", { timeZone: "Europe/London", hour: "2-digit", minute: "2-digit" }); const saturdayNoon = Date.UTC(2026, 2, 28, 12, 0); console.log(london.format(saturdayNoon), london.format(saturdayNoon + 24 * 60 * 60 * 1000));

Adding 24 hours of milliseconds lands at 12:00 UTC on Sunday, which is 13:00 in London after the clocks went forward. "Same time tomorrow" is a calendar step, not a duration.

 Does the 23-hour-day problem affect a delivery schedule computed in Africa/Lagos?

West Africa Time has no DST. The bug appears as soon as the same code handles London, New York or any zone that changes its clocks.

 How does new Date("2026-03-04") interpret the string?

Date-only ISO strings are UTC. Confusingly, a date-time without a zone ("2026-03-04T09:00") is read as local time.

 A form sends "2026-03-04T09:00" for a delivery slot, and the server does new Date(slot). What is wrong?

The same code gives 09:00 UTC on a UTC server and 08:00 UTC on a Lagos server. Refuse zone-less date-times from clients.

 What does this print? console.log(new Date("2026-03-04T09:00:00+01:00").toISOString());

09:00 at +01:00 is 08:00 UTC. toISOString always prints UTC with a Z.

 What does this print in Node.js or Chrome? console.log(new Date("2026-02-30T00:00:00Z").toISOString(), Date.parse("2026-13-01T00:00:00Z"));

V8 accepts day 30 in February and rolls it over into March; month 13 is rejected. Other engines differ, so check parsed dates with a round trip.

 What does the lesson's strict parser do to reject "2026-02-30T00:00:00Z"?

Date.parse alone accepts it in V8. The round-trip check catches every impossible day, whichever engine you run on.

 What does this print? const order = { placedAt: new Date("2026-03-03T23:30:00Z") }; const back = JSON.parse(JSON.stringify(order)); console.log(typeof back.placedAt, back.placedAt);

JSON.stringify uses toJSON, which returns the ISO string. JSON has no date type, so parsing gives back a string that you must convert yourself.

 How should an API store a customer's birthday?

A birthday is not an instant. Stored as midnight UTC and shown in a zone behind UTC, it becomes the previous day.

 Which is the best JSON value for "the moment the payment succeeded"?

An ISO 8601 string in UTC with Z is unambiguous and sorts correctly as text. The others either lack a zone or are meant for people.

 What does this print? const addDays = (date, days) => new Date(Date.parse(`${date}T00:00:00Z`) + days * 86400000).toISOString().slice(0, 10); console.log(addDays("2026-02-27", 2), addDays("2028-02-28", 1), addDays("2026-12-31", 1));

Working in UTC, every day is exactly 86,400,000 ms, so adding days is safe. 2026 is not a leap year; 2028 is.

 What does this print? const d = new Date(Date.UTC(2026, 0, 31)); d.setUTCMonth(d.getUTCMonth() + 1); console.log(d.toISOString().slice(0, 10), new Date(Date.UTC(2026, 2, 0)).getUTCDate());

"31 February" does not exist, so it rolls over three days into March. Day 0 of March rolls back to the last day of February, which is how you find a month's length.

 A subscription starts on 31 January and bills "monthly". Why does the billing code need an explicit rule?

Month arithmetic is a business decision. Clamping gives 28 February (29 in leap years), then 31 March.

 What does this print? const config = { launch: new Date("2026-03-04T00:00:00Z") }; const reminder = config.launch; reminder.setUTCDate(reminder.getUTCDate() - 1); console.log(config.launch.toISOString().slice(0, 10));

reminder and config.launch are the same object, and set… methods change it in place. Copy with new Date(date) before adjusting.

 What does this print? const days = ["Sun", "Mon", "Tue", "Wed", "Thu", "Fri", "Sat"]; console.log(days[new Date("2026-10-01T00:00:00Z").getUTCDay()], days[new Date("2026-03-07T00:00:00Z").getUTCDay()]);

getUTCDay returns 0 (Sunday) to 6 (Saturday). 1 October 2026 is a Thursday and 7 March 2026 a Saturday.

 The shop's rule says "orders before 14:00 Lagos time ship the same day". Which condition matches it?

"Before 14:00" excludes 14:00:00, so < 14. The hour must be read in the shop's zone: UTC is an hour behind Lagos, and local getters depend on the server.

 A delivery date is stored as "2026-03-06". How should it be formatted for display so the day can never shift?

A calendar date has no zone. Formatting midnight UTC in UTC always shows the same day; formatting it in a zone behind UTC shows the day before.

 What does this print? const rtf = new Intl.RelativeTimeFormat("en", { numeric: "auto" }); console.log(rtf.format(-1, "day"), "|", rtf.format(1, "day"), "|", rtf.format(-2, "day"));

numeric: "auto" uses words like "yesterday" where the language has them. In English there is no single common word for −2 days, so it falls back to "2 days ago".

 Why does the lesson's ago(then, now) take now as a parameter instead of calling Date.now() inside?

Reading the clock inside logic makes results depend on when the code runs. Pass the time in, or inject a clock function.

 What does this print? const f = new Intl.DateTimeFormat("en-US", { timeZone: "Africa/Lagos", hourCycle: "h23", year: "numeric", month: "numeric", day: "numeric", hour: "numeric" }); const fields = {}; for (const { type, value } of f.formatToParts(new Date("2026-03-03T23:30:00Z"))) { if (type !== "literal") fields[type] = Number(value); } console.log(fields.year, fields.month, fields.day, fields.hour);

formatToParts returns the pieces of the Lagos wall time. The month is a normal 1-based number here, and hourCycle: "h23" gives 0 for midnight rather than 24.

 An order is placed on Wednesday 30 September 2026 at 16:00 Lagos time. Processing starts the next business day, delivery is 2 business days later, and 1 October is a public holiday. What is the delivery date?

After the cut-off, processing moves to the next business day: Thursday is a holiday, so Friday 2 October. Two business days later, skipping the weekend: Monday 5, then Tuesday 6 October.

 Why does the estimator's test run the same cases with process.env.TZ set to several zones?

A test that only runs in the developer's zone can pass for months and fail on the first deployment elsewhere.

 Which statement about the Temporal API is true at the time of the lesson?

Temporal fixes Date's design problems. Check availability in every runtime you deploy to before relying on it.

 In Temporal, what is Temporal.PlainDate.from("2026-01-31").add({ months: 1 }) by default?

Temporal's default overflow behaviour is to constrain (clamp) to the last valid day, the rule you had to write by hand with Date.

 Two servers record events with Date.now(). Why should you not use those timestamps to decide which of two events happened first when they are milliseconds apart?

Clock drift and synchronisation adjustments make cross-machine timestamps unreliable at fine resolution.
