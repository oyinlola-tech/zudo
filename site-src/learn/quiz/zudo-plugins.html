What is a plugin?

A plugin extends the host through an interface the host defines. The host does not need to change when a new plugin, like a Slack or audit-log plugin, is added.

 What is the difference between a runtime module and a plugin?

The difference is who writes the code and who decides to load it. Your modules are always there. Plugins are chosen per installation, so customers only run code for the features they use.

 In the plugin system, what is the host?

createPluginContext({ name: "task-api", ... }) describes the host and the services it offers to plugins: a logger, config, a container and events.

 What does this print? import { createPluginContext, PluginManager } from "@zudojs/plugins"; const auditLog = { metadata: { name: "audit-log", version: "1.0.0" }, install: () => console.log("install"), initialize: () => console.log("initialize"), start: () => console.log("start"), stop: () => console.log("stop"), dispose: () => console.log("dispose"), }; const manager = new PluginManager(); manager.register(auditLog); const context = createPluginContext({ name: "task-api" }); await manager.start(context); console.log("running"); await manager.stop(context);

manager.start runs install, initialize and start. manager.stop runs stop and dispose. All five hooks are optional.

The context describes the host, but inside a hook, context.plugin is the plugin's own metadata.

 A plugin declares { name: "notifications", version: "^1.2.0" }. Which registered version satisfies it?

^1.2.0 means "1.2.0 or any later 1.x". A new major version like 2.0.0 may have changed its interface, so it is refused.

 What does this print? import { createPluginContext, PluginManager } from "@zudojs/plugins"; const manager = new PluginManager(); manager.register({ metadata: { name: "reminders", version: "1.0.0" }, start(context) { context.onDispose(() => console.log("close file")); context.onDispose(() => console.log("clear timer")); }, }); const context = createPluginContext({ name: "task-api" }); await manager.start(context); await manager.stop(context);

Each plugin has its own cleanup list, which runs when the plugin is disposed, newest first. Things created last are cleaned up first, like closing nested resources.

 A plugin starts a setInterval but never clears it. What goes wrong?

The manager cannot know about your timers. Register the cleanup with context.onDispose(() => clearInterval(timer)), so disposing the plugin really stops its work.

 What is context.signal for?

Pass the signal to slow operations like fetch(url, { signal }). When the host shuts down, they are cancelled instead of holding up the stop.

 What does this print? import { createPluginContext, PluginManager } from "@zudojs/plugins"; let signal; const manager = new PluginManager(); manager.register({ metadata: { name: "sync", version: "1.0.0" }, start(context) { signal = context.signal; }, }); const context = createPluginContext({ name: "task-api" }); await manager.start(context); console.log("while running:", signal.aborted); await manager.stop(context); console.log("after stop:", signal.aborted);

The signal is not aborted while the plugin runs. When the plugin system shuts down, it fires, so any work that listens to it can stop.

 What does this print? import { createPluginContext, PluginManager } from "@zudojs/plugins"; const manager = new PluginManager(); manager.register({ metadata: { name: "reminders", version: "1.0.0" }, install(context, options) { console.log("every", options.everyMs, "ms"); }, }, { everyMs: 40 }); await manager.start(createPluginContext({ name: "task-api" }));

register(plugin, options) hands the options to install(context, options). That is how each installation configures a plugin.

 Why does the reminder plugin check options.everyMs in install and throw when it is wrong?

An interval of 0 ms or "40" as text would misbehave quietly for a long time. Failing at start-up shows the mistake at once.

 Why does manager.start roll back when one plugin's hook throws?

On a failed start, the manager stops and disposes every plugin it had already brought up, then throws the error to you. Nothing is left running.

 A start failed and the manager rolled back. How do you retry?

A disposed plugin cannot be started again: calling manager.start a second time throws a PluginStateError. Factory functions like createAuditLogPlugin() make fresh objects easy.

 What does this print? import { createPluginContext, PluginManager, PluginStateError } from "@zudojs/plugins"; const manager = new PluginManager(); manager.register({ metadata: { name: "audit-log", version: "1.0.0" }, start: () => console.log("start") }); const context = createPluginContext({ name: "task-api" }); await manager.start(context); await manager.stop(context); try { await manager.start(context); } catch (error) { console.log(error instanceof PluginStateError); }

After stop, the plugin is disposed, and a disposed plugin cannot move back to installing. The second start throws a PluginStateError.

 The host passes an event bus from @zudojs/events as context.events. A plugin's task.completed handler throws when the Task API publishes the event with publishEvent. What happens?

A broken plugin handler must not break the request that published the event. The bus catches the error, and the result's failed and errors tell the host what to log.

 The host offers events and a logger to its plugins. What does this print? import { createEventBus } from "@zudojs/events"; import { createPluginContext, PluginManager } from "@zudojs/plugins"; const events = createEventBus(); const logger = { info: (message, meta) => console.log(message, meta), warn() {}, error() {} }; const manager = new PluginManager(); manager.register({ metadata: { name: "audit-log", version: "1.0.0" }, start(context) { const onCompleted = (event) => context.logger.info("audit: task completed", { taskId: event.taskId }); context.events.on("task.completed", onCompleted); context.onDispose(() => context.events.off("task.completed", onCompleted)); }, }); const context = createPluginContext({ name: "task-api" }, { logger, events }); await manager.start(context); await events.publishEvent({ type: "task.completed", payload: { taskId: 7 } }); await manager.stop(context); await events.publishEvent({ type: "task.completed", payload: { taskId: 8 } }); console.log("done");

The plugin subscribes when it starts and unsubscribes in its cleanup list. After stop, nobody listens, so task 8 is not logged.

 The audit-log plugin only uses context.events and context.logger. What is the benefit?

The plugin and the host only share the plugin interface. You can add Slack, statistics or reminder plugins without touching the host, except for one register line.

 The Slack plugin needs a secret webhook address. What does the Task API do?

Secrets never go into code or metadata. The host reads SLACK_WEBHOOK_URL and simply does not register the plugin when it is missing, instead of failing or leaking a secret.

 What does this print? import { PluginManager } from "@zudojs/plugins"; const manager = new PluginManager({ allowedCapabilities: ["events"] }); for (const capabilities of [["events"], ["events", "fs"]]) { try { manager.register({ metadata: { name: `plugin-${capabilities.length}`, version: "1.0.0", capabilities } }); console.log(capabilities.join("+"), "registered"); } catch (error) { console.log(capabilities.join("+"), error.name); } }

allowedCapabilities refuses to register a plugin that asks for more than the host grants. The second plugin asks for fs, which is not in the list.

 A host sets allowedCapabilities: ["events"]. Can a hostile plugin still read process.env and send your data anywhere?

Plugins run in your process with all its rights. Only install plugins you trust, pin their versions and review what they do, exactly as with any other npm dependency.

 Why should a plugin package export a factory like createAuditLogPlugin() instead of a ready-made plugin object?

A shared object would share its state, like a counter or a timer, between hosts and tests. A disposed object also cannot be started again; a factory simply makes a new one.

 Why does a published plugin list @zudojs/plugins in peerDependencies instead of dependencies?

A peer dependency says "the host must provide this". One shared copy keeps instanceof checks working. List it in devDependencies too, so you can build and test.

 Why does the plugin use import type { Plugin } from "@zudojs/plugins" where it can?

A type-only import is removed when TypeScript compiles. The plugin then does not load its own copy of @zudojs/plugins at runtime.

 The package.json has "files": ["dist"]. What does npm pack --dry-run show will be uploaded?

files lists what to ship. Your source, node_modules and any .env file stay at home. Always check with npm pack --dry-run before npm publish.

 What helps other people find your plugin on npm?

Keywords in package.json are searchable on npm. You can only publish under a scope you own, like @acme, not @zudojs.
