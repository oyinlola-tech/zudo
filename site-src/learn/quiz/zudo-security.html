What does defense in depth mean for a public API?

No single check stops everything. Rate limits, CORS, CSRF, authentication, validation and safe headers each stop different attacks, and together one mistake is not a breach.

 How does ZudoJS split security work between @zudojs/security and @zudojs/http?

The security package answers questions like "is this origin allowed?" and knows nothing about servers. The http package wraps those answers into middleware you put in front of your routes.

 Your API runs behind one load balancer that you operate. What should you pass to extractClientIp?

Behind your proxy, every request seems to come from the proxy. trustProxy: 1 reads the address your proxy added and ignores whatever the client wrote before it. Trusting the whole header would let clients fake their address again.

 The in-memory limiter allows max: 5 login attempts. You run three copies of the Task API. How many attempts can an attacker make per window?

The counts live in one process's memory, so each copy allows 5. It still slows guessing a lot, but for an exact limit across servers you need a shared store such as Redis.

 In the attack test, https://evil.example fetched /tasks and got status 200 but allow-origin = null. What protects the user?

CORS is enforced by the browser, not the server, so the status is still 200. The missing Access-Control-Allow-Origin header is what makes the browser refuse to show the response to the script.

 Why does @zudojs/security refuse { origin: "*", credentials: true }?

credentials: true lets the browser send cookies. With "*", any site could send them and read the answer. List the exact origins instead.

 You want to allow only https://app.example.com with a RegExp. Which one is safe?

Anchor both ends with ^ and $. Without them, https://app.example.com.evil.example or https://evil-app.example.com can match. An array of exact strings is even safer.

 The Task API sends its JWT in an Authorization header that your own JavaScript adds. When do you need CSRF tokens?

Another website cannot make the browser add your Authorization header. Cookies are attached automatically, so the moment the token moves into a cookie, add CSRF protection. CORS only hides responses; the forged request still arrives.

 Why was the attacker's POST with Mallory's own valid CSRF token refused for Ada's session?

A token signed for session-mallory does not match session-ada. That is why you always pass sessionId both when you issue and when you verify.

 CSRF protection lets safe methods like GET through without a token. What rule follows from that?

A GET passes without a token, so a GET that deletes or updates something would be open to forged requests. Changes belong in POST, PUT, PATCH or DELETE.

 What does the HttpOnly cookie attribute do?

HttpOnly hides the cookie from JavaScript, so an injected script cannot steal it. Secure means HTTPS only, and SameSite controls sending it on requests from other sites.

 What does the CSP rule script-src 'self' protect against?

It allows only scripts from your own origin. An injected inline script is blocked. That makes CSP the strongest browser-side defence against XSS; 'unsafe-inline' weakens it.

 When should you send Strict-Transport-Security (HSTS)?

HSTS tells the browser to use only HTTPS for a long time. Sent too early, it can lock users out of HTTP-only parts. preload asks browsers to hard-code your domain as HTTPS-only, which is hard to undo.

 A user pastes http://169.254.169.254/latest/meta-data/ into your "link preview" feature. Why is that dangerous?

Your server sits inside your network, so it can reach addresses the attacker cannot. Making your server send requests for an attacker is Server-Side Request Forgery (SSRF).

 isSafeUrl("https://preview.attacker.example/page") returns true. What must you still do before fetching it?

isSafeUrl cannot see DNS. An attacker can point a normal-looking name at 169.254.169.254. If any resolved address is private, refuse it.

 A public page you fetch answers with a redirect to http://169.254.169.254/. How do you close that hole?

An automatic redirect sends your server to the private address without any check. With redirect: "manual" you see each target and run isSafeUrl and the DNS check on it.

 What is the real defence against SQL injection?

With parameters like $1 and $2, the database treats 1 or true as a value and refuses it for an integer column. Detectors and block-lists miss attacks and flag innocent text.

 How should you use detectThreats?

It is a heuristic: it flagged "Please select a date and update the notes" and missed 1 or true. "No threats found" never means "safe".

 A task title contains <script>. What stops it from running on your pages?

Encode text for the place it goes, so < becomes &lt; and shows as text. CSP then blocks injected scripts even if encoding is missed somewhere.
