The tasks part of the app wants the notifications part to send a reminder, and it needs to know whether that worked. Which fits?

Events tell ("this happened") and ignore handler results. Messages ask ("please do this, and tell me how it went"), and the handler's return value comes back to the sender.

 Which is a typical message type name?

A message is an instruction, like reminder.send. The past-tense names announce something that already happened, which makes them events.

 Why send a message instead of importing the notifications code and calling it directly?

A direct call is fine while the app is small. A message keeps the two parts apart: they only agree on a type and a payload shape. Both are still in-process and can be lost in a crash.

 What happens when a handler fails, for events compared with messages?

Event handlers are independent reactions, so one failure does not stop the others. A message asks for one job, so the first failure ends the dispatch with success: false.

 Why give every message handler an id?

An error like Handler "send-reminder" failed: ... tells you exactly where to look, and bus.off("send-reminder") removes that handler.

 What does a branded id like the result of toCorrelationId("req-7f3a") give you?

The brand only exists for the type checker. You brand a string once, and toCorrelationId also rejects empty strings.

 A handler throws. Why does bus.send return { success: false, error } instead of throwing?

Every caller gets a result and checks result.success. The failure is in result.error, wrapped in a MessageHandlerError that names the handler.

 You send reminder.snd (a typo) and nobody handles it. The result says success: true. How do you catch this kind of mistake for a request that needs an answer?

The bus cannot tell "nobody needed to answer" from "you misspelled the address". Checking hasHandlers when the app starts turns the typo into an immediate failure instead of a silent success.

 With allowMultipleHandlers: false, what happens when code registers a second handler for reminder.send?

A second handler for a request is a bug. Failing at registration time, at start-up, is much better than a surprise in production.

 In @zudojs/messaging, in which order does middleware run?

Here 10 runs before 20. That is the opposite of the event bus, so always look it up for the package you use.

 Why validate message payloads in middleware?

Validating in the handler is fine too. In middleware, every dispatch is checked, so a handler never runs with bad data.

 What is a correlation id?

Every message in the chain carries the same correlation id, so one search in the logs finds the whole story. The direct parent is the causation id.

 What is a causation id for?

createDerivedMessage(parent, input) keeps the parent's correlation id and records the parent's id as the cause of the new message.

 In the Task API, what should you use as the correlation id?

The observability lesson puts the same request id on every log line and trace, so one search finds everything that happened for one request.

 A dispatch times out after 45 ms. What happens to the handler that is still running?

JavaScript cannot kill a running function. The caller gets a MessageTimeoutError at once, and the signal is aborted; a handler that ignores the signal keeps wasting resources.

 A handler calls an outside service with fetch. How does it make the request stop when the dispatch is cancelled?

An AbortSignal is the standard "stop, nobody needs this any more" object, and many built-in functions accept it. fetch cancels the request itself when the signal aborts.

 The caller aborts its AbortController. The only handler notices the abort and simply returns "cancelled". What does the caller see?

An aborted dispatch is reported as aborted even when the handler returns normally (since @zudojs/messaging 1.2.0), so the caller can never mistake cancelled work for finished work. send only throws when the signal was already aborted before the dispatch started.

 The reminder handler fails. What should the route send to the client?

Internal error details can leak how your system works. Log the real reason, and give the client a short message that is safe to show.

 The reminder is sent while the user waits for the response. What is the weakness, and what fixes it?

An in-process message lives in memory while the request runs. The background jobs lesson moves this work onto a queue, which survives crashes and retries on its own.
