What does separation of concerns mean for backend code?

The problem with the old BookStore handler was that it did six jobs at once. Separation of concerns gives each piece one job, so you can change one job without reading all the others.

 Which job belongs in a controller?

A controller translates between HTTP and the service. It holds no business rules (those are in the model and the service) and no SQL (that is in a repository).

 What does a service like OrderService know about?

A service carries out a use case such as "place an order". Reading place out loud gives the business process: check the amount, find the book, take the copies, record the order. HTTP and SQL stay outside it.

 What is a DTO?

A DTO describes only what travels over the network. It is not the model: OrderDto shows the total as text and leaves out userId.

 Where should the rule "an order cannot take more copies than there are in stock" live?

It is a business rule that would be true even without computers, so it belongs in the domain. There it needs no server and no database to test.

 A PgliteBookRepository class runs SQL to load and save books. Which layer is it in?

Anything that talks to the outside world (databases, HTTP, e-mail) is infrastructure. It implements a port that the application layer defined.

 In this lesson, what is a port?

The application says what it needs ("something that can find a book") as an interface. Infrastructure provides the how by implementing it.

 Which import breaks the rule "dependencies point inward"?

Outer code may import inner code, never the other way. The domain (model.ts) imports nothing, so a domain file that imports a database repository breaks the rule.

 Why should the domain be the layer that imports nothing?

Drivers, HTTP libraries and frameworks change often. If the domain imported them, every such change would touch your business rules. With arrows pointing inward, you can swap the database and not one rule changes.

 OrderService gets its repositories through its constructor instead of creating them. What is this called?

The service receives what it needs from outside. That is why a test can hand it fake repositories and a real app can hand it PostgreSQL ones.

 Where does the controller get the userId for a new order?

Anything in the body is chosen by the client, so a user could place orders for someone else. The user id must come from the verified token, as in the auth lesson.

 Why does PlaceOrderDto contain only bookId and quantity, and no price?

The incoming DTO holds only the fields a client may send. If the price came from the body, anyone could buy a book for one cent. The service computes book.priceCents * quantity itself.

 Why does the controller answer with toOrderDto(order) instead of the Order model itself?

The outgoing DTO is the public contract. It picks the fields clients see and formats them ("25.98"), so renaming a model field does not break anyone.

 What is the composition root?

Every class receives what it needs, so something must build them all in the right order. That is main.ts, the only file that knows every concrete class.

 Where does the lesson turn DomainError("out_of_stock") into the status code 409?

The domain speaks in words ("out of stock"), HTTP speaks in numbers (409). handleErrors is the one place where they meet, so the domain never learns about status codes.

 For an error that is not a DomainError, handleErrors answers { error: "internal_error" } with status 500. Why not send error.message?

Domain errors are written for users, so their message is safe to show. An unknown error can carry database or code details; the client gets a generic message and you keep the details in your logs.

 Why does loadConfig return Object.freeze({ maxQuantity })?

Settings are read once, checked, and then must stay the same. A frozen object cannot be changed by mistake somewhere deep in the code.

 In the practice, you swap the memory book repository for a PGlite one. Which files change?

The service only knows the BookRepository port. A new class implements it, and main passes that class in. No domain or application file changes: the dependency rule paying off.

 With a real database, "find the book, then save it with less stock" has a gap. What is it, and where is it fixed?

Between the read and the write, another request can read the same stock. The fix (one SQL statement, or a transaction) stays in infrastructure, so the service and domain stay the same.

 Why can a test pass two plain objects to new OrderService(books, orders, 10) instead of real repositories?

The service cannot tell a fake from a database: it only calls find, save and add. Any object with those methods fits the port.

 What is the main cost of the layered design, according to the lesson?

Wiring dozens of services by hand, in order, with their settings and shutdown, becomes a lot of work. That is the job the next lesson hands to a framework.
