A query uses ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 50000 and a matching index exists. Roughly how many index entries does PostgreSQL read?

An index is sorted, but it has no "row number" to jump to. The database reads the rows in order and throws away the first 50,000. The cost of a page grows with its offset, which is why deep pages and full exports get slow.

 What does keyset (cursor) pagination send to the database to get the next page?

Keyset pagination describes the next page by values: "rows that sort after (created_at, id) of the last row I saw". With a matching index the database jumps straight to that point, so every page costs the same.

 In PostgreSQL, when is (created_at, id) < ($1, $2) true?

A row comparison is lexicographic, like sorting words: compare the first column, and only on a tie compare the next. That matches an index on (created_at, id), which is why PostgreSQL can use the index for it.

 A cursor stores only the created_at of the last order, and the next page uses WHERE created_at < $1. Several orders share a timestamp. What goes wrong?

The remaining tied orders are not older than the last one, they are the same age, so < excludes them. Add a unique tie-breaker (the id) to the sort, the cursor and the comparison.

 Why should the last column in a paginated ORDER BY be unique, even with offset pagination?

Rows that compare equal may come back in any order, and that order can change between two runs of the same query. A unique tie-breaker gives every row exactly one position, so pages are repeatable.

 You paginate by (shipped_at, id), but shipped_at is NULL for unshipped orders. What happens to them with WHERE (shipped_at, id) < ($1, $2)?

A comparison with NULL is unknown, not true, so those rows drop out of every page after the first. Sort by NOT NULL columns, or use the same COALESCE(...) in the index and the query.

 A client edits the cursor it received. Assuming your server decodes it, validates its types and passes its values as SQL parameters, what is the worst the edit can do?

With typed values passed as parameters and authorization taken from the session, a forged cursor only moves the starting point. That is why authorization must never live in the cursor.

 A teammate suggests putting customerId inside the cursor "so the next page knows whose orders to load". What is the problem?

Encoding is not protection. A cursor is client input. Authorization is decided on every request from the authenticated user, never from anything the client sends back.

 A client gets a cursor from ?status=paid and sends it with ?status=shipped. What is the best response?

A cursor belongs to one sort and one set of filters. Mixing them gives pages that make no sense. Binding the cursor to a fingerprint of the filters lets you answer with a clear client error.

 The order that a keyset cursor points at is deleted before the client asks for the next page. What happens?

A keyset cursor stores values, not a pointer to a row. "Rows with (created_at, id) less than these" is well defined even if no row has exactly those values anymore.

 Why does listOrders ask the database for limit + 1 rows?

One extra row answers "is there more?" cheaply. The extra row is not sent; the cursor is built from the last row that is sent.

 A product manager wants "Showing 1-20 of N" on a 50-million-row orders list. Which answer is sound?

An exact count visits every matching row, the cost keyset pagination removed. Estimates (such as the planner's statistics) or an on-demand count keep normal paging fast.

 Which of these is a good fit for plain offset pagination?

Offsets are simple, allow jumping to page 7, and are fast enough on small tables that rarely change during paging. Feeds, syncs and exports need cursors.

 Which test would catch the "order shown twice, another never" bug?

The bug only appears when data changes during paging and pages are compared as a whole. A test that reproduces those conditions fails for offsets and passes for correct cursors.

 You add a currency field to every order in the response. When does this break a client?

Additive changes are safe for tolerant readers. Document that clients must ignore unknown fields, and write your own clients that way, and additions become free.

 Which change is the most dangerous for existing clients?

Same name, different meaning: nothing crashes, every client just shows amounts 100 times too large. Change units only under a new name or a new version.

 Is lowering the maximum limit from 100 to 50 a breaking change?

Tightening validation turns valid requests into errors. Keep the old rule for old versions, or ship the change in a new version.

 Your API chooses the version from a Shop-Version header, and a CDN caches GET responses. What must you add?

Caches key on the URL unless told otherwise. Vary lists the request headers that change the response, so a v2 body is never served to a v1 client.

 A request sends Shop-Version: 2026-9-1, which is not a version you have. What should the server do?

Guessing puts the client on a version it was never tested against, silently. A clear 400 makes the typo visible at once.

 What is the main advantage of "one current implementation plus version changes" over copying the code for each version?

Copies drift: a fix applied to one copy is missing in the others. Version changes translate the single current response backwards, and the list of changes doubles as a changelog.

 What do the Deprecation and Sunset response headers tell a client?

RFC 9745 defines Deprecation (a date, written as @ plus a Unix timestamp) and RFC 8594 defines Sunset (an HTTP date). A Link with rel="deprecation" points at the migration guide.

 After the sunset date, which status code should a retired version answer with?

410 says "this existed and has been removed on purpose". A redirect to v2 would send old clients a response shape they cannot parse.
