What does a feature flag separate?

With a flag, new code goes to production switched off (deploy). You switch it on later, for a few users first (release). If something breaks, you switch it off in seconds, without another deploy.

 Which of these is not one of the flag uses the lesson describes?

A flag says whether a feature is switched on. Whether a user may do something is a permission check, which you keep from the permissions lesson.

 In @zudojs/feature-flags, what is a provider?

createFeatureFlags reads definitions from a provider and answers questions. createMemoryProvider keeps them in memory; a real system reads them from a database or a flag service.

 What does this print? import { createFeatureFlags, createMemoryProvider } from "@zudojs/feature-flags"; const flags = createFeatureFlags({ provider: createMemoryProvider([ { key: "task-comments", enabled: true, defaultValue: false }, { key: "task-export", enabled: true, defaultValue: true }, ]), }); console.log(await flags.isEnabled("task-comments"), await flags.isEnabled("task-export"), await flags.isEnabled("task-exprot"));

With no rules, each flag serves its defaultValue. An unknown key, like the typo "task-exprot", is simply off, so a typo never switches a feature on by accident.

 What does this print? import { createFeatureFlags, createMemoryProvider } from "@zudojs/feature-flags"; const flags = createFeatureFlags({ provider: createMemoryProvider([{ key: "task-export", enabled: true, defaultValue: true }]), }); console.log(await flags.evaluate("task-export"));

evaluate returns the value and the reason. No rule decided here, so the reason is default. This is what you log when you wonder why a user sees a feature.

 A flag has several rules. How is the value chosen?

Order matters: put the most specific rule first, like the staff or beta list, and the broad rules, like a percentage, after it.

Anything the client sends can be changed by the client. If plan came from the body or a header, anyone could send "pro" and get pro features for free.

A flag is not a permission. Keep the permission check from the permissions lesson on the server, and read the role from your own authentication, never from a header.

 Why is a percentage rollout deterministic instead of random?

If the answer were random, a feature could appear and vanish on every page load. The rule hashes the flag key and the user id into one of 10,000 buckets, so the same user always lands in the same bucket.

 What does this print? import { getBucket } from "@zudojs/feature-flags"; const first = getBucket("task-comments", "ada"); const second = getBucket("task-comments", "ada"); console.log(first === second, first >= 0 && first < 10000);

The bucket comes from a hash of the flag key and the user id, so the same pair always gives the same bucket, a number from 0 to 9,999.

 The flag key is part of the hash, not only the user id. Why?

With the key in the hash, each flag spreads users differently. Otherwise the same unlucky users would be first in line for every new feature.

 How do you learn which sorting variant wins the A/B test?

A variant label has only two values, so it is safe as a metric label. Comparing completed tasks per variant shows which version works better.

 The file storage is failing, so you switch off the number flag upload-limit-mb with enabled: false. Which definition really stops uploads?

A disabled flag ignores its rules and serves its off value. A boolean flag's off value is false, but a number flag has no natural "off", so without offValue it serves its defaultValue: 50 MB uploads are still allowed. offValue: 0 makes switching it off really stop uploads.

 The mail provider is down, and every task completion fails while sending an email. What does a kill switch give you?

One change to the flag stops the failing optional work. The core feature, completing tasks, keeps working.

 What does "fail closed" mean for feature flags?

An unreachable flag store must never switch a feature on. The safe answer is "off", and the failure is reported to onError.

 The flag store is down. What does this print? import { createFeatureFlags } from "@zudojs/feature-flags"; const brokenProvider = { get: async () => { throw new Error("flag service unreachable"); }, getAll: async () => { throw new Error("flag service unreachable"); }, }; const errors = []; const flags = createFeatureFlags({ provider: brokenProvider, onError: (error) => errors.push(error.message) }); console.log(await flags.isEnabled("task-comments", { userId: "ada" })); console.log(await flags.getBoolean("task-export", true, { userId: "ada" })); console.log(errors);

isEnabled fails closed: false. getBoolean(key, fallback) serves your fallback, here true. After the first failure the instance leaves the provider alone for 5 seconds, so onError received one error, not two.

 When is getBoolean(key, true) a good choice?

The fallback is used when the flag is missing or unreachable. Use true only for features that are safe to keep on; everything new should fall back to off.

 What should the Task API do in onError?

The flags already fail closed, so the request can continue. But someone must learn that the flag store is down, and the log is where they look.

 Why does a snapshot include only flags marked visibility: "client"?

A snapshot sends evaluated values to the browser, and only for flags you chose. Rules and other flags stay on the server, so the client cannot see who else is on the beta list.
