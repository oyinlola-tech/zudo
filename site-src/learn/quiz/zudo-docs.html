The old docs script "finished without errors" while publishing a broken link and an internal runbook. What was missing?

To a script that copies files, docs are only text, so nothing can be wrong. Once each page is a document with an id, metadata and links that can be resolved, a check can fail the build, the same way a failing test does.

 Why should a document's id stay the same when its title changes?

The title is what readers see and may be reworded freely. The id is the page's address. When you must change it, keep a redirect from the old id.

 What does this print? import { documentIdFromPath, isValidDocumentId } from "@zudojs/docs"; console.log(documentIdFromPath("guides/v1.2/routing.md")); console.log(isValidDocumentId("guides.http-routing"), isValidDocumentId("guides/http"));

documentIdFromPath turns separators into dots and removes only the final extension, so the folder v1.2 becomes two segments. Ids are dot-separated segments of letters, digits, _ and -, so a hyphen is fine and a slash is not.

 Given the previous answer, which two files would end up with the same id?

Both become guides.v1.2.routing. start.md and start.mdx would also collide, as the extension is dropped. The registry refuses the second one with DuplicateDocumentError, which is exactly how such a collision is found.

 Documents from createDocument are deep-frozen. What does that protect against?

A docs build passes the same page objects to validators, generators and indexes. If one step could change a page, the others would see different data depending on the order they run in. Frozen documents are values, and a step that wants a change builds a new document.

 What does parseFrontmatter return as metadata here? import { parseFrontmatter } from "@zudojs/docs"; const { metadata } = parseFrontmatter("---\ntags: payments\nversion: 2.10\nretries: 3\nzip: 007\n---\n# Refunds\n"); console.log(metadata);

tags is always a list. version is always a string. Other values become numbers only when nothing is lost: 3 is safe, but 2.10 would become 2.1 and 007 would become 7, so those stay strings.

 A Markdown file from a contributor has __proto__: admin in its frontmatter. What does parseFrontmatter do with it?

Keys that could alter an object's prototype (__proto__, constructor, prototype) are refused. Frontmatter is input, and input must never be able to change how your objects behave. This is prototype pollution, defended by the parser.

 A file starts with --- and a title, but the closing --- is missing. What does parseFrontmatter return?

Only a well-formed block is read. A broken one is not guessed at. The page then has no title from frontmatter, and the loader falls back to the first heading or the file name, or validation reports it.

 What does this print? import { serializeFrontmatter } from "@zudojs/docs"; console.log(serializeFrontmatter({ title: "Refunds", price: "5000", public: "yes" }, "# Refunds\n"));

The serializer quotes a value only when its own parser would read it back differently. "5000" would come back as a number, so it is quoted. yes is not a boolean for this parser, so it is written plainly.

What does this print? import { createDocument, validateDocument } from "@zudojs/docs"; const doc = createDocument({ id: "guides.billing", title: "Billing", content: { type: "markdown", value: "# Billing" }, category: "payments" }); console.log(doc.category); console.log(validateDocument(doc).issues.map((issue) => issue.code));

 Why does the lesson generate the error reference from the @zudojs/errors classes instead of writing it in Markdown?

A hand-written copy of facts that live in code goes stale the first time someone changes the code and forgets the docs. Generating the page removes the copy. The same works for config keys, routes, events and CLI commands.

 Structured content comes from a JSON file that partners can edit.  Why is "fail closed" the right default for visibility?

Compare the costs of the two mistakes. Someone notices a missing page and fixes it. A leaked runbook may already be in search engines and caches. When one direction of error is much worse, the default should avoid it.

 Given that broken links are warnings, what does the lesson's checkDocs do?

The package reports; your project decides the policy. For a public docs site, a dead link is a real defect, so the check fails on every issue. You can also fail only on chosen codes, such as BROKEN_LINK and NAVIGATION_ORPHAN_DOCUMENT.

 A public page links to ../../internal/runbook, which exists. Why does the lesson's check still report it as a broken link?

Validating the "CLIENT" pages as their own set turns "links to an internal page" into "links to a missing page". That is exactly what a reader of the public site would see: a 404.

 What is validateLinks's UNSAFE_LINK check good for, and what is it not?

It reads Markdown link syntax, not every way HTML can end up in a page, and it only reports. Pages written by people outside your team need a real HTML sanitizer at render time; the lint helps your own authors catch mistakes early.

 Which of these links does validateLinks not check against the registry?

Links with a safe scheme such as https: point outside your docs and cannot be checked without the network; links inside code blocks are examples, not links. Relative and bare targets are resolved and looked up.

 Why is the navigation tree kept separate from the documents instead of each page saying where it belongs?

One tree is easy to review and to validate. If order and grouping were spread over dozens of files, a reorder would touch all of them, and nothing would notice two pages claiming the same position.

 validateAll(pages, navigation) reports NAVIGATION_ORPHAN_DOCUMENT. What happened?

Orphans are usually new pages someone forgot to add to the sidebar, as with the "Logging out" page in the lesson. Validate internal pages without a navigation, because they are not meant to be in the public sidebar.

 What does validateExample tell you about a code example?

It checks the shape of the example object. Running examples is a separate job, done by a test suite, which is how every example in this academy is kept correct.

 An example's code contains ```. How does renderExampleMarkdown keep it from closing its own code block?

Markdown closes a fence only with a fence at least as long as the opening one. Choosing a longer fence keeps the example intact without changing a single character of the code.

 The build keeps the runbook out of the public output in three ways. Which one is not among them?

Several independent guards mean one mistake (a missing filter, a wrong option) is not enough to leak a page. Encryption plays no part; internal pages are protected by never being published.

 The docs test "document every status the API sends" compares the generated table with ["400", "401", "403", "404", "409"]. When does it fail?

The page is generated from a list of classes, and that list is still written by a person. The test pins the list to what the API really sends, so adding a TooManyRequestsError without documenting it fails the build.

 Why should links to other websites be checked in a separate, scheduled job rather than in the docs check on every commit?

The per-commit check must be deterministic: same input, same result. External links depend on the outside world, so check them on a schedule, with retries, and open an issue when one stays broken.
