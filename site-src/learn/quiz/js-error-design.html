What does this print? function charge() { throw new Error("gateway timeout"); } function chargeCard() { try { return charge(); } catch { return null; } } const result = chargeCard(); console.log(result?.id ?? "no id", "| status:", result === null ? "confirmed anyway" : "paid");

The catch turned the error into null, an ordinary value. Nothing was thrown, so a caller that does not check the value carries on as if the charge worked. That is swallowing.

 A card is declined for insufficient funds. What kind of failure is that?

Declines are a normal part of payments. The program has a planned path for them. Retrying would fail again and may annoy the bank.

 Code throws TypeError: Cannot read properties of undefined (reading 'total') in the checkout. What should the program do?

A bug means the code's assumptions are wrong, so any recovery code is guessing. Recovering with 0 would charge nothing and confirm the order. Fail loudly and fix it.

 A request to a shipping provider times out. How should it be classified?

The network and other services fail for reasons outside your code. Whether you can recover depends on whether a retry is safe and whether a fallback is acceptable.

 A kindOf(error) helper sees an error that is not one of the app's own classes. What should it return by default?

Unknown errors must be treated as the most serious kind. Showing their message can leak internals; retrying them can repeat damage.

 A function calls something that can throw. Which is not one of the three honest choices?

Logging and returning a default is swallowing: the caller continues on a false assumption. Letting the error pass is the most common correct choice.

 How many log lines does one failure produce? const logs = []; function db() { throw new Error("connection lost"); } function repo() { try { return db(); } catch (e) { logs.push("repo"); throw e; } } function service() { try { return repo(); } catch (e) { logs.push("service"); throw e; } } function handler() { try { return service(); } catch (e) { logs.push("handler"); return 500; } } console.log(handler(), logs.length);

Each layer logged and re-threw, so one failure became three log lines. Log once, where the error is handled (here the handler); the other try/catch blocks add nothing.

 In a layered service, where should an error be logged?

One failure should be one log entry. Intermediate layers add information by translating the error with cause, not by writing extra log lines.

Each wrapper keeps the error below it in cause. Following the links goes from the business-level message down to the root detail.

The wrapper forgot { cause: error }, so the original SyntaxError is gone and nobody can tell what was wrong with the data. Always pass the cause when translating.

 Where is wrapping an error with cause most useful?

A link in the chain should add meaning. Wrapping in every function adds links that repeat the same information.

 A retry loop decides whether to retry. Which check is most robust?

Messages are for people and get reworded. Decisions should read machine-readable facts that the error's designer put there on purpose.

Error.isError checks for a genuine error object (even from another realm), not for something shaped like one. Strings and look-alike objects are not errors.

 A library does throw "insufficient funds". What should your code do where it calls that library?

Code above that point assumes errors have a message and a stack. Normalising at the edge where foreign code is called keeps that assumption true.

 Which situation is the best fit for AggregateError?

AggregateError is for several independent failures reported together. One failure with a history is a cause chain.

 What does this print? const error = new AggregateError( [new Error("TV-99: unknown"), new Error("OIL-1: bad quantity")], "2 cart lines are invalid", ); console.log(error.name, error.errors.length, error.message);

The first argument is the list, stored in .errors; the second is the message. Each inner error keeps its own type and fields.

 A nightly job pays 50 vendors. Two payouts fail. What should the job report?

Independent operations should not stop each other, and a partial success must be recorded so the retry only covers what failed.

 When is it safe to retry "charge ₦23,278.50 for ORD-7" after a timeout?

A timeout does not tell you whether the charge happened. With an idempotency key, the gateway returns the existing charge instead of creating a second one, so the retry is safe.

 Which idempotency key is correct for charging an order?

The key identifies what you are doing, not which attempt. A new key per attempt would make every retry a new charge.

 The card was charged, then saving the order to the database failed. What should the order service do?

Two systems cannot share one transaction, so the program undoes the first step itself. Compensation is cleanup: the request still fails.

A return in finally replaces whatever the try block was doing, including a thrown error. Use finally only for cleanup, never for return.

 What does this print? async function withoutAwait() { try { return Promise.reject(new Error("save failed")); } catch { return "handled inside"; } } async function withAwait() { try { return await Promise.reject(new Error("save failed")); } catch { return "handled inside"; } } withoutAwait().then((v) => console.log("A:", v), (e) => console.log("A rejected:", e.message)); withAwait().then((v) => console.log("B:", v), (e) => console.log("B rejected:", e.message));

Without await, the function returns the promise before it rejects, so the rejection happens outside the try and its own catch never runs: A rejects. return await keeps the rejection inside, so B's catch handles it. B prints first because an async function that returns a promise needs extra microtask steps to adopt that promise's result, while B already had a plain value to return.

 Is an empty catch {} ever acceptable?

An empty catch destroys all evidence of a failure. If ignoring is right, make that decision visible to the next reader and to your monitoring.

 When is returning a result object ({ ok: false, error }) a better design than throwing?

A result object forces the caller to look at the outcome. Throwing fits failures most callers cannot handle and should pass up. The danger is a failure value that looks like success, such as null.

 What is the job of an error boundary in a queue worker?

The unit of work is one job. A bug in job 2 must not stop jobs 3 to 1,000, and it must not disappear either.

 An HTTP boundary catches an error that is not one of the app's own error classes. What should the response contain?

Unexpected errors can reveal file paths, SQL or library versions. Only errors designed for users carry user-facing messages.

 What should a Node service do in its unhandledRejection handler?

An error that escaped every boundary is a bug, and the process may be in an unknown state. The process boundary is a last-resort safety net, not a place to handle errors.

 The payment gateway returns status 200 but no id field. How should the gateway client report it?

Something is wrong with the integration, not with the customer's card. Reporting it as a decline misleads the customer; retrying repeats the problem.

A TypeError can be caught, but catching it does not make the program correct. Fail the unit of work, log it, and fix the code.

A fallback is a business decision that depends on the use. It must be visible in logs or metrics, never silent.
