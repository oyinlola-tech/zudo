What does "make illegal states unrepresentable" mean in practice?

The goal is to move rules from runtime checks that someone must remember into types the compiler checks everywhere. Runtime checks remain for the rules types cannot express.

 Which of these is an invariant of the shop's domain?

An invariant is a rule that must hold for the model at all times. Colours, storage engines and formats are decisions about other layers, not rules of the domain.

 The naive order had status: string, paid: boolean and an optional paymentId. What is the core problem with that design?

A product of independent fields allows every combination. A discriminated union with one interface per state allows exactly the combinations that exist, and ties each piece of data to the state that has it.

 Why does the model have no function that takes a PaidOrder and returns a PaidOrder?

Transitions define the allowed moves. markPaid accepts only a PendingOrder, so a paid order cannot be passed to it, and there is no other way to produce a PaidOrder from a paid one.

 payOrder accepts only a PendingOrder. Why can the same order still be paid twice without a version check?

Types cannot express "this value may be used once" or "this value is outdated". Only the store, which sees every request, can refuse the second write, for example with a version check.

 How does the lesson's VersionedStore refuse the second of two concurrent payments?

Both requests started from version 1 and produced version 2. The first save moves the store to version 2; the second finds 2 where it expected 1 and is refused as stale. This is optimistic concurrency control.

 What is the database equivalent of the version check?

Putting the expected version in the WHERE clause makes the check and the write one atomic statement. Reading first and comparing in code leaves a gap in which another request can write.

 Which type makes [] a compile error for an order's lines?

A tuple with one required element followed by a rest element needs at least one item. TypeScript reports "Source has 0 element(s) but target requires 1".

 Why does an OrderLine store unitPrice instead of looking the price up from the product when needed?

Choosing between copying data (a snapshot) and referring to it is a domain decision. Prices on past orders are facts about that moment and must not change with the catalogue.

 Why does newOrder compute total itself instead of taking it as a parameter?

Derived data that is supplied separately can drift from the data it derives from. Computing it in the only constructor removes the possibility.

 Which rule about refunds does the type of applyRefund(payment: CapturedPayment, …) enforce?

The parameter type encodes the state. The amount rule compares two runtime numbers and is a Result; the permission comes from the use case's permit parameter.

 Why does applyRefund return CapturedPayment | RefundedPayment rather than always a CapturedPayment?

The caller must narrow the result before refunding again. A fully refunded payment then cannot be passed to another refund, which is exactly the rule.

 What stops code outside users.ts from creating a Permit<"payment:refund"> without calling authorize?

An object literal with by and permission is still missing [permitBrand], and nobody outside the module can name that key. A cast could still forge one, which is why casts outside constructors deserve review.

 Why is Permit<"order:pay"> not accepted where Permit<"payment:refund"> is expected?

Parameterising the permit by its permission turns "authorized for something" into "authorized for this". A permit for one operation cannot be reused for another.

 Ada has the order:pay permission. Why does payOrder still compare permit.by with order.customer?

Role-based permissions answer "may this kind of user do this kind of thing?". Resource rules like ownership depend on the specific record and stay runtime checks inside the use case.

 Why do the use cases return their events instead of publishing them directly?

A pure use case returns everything that happened: new states, events and ledger transactions. The shell saves and publishes them, ideally in the same database transaction.

 Why is "debits equal credits" enforced by the transaction() smart constructor and not by a type?

Types can say "a non-empty list of entries", but not "whose amounts sum to zero". A constructor checks the sums once and brands the result, so every function that accepts a Transaction can trust it.

 Why does transaction() throw on unbalanced entries instead of returning a Result?

Expected failures caused by users belong in the return type; programming errors should fail loudly. A ledger that does not balance means the code is wrong.

 Which tool fits the rule "this payment belongs to this order"?

The rule relates two values that exist only at runtime. Types can require a captured payment and a pending order; whether they belong together must be compared.

 What does a database CHECK constraint such as "status = 'paid' implies payment_id IS NOT NULL" add to the model?

Types protect only code that is type-checked with your model. The database is shared, so mirroring the union's rules there keeps illegal rows out regardless of who writes them.

 A repository reads a row with status = 'paid' and payment_id = NULL. What should it do?

The repository is a boundary, like a request handler. It parses rows into the precise union and refuses rows that no state allows, so corrupt data is noticed where it enters the program.

 Why keep API response types (DTOs) separate from the domain types?

If the response type is the domain type, every internal change (a new state, a renamed field) breaks clients. A mapper at the edge absorbs those changes.

 Where does illegal-state modelling pay off least?

The technique costs types, constructors and transitions. It pays for itself where mistakes cost money or trust, not for simple settings with no rules.

 A type test reads // @ts-expect-error above refundPayment(payPermit, failedPayment, …). Why is it a weak test?

The directive only checks that some error occurs. Keep exactly one mistake per expected error, so the test fails when that one rule is lost.

 The use cases never read the clock; at timestamps are passed in. Why?

The clock is a hidden input. Passing time in (from the shell) is the functional core, imperative shell idea applied to a whole domain.
