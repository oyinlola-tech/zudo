A payment SDK takes your callback and, because of a bug, calls it twice. What is the name for the underlying problem with callbacks that this shows?

Passing a callback hands control of your code to the library. It can call you twice, never, or at odd times. Callback hell is the nesting problem, which is real but shallower. A promise gives control back: you get an object and decide what to do with its single result.

 What does this print? const charge = new Promise((resolve, reject) => { resolve("ch_1"); resolve("ch_2"); reject(new Error("declined")); }); charge.then( (id) => console.log("paid", id), (error) => console.log("failed", error.message), );

A promise settles at most once. The first resolve("ch_1") fulfils it; the later resolve and reject calls are ignored.

 The promise is already fulfilled when then is called. What does this print? const price = Promise.resolve(2500); console.log("A"); price.then((p) => console.log("B", p)); console.log("C");

Handlers always run later, after the current synchronous code, even when the promise is already settled. That guarantee is what stops the "sometimes synchronous, sometimes not" bug that callbacks allow.

 A promise was fulfilled a minute ago. Now some code calls .then(handler) on it. What happens?

A settled promise keeps its result. Handlers attached late still receive it, which is different from an event that fires once and is gone.

 What does this print? console.log(1); const order = new Promise((resolve) => { console.log(2); resolve("ok"); console.log(3); }); order.then(() => console.log(4)); console.log(5);

The executor runs synchronously during new Promise, and calling resolve does not stop it, so 3 prints too. Only the then handler waits until the synchronous code (5) is done.

 Promise order was created with new Promise((resolve) => resolve(payment)), where payment is still pending. Which statement is true?

Resolving with a promise (or thenable) makes your promise follow it: this is adoption. Its fate is decided, so it is resolved, but it stays pending until payment settles, and it can still end up rejected.

 What does this print? const payment = Promise.reject(new Error("card declined")); const order = new Promise((resolve, reject) => { resolve(payment); reject(new Error("cancelled")); }); order.then( () => console.log("paid"), (error) => console.log("failed:", error.message), );

resolve(payment) locks order to payment, so the following reject is ignored. payment is rejected, and order copies that. "Resolved" does not mean "succeeded".

 What happens when the executor function passed to new Promise throws an error before calling resolve?

A throw during the executor becomes a rejection. That is why a promisify wrapper calls the SDK inside the executor: a synchronous throw from the SDK then arrives as a rejection like every other failure. A throw in a callback that runs later, such as a timer, is not covered.

 What does this print? const a = Promise.resolve(1); const b = a.then((n) => n + 1); console.log(a === b); b.then((n) => console.log(n)); a.then((n) => console.log(n));

then never changes the promise it is called on. It returns a new promise, b, fulfilled with the handler's return value. a still holds 1. Handlers run in the order their promises were ready: b's value was already waiting, but it only became fulfilled after a's handler ran, which happened before the last a.then was attached.

 What does this print? Promise.resolve({ id: 7, total: 12000 }) .then((order) => { order.total * 1.075; }) .then((withVat) => console.log(withVat));

The handler has braces and no return, so it returns undefined, and the promise from then is fulfilled with undefined. Either drop the braces or write return.

 What does this print? const wait = (ms, value) => new Promise((resolve) => setTimeout(() => resolve(value), ms)); Promise.resolve("order 7") .then((order) => wait(20, `${order} reserved`)) .then((value) => console.log(typeof value, value));

Returning a promise from a handler makes the promise from then follow it. The next handler receives the final value, 20 ms later, never the promise itself. This is what lets chains stay flat.

 Inside a then handler, code calls saveOrder(order), which returns a promise, but does not return it. What goes wrong?

The chain only knows about what the handler returns. A promise started and not returned is a floating promise: nobody waits for it and nobody handles its errors. Return it, or await it.

 What does this print? Promise.reject(new Error("out of stock")) .then(() => console.log("A")) .then(() => console.log("B")) .catch((error) => console.log("C", error.message)) .then(() => console.log("D"));

A rejection skips every step without a rejection handler (A, B). The catch handles it and returns undefined, which fulfils the chain again, so D runs.

 Why is .catch((error) => console.log(error)) in the middle of a checkout chain usually a bug?

A rejection handler's outcome follows the same rules as then: returning (even implicitly) fulfils the chain. If it cannot fix the problem, it must rethrow after logging.

 What does this print? Promise.reject(new Error("timeout")) .catch((error) => { throw new Error("rates unavailable", { cause: error }); }) .then(() => console.log("rates loaded")) .catch((error) => console.log(error.message, "/", error.cause.message));

Throwing inside a catch keeps the chain rejected, now with the new error. The { cause } option keeps the original error attached, so the last handler can see both.

The second argument of then only handles a rejection of the promise before it. An error thrown by the first argument, in the same step, rejects the next promise, which the catch on the next line handles.

finally ignores its handler's return value and passes the original result through. Only a throw (or a rejected promise) in the handler changes the outcome.

 A payment promise is fulfilled. Its .finally handler throws new Error("could not release lock"). What does the promise returned by finally do?

finally passes the result through unless its own handler fails. Then the cleanup error replaces the result, just like an exception thrown in a finally block of try/catch.

 What argument does a .finally handler receive?

finally is for cleanup that must happen either way, so it gets no argument. If you need the value or the error, use then or catch.

 What does this print? async function getTotal() { return 12000; } const result = getTotal(); console.log(result instanceof Promise); console.log(await result);

An async function always returns a new promise. Returning a plain value fulfils it with that value.

 What does this print? const charge = () => Promise.reject(new Error("card declined")); async function payA() { try { return charge(); } catch { return "handled in payA"; } } async function payB() { try { return await charge(); } catch { return "handled in payB"; } } console.log(await payA().catch((error) => `payA rejected: ${error.message}`)); console.log(await payB());

return charge() hands the promise out of the function before it rejects, so the try block is already finished and its catch never runs. return await waits inside the try, so the rejection is thrown there and caught.

 What makes a value a thenable?

Only a callable then counts. await, Promise.resolve and resolve() call it with a resolve and a reject function. { then: "tomorrow" } is just an object.

 What does this print? const lazyTotal = { then(resolve) { console.log("computing"); resolve(3 * 4000); }, }; console.log("before"); const total = await lazyTotal; console.log(total);

Nothing runs when the object is created. await sees a then method, calls it, and continues with the value passed to resolve. Query builders use exactly this to run a query only when it is awaited.

 An async function returns { task: "Call supplier", then(next) { this.next = next; } }. The caller awaits it. What happens?

Any object with a callable then is adopted. Its then stores the resolve function instead of calling it, so the promise stays pending forever, with no error. Do not name a method then unless you mean it.

 What does this print? const reminder = { task: "Call supplier", then: "tomorrow" }; const loaded = await Promise.resolve(reminder); console.log(loaded.then);

A then property that is not a function does not make a thenable, so the object itself becomes the value.

The executor catches a synchronous throw and rejects the promise. Callers of the wrapper then only need await + try/catch (or .catch), never a second try around the call itself.

 What is wrong with return new Promise((resolve) => { chargeCard().then(resolve); });?

Wrapping an existing promise in new Promise adds nothing and loses errors, because nobody calls reject. Just return chargeCard(), or return chargeCard().then(transform).

 When does a rejected promise count as unhandled?

JavaScript gives you until the end of the current task and its microtasks to attach a handler. A handler attached later, such as in a setTimeout, comes too late: the rejection has already been reported, and Node.js crashes by default.

 This runs in Node.js. What does it print? process.on("unhandledRejection", (reason) => console.log("unhandled:", reason.message)); const refund = Promise.reject(new Error("refund failed")); refund.catch((error) => console.log("handled:", error.message));

The catch is attached in the same synchronous block that created the rejected promise, so it is handled in time and the unhandledRejection event never fires.

 What does Node.js do by default when a promise rejection is unhandled?

Since Node.js 15 the default mode is throw: an unhandled rejection crashes the process like an uncaught exception, because an error nobody saw may have left work half done.

 In Node.js, which is the best way to read a file with await?

Node ships promise versions of its APIs (node:fs/promises, node:timers/promises). Use util.promisify or your own wrapper only for callback APIs that have no promise version. Wrapping the sync version still blocks the thread.
