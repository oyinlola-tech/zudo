Which statement about JavaScript on one thread is right?

Concurrency is many jobs in progress; parallelism is many executing at once. Your callbacks run one at a time, but while one request waits on the network, others can be started. Parallel JavaScript needs worker threads.

 Resizing 200 product photos is pure computation. Why does running the resizes with Promise.all not make it faster?

Async concurrency overlaps waiting. Computation still needs the thread. To use several cores, move the work to worker threads.

 Which is not a reason to limit how many jobs run at once?

JavaScript can start as many promises as you like. The limits come from the other side (connections, rate limits) and from your own resources (memory).

 Why does a pool with limit 5 usually finish sooner than batches of 5?

Both respect the limit. The pool keeps all slots busy; batches leave slots idle while the slowest job of each batch finishes.

 In the pool, two workers finish at the same moment and both run const index = next++. Can they get the same index?

Two callbacks never run at the same instant on one thread. Races in JavaScript happen across awaits, not inside synchronous lines.

 What would a pool with limit = 0 do if it did not check its limit?

With no workers, Promise.all([]) resolves at once and no job ever runs: a silent failure. That is why the pool rejects a limit below 1 with its own RangeError.

 In the lesson's pool, job 3 fails while job 4 is running. What happens?

The failed flag stops workers from taking new items. Job 4 cannot be stopped without cancellation, so it runs to the end; its result is ignored.

 When do you need a limiter (like p-limit) rather than mapWithLimit?

A limiter queues each job as it arrives and starts it when a slot is free. mapWithLimit needs the whole list at the start.

 Why are cancellation's two roles split into AbortController and AbortSignal?

Passing only the signal down means a called function cannot cancel work that belongs to its caller.

 What does this print? const controller = new AbortController(); controller.signal.addEventListener("abort", () => console.log("abort event")); console.log(controller.signal.aborted); controller.abort(new Error("customer left")); controller.abort(new Error("second call")); console.log(controller.signal.aborted, controller.signal.reason.message);

 Why should code check error.name === "AbortError" rather than the error's message?

Node says "This operation was aborted", browsers say something else. The name (AbortError, TimeoutError) is the portable way to recognise the kind of error.

 A cancellable sleep(ms, { signal }) finishes normally. Which clean-up step must it still do?

A listener added with addEventListener stays until it fires or is removed. { once: true } only removes it after it fires. A signal that lives for a whole campaign would collect thousands of listeners.

It is a ready-made signal; pass it to fetch or any function that accepts a signal. Its reason's name is "TimeoutError", so you can tell a timeout from a user cancel.

 A request handler aborts its database query when the client disconnects. What else should happen for cancellation to be complete?

Cancellation that stops at the first layer only hides the waste: the calls further down keep running. Pass the signal all the way down.

 What is a race condition?

In async JavaScript, operations overlap across awaits. If the outcome changes with which one finishes first, that is a race condition.

 Earlier searches are slower. What does this print? const wait = (ms, value) => new Promise((resolve) => setTimeout(() => resolve(value), ms)); const search = (query) => wait(query === "ric" ? 40 : 10, `results for ${query}`); let shown = ""; async function onType(query) { shown = await search(query); } onType("ric"); setTimeout(() => onType("rice 5kg"), 5); setTimeout(() => console.log(shown), 80);

 Which fix for stale search results also saves work on the server?

Ignoring stale answers fixes the display. Aborting also closes the old request, so neither side keeps working on it. Combine both, because some APIs cannot be cancelled.

 A wallet service runs on four server processes. Why is an in-process mutex not enough to stop double withdrawals?

An in-process lock only coordinates code in one process. Shared state in a database needs the database's guarantees, or a distributed lock.

 A price is cached for a minute. When the cache expires, 200 requests arrive at once and all query the database. What is this, and what is the fix?

Request coalescing ("single flight") lets the first caller start the lookup and makes later callers await the same promise, so 200 requests cause one query.

 What does this print? let queries = 0; const inFlight = new Map(); function getStock(sku) { if (!inFlight.has(sku)) { const p = new Promise((resolve) => setTimeout(() => { queries++; resolve(12); }, 10)) .finally(() => inFlight.delete(sku)); inFlight.set(sku, p); } return inFlight.get(sku); } await Promise.all([getStock("rice"), getStock("rice"), getStock("oil")]); await getStock("rice"); console.log(queries);

The first two rice calls share one query; oil has its own: 2. After they finish, finally removes the entries, so the last rice call starts a new query: 3.

 Why does the coalescing map delete its entry in finally, not only after success?

If a failed promise stayed in the map, every later caller would receive that same failure. Removing it either way makes the map hold only lookups that are still in progress.

 How can a test make a stale-response bug happen every time instead of occasionally?

When the test controls when each fake request completes, the problematic order is forced deterministically, and the fix can be proven.

 Should a cancelled search be logged as an error?

Logging normal cancellations as errors floods the logs and hides real failures. Check signal.aborted or the error's name first.
