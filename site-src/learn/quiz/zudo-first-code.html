Your code has a NewTask interface. Why is that not enough to check a request body?

TypeScript types disappear when the code is compiled. A request body arrives while the program runs, so you need a check that exists at runtime: a schema.

 Why is it npm install @zudojs/schema @zudojs/errors, with no -D?

-D is for tools you only need while developing, like tsc or tsx. Schema and errors run inside your program, so they are normal dependencies.

 You asked npm for two packages, and it added four. Why?

A package's own dependencies are installed with it. @zudojs/schema builds on a couple of smaller ZudoJS packages, so npm adds those for you.

 What is a schema?

A schema is a value in your program, not just a type. It can check any real value while the program runs, and it can also give you the type through Infer.

 What does type NewTask = Infer<typeof NewTaskSchema> give you?

You describe the data once. The schema checks it at runtime, and Infer produces the matching compile-time type. Change the schema and the type changes with it.

 The title rule is schema.string().trim().min(3).max(100). Why does the title " " fail?

The steps run in order. After trimming, " " is an empty string, so .min(3) refuses it. Without .trim(), three spaces would pass as a title.

 What does done: schema.default(schema.boolean(), false) mean?

A default fills in a missing field. A value that is present must still pass the check: "sometimes" is refused, because it is not a boolean.

 What does NewTaskSchema.parse(value) return when the value is good?

parse gives back new, clean data. That is why you use its result, not the original input. { success, data } is what safeParse returns.

 Inside an API, where bad data means "stop here", which method is the usual choice?

parse stops the work at once with a SchemaError, which is already a 400. A type assertion checks nothing at runtime, so it would let bad data through.

 When should you use safeParse instead of parse?

safeParse never throws. It returns { success: false, issues }, and you decide what to do with each issue.

 Each issue has a path, a code and a message. Which one should your code check to decide what went wrong?

The message is written for people and may change. The code is a stable word for programs. The path tells you where, not what kind of problem.

 In TypeScript, after if (!result.success) { … }, what does TypeScript know?

safeParse returns a discriminated union, like the Result type from Generics. Checking success narrows it: issues when false, data when true.

 A client tries to create a task with a title that already exists. Which error should the service throw?

The input is well-formed, but it clashes with what already exists: that is a 409 Conflict. A 400 is for data that breaks the schema, and a 404 is for something missing.

 Why does TaskService.create take input: unknown instead of input: NewTask?

The input may come straight from a request body. Typing it unknown forces the service to check it before use; parse then gives back a real NewTask.

 In respond, what does error.expose tell you?

Errors like NotFoundError have messages written for clients. When expose is false, the message may hold internal details, so it must not be sent.

 An unexpected error (say, a bug that throws a TypeError) reaches respond. What is the safe answer?

You never send internal details, such as a stack trace or a database message, to the outside world. The client gets "Something went wrong"; your logs keep the rest.

 The service throws errors. Where are they turned into a status code and a JSON body?

The service only throws the right error. One place at the edge maps every error to a status and body, so the rules never mix with HTTP.
