After tsc removes the types, what does const task = raw as Task; become?

A type assertion is erased completely: no check, no conversion. That is type erasure. as only changes what the compiler believes about the value.

 Which part of function label(task: Task, status: Status = "todo"): string is still there when Node.js runs the code?

A default value is plain JavaScript, so it stays: the compiled line is function label(task, status = "todo"). Annotations, interfaces and type aliases are removed.

 Which of these still does something when the program runs?

typeof, in, instanceof, Array.isArray, #private and Object.freeze are real JavaScript. readonly, as, private and import type exist only at compile time.

 Task is an interface. What does tsc say about return value instanceof Task;?

An interface does not exist at runtime, so there is nothing to compare with (TS2693). instanceof works with classes, because a class is also a real JavaScript value. For an interface, check its parts with typeof, in and Array.isArray.

 Why does const task: Task = JSON.parse(requestBody); compile even when the body is {"title": 42}?

The JSON arrives while the program runs; the compiler never saw it. any switches checking off, so the type annotation is a promise nobody checks. Type the result as unknown and validate it.

 Which of these values was never seen by the compiler, and must be checked at runtime?

Request bodies, query strings, environment variables, files, database rows and other APIs all arrive as text while the program runs, possibly from an attacker. Values you create in your own code are followed by the compiler.

 What does the type assertion body as NewTask do?

as means "trust me". It compiles to nothing, so a wrong value stays wrong and fails later. On outside data, as is never a check.

 Which use of as is always safe?

as const makes a type narrower (readonly literal types), not different, so it cannot lie. The others claim outside data or a string is something it is not. (Type assertions compares the safer tools.)

 What does the ! in users.get(id)!.email do?

Like as and any, ! switches the compiler off for one spot. If the user is missing, the program crashes when reading .email. Prefer a real check (the non-null assertion).

 What does the return type value is NewTask tell TypeScript?

This is a type predicate, from Narrowing. The function returns a boolean, and inside if (isNewTask(body)) TypeScript narrows body to NewTask.

 A type guard declares value is User but its body only checks that email exists. What does tsc do?

TypeScript does not compare a guard's body with its value is T promise. Guards are the one place where a type can lie, so keep them short and write tests for them.

 When should you use an assertion function (asserts value is T) instead of a type guard (value is T)?

A type guard returns a boolean and you write the if. An assertion function throws on bad data; when it returns normally, the value has the checked type on every following line (Narrowing covers both).

 With strict on, why is console.log(error.message) inside catch (error) an error?

throw "a plain string" is legal, and a string has no message. So error is unknown (TS18046). Check it with error instanceof Error first, as in Special types. Never write catch (error: any): it only hides the question.

 A client sends {"title": "Fix bug", "id": 999, "role": "admin"} to create a task. What is the safe way to build the new task?

Allow-list the fields. Spreading or asserting keeps whatever the client added, which is the mass assignment hole. Deleting known-bad fields misses the next one someone invents.

 Where should raw request data be validated?

Validate once at the boundary. Inner functions like createTask(input: NewTask) take only checked types, so the compiler guarantees they never see unchecked data and never need to check again.

 The create-task handler answers three cases. Which set of status codes does the lesson use?

Text that is not JSON at all is a bad request (400). Valid JSON with wrong fields is 422 with the list of issues. A new task is 201 Created.

 What type does process.env.PORT have?

Environment variables are always strings, or missing. That is why readPort takes string | undefined and converts and checks the value itself.

 In parseNewTask, the last if repeats typeof done !== "boolean" even though issues already records it. Why?

Narrowing follows the checks the compiler can see. An empty issues array says nothing about the type of done, so without the repeated check, done would still be unknown in the returned object.

 What is the main risk of a hand-written validator next to a separate NewTask interface?

The type and the check are written twice and can drift apart. @zudojs/schema describes the shape once and gives you the type with Infer, so they can never disagree.
