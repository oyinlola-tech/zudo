Binary-search debugging (including git bisect) needs one property of the history. Which?

Binary search throws away half the suspects on each check, which is only valid when "bad" does not come and go. A flaky check or a bug that appears and disappears breaks that, so make the check reliable first.

 About how many times does git bisect run execute your test on a history of 1,000 commits between good and bad?

Each run halves the range: 1000 → 500 → 250 → … → 1 takes about log₂ 1000 ≈ 10 steps. A million commits would take about 20.

 During git bisect run, what does it mean when your check script exits with code 125?

Exit 0 is good and 1 to 127 is bad, except 125, which tells bisect to skip the commit. Use it for commits that do not build or start for unrelated reasons.

 Why should the check script for git bisect run be untracked (or outside the repository)?

You want the same check at every commit. Old commits may predate the script or contain an older version of it.

 What does git bisect reset do?

During bisect, your folder holds whichever old commit was being tested. reset returns you to where you were; it changes nothing in the history.

 On some old commits your check crashes with "Cannot find module './invoice.js'" because the file had another name back then. What happens if the script exits 1 there?

Bisect only sees the exit code. A check must fail only for the bug it tests; for "cannot test this commit", exit 125 so it is skipped.

 Before starting bisect, why run the check on the commit you plan to mark good?

"It worked last week" is a memory, not evidence. Bisect trusts your good and bad markers completely, so verify them.

 In a five-whys analysis, which answer to "Why did the refactor remove the cancelled check?" leads to a useful action?

Blaming a person is a dead end: the next person in the same situation would make the same mistake. The useful answer names something in the situation you can change: give the rule a name and a test.

 When should you stop asking "why?"

"Because floating point is inexact" is true but not actionable; "because we store money as naira floats" is. Five is a guideline, not a rule.

 For the invoice bug, which action works at the level of the root cause rather than the symptom or the direct cause?

Reissuing fixes the symptom; restoring the check fixes this bug; the checklist stops the same kind of bug for other rules. A good analysis produces actions at all three levels.

 Why does items.slice(start, start + pageSize - 1) lose an item on every page?

Mixing an inclusive end (how people count) with an exclusive one (how slice works) is the classic off-by-one. The end for slice is simply start + pageSize.

Four full pages and one partial page make 5. floor gives 4 and hides the last three orders; round happens to work for 23 but fails for 21 (it gives 4).

 What makes the pagination verification in the lesson stronger than three hand-picked test cases?

A property checked over many generated inputs covers boundaries you might not think of: empty lists, exact multiples, one item. This is property-based testing.

 Why did the lost-update deposit bug never show up on the developer's laptop?

The race window is the time between reading and writing the balance. Network latency in production makes it wide; locally it is tiny. Reproduce races by controlling the timing, as the lesson's fake database does.

 A race condition disappears as soon as you add console.log calls. What is this called, and what is the better approach?

Logging takes time and shifts when things run. A reproduction that fixes the timing (deliberate delays, a controlled order) shows the bug every time, with or without logs.

An in-memory lock only serialises deposits inside one process. The database is the one place all processes share, and a single atomic statement cannot be interleaved.

Verification should try hard to break the fix. Races are about probability, so test under more pressure than the original report.

The message says the thing before .sent was undefined, and that thing is this. In class code (strict mode), a detached method called as a plain function gets this === undefined.

Arrow functions capture this from where they are created, so a class-field arrow is created per instance. For a few objects that does not matter; for millions it costs memory.

To measure a bug across 100,000 inputs you need an oracle you trust. Exact integer arithmetic has no rounding errors to hide behind.

Module-level objects are created once per process. State that leaks into them persists until the process restarts, which makes such bugs look intermittent.

Cloning fixes today's code. Freezing guards against the whole class of bug: a mutation of the shared object now fails loudly where it happens.

The moment is the same; the local calendar date differs by time zone. Decide which zone a business day belongs to, and compute in it explicitly.

A clean environment has no leftover files, local settings or cached data. If the tests pass there, you know they do not depend on your machine.
