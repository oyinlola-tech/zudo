In the opening example, why did adding "opay" to the Provider union not produce a compile error in feeKobo?

A default that returns a real value answers silently for kinds it has never heard of. Either end with an exhaustive check (provider satisfies never) or put the behaviour in an object that must implement every method.

 What is the main purpose of encapsulation?

An invariant, such as "the balance is never negative" or "balance equals the ledger", can only be guaranteed if nothing outside the object can change the state around the methods that enforce it.

 A getter returns the object's internal array typed as readonly LedgerEntry[]. What can still go wrong?

The type stops typed callers, but the value is the object's own array. Return a copy, or a frozen copy, so the object stays the only owner of its state.

 Which kind of private field is also enforced at runtime?

private is a compile-time check that is erased. # fields are a JavaScript feature: code outside the class cannot read them at all, even with a cast.

 The checkout needs payment providers. Whose view should the PaymentProvider interface be written from?

An interface written for the caller stays stable when providers change, and every provider can implement it honestly. An interface copied from one SDK forces every other provider to pretend to be that one.

 Bank transfers cannot be refunded automatically. What is the best way to model refunds?

Small interfaces that each mean something (interface segregation) keep implementers honest. Callers that need refunds ask for PaymentProvider & Refunds or check with canRefund, and the compiler stops code that assumes every provider can refund.

 An object literal { name, charge, feeKobo } with the right types is assigned to a PaymentProvider variable. Does it need implements or a class?

Structural typing: anything with the right members is a PaymentProvider. implements adds no code; it moves the check to where the class is declared.

 class Money { readonly #checked = true; constructor(readonly kobo: number) {} }. Why does payout({ kobo: 0.5 }) fail when payout expects a Money?

Private members make a class behave nominally. That guarantees every Money went through the constructor, where it can be validated. The compiler knows nothing about the value 0.5.

 A base class implements feeKobo using this.percent() and this.capKobo(), which subclasses supply. What is this pattern called?

The base class fixes the algorithm (percentage with a cap) and subclasses fill in the steps. It is the most defensible use of inheritance, and still couples every subclass to the base class's algorithm.

 What does the override keyword add?

Without it, a renamed parent method turns the child's method into an unrelated new method that nobody calls. override is erased from the output; it only adds the check.

 What does noImplicitOverride in tsconfig.json enforce?

It makes every override visible in the code, so readers know a method replaces inherited behaviour, and a rename in the parent is always caught.

 SavingsWallet extends Wallet overrides withdraw to throw for amounts over ₦50,000. It compiles. What principle does it break?

The override's types match, so the compiler is satisfied. The behaviour does not: a subclass must accept at least what the parent accepts and keep its guarantees. Only tests, such as contract tests, can check that.

 Which is a sound way to support withdrawal limits?

If callers must respect a limit, the abstraction must tell them about it. Otherwise the subclass is not really a Wallet and should not claim to be one.

 What makes await provider.charge(amount, email) polymorphic?

Polymorphism means one piece of code works with many kinds of object. With interfaces it needs no inheritance: Paystack's class and the bank-transfer object literal both work.

 withRetry(channel) returns a new NotificationChannel that calls channel.send up to N times. Why is this better than a RetryingSmsChannel extends SmsChannel class?

Wrapping objects that share an interface (the decorator pattern) combines freely: withFallback(withRetry(sms, 2), email). With inheritance, SmsWithRetry, EmailWithRetry, SmsWithRetryAndFallback… multiply.

 In dependency inversion, which module owns the PaymentProvider interface?

The abstraction belongs to the code with the business rules. Adapters import it and implement it, so imports point toward the checkout, and a change in a provider's API only changes its adapter.

 Which file should import the concrete PaystackAdapter class?

If only one place knows concrete classes, swapping a provider or using a fake in tests changes only that place. A DI container automates this wiring; it does not change the direction of the imports.

 A class implements PaymentProvider and its charge method returns { reference, status: "success" } without a return type annotation. Why does it fail the implements check?

implements checks the finished class; it does not guide inference inside it. Annotate the method's return type (Promise<ChargeResult>) so the literal is checked against the union.

 The payment succeeds, then sending the SMS receipt fails. What should the checkout do?

The money has moved; that fact must not be lost or undone because a secondary step failed. Retrying the whole payment could charge the customer twice.

 What is a contract test?

The compiler checks that implementations have the right types; a contract test checks they keep the interface's promises (fees never negative, references never empty). It is the Liskov principle turned into a test.

 Which change is cheaper in the functional design (a discriminated union plus functions) than in the object-oriented one?

A new operation is one new function with one switch. In the class design, every class must gain the method. For a new kind, it is the other way round. That trade-off is the expression problem.

 Other teams must be able to add notification channels without editing your module. Which design fits?

An interface is an open set: anyone can implement it without touching your code. A union is a closed set that only its owner can extend.

 Which part of a shop is usually the better fit for plain data and functions?

Closed sets of data that travel across boundaries serialize cleanly and grow by operations: a union with functions fits. Stateful adapters to the outside world fit objects behind interfaces.
