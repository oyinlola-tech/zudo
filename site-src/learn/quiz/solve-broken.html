Which of these is a logic error?

A logic error is valid code that runs to the end and produces the wrong answer. There is no error message to read, so you find it by predicting and tracing.

 You traced a loop and compared each row with your prediction. Rows 1 to 4 match, rows 5 and 6 do not. Where do you look first?

Once a value goes wrong, everything computed from it goes wrong too. Row 6 may only be wrong because row 5 was. The first disagreement is closest to the cause.

 A report is wrong for a shop with 12,000 orders. Why is it worth finding a list of 3 or 4 orders that shows the same bug?

A trace table of 12,000 rows is useless. With the smallest input that still shows the bug, every step fits on paper and the first wrong step is easy to spot.

 Why is "change things until the output looks right" a poor way to fix a logic error?

Changing === to >= made the invoice example "work" by luck, while other amounts still failed. A fix should come from an explanation of the cause, proven by a test that failed before.

 A loop is for (let i = 0; i <= list.length; i++) and adds up list[i]. What goes wrong?

Positions run from 0 to length − 1. With <= the loop makes one extra step past the end, and number + undefined is NaN.

 A hotel serves breakfast every day from the 3rd to the 7th of the month, both days included. How many breakfasts?

7 − 3 = 4 counts the gaps between days, not the days. With both ends included you need one more: 7 − 3 + 1 = 5. This is the fencepost error.

 A 30-metre fence has a post every 3 metres, including one at each end. How many posts?

There are 30 / 3 = 10 gaps, and one more post than gaps because both ends have a post. Counting gaps when you meant items (or the reverse) is the classic off-by-one.

 Which return in this function can never run? function shippingFee(weightKg) { if (weightKg > 1) return 1500; if (weightKg > 10) return 5000; if (weightKg > 0) return 800; return 0; }

The second line is only reached when the weight is 1 kg or less, and none of those weights is over 10 kg. Ask "which inputs reach this line?" for each line; an empty answer means dead code.

 A function has several overlapping checks like total >= 5000000 and total >= 1000000, each returning straight away. In what order should they go?

Every total over ₦50,000 is also over ₦10,000. If the broader check comes first, it catches everything and the specific rule is unreachable.

 Why does this crash for canCheckout(null), even though it checks for null? function canCheckout(user) { if (user.banned) return "no: banned"; if (user === null) return "no: please log in"; return "yes"; }

A check that makes a later line safe must come before that line. Reading a property of null throws a TypeError, so the protecting check never gets a chance.

 In a recursive function, what is the base case?

Recursion solves a problem through a smaller version of itself. The base case is the smallest version, answered directly. Without one that every input reaches, the calls never stop.

 What does "RangeError: Maximum call stack size exceeded" usually tell you?

Each call waits for the inner one, and waiting calls pile up. When there are too many, JavaScript stops the program. Look for a missing or unreachable base case.

 function sumTo(n) { if (n === 0) return 0; return n + sumTo(n - 1); } works for 5. Which call never stops?

2.5, 1.5, 0.5, −0.5, … skips over 0, so n === 0 is never true. A base case of n <= 0 is reachable from every number.

 Why does the fixed founder function keep a visited set of users?

With a cycle the chain never reaches null. Remembering who has been visited gives the function another way out: if a user comes round again, report the broken data instead of looping forever.

 Removing cancelled orders with splice inside a forward loop leaves one behind "only sometimes". When?

After a removal, the next order slides into the position the loop just checked, and the loop moves on. The skipped order only matters when it is also cancelled, which happens when two are adjacent.

 What is the simplest reliable fix for removing items from a list while looping over it?

If the list you are walking through never changes, the loop and the list cannot disagree. (Walking backwards also works when you must change the list in place; i++ after a removal would make things worse.)

 An invoice check paid === due fails because 1.1 + 2.2 is 3.3000000000000003. Why is changing it to paid >= due not a real fix?

0.7 + 0.1 is 0.7999999999999999, which is less than 0.8. The error's direction depends on the numbers, so >= only works by luck. Store whole kobo instead.

 What removes the root cause of wrong comparisons on money amounts?

Whole numbers are stored exactly, so sums of kobo are exact and === works. Decimals are converted only for display.

 A cart function writes total = item.price * item.quantity instead of adding to the total. Which test would not catch this?

With one item, replacing and adding give the same answer. You need at least two items to see that earlier items are thrown away, which is why "one item" and "several items" are separate edge cases.

 How do you know you have really found and fixed a bug?

The failing test proves your explanation matches the program's behaviour, and it keeps the bug from coming back unnoticed. If you cannot make a test fail before your fix, you have not found the bug yet.

 A total prints as NaN. Which suspect should you check first?

NaN is what arithmetic produces from undefined or non-numeric text, and it spreads to every later result. Loop bounds and starting values are the usual culprits.
