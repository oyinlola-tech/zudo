What does it mean that TypeScript is a "superset" of JavaScript?

"Superset" is about syntax. let balance = 5000; balance = "empty"; is valid JavaScript and valid TypeScript syntax, but it fails the type check. Programs still run as JavaScript; TypeScript never has its own engine.

 Why is TypeScript's checking called static?

Static analysis reads the source text and works out types for every expression. Dynamic checks, like JavaScript's TypeError, only happen on lines that actually run.

 A project runs its server with node src/server.ts in production and tsx src/server.ts in development. Which step in this setup finds type errors?

Node's type stripping and tsx both remove types and run the rest. Neither asks whether the types are right. Without a tsc --noEmit step, a type error can reach production.

 You run npx tsc --noEmit false --outDir dist on a project with one type error, and no other settings. What happens?

Checking and emitting are independent. By default tsc writes the JavaScript anyway and signals it with exit code 2. Turn on noEmitOnError to stop it writing anything while there are errors.

 Your CI runs npm run check && npm test, where check is tsc --noEmit. There is a type error. What happens to the tests?

tsc --noEmit exits with 1 when it finds errors. a && b runs b only when a exited with 0, so a type error stops the chain. That is what makes the check a gate.

 When does "noEmitOnError": true make a difference?

It does not change what is checked. It only decides whether files are written when the check fails. In a check-only project (noEmit) nothing is written anyway.

 Which of these survives in the JavaScript that tsc emits?

A default parameter value is JavaScript, so it stays: currency = "NGN". as, satisfies, ! and the annotation : Currency are type syntax and are erased without a trace.

 What does import { transferFee, type Transfer } from "./transfer.js"; become in the emitted JavaScript?

Only the part marked type is removed. transferFee is a real function, so its import stays. If the whole import were import type { … }, the whole line would go.

 Which of these makes tsc generate new JavaScript code that was not in your file?

A parameter property (private, public, protected or readonly on a constructor parameter) makes tsc write a class field and this.balance = balance;. The others are erased completely.

 What does the erasableSyntaxOnly setting do?

With it on, the checker refuses the syntax that type-stripping tools such as Node.js cannot handle. You find out at check time instead of when the server fails to start.

 With "target": "ES2019", tsc rewrites order.discount?.percent ?? 0 into a long expression with === null and void 0. Why?

That translation between versions of the same language is transpiling. ?. and ?? are JavaScript (ES2020), not TypeScript; with a modern target they are left as they are.

 Your target is ES2019 and you call amounts.findLast(…), an ES2023 array method. What happens?

target rewrites syntax but never adds functions (polyfills). Its default lib matches the target, so the checker reports TS2550 and suggests a newer lib.

 What is in a .d.ts file that tsc --declaration writes for a module with one exported function?

A declaration file holds only types. Packages ship .js for running and .d.ts so that editors and tsc know every exported function's parameters and return type.

 A production server runs node dist/main.js. Error stack traces in the logs point at dist/main.js:3:15, which is hard to relate to the source. What fixes that?

A source map maps positions in the emitted JavaScript back to the .ts file. With --enable-source-maps, Node uses it, and stack traces name main.ts and the line you wrote.

 What does npx tsc --noEmit --watch do?

Watch mode is a long-running checker. With --noEmit it writes nothing. It does not run your program; you pair it with something like node --watch or tsx watch in a second terminal.

 With Node.js type stripping, import { Transfer } from "./types.ts" fails at startup with "does not provide an export named 'Transfer'", where Transfer is an interface. Why?

Writing import type { Transfer } tells every tool the import can be deleted. verbatimModuleSyntax makes tsc require it (TS1484), so the checker catches this before Node does.

 A project runs with plain node src/main.ts and also compiles with tsc for production. Which pair of settings lets you write import { transferFee } from "./fees.ts" in the source and still get ./fees.js in the emitted JavaScript?

Node needs the real file name, ./fees.ts. allowImportingTsExtensions lets the checker accept that path, and rewriteRelativeImportExtensions makes tsc change it to ./fees.js when it emits.

 Which statement about node file.ts in Node.js 24 is true?

Node's type stripping has no configuration from tsconfig.json, never checks types, and refuses to strip files inside node_modules. That is why packages are published as compiled JavaScript.

 What does the <Transfer> in parseJson<Transfer>(text) do at runtime?

Type arguments only shape what the compiler believes about the result. After erasure, parseJson is just JSON.parse, whatever T you wrote.

 Why does type Currency = "NGN" | "USD"; Currency.includes(code) fail with TS2693?

Types are erased, so there is nothing to call includes on. Start from a value instead, const currencies = ["NGN", "USD"] as const, and derive the type with (typeof currencies)[number].

 A type test contains // @ts-expect-error above transferFee("2500");. One day someone changes transferFee(amount: number) to transferFee(amount: any). What does tsc --noEmit do?

@ts-expect-error demands an error on the next line. When the type was loosened to any, the error disappeared, and the unused directive became the error. That is how a type test catches a weakened type.

 const limit: number = Number(env.TRANSFER_LIMIT) compiles. The variable is set to "5O000" (letter O). Why can the compiler not warn you?

The compiler knows the variable's type (string | undefined), never its content. Number("5O000") is NaN, whose type is number. Only a runtime check can refuse it.

 With limit = NaN, which check refuses every transfer (fails closed) instead of allowing every transfer (fails open)?

Every comparison with NaN is false. amount <= NaN is false, so the code refuses. amount > NaN is also false, so "refuse when above" never refuses, and !(amount > NaN) always allows. Even better: validate the limit when you read it, so it can never be NaN.

 Which package.json script is the one that must run in CI for type errors to block a release?

Only tsc checks types. Vitest, like tsx, strips types and runs the tests without checking them.
