What does a rate limiter actually do for an API under heavy load?

A limiter refuses the excess from greedy or broken clients cheaply, protecting everyone else. Capacity itself comes from the database, instances and code efficiency.

 A fixed-window limiter allows 100 requests per minute. What is the most a client can get through in about two seconds?

Each window counts on its own. Straddling a boundary doubles the burst. Sliding windows and token buckets do not have this edge.

 What is the main cost of the sliding window log?

Exactness comes from remembering every recent request. For small limits that is fine; for large limits across millions of keys, the memory adds up, which is why the sliding counter exists.

 A sliding window counter with a 60-second window is 15 seconds into the current window. How does it estimate the last 60 seconds?

The last 60 seconds contain 15 seconds of the current window and the last 45 seconds of the previous one. Assuming the previous window's requests were spread evenly, 45/60 of them are still inside.

 A token bucket has capacity 20 and refills 5 tokens per second. What do the two numbers control?

A full bucket lets 20 requests through at once. After that, the client can only sustain 5 per second, the rate at which tokens come back.

 Why does a token bucket store "tokens and last update time" instead of using a timer to add tokens?

Lazy refill: tokens now = min(capacity, stored + elapsed × rate). No background work, and idle keys cost nothing but their stored numbers.

 How does a leaky bucket differ from a token bucket?

A leaky bucket smooths output, useful in front of a slow downstream system. Public APIs usually prefer refusing quickly with 429 over making clients wait in a queue.

 Which algorithm best fits "at most 5 log-in attempts per account per 15 minutes"?

With a fixed window an attacker could make 10 attempts around a boundary. The exact sliding log costs only a few timestamps per account here.

 Opening your web app's dashboard fires 8 API requests at once, then nothing for a minute. Which limiter suits this traffic?

Normal use is bursty. A token bucket allows the burst and still caps the long-run rate, so real users are never refused while a script hammering the API is.

 Why can a strict per-IP limit hurt legitimate users?

Network address translation puts many devices behind one address. Keep per-IP limits generous and use per-user limits for fairness.

 An API limits requests per API key, checked before verifying that the key exists. What does an attacker do?

Keys the attacker controls cannot be limit keys. Verify the key first, and count requests with unknown keys against the IP address.

 Your API runs behind your own load balancer, which appends the client's address to X-Forwarded-For. Which entry should the limiter use?

Anyone can send an X-Forwarded-For header with any content, so the left-most values are client-controlled. Only entries added by proxies you run can be trusted. remoteAddress would be the load balancer itself.

 Why do limiters often key IPv6 clients by their /64 prefix?

A /64 contains 264 addresses. Limiting per full address would let one client rotate through them freely.

 A limiter computes that the client must wait 2.4 seconds. What should Retry-After say?

Retry-After is a whole number of seconds. Rounding down tells the client to come back too early, when it will be refused again. Always round up.

 Where in the request path should a per-IP limiter run?

A refusal must be cheaper than the work it prevents. Anything expensive done before the check is done for the attacker, too.

 A token bucket charges POST /transfers 5 tokens and GET /rates 1 token. Why?

Weighted costs make the limit track real load. One allowance covers both, and a client doing expensive work reaches the limit sooner.

 A limit of 5 log-in attempts per 15 minutes is kept in memory, and the API runs as 4 instances behind a round-robin load balancer. How many attempts can an attacker make?

In-memory counts are per process. Security limits need a shared store with an atomic increment, such as a database row or Redis.

 Two instances share a counter. Each does SELECT count, adds one in JavaScript, then UPDATE. What can go wrong?

Read-then-write has a gap. Use one atomic statement, such as INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING count, or Redis INCR.

 The Redis that stores rate limits is unreachable. What is a sensible policy?

A limiter outage should not take the whole API down, but it must not open an unlimited password-guessing window either. The choice is per limit, and it must be visible in monitoring.

 An API gets 50,000 transfer requests per second. The database pool has 100 connections and each transfer holds one for 5 ms. What does a rate limiter change?

100 / 0.005 s = 20,000 per second at best. A global limit below the ceiling keeps the database responsive; the excess gets a fast 429 or 503 with Retry-After instead of a slow timeout.

 By Little's law, how many requests are in flight when 2,000 requests per second arrive and each takes 0.25 seconds?

In flight = arrival rate × time in the system = 2,000 × 0.25 = 500. If requests get slower, the number in flight grows, and so does memory use.
