Which of these is a bug (a programmer error), not an expected failure?

The other three are operational errors: the client did something wrong and deserves a clear 4xx. A TypeError in your own code was never planned: it is a bug, a 500 for the client and full details in your logs.

 Framework errors (SchemaError, HttpError, CircularDependencyError) and application errors (NotFoundError, your own classes) all extend BaseError. Why does that help?

An error handler does not need to know every class. It reads the same fields from any BaseError and builds the right response.

 A client wants to react when a task title is taken. What should it check?

The code is a stable, machine-readable name. Messages are for people and may be reworded at any time; code that checks messages breaks when you do.

 By default, expose is true for 4xx errors and false for 5xx errors. Why?

"Task 9 not found" is safe to show. "relation tasks does not exist" or a file path tells an attacker how your system is built, so 5xx messages are hidden.

 What does error.isOperational tell you?

Operational errors are part of normal life (a missing task). Non-operational ones are bugs, the kind you want an alert for.

 Why does an error handler start with normalizeToBaseError(thrown)?

A BaseError passes through unchanged. Anything else (a TypeError, a thrown string) becomes a hidden, non-operational 500 with code ERR_INTERNAL_ERROR: treated as a bug.

 Why does TaskAlreadyDoneError set its code, category and statusCode inside its constructor?

With the options fixed in one place, throw new TaskAlreadyDoneError(3) always means 409 and ERR_TASK_ALREADY_DONE. Nobody can get it half right.

 Which is the best code for your own "task already done" error?

Prefix it with ERR_ and keep it stable: clients will write if (body.error.code === "ERR_TASK_ALREADY_DONE"). The status already has its own field.

 What may you put in an error's metadata?

Metadata can end up in responses and logs. Never put a password or a token in it. The serializers redact secret-looking names as a safety net, but do not rely on that.

 A client tries to complete a task that is already done. Which status fits TaskAlreadyDoneError?

The request itself is well-formed and the task exists, but it clashes with the task's current state. That is a conflict.

 Where should the rule "a done task cannot be completed again" and its error live?

The service only says "this task is already done". The status travels with the error, and the same service works from a queue worker or a command-line tool, where HTTP means nothing.

 What is the difference between SchemaError and ValidationError?

Both mean bad input and carry status 400. For your own checks, build the issues with helpers such as requiredFieldIssue and invalidFieldIssue.

 Which code should throw HttpError (for example badRequest() or a 415)?

Services throw @zudojs/errors classes that describe the problem in your application's terms (NotFoundError). A wrong content type or unreadable JSON only means something in HTTP.

 Which pairing is right?

The client needs a code and a safe message. Your logs need everything: the stack, the cause, the metadata. toJSON() gives the full picture, so it must never reach a client.

 A route answers errors with createResponseContext({ status: 500 }).json(error). What is the problem?

A stack trace shows your file layout, libraries and failing lines: a map for an attacker. Build client bodies from serializePublicError or from chosen fields only.

 What does ErrorHandler.handlePublic(error, context) do?

It packs the usual steps into one call: normalize, report (to a logger or an error-tracking service), and build a body that is safe for the client.

 Why does the Task API's toErrorResponse report only errors that are not operational or have status 500 or more?

Reports are for things you must act on. Bugs and server failures need attention; a client asking for a missing task is normal life.

 Why does every error body in the Task API include the requestId?

The client sees only a safe message. The request id connects it to the full details in your logs, without exposing anything.
