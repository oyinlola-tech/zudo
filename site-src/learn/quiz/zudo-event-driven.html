An order.created handler throws. What does await bus.publishEvent(...) do with @zudojs/events in its default settings?

The default error mode is CONTINUE: every handler runs, failures are collected, and the promise resolves. That is why code that only awaits publishEvent, such as a naive relay, never notices a failed delivery. Check result.failed, or log in onError.

 In the first example, publishing order.created a second time fixed the missing receipt but doubled the revenue. What is the root cause?

Re-publishing runs every subscriber again. Handlers that apply their effect every time they run (append a row, add to a total) double it. The fix has two parts: retry per consumer, and make each consumer ignore events it already handled.

 ShopFlow commits the order row, then the process is killed before publishEvent runs. With only an in-memory event bus, what happens to the receipt, audit and analytics work?

The event only existed in memory. The order is committed, and nothing anywhere says "announce this order". The outbox fixes this by writing the event in the same transaction as the order.

 Which of these is not a way the same event can reach a consumer twice?

The first three are everyday causes of duplicates, which is why delivery is "at least once". A unique constraint is part of the defence: it lets the database decide which delivery claimed the event first.

 Why does bus.on<Event<OrderCreated>>("payment.failed", handler) compile?

The name is a plain string at runtime and the type argument is chosen by the caller, so nothing ties them together. The handler then reads fields that do not exist. Let a contract choose both the name and the type, and parse the payload before the handler runs.

 Who should own and change the order.created contract module?

The producer owns the event, just as a module owns its public API. Consumers import the same contract instead of redeclaring it, so a change shows up in their code review and their compiler.

 Which change to order.created needs a new version?

A consumer written for the old shape reads payload.email and gets undefined. Adding an optional field is not breaking: tolerant readers ignore fields they do not know.

 A developer wants to change totalKobo to hold naira instead of kobo, keeping the name and type (number). Why is this the most dangerous kind of change?

A change of meaning is invisible to every check that only looks at shape. Give it a new version or, better, a new field name such as totalNaira, so old code cannot mistake one for the other.

 Why does the lesson upcast v1 events when a consumer reads them, instead of converting them once when v2 is deployed?

Events live in many places: unrelayed outbox rows, jobs waiting for a retry, dead letters replayed next week, a broker's log. Converting at read time handles all of them the same way, and the stored events stay a true record of what was published.

 The v1 → v2 upcaster sets customer.name to null. Why not a friendly default such as "Customer"?

An upcaster may only add what it can derive. Unknown data becomes an explicit "unknown" (null here), and the v2 contract allows it, so consumers are forced to handle it, as the email consumer does with "Hello".

 A consumer that knows up to v2 receives a v3 order.created. What does the lesson's readOrderCreated do, and why?

Parsing a newer version as an older one might work by luck, or silently lose a field that matters. Refusing makes the problem loud and recoverable. The usual order of deployment is: consumers first, producers last.

 ShopFlow adds order.created v3. Which upcasters exist afterwards?

Upcasters form a chain, one version step each. Every new version adds exactly one function, and all older versions reach the latest by running the steps in order.

 Why must the INSERT INTO outbox run in the same database transaction as INSERT INTO orders?

Two separate commits leave a gap where a crash creates exactly the inconsistency the outbox exists to prevent. One transaction closes the gap.

 A relay publishes each outbox row with await bus.publishEvent(...) and then marks it published, without looking at the result. What goes wrong?

In CONTINUE mode publishEvent resolves even when a handler threw. The relay must check result.failed and leave the row unpublished (and stop, to keep the order) when it is greater than zero.

 A consumer does SELECT from processed_events, then the work, then INSERT into processed_events. Two deliveries of the same event arrive together. Why can the work happen twice?

That is the check-then-act race. The primary key stops the second INSERT, but only after the work was done. Claim first with INSERT … ON CONFLICT DO NOTHING RETURNING, so the database decides the winner.

 In handleOnce, why is the claim row inserted in the same transaction as the work?

A claim committed without its work would make the event look done when it is not, and the retry would skip it forever. Work committed without its claim would be repeated by the next delivery. Only committing them together is correct.

 Sending an email cannot be part of a database transaction. What is the best protection against a duplicate email when the consumer crashes between sending and recording?

The event id is the same on every delivery, which makes it a perfect idempotency key. Recording the claim first and never retrying turns a crash into a lost email instead.

 Why does each consumer get its own queue, instead of the relay re-publishing the event until every handler succeeds?

Retry state belongs to a consumer, not to an event. The bus handler only enqueues, which is fast and rarely fails; the queue does the slow, unreliable work with retries for that consumer alone.

 Which failure should the email consumer park in the dead-letter table at once, instead of throwing for a retry?

A mailbox that does not exist will not start existing after a backoff. Retrying only delays the alert. Timeouts, 429s and reset connections are transient, and the queue's retries are the right answer.

 The replay in the lesson clears published_at on the outbox row instead of calling the email handler directly. What is the main benefit?

A replay tool that skips the normal path skips the checks you rely on. Because every consumer is idempotent, re-publishing is safe: audit and analytics answer duplicate, and email does its job.

 Before accepting an order, the orders module needs to know whether a product is in stock. Which tool fits?

Events announce facts to whoever cares; they do not return answers. When one module needs an answer to continue, it asks: a query, an RPC call or a function call.
