Nobody said the division would come out even; the code simply treated it as true. With ₦10,000 among 3 it did not, and the shares came out as fractions of a kobo.

 What should you do with every assumption you notice?

An assumption that is checked becomes a precondition with a clear refusal. One that is confirmed becomes a documented rule. One that is neither is a bug waiting for the right input.

 What is a precondition?

For the bill splitter: people is a whole number, at least 1; the total is a whole number, 0 or more. If they fail, the algorithm should refuse rather than compute.

 Which of these is a postcondition of the bill splitter?

A postcondition must be true after the algorithm runs. The other three are preconditions on the input.

 A precondition fails: someone asks to split ₦5,000 among 0 people. What should the program do?

A number that looks like an answer, such as Infinity, NaN or a silent guess, is worse than a clear refusal. It gets saved, shown and used as if it were real.

 Which of these is an edge case for the bill splitter?

A total smaller than the number of people sits at the edge of what the algorithm handles: someone's share becomes ₦0. The other three are ordinary cases that divide evenly.

 What is an invariant?

Because it holds at every step, you can check it after every step. When it breaks, you know exactly which step broke it.

 A hall has 500 seats. Which of these is an invariant of the ticket seller?

Selling moves seats from "available" to "sold"; it never creates or destroys them. So the two always add up to the capacity. The other invariant is sold <= 500.

 The first ticket seller checked sold < capacity before selling and still sold 501 tickets. Why?

With 2 seats left, a group of 3 passed the check. The right precondition for each sale is request <= available.

Once the state is wrong it stays wrong, so every later check fails too. The first failure points at the step that caused it.

 What are the three steps of the argument that a loop keeps an invariant, and so is correct?

For "best so far": the first item is the biggest of itself; each new item either replaces biggest or does not, keeping it the biggest seen; when everything is seen, it is the biggest of the list.

An invariant has to be true at the start. 0 is not one of the items, so the argument fails at step 1, and the wrong answer (₦0) follows.

 What can an argument about an algorithm do that no number of tests can?

"The shares add up because total = base × people + extra" is true for any total and any number of people. Tests only cover the inputs they try, which is why you use both.

 A test tries 1,010 combinations of total and people and, for each, checks that the shares add up and differ by at most ₦1. What is this style called?

Instead of writing an expected output for each case, you check rules that must always be true. That lets you test far more inputs than you could ever work out by hand.

 Two customers try to buy the last concert ticket at the same moment. Both see 1 seat available, and both succeed. What is this called?

Each request is correct on its own; the problem is two of them running at once. Tracing one request never finds it; asking "what if this happens twice, at the same time?" does. Databases solve it with transactions and locks.

0.1 + 0.2 is 0.30000000000000004, not 0.3. Whole numbers of kobo have no such error, so totals always add up.
