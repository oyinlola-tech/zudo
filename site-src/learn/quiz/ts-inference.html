What type does TypeScript infer for currency? const currency = "NGN";

A const binding can never be reassigned, so the most precise type, the literal type "NGN", is safe. That is literal inference.

 What type does TypeScript infer for currency here? let currency = "NGN";

A let can be reassigned later, so the literal type is widened to string. Otherwise currency = "USD" would be an error.

 What is the type of order.status? const order = { id: 1042, status: "paid" };

The const only stops order itself from being reassigned. Its properties can still change (order.status = "refunded"), so they widen: status is string.

 What is the type of fee? const fee: number = 50;

An annotation is the declared type and it wins. TypeScript checks that 50 fits number, then treats fee as a number from then on.

 What type does as const give roles? const roles = ["customer", "teller", "manager"] as const;

A const assertion stops widening at every level and makes arrays and properties readonly. The array becomes a readonly tuple of the exact strings, in order.

 What type does TypeScript infer for lines? const lines = [2500, "delivery", 700];

For an array, TypeScript builds the best common type of all elements, which here is a union, and widens the literals because arrays can change. It never infers a tuple on its own; you write the tuple type or use as const.

 What type does TypeScript infer for fee? declare const isVip: boolean; const fee = isVip ? 0 : "standard";

A conditional expression has the union of its two branch types. Because fee is a const, the literals are kept. TypeScript 7 may print the members in a different order, which means nothing.

 Why should you write const pending: Transfer[] = [] instead of const pending = []?

An unannotated empty array's type grows with each push. The type of a list should be decided by you, not by the first value someone happens to add.

 What does strict report here? let approvedBy = null; function report(): string { return `approved by ${approvedBy}`; }

A let starting as null gets an evolving type. Inside another function TypeScript cannot know which assignment happened, so there it is any, which strict mode reports. Annotate it: let approvedBy: string | null = null.

 Why does orders.filter((o) => o.total > 10000) need no annotation on o?

That is contextual typing: the type flows from the place the expression is written into the expression. filter's declaration says it calls the callback with an element, so o is an Order.

 Why does this report TS7006 "Parameter 'o' implicitly has an 'any' type"? const isLarge = (o) => o.total > 10000; console.log(orders.filter(isLarge));

Context only reaches an expression written in the place that has the expected type. Fix it with (o: Order) => … or by typing the variable: const isLarge: (o: Order) => boolean = ….

 ship({ id: 1, status: "paid" }) compiles, but const o = { id: 1, status: "paid" }; ship(o); does not, where ship expects status: "pending" | "paid". Why?

Same value, different type. Where an expected type exists, literals are checked against it and not widened. On its own line, o.status becomes string, which is wider than the union.

 What return type does TypeScript infer for discount? function discount(total: number) { if (total >= 50000) return 0.1; if (total >= 5000) return 0.05; }

The inferred return type is the union of every return, plus undefined for the path that falls off the end. A union of literals is kept as it is; only a function whose one and only result is a single literal (return "a") gets it widened to string or number. Either way undefined is in the type: without a return type annotation this compiles, and the error shows up at a caller that tries to multiply by the result.

 What is the main benefit of writing : number as the return type of discount above?

A return type is a promise the compiler holds the function to. It also stops the function's public type from changing silently when someone edits the body.

 An exported function has no return type annotation. A teammate adds return "free" in one branch. What can happen?

An inferred return type is whatever the body returns today. For exported functions it is part of the public API, so write it down and it only changes when you mean it to.

 Which of these is the best place to add an annotation?

Annotate at boundaries, infer inside. Parameters have nothing to infer from and form the contract with callers. The other three are inferred exactly already.

 What is wrong with const fees: Record<string, number> = { transfer: 10, withdrawal: 25 }; when the keys are fixed?

An annotation wider than the value throws information away. Leave it to inference, or use satisfies Record<string, number> to check the values while keeping the exact keys.

 What does satisfies do in const fees = { transfer: 10 } satisfies Record<string, number>?

satisfies gives you the check of an annotation without its widening. fees.tranfer is then an error, and so is a fee written as a string.

 When is Record<K, V> as an annotation a good choice?

With a union of keys, Record is precise: forgetting a key is an error and typos are errors. With string keys it only fits data whose keys really are unknown until runtime.

 Why should you write string and not String as a parameter type?

The lowercase name is the primitive type. The capitalised one describes the wrapper object (and anything with the string methods), so wrapper objects can slip in. TypeScript even says: "Prefer using 'string' when possible."

 What is the purpose of writing const probe: never = value; while learning?

The error text is the compiler's own description of the value's type. An editor's hover shows the same thing; delete the probe once you have seen it.

 What return type is inferred here? function outcome(ok: boolean) { return ok ? "approved" : "rejected"; }

The conditional's type is the union of both literals, and a function's inferred return type keeps such a union (a let with the same value would widen to string). Callers get a precise union they can check exhaustively.

 A function returns { ok: true, left: 500 } in one branch and { ok: false, reason: "insufficient funds" } in another, with no annotation. What is the practical problem with the inferred type?

TypeScript normalises the shapes (adding left?: undefined and reason?: undefined) and widens true/false. Name a discriminated union yourself, with ok: true and ok: false, as the next lessons show.

as const is erased. It only changes what the compiler allows; the object is an ordinary, unfrozen object at runtime. Use Object.freeze when the runtime must enforce it.

 What does this print? const a = new String("NGN"); const b = new String("NGN"); console.log(a === b, a == "NGN", typeof a);

Wrapper objects are objects: === compares identity, and two separate objects are never identical. == converts the wrapper to its primitive first, so a == "NGN" is true. typeof says "object".

Every object is truthy, including a Boolean wrapper holding false. valueOf() gives back the primitive false. Another reason to write boolean, never Boolean.

 Widening is a compile-time idea. What does this print? let status = "pending"; const fixed = "pending"; status = "paid"; console.log(status, fixed, typeof status === typeof fixed);

status is inferred as string, so assigning "paid" is allowed. At runtime both variables are ordinary strings, so their typeof is the same. Literal types and widening only exist for the compiler.
