You call totals.sort() on an array of order totals in naira, with no comparator. What rule does it use?

Without a comparator, sort compares string forms, so "1200000" comes before "25000" because "1" is before "2". For numbers always pass (a, b) => a - b.

 What does this print? const totals = [25, 100, 3, 1000]; console.log(totals.sort().join(", "));

The strings "100", "1000", "25", "3" are ordered by their first characters: "1" before "2" before "3". "100" is a prefix of "1000", so it comes first.

 A comparator compare(a, b) should say that b must come before a. What must it return?

Negative means a first, positive means a after b (so b first), zero means equal. That is why b - a gives a descending order.

 A colleague writes prices.sort((a, b) => a > b). What is wrong with it?

true becomes 1 and false becomes 0. The comparator can say "after" or "equal" but never "before", which breaks its contract. No error is thrown; the array just comes back in a wrong order. Use a - b.

 Bubble sort is fast when a large item is out of place near the front, but slow when a small item is out of place near the end. Why?

A pass keeps swapping the same large item forward until it meets a larger one. A small item near the end is swapped back only once per pass. Insertion sort does not have this weakness: it slides an item left as far as it needs in one step.

 How many comparisons does selection sort make on an array of 100 items that is already sorted?

Selection sort must scan the whole unsorted part to be sure it found the minimum, whatever the input: 99 + 98 + … + 1 = 100 × 99 / 2 = 4,950. It is Θ(n²) in every case.

 When could selection sort be a reasonable choice despite its n²/2 comparisons?

Selection sort makes at most n − 1 swaps. If each write is costly (large records, worn-out flash memory), that can outweigh its comparisons for small n. For nearly sorted data insertion sort is better, and selection sort is not stable.

 A leaderboard of 5,000 customers is sorted by points. One customer's points just increased and the board must be re-sorted. Which of these sorts does the least work?

Insertion sort does about one comparison per item plus one per place the changed customer moves: roughly n. Selection sort still does n²/2, quick sort with a last-item pivot is quadratic on sorted data, bubble sort needs one pass per place the customer moves towards the front, and merge sort does about n log₂ n / 2 even on sorted data.

 An inversion is a pair of items in the wrong order relative to each other. How many does [3, 1, 2, 5, 4] have, and so how many shifts does insertion sort make on it?

The pairs in the wrong order are (3, 1), (3, 2) and (5, 4). Insertion sort shifts one item per inversion, so it makes 3 shifts. A sorted array has 0 inversions, a reversed one n(n − 1)/2.

 Merge sort is O(n log n) for every input. What does it cost that quick sort does not?

Merging writes into a new array, so merge sort needs memory proportional to n. Quick sort partitions in place and only needs the recursion stack, O(log n) on average.

 Why does merge sort make about n log₂ n comparisons?

An array of n items can be halved about log₂ n times before the pieces have one item. On every level, the merges together process all n items once. n work times log₂ n levels is O(n log n).

 A quick sort always picks the last item of the range as its pivot. Why is it O(n²) on data that is already sorted?

A good pivot splits the range into two similar halves (log n levels). The largest item splits it into n − 1 and 0, so there are n levels costing n, n − 1, n − 2, … comparisons: about n²/2. The recursion also gets n calls deep.

 What does choosing the pivot at random change?

With a fixed pivot rule, some inputs (such as sorted data) are always bad. With a random pivot, badness depends on the coin flips, not on the input. The worst case is still possible in theory, but vanishingly unlikely for large arrays.

 You sort 50,000 order lines by status, which has only four possible values. A two-way quick sort with a random pivot is very slow. Why, and what fixes it?

Once a range contains only one status, a two-way partition behaves like sorted input: O(n²). Three-way partitioning groups the equal items around the pivot and never recurses into them.

 Why can no sort that only compares pairs of items beat O(n log n) in the worst case?

The sort must be able to tell all n! arrangements apart. With yes/no answers, k comparisons distinguish at most 2k cases, so k must be at least log₂(n!), which is about n log₂ n. Sorts that do not compare, like counting sort, are not bound by this.

 You must order 2 million product reviews by star rating (1 to 5). What is the fastest reasonable approach?

When keys are small whole numbers known in advance, you do not need comparisons at all. One pass counts (or groups) the reviews per rating, and a second writes them out. Grouping into five lists in input order is also stable.

 What does it mean that a sort is stable?

Stability is about ties. If two orders have the same date and you sort by date, a stable sort keeps them in the order they were in before. Not changing the input is a different property (copying, like toSorted).

 You want orders grouped by date, and within each date the largest amount first, using two sorts with a stable sort. In which order do you sort?

The last sort decides the main grouping, so it must be by date. Because it is stable, orders with equal dates keep the order the first sort gave them: by amount. Sort by the least important key first.
