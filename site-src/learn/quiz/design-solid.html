"One thing" is too vague to apply. Asking who requests changes (finance, accounting, customer service) shows where two groups' wishes can collide inside one module.

The total is one piece of knowledge and should be shared. How it is displayed belongs to each consumer. A boolean parameter would keep both actors tied to the same function and is control coupling.

The test is who asks for changes, not size. One actor, one reason to change: one module. Splitting it lowers cohesion.

 What does "open for extension, closed for modification" mean in practice?

Bug fixes are still made in place. OCP is about the axis that keeps changing: new cases arrive as new objects behind a stable interface.

 Which of these most deserves an extension point (a list of pluggable objects) rather than a switch?

Extension points pay off where cases arrive often. Small closed sets that belong to the domain are better as a union with an exhaustive switch.

 In an exhaustive switch over "draft" | "sent" | "paid", what does const unhandled: never = status; after the switch do?

After every handled case, the remaining type is never. A new union member leaves a real type there, and assigning it to never fails. The compiler finds every switch that needs updating.

 InvoiceStore.find(number) is documented to return undefined for an unknown number. Which implementation breaks the Liskov substitution principle?

Callers written against the interface check for undefined; they do not expect an exception. The implementation promises less than the interface, so code that works with other stores crashes with this one.

 Both store classes say implements InvoiceStore and compile. Why can one still break LSP?

Types describe shapes. Behavioural promises need tests, which is what a contract test run against every implementation provides.

 What is a contract test?

A contract test is the practical tool for LSP. It also keeps in-memory fakes honest: if the fake passes and the real adapter fails, the fake has been lying to your other tests.

 Which change to an implementation is allowed by LSP?

An implementation may demand less and promise more, never demand more or promise less. Extra requirements break callers that rely on the interface.

 A test fake for a reminder job has to stub eleven repository methods with throw new Error("not used"). Which principle is this pointing at?

The job should ask for a small interface such as OverdueInvoices with listOverdue. Then its fake is one function, and changes to unrelated repository methods cannot affect it.

 After you define a small OverdueInvoices interface, does the big repository class need implements OverdueInvoices to be passed to the job?

Structural typing makes ISP cheap in TypeScript: the consumer declares what it needs, and existing classes fit automatically. implements is still useful as a check where the class is written.

 What is the misapplied form of interface segregation?

Segregate by consumer. An interface should match what one kind of caller needs, often a few methods that belong together.

 In dependency inversion, who owns (defines) the ReminderSender interface?

The inversion is in the source dependency: details import the interface that policy defines, so policy never imports details.

 Which statement correctly separates dependency inversion, dependency injection and a DI container?

You can invert dependencies and inject by hand with no container at all, as the reminder job does. A container only automates the wiring.

 When is an interface in front of a class with only one real implementation worth it?

A class that calls a bank's API effectively has two implementations: the real one and the test fake. Internal logic with one implementation gets no benefit from an IThing/ThingImpl pair.

 A function takes rates: ExchangeRates (a class). Tests passed { rate: async () => 0.00065 }. After a #cache field is added to the class, the test no longer compiles. Why?

That is the moment to extract an interface owned by the consumer, such as RateSource. The change is local: callers that pass real instances do not change.

 Which is real duplication that DRY asks you to remove?

DRY is about knowledge. If the VAT rate changes, all three copies must change: one fact, three places. The two fees only look alike; they change for different reasons.

 A merged feeKobo(subtotal, kind, options) has grown flags, and a weekend surcharge meant for delivery now also applies to the service fee. What is the best next step?

Duplication is cheaper than the wrong abstraction. Once a shared function needs kind === … checks, the cases were never the same knowledge. Undo the merge and let each rule evolve on its own.

 What does the "rule of three" suggest?

Two examples are rarely enough to tell real shared knowledge from coincidence. With three, the common part and the differences are clearer.

 A configurable discount "rule engine" stores operators as strings like "gte". A rule with "gte " (trailing space) silently never matches. Which principle does this illustrate?

The simplest design that solves the real problem was a five-line function. The engine added moving parts that nobody needed and hid bugs from every tool.

 A developer says: "KISS, so I skipped input validation and error handling." What is wrong with this?

The tangled checkout function was easy to write and very hard to change. Simplicity is about the result, not about how little effort went in today.

 Which of these should you decide now, even though YAGNI says to avoid speculative work?

YAGNI is about cost of adding later. Money stored as floats cannot be fixed by refactoring: the rounded values are already in the database. The other three can be added when needed.

 Which pair of principles pulled against each other in the invoice money() helper?

Shared code couples everyone who uses it. When the users are different actors with different wishes, a small duplication can be the better design.

 Which code review comment is most useful?

Principles are vocabulary for explaining a concrete risk, not verdicts. Naming the risk lets the author judge whether the trade-off is worth it.
