Workspaces link local packages. A change in packages/core is visible through the link immediately, although dependents still read core's built output through its exports map.

 In the shop monorepo, @shop/database imports "@shop/core". Which core files does the compiler read to check database?

The link leads to core's package.json, whose "types" condition points into dist. That is why build order matters, and why project references exist.

 Which of these does "composite": true NOT require or imply?

composite is about being referenced by other projects: declarations, a complete file list and incremental information. Publishing is unrelated; internal packages are usually "private": true.

 Why do the shop packages (and ZudoJS's) set "tsBuildInfoFile": "dist/.tsbuildinfo"?

Incremental builds trust the .tsbuildinfo file. If "clean" removes dist but leaves that file elsewhere, the next build can skip emitting and still exit with 0.

 What is the root tsconfig.json with "files": [] and a references list for?

tsc -b at the root follows the references to every package and builds them in order. "files": [] prevents the root from also compiling every .ts file it can see as one big project.

 What does tsc -b do that tsc -p packages/http does not?

-b turns tsc into a build orchestrator over the reference graph. -p compiles one project and expects its dependencies' declarations to exist already.

 tsc -b --verbose says a dependent is "up to date with .d.ts files from its dependencies" and only updates its output timestamps. What changed?

A change inside a function body changes a package's .js but not its .d.ts. Dependents only see declarations, so their result cannot change.

 You add a JSDoc comment to the exported Logger interface. Why does tsc -b rebuild database, auth and http?

The decision is made by comparing declaration output. Even a comment counts, because it is part of the .d.ts file (and useful to users on hover).

 http imports @shop/auth and lists it in package.json, but its tsconfig.json has no reference to ../auth. What happens?

tsc -b only knows the reference graph. Without the reference, auth is not in http's build at all, and its dist/index.d.ts does not exist when http is compiled.

 What does error TS6202, "Project references may not form a circular graph", tell you to do?

Two projects that need each other's declarations cannot be built in any order. The fix is a design change, not a build trick.

 database imports "../../core/src/index.js" instead of "@shop/core", and database references core. What does the lesson show happens?

The emitted JavaScript keeps the relative path, which points at a folder with only .ts files. Without the reference the compiler reports TS6059/TS6307 instead. Import across packages by name only.

 What is a phantom dependency?

It works while the accident holds: a previous build left output, or the installer hoisted the package. On a clean build, with pnpm, or after publishing, it fails.

 With a phantom import of @shop/auth in database, the lesson's clean build failed and the next build passed. Why is that the worst outcome?

An order-dependent build depends on leftovers. CI should always build from clean, and the real fix is to declare the dependency (and its reference), or remove the import.

 Why does pnpm turn the phantom dependency into an error on every machine?

In the lesson, packages/database/node_modules/@shop held only core and logger, and the root had no node_modules/@shop at all, so @shop/auth could not resolve from database.

When ZudoJS pinned its siblings to 0.1.0, a build break, two failing tests and a timer leak stayed hidden until the packages were linked to source. workspace:* can only mean the local folder.
