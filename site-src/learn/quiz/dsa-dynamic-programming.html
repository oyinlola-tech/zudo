Which two properties make a problem a good fit for dynamic programming?

Without overlap, plain recursion or divide and conquer is enough. Without optimal substructure, combining best sub-answers does not give the best answer. DP needs both.

 Merge sort also splits a problem into subproblems. Why is it divide and conquer rather than dynamic programming?

DP pays off when the recursion reaches the same subproblem repeatedly. Merge sort's halves share no items, so caching their answers would never produce a hit.

 How many calls does the plain recursive Fibonacci make for fib(5)? let calls = 0; function fib(n) { calls++; return n < 2 ? n : fib(n - 1) + fib(n - 2); } console.log(fib(5), calls);

fib(5) calls fib(4) and fib(3); fib(4) calls fib(3) again, and so on. The call tree has 15 nodes for only 6 distinct subproblems (fib(0) to fib(5)).

 The same function with a memo. What does it print? let calls = 0; const memo = new Map(); function fib(n) { calls++; if (n < 2) return n; if (memo.has(n)) return memo.get(n); const value = fib(n - 1) + fib(n - 2); memo.set(n, value); return value; } console.log(fib(10), calls, memo.size);

Each fib(k) for k from 2 to 10 is computed once (9 memo entries). Each of those makes two calls, and the second call is always a cache hit or a base case: 1 + 2 × 9 = 19 calls, instead of 177 without the memo.

 How do you estimate the running time of a dynamic programming solution?

Every state is computed once. Coin change has amount + 1 states and does one check per denomination in each: O(amount × d). Knapsack has (n + 1) × (C + 1) states with O(1) work each.

 The van problem has 20 parcels and 200 kg of capacity. How many distinct subproblems best(i, room) can there be at most?

i ranges from 0 to 20 and room from 0 to 200. The plain search makes over a million calls, but only these 4,221 questions are different: that gap is the overlap DP removes.

 What is memoization in dynamic programming?

Memoization is top-down: the recursion drives the order, and the cache ensures each state is computed once. Filling a table from the bottom is tabulation.

 When filling a DP table bottom-up, what must be true about the order?

That is the whole job of the loop order. For coin change, fewest[a] reads smaller amounts, so amounts go upwards. The transport-pass table reads later days, so it is filled backwards from the last day.

 A DP has a chain of 200,000 states, each depending on the previous one. Why prefer tabulation over memoization here?

Both compute the same values. The recursion depth of memoization equals the longest chain of dependent states. Tabulation replaces the call stack with a loop.

 When can memoization do less work than tabulation?

A table computes every cell. The recursion only follows the dependencies of the question asked. If most cells are irrelevant, top-down can be much cheaper.

 What does this tabulation print? const ways = [1, 1]; for (let n = 2; n <= 6; n++) ways[n] = ways[n - 1] + ways[n - 2]; console.log(ways.join(" "));

This counts the ways to climb n stairs one or two at a time: ways[n] = ways ending with a one-step plus ways ending with a two-step. Starting from [1, 1] (one way to climb 0 or 1 stairs), the table for 0 to 6 has seven entries.

 Each Fibonacci entry depends only on the previous two. What does that allow?

The time is still O(n), one step per entry. Only the memory shrinks. The same idea keeps one or two rows of a knapsack or LCS table when you only need the final value.

 fib(79) computed with ordinary numbers gives a value that looks fine. What is the problem?

Numbers above 253 − 1 cannot represent every integer, and arithmetic on them rounds without warning. fib(78) is the last Fibonacci number that is safe. Check with Number.isSafeInteger.

 In the coin change table, what is fewest[0], and why does it matter?

A wrong base case shifts every answer. With fewest[0] = 1, every amount would come out one piece too high.

 Why does the coin change table use Infinity for amounts that cannot be made?

With -1 or null, 1 + fewest[a - v] would produce 0 or 1 and look like a great option. Convert Infinity to "impossible" only when returning to the caller.

With denominations in the outer loop, each combination is built in one fixed order of denominations, so it is counted once. With amounts outside, every order of choosing is a separate path. Decide which question the business is asking.

Every 0/1 decision is "skip or take". Taking it uses room, so the rest must fit in c − kg. Both options only look at row i − 1, which is why each parcel is used at most once.

 The knapsack table works well with capacity in kilograms. Someone switches all weights to grams. What happens?

O(n × C) depends on the numeric value C, not on how many inputs there are. Choose the coarsest unit the business allows, and validate the capacity before allocating a table.

 In the one-row knapsack, why must the capacity loop go down from the capacity to the parcel's weight?

Going up solves the unbounded knapsack, where each item can be taken many times. With a 0/1 van it silently reports impossible loads, such as one 50 kg parcel earning four times its fee.

 One parcel of 2 kg worth ₦3,000, a 6 kg van. What does this print? function oneRow(capacity, kg, naira, down) { const best = new Array(capacity + 1).fill(0); if (down) { for (let c = capacity; c >= kg; c--) best[c] = Math.max(best[c], naira + best[c - kg]); } else { for (let c = kg; c <= capacity; c++) best[c] = Math.max(best[c], naira + best[c - kg]); } return best[capacity]; } console.log(oneRow(6, 2, 3000, true), oneRow(6, 2, 3000, false));

 The one-row knapsack uses O(C) memory instead of O(n × C). What do you lose?

The walk back needs to compare best[i][c] with best[i − 1][c]. With one row, those values are gone. Keep the full table (or a compact record of decisions) when you need the list.

 What is the difference between a subsequence and a substring of "PAYMENT"?

The LCS of two texts allows gaps, which is what lets a diff keep all unchanged lines even when lines are inserted or deleted between them.

 What does this print? function lcs(a, b) { const L = Array.from({ length: a.length + 1 }, () => new Array(b.length + 1).fill(0)); for (let i = 1; i <= a.length; i++) { for (let j = 1; j <= b.length; j++) { L[i][j] = a[i - 1] === b[j - 1] ?  Why don't tools like git use the plain LCS table to diff two versions of a 100,000-line file?

O(n × m) time and memory is fine for a delivery note, not for large files. Myers' algorithm runs in O((n + m) × d) for d differences.

One replacement (e → a) is enough here. The DP table D[i][j] for prefixes takes the cheapest of replace, delete and insert at each cell: O(n × m).

 You are designing a DP and find that the answer for a subproblem depends on the entire list of choices made so far. What does that usually mean?

A good state is small: amount left, parcels considered and room left, lines consumed in each text. If you need the whole history, there are as many states as histories, and DP saves nothing.

 A service memoizes knapsack answers in a module-level Map that lives as long as the process. What is the risk?

A memo is a cache. Inside a single computation it is released when the function returns; at module level it keeps every entry from every request forever. It can also return stale answers if the inputs it depends on change.

 What is the most convincing test for a knapsack DP?

Brute force is slow but obviously right on small inputs. The consistency check catches a wrong walk-back even when the number is right. Include the edges: no parcels, zero capacity, parcels heavier than the van.
