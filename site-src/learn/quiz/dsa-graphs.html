How does a general graph differ from a tree?

A graph is just vertices and edges. A tree is a special graph: connected, no cycles, one root, and exactly n − 1 edges. Graphs drop all of those rules, which is why walking them needs more care.

 Which relationship should be modelled with directed edges?

"A uses B" does not imply "B uses A", so the edge has a direction. Mutual friendship, two-way roads and "bought together" are symmetric, so undirected edges fit.

 A rider-routing app asks for the fastest route. What should the edge weights be?

The algorithm optimises whatever the weights mean. Distance gives the shortest route, not the fastest; a short road through a busy market can be slower. Travel times change, so they must be updatable.

 A city map is stored as an undirected graph. What bug does that cause?

An undirected edge can be used in both directions. One-way streets need a directed edge; a two-way street becomes two directed edges, one each way.

 In a directed "follows" graph, what does the in-degree of a person count?

In-degree counts edges arriving at a vertex; an edge A → B means A follows B, so arrows into B are B's followers. Out-degree counts the people B follows.

 A delivery map has 100,000 junctions and about 250,000 road segments. Which representation fits, and why?

A matrix always uses V² cells. With 100,000 vertices that is 10¹⁰ cells for a few hundred thousand edges. An adjacency list uses O(V + E) memory and lists a junction's roads in O(degree).

 When is an adjacency matrix a good choice?

The matrix answers "edge a → b?" with one array access, but costs O(V²) memory and O(V) to list neighbours. That trade only pays off when V is small or the graph is dense.

Storing both directions doubles the memory but makes both questions O(degree). An undirected graph would lose the difference between following and being followed.

 Why does every graph walk need a visited set, when a tree walk does not?

A tree has exactly one path to each node. In a graph, shared dependencies create many paths (the number can double at every layer) and a cycle creates infinitely many.

 With a visited set, what does finding everything reachable from one vertex cost?

Each vertex is pushed at most once and each edge is examined at most once (from its source vertex). That is linear in the size of the graph.

 What is a topological order of a directed graph?

It is an order that respects every edge. For dependencies, with edges from a dependency to the packages that need it, it is a valid build order.

 When does a topological order exist?

On a cycle, each vertex must come before the next one, all the way round, which is impossible. Without cycles, Kahn's algorithm always succeeds.

 config, logger and money have no dependencies and nothing relates them. What does that mean for the build order?

Topological order is usually not unique. Any order of unrelated packages is correct, but a build that changes order between machines can hide order-dependent bugs, so tie-breaking should be fixed (declaration order or sorted names).

 A developer runs Kahn's algorithm directly on the "uses" edges (api → auth, auth → db). What comes out?

Kahn's algorithm puts every edge's source first. With "uses" edges, the package that uses things comes first, which is backwards for building. Either reverse the edges ("is needed by") or reverse the result.

Computing in-degrees looks at every edge once, and so does processing the queue. Rescanning all packages each round, as the naive version at the start does, is what makes that one slower.

Packages on a chain must be built one after another, so the longest chain (the critical path) sets the minimum: 6 × 2 = 12 minutes. More workers help with wide stages but can never shorten the chain.

The self-edge gives it in-degree 1, and only the package itself could lower that. It never enters the queue, so it appears in blocked, as the lesson's test checks.

Any valid order is correct, but a build that orders things differently from run to run makes order-dependent bugs appear and vanish. A fixed tie-break makes builds reproducible.

 The test generates random DAGs by shuffling vertices and only adding edges from earlier to later positions. Why can that never create a cycle?

A cycle would need at least one edge going backwards. The shuffled order is itself a topological order of the graph, by construction.

 Which property check proves an output is a valid topological order?

That is the definition, checked directly: completeness (every vertex, once) plus order (every edge forwards). The other checks can pass for wrong outputs.
