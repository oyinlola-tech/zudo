Which description of the event loop is right?

After each task, the microtask queue is drained completely, including microtasks added during the drain. Only then does the next task start.

 A request handler runs a synchronous loop for 300 ms. A timer was due after 10 ms. When does the timer's callback run?

Run to completion: nothing interrupts a running task. The due timer waits in the task queue until the stack is empty and microtasks are drained.

 Where do the timer and network features that feed the task queue come from?

The language defines promises and the microtask queue (called jobs in the specification). Timers, I/O and events are provided by the host, which queues their callbacks as tasks.

 Which of these is scheduled as a microtask?

Code after await, promise handlers and queueMicrotask callbacks are microtasks. Timers, events, I/O and setImmediate are tasks.

 What does this print? setTimeout(() => console.log("timer"), 0); Promise.resolve().then(() => console.log("then")); queueMicrotask(() => console.log("micro")); console.log("sync");

Synchronous code first. Then the microtasks in the order they were queued (then before micro). The timer is a task, so it runs after the drain, despite being scheduled first with 0 ms.

An async function runs synchronously up to its first await. Even await null pauses it, so the rest becomes a microtask that runs after the current synchronous code.

 What does the 100 in setTimeout(fn, 100) promise?

The delay is a minimum. After it passes, the callback is queued and waits for the current task and microtasks, and for tasks ahead of it.

 What does this print? const start = Date.now(); setTimeout(() => { console.log("timer ran after 100 ms or more:", Date.now() - start >= 100); }, 10); while (Date.now() - start < 100) {} console.log("loop done");

The busy loop is part of the current task and cannot be interrupted. The timer was due at 10 ms but could only run after the loop ended, at 100 ms or later.

 A cart's add method may be called ten times in one task. What does scheduling the "save cart" call with queueMicrotask (once per task) achieve?

Batching: the first change schedules one microtask; later changes in the same task just add to the pending state. The flush still happens before anything else in the task queue.

Both notifications in the first task are collected and sent in one microtask after handler done. The notification in the later timer task starts a new batch.

 How does queueMicrotask(fn) differ from Promise.resolve().then(fn)?

Same queue, same timing. queueMicrotask states the intent directly and does not turn errors into promise rejections.

 This runs in Node.js. What does it print? setTimeout(() => { setTimeout(() => console.log("timeout"), 0); setImmediate(() => console.log("immediate")); Promise.resolve().then(() => console.log("promise")); process.nextTick(() => console.log("nextTick")); }, 5);

After the timer callback, Node drains nextTick first, then promise microtasks. The loop then continues from the timers phase to the check phase (setImmediate) before it comes round to timers again (setTimeout 0).

 In Node.js, when do process.nextTick callbacks run?

Node keeps a separate nextTick queue, drained after each callback just before the promise microtask queue. (At the very top level of an ES module, a promise may run first, as the Node.js runtime lesson showed.)

 In Node.js, a long job runs in pieces and wants to let pending I/O (incoming requests) be handled between pieces. Which should schedule the next piece?

setImmediate runs in the check phase, after the poll phase has handled I/O. nextTick and microtasks run before the loop moves on, so they would starve I/O.

 A function reschedules itself forever with process.nextTick. What happens to a server's incoming requests?

The nextTick queue (like the microtask queue) is drained completely before the loop moves on. An endless chain starves everything else.

 Which of these exists only in Node.js, not in browsers?

setImmediate and process.nextTick are Node APIs. Portable code uses queueMicrotask and setTimeout.

 A loop does await null on every iteration for 2 seconds. Can a 0 ms timer that was queued before the loop run during those 2 seconds?

Awaiting an already-available value resumes in the same microtask drain. To let tasks run, you must return to the task queue, for example by awaiting a timer.

 What does this print? let timerRan = false; setTimeout(() => (timerRan = true), 0); let rounds = 0; async function work() { while (rounds < 10_000) { await null; rounds += 1; } console.log("timer ran during the loop:", timerRan); } work();

All 10,000 iterations run inside one microtask drain, so the timer task cannot run until the loop is over. await does not yield to timers by itself.

 What does this print? let timerRan = false; setTimeout(() => (timerRan = true), 0); const yieldToLoop = () => new Promise((resolve) => setTimeout(resolve, 0)); async function work() { for (let round = 1; round <= 3; round++) { await yieldToLoop(); console.log(`round ${round}, timer ran: ${timerRan}`); } } work();

Awaiting a timer puts the rest of the loop into the task queue behind the timer that was already waiting. So that timer runs before round 1 continues.

 Why does the export use a time budget per slice (process rows until about 8 ms have passed) rather than a fixed number of rows?

What matters to other work is how long each slice holds the thread. A time budget bounds that directly; a row count only bounds it on the machine you tested.

 Compared with doing it in one go, a time-sliced export…

Slicing does the same work, plus a little overhead for each yield. It does not make the work parallel; it shares the thread fairly. Truly heavy work belongs in a worker thread or a job queue.

 A report takes 20 seconds of pure computation. What is the best way to keep the server responsive?

Slicing 20 seconds of work only spreads the slowdown. A worker thread has its own event loop and runs in parallel, so the main loop stays free for requests.

 What does event-loop lag measure?

A healthy loop runs timers within a millisecond or two of their due time. Large lag means long tasks (or microtask chains) are blocking the thread, so every request waits.

 In a browser, a microtask chain runs for 3 seconds. What happens to the page?

The render step comes after the microtask drain. A long microtask chain blocks rendering and input exactly like a long synchronous task.

 A retry helper waits 30 seconds between attempts. How do you test it without the test taking minutes?

Fake timers replace setTimeout with a clock the test controls, so a 30-second wait is tested instantly and deterministically.

 Code works only because one promise chain happens to finish two microtask steps before another. What is the right fix?

Step counts change when anyone refactors (one more await, one fewer then). If B needs A, express the dependency; do not rely on accidental timing.
