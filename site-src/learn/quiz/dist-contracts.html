Which team owns the schema of the order.placed event?

An event is owned by its producer. Consumers adapt to it, and the producer has to keep old and new consumers working, which is what versions and tolerant readers are for.

 Checkout, the admin panel and the subscriptions service all send a payments.charge command to the payments service's queue. Who should own the command's schema?

A command has many senders and one handler. The handler says what it accepts, exactly like an API provider, and senders adapt to it.

 What does forward compatible mean for a message format?

Forward compatibility is old readers surviving new writers. Backward compatibility is the other direction: new readers reading old data, such as v1 events still in a queue.

 In the ₦NaN bug, orders v2 sent total: { … } and the unchanged payments service read totalKobo. Which property was missing?

Payments was the old reader, orders v2 the new writer. The top-right cell of the compatibility matrix was broken.

 You must change a field's shape in an event with three consumers. Which release order is safe?

Readers first means that when the new shape appears, everyone already understands it. Old-version support can only go once no old message can exist anywhere. A "coordinated release" never happens atomically across machines.

 When can the payments team delete the upcaster that turns order.placed v1 into v2?

v1 messages outlive the code that wrote them. Measure versions in flight and know your retention periods; then deleting old support is a decision backed by evidence. (If you keep an event store forever, the upcaster may indeed be permanent.)

 Payments v2 (reads v1 and v2) and orders v2 (writes v2) are in production. Which rollback is dangerous?

Rolling back a writer is safe because readers already understand both versions. Rolling back a reader re-creates the ₦NaN situation. Readers must be forward compatible, or at least park what they cannot read.

 A payments instance receives order.placed with schemaVersion: 3, but its build only knows up to v2. What should it do?

A message from the future means a producer is ahead. Dropping it loses a real order; guessing risks misreading; endless retries burn resources. Parking keeps it safe until the reader can handle it.

 A producer bug sends a v1 body labelled schemaVersion: 2. In the lesson's reader, what catches it?

The version routes the message; the schema is still the judge. Validating the body against the schema of its claimed version catches producer bugs like this one.

 ShopFlow's message has schemaVersion, and its body envelope from @zudojs/serialization has metadata.version. What is the difference?

Two layers, two versions. The package owns the encoding; you own the payload's shape. Mixing them means a package upgrade could look like a schema change, or the other way round.

 Where is a schema that rejects unknown fields (.strict()) a good choice?

Between your own services, readers should tolerate unknown fields so producers can add optional ones. At the public edge you are not expecting newer versions of yourself, so rejecting unknown input is reasonable.

 During a rolling deploy, an old orders instance reads an order document, changes the address and saves the whole document. The giftMessage added by the new version is gone. What is the best fix?

Stripping is safe for reading and dangerous for read-modify-write. Updating only your own fields, or passing unknown ones through, keeps data you do not understand.

 The checkout team wants to add "ussd" to the method enum in payment.requested. Which statement is right?

An added enum value is new data for old readers. Map unknown values to an explicit, handled case (like "hold for manual review"), deploy that first, and only then start sending the new value.

 Orders v3 registers a Money transformer and starts sending Money objects with preserveTypes. What does an older reader that never registered Money see?

A reader can only rebuild types it knows. A new tagged type is a breaking change for old readers: register the transformer in readers first, then start sending it.

 Which of these does not belong in a shared contracts package?

A contract is data about data. Behaviour in a shared package forces lock-step upgrades whenever it changes, which recreates the monolith's coupling with extra network hops.

 Both services import type OrderPlacedV2 from the contracts package. Why must payments still parse incoming events with the schema?

The type is what you hope arrives. Services deploy independently, so the bytes on the wire may come from a different version of the contracts than the one you compiled with.

 What does consumer-driven contract testing tell the provider that a schema alone does not?

A schema says what may be sent. Consumer expectations say what is used. That turns "is this change safe?" from a guess into a test result with names attached.

 What is a provider state such as "order ord_1 is pending with 2 lamps at ₦1,250"?

The consumer names the situation it assumes; the provider's verification code creates that data (here, an order in a map) before calling its real service.

 Why did the payments pact use exact(250000) for totalKobo but like("NGN") for currency?

Exact values tied to a state catch semantic changes such as naira instead of kobo. Exact values that do not follow from the state make pacts brittle.

 A release changes totalKobo from 250000 to 2500 (naira) without renaming it. Which check fails?

Same name, same type, different meaning. Only a check that knows the expected value for a known situation can catch it.

 Orders 2.5.0 has been verified against payments 1.9.0. Production runs payments 1.8.0. May orders 2.5.0 be deployed?

can-i-deploy asks about the consumer versions actually in production. A verification against a version nobody runs yet proves nothing about today's traffic.

 In the consumer test, payments' code ran against a fake orders server that returned only values built from the pact. Why?

The consumer test keeps the pact honest. Without it, a consumer could depend on a field it never declared, and provider verification would miss that dependency.

 A week after publishing order.placed v2, you notice couponCode should have been an object. What do you do?

Once a version is published, messages of that shape exist in queues and stores. Changing the schema under them turns valid messages invalid. A fix is always a new version.

 Why is a table read directly by two services described as "a contract with no version, no owner and no tests"?

A shared table couples both services to its exact layout. An event or an API puts a versioned, testable contract at the boundary instead.
