Why does an application need a runtime like @zudojs/runtime?

With two parts, ordering by hand works; at ten it becomes fragile. You describe each part and what it needs, and the runtime works out the order, starts everything, and stops it cleanly.

 What does a runtime module consist of?

The runtime manages modules. Each one says who it is, which other modules it needs (by id), and which hooks the runtime should call at fixed moments.

 Your store module must open a database connection when the app starts. Which hook is for that?

onInitialize runs during start(), dependencies first: the place to open connections and load data. onReady is for starting to accept work, once every module has initialized.

 When does the runtime call onReady?

Startup has two rounds: every module is initialized before any becomes ready. So when http becomes ready, every other module has at least been initialized.

 What is the difference between onShutdown and onDestroy?

Stopping also has two rounds, both in reverse order: first every onShutdown, then every onDestroy, which releases what the module still holds.

 You register http, then tasks, then store, but store initializes first. Why?

tasks needs store, and http needs tasks. The runtime sorts that dependency graph (a topological sort), so the list order does not matter.

 A module lists a dependency that is not registered. When does the runtime notice?

The runtime refuses a cycle or a missing dependency before it touches any module. A wiring mistake shows up the first time you start the app, not hours later.

 The runtime says Module "tasks" depends on "databse" which is not registered. What is the most likely cause?

A missing dependency is usually a typo (here databse) or a forgotten registration. It is about the wiring, not about a server being reachable.

 The http module fails to start because its port is in use, while store and tasks are already up. Why does the runtime roll back?

If the runtime simply gave up, open connections would leak. Rolling back undoes what already happened, in reverse order, before start() rejects.

 During that rollback, onShutdown ran for tasks and store, but not for http. Why?

Shutdown undoes "ready", so it only runs where ready succeeded. onDestroy ran for all three, because all three had initialized and may hold resources.

 A module's onInitialize throws halfway through. The runtime still calls its onDestroy. What does that mean for your code?

The module may have opened something before it threw. So onDestroy runs, and it must check what is actually open instead of assuming a full setup.

 A failed start() rejects with a RuntimeStartError. Where do you find what went wrong?

The RuntimeStartError names the module and the phase. The original error, such as "Port 3000 is already in use", is kept as its cause.

 In src/server.ts, a failed start should log the error, call runtime.stop(), and exit with code 1. Why code 1?

Exiting with 0 would report success, and nobody would be alerted. Calling stop() first releases anything the rollback did not reach; it is safe to call even when nothing is left.

 A readiness check for the store starts returning false while the app keeps running. What does the runtime report?

runtime.ready and runtime.health are worked out from all the readiness checks. A platform then sends traffic elsewhere until the app is ready again.

 What is SIGTERM?

Platforms send SIGTERM; pressing Ctrl + C sends SIGINT. By default Node.js ends the process at once, cutting off requests in progress.

 What does a graceful shutdown do?

With handleSignals: true the runtime catches the signal and runs stop(). A second signal exits at once, and shutdownTimeout puts an upper limit on the whole thing.

 Why does the generated src/app.ts pass handleSignals: false?

The HTTP server is not a module. server.ts calls server.stop() (no new requests), then runtime.stop() (close what the requests used). One owner of the signals keeps the order right.

 What is runtime.context.runtimeId for?

Two copies of task-api may run at once. The id, like rt_…, lets you see which copy wrote which log line.

 What does @zudojs/lifecycle add, next to the runtime?

A module may own a pool, a cache and a mailer. Lifecycle starts and stops such components in order, rolls back on failure, and lets a non-critical one fail without stopping startup.

 TasksModule passes dependencies: ["store"] to BaseModule. What does that guarantee?

Because of the dependency, the store is connected before TasksModule.onInitialize adds its example task. Both modules receive the same TaskStore object.

Finish boot(runtime), like src/server.ts should do: try await runtime.start(). If it throws, print Startup failed: MESSAGE, await runtime.stop(), and return 1. On success return 0. The number is the exit code.

Stop after a failed start to release anything the rollback did not reach, then exit non-zero. Exit code 1 tells the platform the app did not start, so it can restart it or alert you.
