Why does POST /invoices/:id/send answer 202 Accepted?

202 means "accepted for processing, not finished". The response carries the delivery id, so the client can show progress without waiting for the provider.

 Why is the deliveries row inserted in the same transaction as the invoice's change to sending?

This is the outbox pattern. Before it, a deploy that restarted a server between the two steps left invoices "sending" forever. With one transaction, a crash rolls back both.

 The in-memory queue already retries and dead-letters jobs. Why does InvoiceHub also keep a ledger table?

The ledger is the truth, the queue is only the executor. After a crash the dispatcher finds the unfinished rows again; nothing depended on the dead process's memory.

 A queue delivers "at least once". What gives the customer "exactly one e-mail" anyway?

You cannot prevent a job from running twice (a crash after the send guarantees it sometimes will). You can make the second run harmless. The key has to reach the system that has the side effect, here the provider.

 What does deliveries.dedupe_key text not null unique protect against?

The key names the intent: invoice:1, reminder:1:2026-10-05. The database refuses a second row with the same key, and on conflict do nothing turns the second request into "return the existing delivery".

 Right after worker A died, worker B's dispatch claimed nothing. Why is that correct?

The lease is a promise: "this row is mine until then". Only when it expires may someone else assume the owner is gone. A minute later, worker B claimed it.

 InvoiceHub jobs have a 5-second timeout, 4 attempts and backoff between them. Which lease is safe?

If the lease runs out while a live worker is still retrying, a second worker claims the same row and both run it at once. The lease must outlast the longest legitimate run; longer jobs renew it with a heartbeat.

 The queue already stops after 4 failed attempts. Why does the ledger also retire a row after 3 claims?

An out-of-memory crash kills the process before any error handling runs. Without the claim cap, that poison message would take down a worker every time its lease expired, forever.

 Which provider answers should the processor retry?

A 503, a 429 or a timeout may go away. A 422 says the request itself is wrong and will fail the same way every time, so the delivery is marked dead at once and a person fixes the address.

 INV-0004 throws a TypeError in our own rendering code on every attempt. What does the queue do with it?

Only the processor knows what an error means. isPermanent covers the provider's 4xx answers; an unexpected exception is treated as temporary, which costs a few wasted attempts but loses nothing.

 With concurrency: 5, a poison job fails 4 times with backoff. What happens to the 12 other deliveries meanwhile?

A job waiting for its next retry does not hold a slot, and a running one holds only one of five. The demo delivered twelve e-mails while delivery 4 kept failing.

 Why is the worker's concurrency 5 and not 100?

With 100, the provider would answer 429 to most calls, which would turn into retries and even more load. The demo measured at most 5 e-mails at the provider at once.

 The HTTP handler runs inside a correlation context (AsyncLocalStorage). Why is that context gone when the worker runs the job?

AsyncLocalStorage follows one chain of async calls in one process. A durable hop breaks the chain, so the id must be written down with the job (the ledger's correlation_id) and restored on the other side.

 What does the queue's contextCarriers option do in InvoiceHub?

The dispatcher sets the context from the ledger row just before queue.add(). The carrier's capture stores it in the job's metadata and restore runs the processor inside it.

 Why does the 08:00 reminder handler only record reminder deliveries instead of sending the e-mails itself?

A handler that sent 500 e-mails itself would need all of those features again. Recording rows takes milliseconds and hands the slow, unreliable part to the machinery built for it.

 The reminder handler builds its dedupe key from ctx.scheduledAt, not from new Date(). Why?

The key should describe which run this is, and that is the time it was due. The current time depends on how late the process was.

 Two servers each run the scheduler, and both fire at 08:00 on Monday. What stops customers from getting two reminders?

The demo played exactly that: server A created 1, server B created 0. Running the schedule on one instance also works, but then that instance is a single point of failure.

 What does for update skip locked in claimDue give you?

Without it, two dispatchers could select the same queued row and both mark it running. With it, the second one simply takes the next free rows.

 The job carries only { deliveryId }, and the processor loads the invoice itself. Why not put the whole invoice in the job?

A copy in the job goes stale. It also spreads customer data into queue storage, logs and dashboards. Ids in, fresh data loaded inside.

 Why does the dead-letter handler call markDead(...).catch(...) instead of void markDead(...)?

The catch logs the failure and moves on. The row stays running, and its lease brings it back later, so nothing is lost.

 Which pair of numbers best tells operations that deliveries are in trouble?

Dead deliveries need a person. The oldest waiting delivery (the lag) catches stuck or too few workers, even when no error is ever logged.

 On SIGTERM, in which order should a worker process shut down?

New claims first, running work second, resources last. Leases are the safety net for real crashes, not the plan for a routine deploy: they cost a minute of delay per claimed row.

 Why does replay(id) only update rows where status = 'dead', and reset claims to 0?

The key stays delivery-<id>, so if the earlier attempt did reach the provider after all, the replay still does not send a second e-mail.
