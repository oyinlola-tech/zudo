What is RPC, a remote procedure call?

With RPC you think in functions, not URLs: tasks.call("tasks.count", { userId }) runs code in the task service and returns its result. It is most useful between your own services.

 In @zudojs/rpc, what does the transport do?

A procedure is the function on the far side, the server holds the procedures, the client builds requests, and the transport carries them, for example over HTTP.

 What does this print? import { createRPCProcedure } from "@zudojs/rpc"; for (const name of ["tasks.create", "Tasks Create"]) { try { createRPCProcedure(name, async () => null); console.log(name, "ok"); } catch (error) { console.log(name, "refused"); } }

A procedure name is dot-separated words, like tasks.create. A name with a space is refused when you create the procedure, long before anyone calls it.

 What does this print? import { createRPCProcedure, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.list", async () => [])); try { server.register(createRPCProcedure("tasks.list", async () => ["other"])); console.log("replaced"); } catch (error) { console.log(error.message); }

Two procedures with the same name would make calls ambiguous, so the second register throws. Nothing is silently replaced.

 A procedure is created with { input: NewTask }, a schema. When does the schema run?

The server checks every payload against the input schema first. A payload that fails never reaches your handler, and a payload that passes arrives cleaned, for example with the title trimmed.

 What does this print? import { createRPCProcedure, createRPCRequest, RPCServer } from "@zudojs/rpc"; import { schema } from "@zudojs/schema"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.create", async (input) => ({ title: input.title }), { input: schema.object({ title: schema.string().trim().min(3) }), })); const response = await server.handle(createRPCRequest({ id: "req-1", procedure: "tasks.create", payload: { title: " Buy milk " }, })); console.log(response.id, response.success, response.result);

The response carries the same id as the request, so the caller knows which answer belongs to which question. The handler received the value the schema produced, so the title was trimmed.

 What does this print? import { createRPCRequest, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); try { const response = await server.handle(createRPCRequest({ id: "req-2", procedure: "tasks.delete", payload: { id: 1 }, })); console.log("answered:", response.success); } catch (error) { console.log("threw"); }

handle never throws for a bad request. An unknown procedure comes back as a response with success: false and an error, so one bad call cannot crash the server.

 What is the smallest thing that works as an RPCTransport?

Any object with send(request) works. The package ships ready-made ones, createRPCMemoryTransport(server) and createRPCHttpTransport({ url }), and the retry example wraps one in a small object of its own.

 What does this print? import { createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; const tasks = []; const server = new RPCServer(); server.register(createRPCProcedure("tasks.create", async (input) => { tasks.push(input.title); return { id: tasks.length, title: input.title }; })); server.register(createRPCProcedure("tasks.list", async () => tasks)); const client = new RPCClient({ send: (request) => server.handle(request) }); const task = await client.call("tasks.create", { title: "Buy milk" }); await client.call("tasks.create", { title: "Walk the dog" }); console.log(task.id, await client.call("tasks.list", {}));

The client turns each response into a normal return value. The first task got id 1, and the list holds both titles. The transport here is just an object with send that calls the server in the same process.

 You write client.call<{ id: number }, Task>("tasks.get", { id: 1 }). What does the Task type guarantee at runtime?

Types disappear when the code runs. The other service could send anything. Treat its answer like any other outside data.

 The billing service calling your task service is also yours. Should the task service validate its payloads?

The other service can have bugs, old versions or be compromised. An input schema stops a payload like { id: "1; DROP TABLE tasks" } before it reaches the handler.

 What does this print? import { createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; import { schema } from "@zudojs/schema"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.create", async (input) => input, { input: schema.object({ title: schema.string().trim().min(3) }), })); const client = new RPCClient({ send: (request) => server.handle(request) }); let handlerRan = false; try { await client.call("tasks.create", { title: "no" }); handlerRan = true; } catch (error) { console.log(error.details.map((issue) => issue.path).join(","), handlerRan); }

The title is too short, so the schema rejected the payload and the handler never ran. The client throws, and details lists every problem with its path so the caller can fix the request.

 What does this print? import { createRPCProcedure, RPCClient, RPCError, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.get", async (input) => { throw new RPCError(`Task ${input.id} not found`, { code: "TASK_NOT_FOUND", statusCode: 404, expose: true, }); })); const client = new RPCClient({ send: (request) => server.handle(request) }); try { await client.call("tasks.get", { id: 7 }); } catch (error) { console.log(error.code, "-", error.message); }

The handler threw an RPCError with expose: true, so its code and message reach the caller unchanged. That is how you send a deliberate, safe error message.

 A handler crashes with an ordinary error. What does this print? import { createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(undefined, undefined, { onInternalError: (error) => console.log("[server log]", error.message), }); server.register(createRPCProcedure("tasks.export", async () => { throw new Error("connect ECONNREFUSED 10.0.0.5:5432"); })); const client = new RPCClient({ send: (request) => server.handle(request) }); try { await client.call("tasks.export", {}); } catch (error) { console.log("[caller]", error.message); }

The real message contains a host and a port that an outsider must never see. The caller gets a fixed message, and the real error goes to onInternalError, where you log it.

 A handler throws a NotFoundError from @zudojs/errors. What does this print? import { NotFoundError } from "@zudojs/errors"; import { createRPCMemoryTransport, createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.get", async (input) => { throw new NotFoundError(`Task ${input.id} not found`); })); const client = new RPCClient(createRPCMemoryTransport(server)); try { await client.call("tasks.get", { id: 7 }); } catch (error) { console.log(error.code, "-", error.message); }

A NotFoundError is meant for the caller (its expose flag is true), so its message arrives under the matching code, RPC_NOT_FOUND. An ordinary error, with no expose, would become RPC_INTERNAL_ERROR with the fixed message.

 The memory transport copies each frame through JSON, as a network would. What does this print? import { createRPCMemoryTransport, createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); server.register(createRPCProcedure("tasks.summary", async () => ({ dueAt: new Date(Date.UTC(2026, 9, 1, 9, 0)), tags: new Set(["home", "shopping"]), note: undefined, count: 2, }))); const client = new RPCClient(createRPCMemoryTransport(server)); console.log(await client.call("tasks.summary", {}));

With plain JSON, the default, the Date became a string, the Set became an empty object, and the undefined field disappeared, all without an error. Design results as plain JSON: ISO strings, arrays and null.

 A procedure returns a due date and a set of tags. What is the safest result shape?

Results travel as JSON. Dates as ISO strings and sets as arrays arrive exactly as sent, and even programs not written in JavaScript can read them. When both sides are your own TypeScript code, createRPCJsonSerializer({ preserveTypes: true }) on both ends keeps richer types.

 A frame's metadata says { userId: "admin" }. Can the handler trust it?

Metadata is useful for request ids and trace ids, but never for deciding who the caller is. Identity that your code verified (for example after checking a token) goes in handle(frame, { auth }).

 What does this print? import { createRPCProcedure, createRPCRequest, RPCAuthenticationError, RPCMiddlewareStack, RPCServer } from "@zudojs/rpc"; const requireUser = async (context, next) => { const userId = context.auth?.userId; if (typeof userId !== "string") throw new RPCAuthenticationError("Sign in first."); context.set("userId", userId); return next(); }; const server = new RPCServer(undefined, new RPCMiddlewareStack([requireUser])); server.register(createRPCProcedure("tasks.mine", async (_input, context) => context.get("userId"))); const frame = createRPCRequest({ id: "req-1", procedure: "tasks.mine", payload: {}, metadata: { userId: "admin" }, }); const anonymous = await server.handle(frame); const verified = await server.handle(frame, { auth: { userId: "ada" } }); console.log(anonymous.success, verified.success, verified.result);

The first call only claimed to be admin in its metadata, and nothing verified that, so the middleware refused it. The second call had a verified identity, and the handler used ada.

 What does this print? import { createRPCProcedure, createRPCRequest, RPCForbiddenError, RPCMiddlewareStack, RPCServer } from "@zudojs/rpc"; const adminOnly = async (context, next) => { if (context.auth?.role !== "admin") throw new RPCForbiddenError("Admins only."); return next(); }; const server = new RPCServer(undefined, new RPCMiddlewareStack([adminOnly])); server.register(createRPCProcedure("tasks.deleteAll", async () => "deleted")); const frame = createRPCRequest({ id: "r1", procedure: "tasks.deleteAll", payload: {}, metadata: { role: "admin" }, }); const user = await server.handle(frame, { auth: { userId: "bo", role: "user" } }); const admin = await server.handle(frame, { auth: { userId: "ada", role: "admin" } }); console.log(user.error.message, admin.result);

The middleware only reads context.auth. Bo's metadata claims role: "admin", but his verified role is user, so he is refused. Ada's verified role is admin.

 RPC middleware works like HTTP middleware. What does this print? import { createRPCProcedure, createRPCRequest, RPCMiddlewareStack, RPCServer } from "@zudojs/rpc"; const log = []; const outer = async (context, next) => { log.push("outer before"); const result = await next(); log.push("outer after"); return result; }; const inner = async (context, next) => { log.push("inner"); return next(); }; const server = new RPCServer(undefined, new RPCMiddlewareStack([outer, inner])); server.register(createRPCProcedure("tasks.list", async () => { log.push("handler"); return []; })); await server.handle(createRPCRequest({ id: "r1", procedure: "tasks.list", payload: {} })); console.log(log.join(" > "));

Each middleware gets next(). Code before await next() runs on the way in, in order. Code after it runs on the way out, once the handler and the inner middleware are done.

 Why does the fetch handler's auth option compare the token with timingSafeEqualString instead of ===?

A constant-time comparison takes the same time whether the first or the last character is wrong, so the timing reveals nothing about the secret.

 Two real services must share the RPC token. How should they get it?

Secrets never go in source code. Each side reads TASKS_RPC_TOKEN from the environment, and a service that finds it missing or shorter than 32 characters stops at startup instead of running unprotected.

 The HTTP transport's fetch option hands each request straight to the fetch handler, so no real server is needed. A caller sends a guessed token. What does this print? import { createRPCFetchHandler, createRPCHttpTransport, createRPCProcedure, RPCAuthenticationError, RPCClient, RPCServer } from "@zudojs/rpc"; let runs = 0; const server = new RPCServer(); server.register(createRPCProcedure("tasks.list", async () => { runs += 1; return []; })); const handler = createRPCFetchHandler(server, { auth: (request) => { if (request.headers.get("authorization") !== "Bearer right-token") { throw new RPCAuthenticationError("A valid service token is required."); } return { caller: "web-app" }; }, }); const intruder = new RPCClient(createRPCHttpTransport({ url: "http://tasks.local/rpc", headers: { authorization: "Bearer guessed-token" }, fetch: (input, init) => handler(new Request(input, init)), })); try { await intruder.call("tasks.list", {}); } catch (error) { console.log(error.name, error.code, "runs:", runs); }

Throwing RPCAuthenticationError in auth refuses the call before any procedure runs. The handler answers with an RPC error frame, and the client rebuilds it as a typed RPCAuthenticationError. Any other error thrown in auth would be answered as an internal error.

 Someone posts a plain-text body to the RPC endpoint, as an HTML form or a curious visitor might. What does this print? import { createRPCFetchHandler, RPCServer } from "@zudojs/rpc"; const handler = createRPCFetchHandler(new RPCServer()); const response = await handler(new Request("http://tasks.local/rpc", { method: "POST", headers: { "content-type": "text/plain" }, body: "hello", })); const body = await response.json(); console.log(response.status, body.success, body.error.code);

The fetch handler refuses anything that is not a JSON POST, limits the body size (1 MiB by default), and answers every failure with an RPC error frame, never an HTML page or a stack trace.

 A call through createRPCHttpTransport times out on the client. What happens on the server?

The HTTP transport passes cancellation along. The server stops working for a caller that has left, as long as the handler looks at context.signal or passes it on.

 A procedure has a timeout and its handler loops through slow steps. What must the handler do so it really stops?

A timeout does not stop a handler by force. The server aborts context.signal, and the handler must look at it, or pass it on to fetch and database calls.

 When does a caller need to send a deadline in metadata.deadline?

createRPCMemoryTransport and createRPCHttpTransport carry a timeout or an abort to the server, which aborts context.signal. A hand-written transport may not, so the caller sends a point in time instead, and the server stops by then, never later.

 Which error is worth retrying?

Only retry errors that can go away. A validation or permission error fails the same way every time, so retrying only adds load.

 A tasks.create call timed out. Is it safe to retry it automatically?

Only retry calls that are safe to repeat, like reading a list. idempotent: true on a procedure documents that; the package does not retry anything by itself.

 What does this print? import { retry, RPCUnavailableError } from "@zudojs/rpc"; let calls = 0; const result = await retry(async () => { calls += 1; if (calls < 3) throw new RPCUnavailableError("restarting"); return "tasks"; }, { attempts: 4, delay: 10, backoff: "exponential", jitter: "none", onRetry: (error, attempt, wait) => console.log(`attempt ${attempt}: wait ${wait} ms`), }); console.log(result, calls);

With exponential backoff the wait doubles after each failure: 10 ms, then 20 ms. The third attempt worked, so retry returned its result and did not use the fourth.

 What does this print? import { retry, RPCError, RPCUnavailableError } from "@zudojs/rpc"; let calls = 0; try { await retry(async () => { calls += 1; throw new RPCError("Title is too short", { code: "BAD_TITLE" }); }, { attempts: 4, delay: 10, jitter: "none", retryIf: (error) => error instanceof RPCUnavailableError, }); } catch (error) { console.log(`gave up after ${calls} call(s): ${error.message}`); }

retryIf says only unavailable errors are worth another try. This error is not one, so retry gives up at once and throws the original error.

 The lesson uses jitter: "none". What should you use in production, and why?

If a thousand clients all retry after exactly 100 ms, they hit the service together and knock it down again. Random jitter spreads them out. The example only turns it off so its output is the same every run.

Build a tiny RPC server by hand. Finish handle(frame): look up frame.procedure in procedures. If it exists, return { id, success: true, result } with the handler's result. If not, return { id, success: false, error: "not found" }. Never throw. The program should print the two lines in the comments.

 const procedures = new Map([ ["tasks.count", async (input) => input.titles.length], ]); async function handle(frame) { // your code here } console.log(await handle({ id: "r1", procedure: "tasks.count", payload: { titles: ["a", "b"] } })); // { id: 'r1', success: true, result: 2 } console.log(await handle({ id: "r2", procedure: "tasks.delete", payload: {} })); // { id: 'r2', success: false, error: 'not found' } const procedures = new Map([ ["tasks.count", async (input) => input.titles.length], ]); async function handle(frame) { const procedure = procedures.get(frame.procedure); if (!procedure) return { id: frame.id, success: false, error: "not found" }; const result = await procedure(frame.payload); return { id: frame.id, success: true, result }; } console.log(await handle({ id: "r1", procedure: "tasks.count", payload: { titles: ["a", "b"] } })); // { id: 'r1', success: true, result: 2 } console.log(await handle({ id: "r2", procedure: "tasks.delete", payload: {} })); // { id: 'r2', success: false, error: 'not found' } { id: 'r1', success: true, result: 2 } { id: 'r2', success: false, error: 'not found' }

This is the core of an RPC server: find the procedure by name, run it, and answer with the request's id. An unknown name becomes an answer with success: false, never a crash.

Finish toWire(error), which turns a thrown error into what the caller may see. If error.expose is true, return { code: error.code, message: error.message }. Otherwise return { code: "INTERNAL", message: "Something went wrong." } and never the real message. The program should print the two lines in the comments.

 function toWire(error) { // your code here } const notFound = Object.assign(new Error("Task 7 not found"), { code: "TASK_NOT_FOUND", expose: true }); const crash = new Error("connect ECONNREFUSED 10.0.0.5:5432"); console.log(toWire(notFound)); // { code: 'TASK_NOT_FOUND', message: 'Task 7 not found' } console.log(toWire(crash)); // { code: 'INTERNAL', message: 'Something went wrong.' } function toWire(error) { if (error.expose === true) return { code: error.code, message: error.message }; return { code: "INTERNAL", message: "Something went wrong." }; } const notFound = Object.assign(new Error("Task 7 not found"), { code: "TASK_NOT_FOUND", expose: true }); const crash = new Error("connect ECONNREFUSED 10.0.0.5:5432"); console.log(toWire(notFound)); // { code: 'TASK_NOT_FOUND', message: 'Task 7 not found' } console.log(toWire(crash)); // { code: 'INTERNAL', message: 'Something went wrong.' } { code: 'TASK_NOT_FOUND', message: 'Task 7 not found' } { code: 'INTERNAL', message: 'Something went wrong.' }

Hiding is the default; showing is the exception you opt into. The crash's message names a host and a port, so it must stay on the server, in the logs.

Make a result safe for the wire. Finish toPlain(summary): return an object where dueAt is an ISO string, tags is an array, and note is null when it is undefined. The program should print the line in the comment.

Write the check a requireUser middleware makes. Finish callerId(context): return context.auth.userId when it is a string, and throw an Error with the message Sign in first. otherwise. Never read context.metadata. The program should print the two lines in the comments.

Finish waits(delay, failures, backoff): return the list of waits before each retry. With "exponential" the wait doubles each time; with "linear" it grows by delay each time. The program should print [ 100, 200, 400 ] and then [ 100, 200, 300 ].

 function waits(delay, failures, backoff) { // your code here } console.log(waits(100, 3, "exponential")); console.log(waits(100, 3, "linear")); function waits(delay, failures, backoff) { const out = []; for (let attempt = 1; attempt <= failures; attempt++) { out.push(backoff === "exponential" ? delay * 2 ** (attempt - 1) : delay * attempt); } return out; } console.log(waits(100, 3, "exponential")); console.log(waits(100, 3, "linear")); [ 100, 200, 400 ] [ 100, 200, 300 ]

Exponential backoff is delay * 2 ** (attempt - 1): 100, 200, 400. Linear is delay * attempt: 100, 200, 300. Growing waits give a struggling service time to recover.

Finish sameToken(a, b), a comparison that does not stop at the first difference. If the lengths differ, return false. Otherwise look at every character: combine the differences of charCodeAt with |= and ^, and return whether the total is 0. The program should print true false false.

 function sameToken(a, b) { // your code here } console.log(sameToken("s3cret-token", "s3cret-token"), sameToken("s3cret-token", "x3cret-token"), sameToken("short", "longer")); function sameToken(a, b) { if (a.length !== b.length) return false; let diff = 0; for (let i = 0; i < a.length; i++) { diff |= a.charCodeAt(i) ^ b.charCodeAt(i); } return diff === 0; } console.log(sameToken("s3cret-token", "s3cret-token"), sameToken("s3cret-token", "x3cret-token"), sameToken("short", "longer")); true false false

 A body that is valid JSON but not a frame reaches handle. What does this print? import { RPCServer } from "@zudojs/rpc"; const server = new RPCServer(); try { const response = await server.handle({ hello: "world" }); console.log("answered:", response.success); } catch { console.log("threw"); }

 The service never comes back. What does this print? import { retry, RPCUnavailableError } from "@zudojs/rpc"; let calls = 0; try { await retry(async () => { calls += 1; throw new RPCUnavailableError("down"); }, { attempts: 3, delay: 5, backoff: "linear", jitter: "none" }); } catch (error) { console.log(`gave up after ${calls} calls`, error instanceof RPCUnavailableError); }

 Each step takes 50 ms and the client gives up after 75 ms, first through the memory transport, then through a hand-written one. What does this print? import { createRPCMemoryTransport, createRPCProcedure, RPCClient, RPCServer } from "@zudojs/rpc"; const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const server = new RPCServer(); server.register(createRPCProcedure("tasks.report", async (_input, context) => { for (let step = 1; step <= 5; step += 1) { await sleep(50); if (context.signal.aborted) return console.log(`stopped at step ${step}`); } console.log("ran all 5 steps"); })); for (const transport of [createRPCMemoryTransport(server), { send: (request) => server.handle(request) }]) { try { await new RPCClient(transport).call("tasks.report", {}, { timeout: 75 }); } catch (error) { console.log(error.code); } await sleep(300); }
