"npm" is two things with one name. Which two?

The registry is the huge public library. The npm command, installed with Node.js, downloads packages from it, runs your scripts and publishes your own packages.

 Before you install a package you have not used before, what does the lesson tell you to do first?

Anyone can publish to the registry, so look before you install. npm view shows what the registry knows, including how many dependencies the package pulls in.

 After npm install ms in a new project, which three things changed?

The code goes into node_modules, the range goes into package.json ("ms": "^2.1.3"), and the exact version goes into the lockfile.

 The ms package is installed. What does this print? import ms from "ms"; console.log(ms("2 days")); console.log(ms("10s")); console.log(ms(3_600_000), ms(3_600_000, { long: true }));

ms turns text into milliseconds (2 days is 172,800,000 ms) and a number back into short text, or long text with { long: true }.

 What does this print? import ms from "ms"; console.log(ms(90_000), ms(1_500), ms("hello"));

ms rounds when it turns a number into text, so 90,000 ms (1.5 minutes) becomes 2m. Text it does not understand gives undefined. The README tells you about details like these.

 You write import ms from "ms" (no ./ in front). Where does Node.js look for it?

A name without ./ or ../ is a package name, and Node.js looks for it in node_modules. It never downloads anything while your program runs.

 Should you commit node_modules to Git?

node_modules can hold thousands of files and is rebuilt with one command. The lockfile, on the other hand, must be committed.

 Which package belongs in devDependencies (npm install -D)?

Dev dependencies are tools for developing: formatters, test runners, TypeScript. Anything your program imports while it runs is a normal dependency.

 Why does it help to keep tools like Prettier out of the normal dependencies?

Every installed package is code from strangers. Leaving tools off the server means less code there that could be attacked.

 What does "type": "module" in package.json do?

With "type": "module", Node.js treats your .js files as ES modules. You set it with npm pkg set type=module.

 package.json is plain JSON, so code can read it. What does this print? const pkg = JSON.parse(`{ "name": "task-tools", "version": "1.0.0", "dependencies": { "ms": "^2.1.3" }, "devDependencies": { "prettier": "^3.9.9", "esbuild": "^0.28.2" } }`); console.log(`${pkg.name} ${pkg.version}`); for (const section of ["dependencies", "devDependencies", "peerDependencies"]) { console.log(section, Object.keys(pkg[section] ?? {}).length); }

The file has no peerDependencies, so pkg[section] is undefined, and ?? {} gives an empty object with 0 keys instead of throwing.

 What does this print? const pkg = { scripts: { start: "node due.js", format: "prettier --write .", "check-format": "prettier --check .", }, }; for (const [name, command] of Object.entries(pkg.scripts)) { const how = name === "start" || name === "test" ? `npm ${name}` : `npm run ${name}`; console.log(`${how} -> ${command}`); }

start and test are special names that work without run. Every other script needs npm run <name>.

 The script "format": "prettier --write ." works even though prettier is not installed globally. Why?

When npm runs a script, the tools from node_modules are available by name, so you don't need npx or a global install.

 npm run check-format finds a badly formatted file. Why is it useful that it ends with a non-zero exit code?

Exit code 0 means success, anything else means failure. Automated builds look at the exit code, not at the text, to decide whether a step passed.

 What does the script "dev": "node --watch server.js" do?

--watch is built into Node.js. It is handy while writing a server: save, and the new code is already running.

 A package goes from 2.1.3 to 3.0.0. What does semantic versioning tell you?

In MAJOR.MINOR.PATCH, PATCH is for bug fixes, MINOR for new features that keep old code working, and MAJOR for changes that can break it.

 Your package.json says "ms": "^2.1.0". Which version could npm install?

A caret accepts new minor and patch versions, starting at the version given, but never a new major. So 2.9.0 fits; 2.0.0 is too old and 3.0.0 is a new major.

 Your package.json says "ms": "~2.0.1". Which versions from this list could npm install: 2.0.0, 2.0.1, 2.0.9, 2.1.0, 3.0.0?

A tilde range allows only newer patch versions, starting at the version given. 2.1.0 is a new minor, and 2.0.0 is older than 2.0.1.

 What does a range with no symbol, like "ms": "2.1.0", accept?

No symbol means exact: that version and nothing else. npm install writes a caret (^) by default.

 Why does ^0.2.0 accept only 0.2.x versions, and not 0.3.0?

Versions starting with 0. are treated as unstable. Edge cases like this are why real code uses the semver package instead of a hand-written check.

 What does this print? const parse = (version) => version.split(".").map(Number); console.log(parse("2.10.3")); console.log("2.10.0" > "2.9.0");

map(Number) turns each part into a number. Comparing whole version strings is wrong: text is compared character by character, and "1" comes before "9", so "2.10.0" > "2.9.0" is false.

 This is the lesson's caret check. What does it print? function parse(version) { return version.split(".").map(Number); } function isNewerOrSame(a, b) { for (let i = 0; i < 3; i++) { if (a[i] !== b[i]) return a[i] > b[i]; } return true; } function satisfiesCaret(version, range) { const v = parse(version); const base = parse(range.slice(1)); return v[0] === base[0] && isNewerOrSame(v, base); } console.log(["1.4.0", "1.3.9", "1.10.0", "2.0.0"].map((v) => satisfiesCaret(v, "^1.4.0")));

The major number must be 1, and the version must be at least 1.4.0. 1.3.9 is too old, 1.10.0 is newer (10 is more than 4 as a number), and 2.0.0 is a new major.

 What does this print? const versions = ["2.10.0", "2.9.0", "2.1.3"]; console.log([...versions].sort()); const byNumber = (a, b) => { const x = a.split(".").map(Number); const y = b.split(".").map(Number); return x[0] - y[0] || x[1] - y[1] || x[2] - y[2]; }; console.log([...versions].sort(byNumber));

Plain sort() compares text, so 2.10.0 lands before 2.9.0. Comparing the numbers part by part gives the real order.

 You type npx semvr --range "^2.1.0" 2.9.0 (with a typo) and npx asks "Ok to proceed?". What should you do?

npx downloads a package and runs it on your computer. A spelling mistake can run someone else's package, so read the name before you type y.

 What does package-lock.json record?

A range can match a different version next month. The lockfile pins the exact version, the download address and an integrity hash, so everyone gets the same code.

 What does npm do with the integrity value in the lockfile?

integrity is a SHA-512 fingerprint of the package. If the file you download has been changed, the fingerprint differs and npm stops.

 Which command should a server or an automated build use to install packages?

npm ci ("clean install") gives the server the code you tested, byte for byte. If package.json and the lockfile are out of sync, it stops instead of guessing.

 npm outdated shows ms Current 2.0.0 Wanted 2.1.3 Latest 3.0.0. What does "Wanted" mean?

Current is what is installed, Wanted is the newest version your range allows, and Latest is the newest version published. npm update moves to Wanted.

 ms is at 2.1.3, the range is ^2.0.0, and 3.0.0 is out. What happens when you run npm update?

A major version can break your code, so you move to it on purpose with npm install ms@latest, after reading the changelog.

 This works out what npm outdated calls "Wanted". What does it print? const published = ["2.0.0", "2.1.3", "2.4.1", "3.0.0", "3.1.0"]; const major = (v) => Number(v.split(".")[0]); const allowed = published.filter((v) => major(v) === 2); console.log("Wanted:", allowed.at(-1), "Latest:", published.at(-1));

With a caret range on major 2, the newest allowed version is 2.4.1. "Latest" ignores your range and is simply the newest published version.

 What do npm workspaces let you do?

The root lists package folders with "workspaces": ["packages/*"]. npm install links them into node_modules, so a change in the folder is seen at once.

 Why does the workspace root's package.json have "private": true?

npm refuses to publish a package marked private. The root only groups the real packages, so it should never be published.

 What should you always do before npm publish?

The registry is public and permanent. npm pack --dry-run lists the files without sending anything, so you can spot a test file or, much worse, a .env.

 A package folder contains index.js, index.test.js and a .env file with secrets. What is the safe way to publish only index.js?

By default npm packs everything in the folder, including .env. An allow-list keeps every new file private until you add it on purpose. A secret that was published once must be treated as leaked.

 What does npm audit do?

npm audit reports packages with known vulnerabilities, how serious they are and whether a fixed version exists. npm audit fix moves to a fixed version inside your range.

 npm audit suggests npm audit fix --force. What is the risk?

Plain npm audit fix stays inside your ranges. --force is allowed to cross a major version, so check the changes before you use it.

 A package you have never heard of asks to run an install script. What should you do?

An install script can do anything your user can do, which is why malicious packages love them. Only approve a script you have reviewed from a package you trust.

 After npm install-scripts approve esbuild, package.json contains "allowScripts": { "esbuild@0.28.2": true }. What happens when esbuild releases a new version?

The approval is pinned to one version. A new version could contain a changed script, so you review it again.

 What is typosquatting?

In 2017, crossenv copied the popular cross-env and sent everyone's environment variables to its author. Copy names from official docs and check them with npm view.

 What does provenance on an npm package tell you?

Provenance lets you trace a package back to its source. npm audit signatures checks it, and you add --provenance to npm publish when publishing from GitHub Actions.

Finish bump(version, part), like npm version patch|minor|major. Raising a part sets the parts after it to 0.

 function bump(version, part) { // your code here } console.log(bump("1.4.2", "patch"), bump("1.4.2", "minor"), bump("1.4.2", "major"), bump("0.9.9", "patch")); function bump(version, part) { const [major, minor, patch] = version.split(".").map(Number); if (part === "major") return `${major + 1}.0.0`; if (part === "minor") return `${major}.${minor + 1}.0`; return `${major}.${minor}.${patch + 1}`; } console.log(bump("1.4.2", "patch"), bump("1.4.2", "minor"), bump("1.4.2", "major"), bump("0.9.9", "patch")); 1.4.3 1.5.0 2.0.0 0.9.10

Split the version into three numbers. A major bump resets minor and patch, a minor bump resets patch, and a patch bump only adds 1 to the last number (so 0.9.9 becomes 0.9.10).
