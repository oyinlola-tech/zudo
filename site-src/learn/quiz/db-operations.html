Why do servers talk to PostgreSQL through a connection pool instead of opening a connection per request?

Reusing a few open connections removes the setup cost from every request and keeps the total under max_connections.

 PostgreSQL allows 100 connections. You run 6 app servers, each with new pg.Pool({ max: 20 }). What happens at peak traffic?

Pools do not know about each other. Instances × pool size (plus migrations, cron and people) must stay below max_connections, or you need a pooler such as PgBouncer.

 The lesson's pool of 20 finished 20 pg_sleep(0.2) queries faster than a pool of 5. Why doesn't that mean "bigger pools are always faster"?

A database server with 8 cores cannot execute 200 CPU-bound queries faster than 20. Size pools from the database's capacity, then measure.

 A site works for an hour after each restart, then every request hangs, while the database looks idle. What is the most likely cause?

A leaked client never returns. Once all are leaked, every request waits for a connection. Release in finally, set connectionTimeoutMillis so the failure is loud, and monitor the pool's waiting count.

 What does PgBouncer in transaction pooling mode change?

It lets hundreds of app processes use a database that should hold only dozens of connections. The catch: session state (set, session advisory locks, listen) does not stick to a client between transactions.

 Why did renaming phone to phone_number in one migration break checkouts, although the new code used the new name correctly?

For some minutes, old and new versions share one database. Every schema state must work with every version running at that moment, which a one-step rename cannot.

 What is the correct order for an expand and contract column rename?

Each step is compatible with every version running at that moment. The old column is removed only when no running code uses it.

 An instant alter table … add column is waiting for its lock behind a long report transaction. Why do simple selects on the table start hanging too?

Lock requests are served in order. The migration's request conflicts with everything, so every later query waits behind it. lock_timeout makes the migration give up instead of freezing the table.

 What does set lock_timeout = '2s' before a migration achieve?

It limits waiting for locks, not the work itself. A failed attempt is harmless and retryable; a frozen table is an outage.

 What does adding a check constraint with not valid do?

Adding the constraint becomes quick, and the full scan happens later in validate constraint, under a lock that does not block writes. Existing bad rows can be fixed in between.

 How do you make an existing column not null on a large, busy table without a long exclusive lock?

A plain set not null scans the whole table under an exclusive lock. PostgreSQL 12+ skips that scan when a validated check constraint already proves no nulls exist.

 Why backfill ten million rows in batches of a few thousand instead of one update?

Small batches commit often, can be paused, resumed after a crash, throttled, and watched. Each touches few rows for a short time.

 A migration that ran in production last week has a bug. What should you do?

Databases that already ran the old version will never run an edited one, and down scripts can destroy data written since. Fix forward; the checksum check refuses in-place edits.

 Which rows belong in a seed that runs on every deploy, including production?

Reference data is part of the application's correct behaviour. Development data must never reach production, and test fixtures belong to the tests that use them.

 Why must a deploy-time seed be idempotent?

insert … on conflict (natural key) do update or do nothing makes a seed safe to repeat. Plain inserts duplicate rows or fail on the second run.

 A seed inserts child categories with parent_id = 3, a generated id copied from the developer's laptop. What is the problem?

Seeds must refer to rows by stable natural keys (a slug or code) and look up ids inside the insert, as the lesson's tree seed does.

 Why is a streaming replica not a backup?

Replication protects against losing a server. Backups (and point-in-time recovery) protect against losing data through mistakes, which replicas faithfully reproduce.

 You take a pg_dump every night at 02:00. At 17:30 someone deletes all orders. With only the dump, what is lost?

A dump is a snapshot. Your recovery point objective (RPO) with nightly dumps is up to 24 hours. Point-in-time recovery, from a base backup plus archived WAL, can restore to 17:29:59.

 What proves that your backups work?

Backups fail in quiet ways: wrong database, missing permissions, corrupted files, an encryption key nobody has. Only a restore proves a backup, and it also measures your recovery time.

 With default (asynchronous) streaming replication, what can a read from a replica return right after a commit on the primary?

The primary does not wait for replicas, so they lag by milliseconds normally and by much more under load. Synchronous replication removes the lag for confirmed commits at the cost of slower commits.

 Ada pays for an order and is redirected to her order page, which reads from a replica and shows "unpaid". Which guarantee is broken, and what is a simple fix?

Users expect to see their own changes. Sticky reads after a write, or waiting until the replica has replayed the write's WAL position, keeps that promise while other reads still use replicas.
