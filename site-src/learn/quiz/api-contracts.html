Which of these is part of an API's contract?

A contract is what clients can observe and depend on. Internals such as function names and tables can change freely as long as the observable behaviour does not.

 After switching from PGlite to the pg driver, amountKobo starts arriving as "1000000" instead of 1000000. Why does the driver do this?

The driver chooses correctness over convenience. Your mapper must turn the string into the representation your contract promises, checking that it is a safe integer.

 Transfer ids may one day exceed 253. How should the contract represent them?

JavaScript clients parse JSON numbers into doubles, which cannot hold every integer above 253. A string keeps the exact digits, and JSON has no BigInt type.

 A handler returns { createdAt: new Date(...) }. What does a JavaScript client get after JSON.parse?

JSON.stringify calls the date's toJSON, producing an ISO string, and JSON.parse leaves it as a string. The contract says "type": "string", "format": "date-time".

 What does { "$ref": "#/components/schemas/Transfer" } mean in an OpenAPI document?

# is the document itself, and the rest is a path into it. Shared schemas are written once under components and referenced wherever they are used.

 Why does TransferRequest use additionalProperties: false, while Transfer (the response) does not?

The server controls both schemas but plays different roles: it reads requests (be precise about what you accept) and writes responses (leave room to add fields later).

 What is the difference between a response field typed ["string", "null"] and required, and a field that is simply not required?

Clients write different code for "always there, maybe null" and "maybe not there". The contract should say which one you mean.

 What is the main risk when a team keeps a hand-written OpenAPI document and separate hand-written validation code?

Keep one source of truth: generate validation from the document (contract-first) or the document from the code (code-first), and test the running server against it.

 What does a provider contract test check?

The provider (the server) is exercised like a client would use it, and each response is validated against the contract. It catches drift such as the pg string amounts before release.

 A handler returns 500 with { "error": "oops" } for one test case, and the contract does not list 500 for that operation. What should the provider contract test do?

An undocumented status is contract drift too. Either the handler is wrong, or the contract is missing a response that clients need to know about.

 What does consumer-driven contract testing add to provider tests?

A document says what exists; consumer expectations say what is used. A field no consumer reads can change freely; one the fraud service reads cannot.

 You make the optional request field note required. Who breaks?

For requests, the server is the reader. Narrowing what it accepts turns yesterday's valid requests into today's 400s.

 You add "reversed" to the response enum Transfer.status. Why can this break clients?

Widening a response widens what readers must handle. Announce it, document that clients must handle unknown values, or gate it behind a new version.

 You add "USD" to the enum of the request field currency (which already allowed "NGN"). Is this breaking?

Widening what a reader accepts is safe for writers. The same change on a response enum would be risky, because there the client is the reader.

 Which rule summarises safe evolution?

A change is safe when every unchanged old party can still read what the new party writes. Servers read requests and write responses, so the rules are mirror images.

 You want to rename the response field note to memo without breaking anyone. Which plan works?

Expand, migrate, contract: each step is compatible on its own, and the removal happens only when the evidence (consumer expectations, logs) says nobody depends on the old field.

 Why is evolving an event schema harder than evolving an HTTP response?

An HTTP response is read once, right away. An event written last year can be read again today by a consumer you have never heard of.

 Why does every event carry a unique id in its envelope?

Message delivery is at-least-once. The event id lets a consumer skip events it already handled, exactly as the idempotency key did for transfer requests.

 What does an upcaster do?

Stored events are never rewritten. Upcasters translate them on read, one version step at a time, so adding version 3 means writing one new function.

 Why should a producer validate an event against its schema before publishing it?

A bad HTTP response affects one request. A bad event is permanent history. Catch it where it is created.
