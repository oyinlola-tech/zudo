In the BookStore, what does POST /sessions do?

Register is POST /users. Log in is POST /sessions, which answers with a token. After that, every protected request proves who it is by sending the token in the Authorization header.

 Where does the token-signing secret come from?

Anyone who has the secret can make tokens for any user, so it never goes into the code or into git. loadConfig reads it from the environment and fails fast if it is missing or too short.

 Why does loadConfig refuse TOKEN_SECRET=secret?

A secret is only safe if nobody can guess it. randomBytes(32).toString("hex") gives 64 random characters. A missing secret and a short one are both refused.

 Which is the right way to handle token secrets?

A secret that has been seen elsewhere is not a secret. If it leaks, replacing it makes every token signed with the old one stop working, which is exactly what you want.

 Why does the users table store a password hash and not the password?

A hash is the output of a one-way function. You can check a password against it, but not recover the password from it. Nobody, not even you, should be able to read users' passwords.

 Why is a fast hash like SHA-256 the wrong tool for passwords?

Speed helps the attacker, who tries guess after guess against the stolen hashes. scrypt makes each guess expensive, while one check at log-in is still quick enough for a real user.

 What does the random salt in hashPassword achieve?

Each password gets its own salt, and the salt is stored next to the key: scrypt$salt$key. The same password hashed twice gives different strings, yet both verify correctly.

 Why does verifyPassword compare with timingSafeEqual instead of ===?

timingSafeEqual always takes the same time, wherever the values differ. It throws when the lengths differ, which is why the code checks actual.length === expected.length first.

 What does the HMAC signature on a BookStore token protect against?

The signature is a hash of the content mixed with the secret. Change one character and it no longer matches; without the secret, nobody can make a new one. It does not hide the content.

 A token's payload part decodes to {"sub":7,"exp":1790168400}. What follows from this?

base64url is just a way to write bytes as text; it is not encryption. The signature stops changes, not reading. Keep only what is needed, like the user id and the expiry.

 In the token payload, what are sub and exp?

The payload says who and until when. A BookStore token lives one hour; readToken refuses it once exp * 1000 <= now.

 Why do createToken and readToken take now = Date.now() as a parameter?

Time is an outside dependency, like the fake clock in Classes in TypeScript. The default uses the real time, while tests pass fixed times and get the same result on every run.

 Why does log-in answer Wrong e-mail or password both when the e-mail is unknown and when the password is wrong?

Different messages would let anyone test a list of e-mail addresses and learn who uses the shop. One message for both cases gives them nothing.

 A logged-in client sends {"bookId": 1, "quantity": 1, "userId": 2} to POST /orders. Where must the order's user id come from?

If the client could name the user, any logged-in user could order in someone else's name or read their orders by changing a number. Only the signed token proves who is calling.

 A client calls GET /orders with no Authorization header. What does requireUserId do?

No token, a bad signature and an expired token all mean "we do not know who you are": 401. The route never runs, so nobody's orders are shown.

 Which rule does parseCredentials follow?

Ada@Example.com and ada@example.com are one account. A password is used exactly as typed, but its length is checked (10 to 200 characters).

 UserRepository.create runs INSERT … RETURNING id, email and returns a User with no hash. Why?

Build what you send from chosen fields. The hash is only read in one place, where it is needed, and never sent to a client.

 What is still missing to protect POST /sessions from a script trying a million passwords?

A public log-in route needs a rate limit. The lesson lists it among the missing security layers. The Rate limiting lesson builds one, and ZudoJS provides one in @zudojs/security.

 The token tests start with const secret = randomBytes(32).toString("hex"). Why not paste the real TOKEN_SECRET into the test file?

No real secret ever appears in a test file. The tests only need a secret, and a fresh random one checks the same rules.

 The honest review says the router has no middleware. What is the risk that follows?

Security that depends on remembering a line in each handler fails the first time someone forgets. A framework can attach the check to a whole group of routes in one place.

 Why does the review say the BookStore has no real log-out?

The server checks only the signature and the expiry. A stolen token keeps working for up to an hour. Revoking tokens needs extra state on the server, one of the security layers still missing.
