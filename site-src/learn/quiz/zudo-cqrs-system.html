Ada was charged ₦14,000 but "My orders" showed ₦12,500. What is the real cause?

Every read that re-derives a business decision is a second copy of the rules, and copies drift. A read model built from what the write side decided (the total in the event) cannot disagree with it.

 A new rule says a customer may have at most 5 open orders. Where must it be enforced?

The read model may be seconds behind, so any check against it can let a sixth order through. Rules are enforced where the truth is: the write model, in the transaction that makes the change.

 Who writes to order_summaries in the lesson's design?

One writer per read model keeps it consistent with the events and makes it rebuildable. If command handlers also wrote to it, a rebuild from events would not reproduce what they wrote.

 Right after a successful POST /orders, GET /orders/ORD-1042?minVersion=1 answers 503 with Retry-After: 1. Why is that better than a 404?

Eventual consistency has to be visible in the API. The client passed the version it just received, the server could see it was behind, and it said so with a status that means "temporarily unavailable, retry".

 What does expectedVersion on CancelOrder protect against?

This is optimistic concurrency. The UPDATE … WHERE version = $expected matches only if nothing changed since the client read the order. Ownership is a separate check (customer_id).

 Tunde tries to cancel Ada's order ORD-1. Why does the command answer NotFoundError rather than a "forbidden" error?

Answering the same way for "does not exist" and "not yours" avoids leaking which ids exist. The query side does the same by filtering on the signed-in customer.

 Why does the client choose the order id in PlaceOrder?

A timeout does not tell the client whether the order was placed. With a client-generated id (a UUID in a real app), sending the same command again is safe: the handler finds the existing order and returns its result.

 Why does PlaceOrder read the product with SELECT … FOR UPDATE before decrementing the stock?

Without the lock, two transactions can both read stock 1, both pass the check and both decrement. The CHECK (stock >= 0) constraint is a last line of defence, but the lock makes the check itself correct.

 Tunde's order reserved 1 bottle of oil, then failed on the rice. Afterwards the oil stock is unchanged. Why?

manager.run commits when the callback returns and rolls back when it throws. Every change the command made, including the outbox row it never reached, disappears together.

 With plain @zudojs/cqrs, what does await bus.execute<PlaceOrder, { receiptUrl: string }>(command) do when the handler returns { orderId, version, totalKobo }?

The result type argument is not connected to the handler, so it is a claim. The typed facade in the lesson derives the result type from one map for both registration and execution, which turns this mistake into a compile error.

 The typed facade contains one cast, bus.execute(request, context) as Promise<never>. Why is that acceptable?

You cannot avoid the claim entirely, because the bus stores handlers in an untyped table. You can make it once, in a place whose other half (registration) enforces the same types.

 What does putting @CommandHandlerFor("CancelOrder") on a class do?

The decorator marks; it does not wire. bus.has("CancelOrder") stays false until something reads getCommandHandlerMetadata and registers an instance. Forgetting that step only shows up at runtime.

 The read model of ORD-7 is at version 1, and the projector receives the event with version 3. What does it do, and why?

Only the next version is applied. A gap means an earlier event is still on its way (for example a retry), and the queue's retry gives it time to arrive.

 The event-driven lesson used a processed_events table for idempotency. Why does this projector not need one?

When events of one aggregate are numbered, the version does the job of the processed-events table and also detects out-of-order delivery. Without versions, you need the table.

 Why do the query handlers run in readOnly transactions?

"A query never changes anything" becomes a rule the database enforces, not a convention. The lesson's example tried a DELETE in a read-only transaction and got "cannot execute DELETE in a read-only transaction".

 Why does the command store the traceparent in the outbox row instead of relying on AsyncLocalStorage?

Every storage boundary (a table, a queue, a broker message) breaks the chain. Context crosses it only if you write it down on one side and restore it on the other.

 What does a QueueContextCarrier passed to createInMemoryQueue({ contextCarriers }) do?

The lesson's carrier captured the current traceparent and restored it by starting a consumer span with that parent, so the projection joined the request's trace.

 The queue discards any value a caller puts in job metadata under its own key "zudo:context". Why?

Context that decides behaviour (a tenant, for example) must come from the trusted side. Letting any enqueuer set it would let one tenant's request run work as another.

 What makes it possible to delete order_summaries and rebuild it?

Replaying the recorded events through the projector reproduces the read model. That only holds if nothing else writes to it and the events are kept.

 While backfilling customer_stats, the projector had to remember each order's total from order.placed to handle order.cancelled. What does that teach?

Design events with their consumers in mind: the facts that happened, with enough context to use them. Not everything, but not so little that every projector needs its own memory.

 Where is full CQRS (separate read models fed by events) most likely not worth it?

A small form over one table gains nothing from a projector, a queue and eventual consistency. Use a transaction and a query over the same table, and keep CQRS for reads that really differ from the writes.

Here the fake read model catches up on the fourth request. The first read succeeds then; the second gives up after three tries because version 2 never arrives, and the app can show "still processing" instead of waiting forever. A real client would also honour the Retry-After header.
