Why does reading the 5,000th item of a linked list cost O(n), when it is O(1) in an array?

An array computes the slot's address from the index. A list only knows its head, so reaching item i takes i steps.

 You hold a reference to a node in the middle of a 100,000-node singly linked list. What does inserting a new node right after it cost?

Nothing shifts in a linked list. That is its main advantage over an array, where inserting in the middle moves every later item.

 A singly linked list keeps both head and tail. Why is removing the last node still O(n)?

A prev pointer (a doubly linked list) makes this O(1). Adding at the back and removing at the front are O(1) either way.

 Which pair of operations turns a singly linked list with a tail into an O(1) queue?

Adding at the tail and removing at the head are both O(1). The last option is a stack (LIFO), and the first two need the O(n) remove-last.

 A popFront sets this.head = node.next but never touches this.tail. What goes wrong after popping the only node?

When the list becomes empty, both head and tail must become null. One-node and empty lists are where most linked list bugs hide.

 In the in-place reversal, why must const next = current.next run before current.next = previous?

Turning the arrow around destroys the only link forward. Save it first, then rewire, then advance.

 A recursive reversal is only a few lines long. What does it cost compared with the loop?

Each recursive call waits for the next one, so all n frames exist at once. The three-pointer loop uses O(1) extra space.

 The Set-based cycle detector stores node objects, not approver names. Why?

Sets compare objects by identity, which is exactly "have I been at this node before?". Names would report false cycles.

 In Floyd's cycle detection, why must the fast pointer eventually land on the slow one when there is a cycle?

A gap that shrinks by one per step cannot jump over zero. Without a cycle, the fast pointer simply reaches null.

 What is the main advantage of Floyd's algorithm over the Set version?

Both are O(n) time and both are correct. Floyd's needs only two pointers, which matters for huge lists or many checks.

 An admin can set any approver's "next approver". What is the best way to handle cycles in the approval chain?

Validating at write time stops bad data entering the system. Defensive reads protect against data that got in anyway.

 What does the extra prev pointer in a doubly linked list buy you?

It costs one more pointer per node. In return, removing a node never needs a search for its predecessor, which is what an LRU cache relies on.

 Why does the doubly linked list use two permanent dummy (sentinel) nodes?

With sentinels, remove is always the same two pointer updates. Without them, removing the first or last node needs extra branches, a common source of bugs.

 remove(node) sets node.prev = node.next = null after unlinking it. What does that protect against?

A second remove on a detached node now throws a TypeError (reading next of null) instead of silently breaking other nodes.

 In the LRU cache, what is the Map for, and what is the doubly linked list for?

Neither is enough alone: a list cannot find a key without scanning, and (conceptually) a plain hash map has no order. Together every operation is O(1).

 Why does each list node in the LRU store its key, not only its value?

Eviction starts from the list (the least recently used node) and must clean up the map too. Without the key in the node, you would need an O(n) search of the map.

 In an LRU cache, why must get move the entry to the front?

"Least recently used" means reads count. The trace in the lesson shows RICE surviving an eviction only because it was read again.

 A price changes in the pricing service but the LRU cache keeps serving the old one for hours, because the product is popular. What is missing?

Eviction and freshness are separate policies. Popular entries never get evicted, so they need a time limit or an explicit delete when the source changes.

 A popular product's cache entry expires, and 500 requests for it arrive in the next 100 ms. With a simple cache, each misses and calls the pricing service. What is the usual fix?

This is a cache stampede. Sharing one in-flight request per key turns 500 service calls into 1.

 Summing a million numbers takes O(n) in both an array and a linked list, yet the array is many times faster. Why?

Big O ignores memory layout. In practice, cache locality often decides, which is why arrays are the default and linked lists are used for their O(1) moves.

 How can you build an LRU cache in JavaScript with only a Map?

Maps iterate in insertion order, and re-inserting moves a key to the end. Both steps are O(1), so this is a real, short LRU in JavaScript.

 A product cache has 2,000 hits and 8,000 misses per hour. What does this suggest?

Hit rate = hits / (hits + misses). Measure it before and after changing capacity or key design; a cache that rarely hits is mostly overhead.
