A restaurant asks you for "a function that splits the bill between friends". What should you do before writing any code?

The method starts on paper: understand, inputs, outputs, edge cases, pseudocode. Questions like "what if there are 0 friends?" or "who pays the leftover kobo?" are cheap to answer now and expensive to discover later.

 You are writing averageScore(scores) for a class. Which input is an edge case that needs its own decision?

An empty class means dividing by zero students. The function must decide what to return (for example "no average"), and a test should record that decision. The other options are normal cases.

 Why does if (n % 2 === 1) return "odd"; return "even"; call -3 even?

In JavaScript the remainder keeps the sign of the left number: -3 % 2 is -1. Comparing with 0 (n % 2 === 0 means even) works for every sign.

 A largest-of-three function starts with let best = 0; and then replaces best with any bigger input. Which test exposes the bug?

With all negative inputs nothing is bigger than 0, so it returns 0, which is not one of the inputs. Start with the first input instead: it is a real candidate.

 A grade function checks score >= 40 (E) first, then score >= 45 (D), and so on up to score >= 70 (A), returning at the first match. What grade does a score of 95 get?

95 is at least 40, so the very first check matches and returns E. With a chain of >= checks, go from the highest grade down, so each check only sees scores that failed the ones above.

 Delivery is free when the goods cost ₦20,000 or more. Prices are in kobo. Which pair of tests best checks this rule?

A boundary pair tests one value exactly on the limit and one just past it. It is the only way to tell >= from >: both give the same answer for ₦5,000 and ₦50,000.

 An ATM function checks "amount is more than the balance" before "amount is a positive whole number". What goes wrong?

All checks must still pass, so the same requests are refused. But the first failing check decides the message. Check whether the request makes sense at all before you look at the account.

 Why does ageOn take today's date as parameters instead of reading the computer's clock?

A function that reads the clock gives a different answer every day. Making time an input keeps the function predictable and testable; the real program passes in the clock's date at its very edge.

 Why does the workshop store ₦149.99 as 14999?

Decimal fractions are stored approximately, so sums drift by tiny amounts. Whole kobo are exact. You divide by 100 only to display the amount.

 A test fails with FAIL body heat: got 97.88000000000001, expected 97.88. What is the best fix?

The formula is right; decimals are stored approximately. Decide what precision matters and compare at that precision. Copying the strange number into the test would lock in an accident, not a requirement.

 With the workshop's made-up bands (first ₦800,000 at 0%, next ₦2,200,000 at 15%, the rest at 20%), how much tax does someone earning ₦3,500,000 pay?

₦0 on the first ₦800,000, 15% of ₦2,200,000 = ₦330,000, and 20% of the last ₦500,000 = ₦100,000. Total ₦430,000. Only the slice above each line pays the higher rate; 20% of the whole income (₦700,000) is the classic misunderstanding.

 A cart function adds ₦1,500 delivery whenever the subtotal is below ₦20,000. What does it charge for an empty cart, and is that right?

0 is below ₦20,000, so the rule charges delivery for nothing. The empty cart needs its own rule, which is why "empty input" belongs in every edge-case table.

 The grading scale says "B: 60–69, A: 70–100" and nothing about 69.5. What should you do?

When the problem statement leaves a gap, you have to make a decision. Writing it down and recording it in a test means the next developer knows it was on purpose, and can check it with whoever owns the rules.

 Where should the expected value in a test come from?

A test compares the program with your understanding of the problem. Copying the program's own output only proves the program agrees with itself, bugs included.

 The password checker returns a list of problems instead of true or false. Why?

The output was chosen from the requirement. A boolean says "no" without saying why; a list of problems gives every reason, and its length tells you whether there are any.

 What is a guard clause?

if (!Number.isInteger(amount) || amount <= 0) return "Declined: invalid amount"; is a guard clause. Bad cases leave first; only valid input reaches the main logic.

 Why does the parity problem include a test with "4" (in quotes)?

Text that looks like a number is one of the most common inputs a real program meets. Number.isInteger("4") is false, so the function answers "invalid" instead of guessing.

 The leap-year rule is: divisible by 4, except years divisible by 100, unless also divisible by 400. Which set of test years covers every part of the rule?

2024 (by 4: leap), 2026 (not by 4), 1900 (by 100 but not 400: not leap) and 2000 (by 400: leap). Each part of the rule gets at least one test; the other sets leave parts untested.

 Someone writes f - 32 * 5 / 9 for Fahrenheit to Celsius. What happens?

As in school maths, * and / run before -. The formula needs (f - 32) * 5 / 9. A known test like 212 °F = 100 °C catches the mistake at once.

 A promotion gives "20% off, up to ₦5,000 off". Which price shows that the cap is working?

20% of ₦40,000 is ₦8,000, over the cap, so the discount must become ₦5,000. At ₦10,000 or ₦20,000 the discount is under the cap and the cap never runs.

−2 × price is a negative amount, so the total goes down. Invalid input that changes money is a security problem, not just a bug: refuse it.
