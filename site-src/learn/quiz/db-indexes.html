In which order should you read an explain plan?

A plan is a tree. Leaves such as scans produce rows, and each parent (Sort, Limit, Join) consumes its children's rows. The top line is the last step, which returns the result.

 A plan shows Seq Scan on orders (actual rows=10 loops=1) with Rows Removed by Filter: 99990. What does it tell you?

The scan checked every row against the filter and threw almost all of them away. Work proportional to the table, for an answer of 10 rows, is the classic sign of a missing index.

 Why does a lookup in a B-tree index on 100,000 rows read only two or three index pages?

With hundreds of entries per page, one level narrows the search by a factor of hundreds. The depth grows with the logarithm of the row count, so even billions of rows need only a few levels.

 You have an index on (customer_id, placed_at). Which query can use it efficiently?

A composite index is sorted by its first column, then by the second within each first value. Conditions on a leftmost prefix (customer_id, or customer_id plus placed_at) use it; a condition on placed_at alone finds matches scattered through the whole index.

 The query is where customer_id = $1 and placed_at >= $2 order by placed_at. Which index fits best?

Equality columns first, then the range or sort column. Inside the entries for one customer, the index is ordered by placed_at, so the range is one contiguous stretch and already sorted.

 After adding an index on (customer_id, placed_at desc), the "My orders" plan loses its Sort node. Why does that matter with limit 5?

For a customer with 5,000 orders, a Sort must fetch all 5,000 first. An index in the right order lets the query stop after the first 5, so the cost no longer depends on how many orders the customer has.

 90% of orders have status = 'paid'. There is an index on status, yet where status = 'paid' uses a Seq Scan. Why?

Indexes help selective conditions. The planner estimates the matching fraction from statistics and chooses the cheaper plan. For a rare value such as 'cancelled', the same index is used.

 After a nightly import doubled a table, a query's plan shows rows=120 estimated but actual rows=250000. What should you do first?

Estimates that far from reality mean the statistics are stale, and a plan built on them is probably wrong. Autovacuum analyzes eventually, but after a bulk load you run analyze yourself.

 There is a B-tree index on placed_at. Which condition can use it?

Only the half-open range compares the bare column. The others compute something from the column for every row first, so the index on the column does not match; they would need an index on exactly that expression.

 A unique index exists on lower(email). Which lookup uses it?

An expression index serves queries that use exactly the same expression. Write lookups the way the index is defined, or the planner falls back to a Seq Scan.

 An index is defined as on orders (placed_at) where status = 'pending'. When can the planner use it?

A partial index contains only the rows matching its condition. A query that might need other rows cannot use it, so the query must include that condition (or one that implies it).

 Which rule does create unique index on carts (customer_id) where status = 'open' enforce?

Uniqueness applies only among the rows in the partial index, the open carts. It is also how you keep a value unique among non-deleted rows with soft deletes.

 What does include (total_kobo) add to an index on (customer_id)?

Included columns are payload, not part of the key: they do not affect sorting or searching, but they let the index "cover" the query without visiting the heap.

 An Index Only Scan shows Heap Fetches: 1440 for 1,440 rows. What is going on?

An index cannot tell whether a row is visible to your transaction. For pages the visibility map marks all-visible, the heap visit is skipped. Right after a bulk load nothing is marked yet; vacuum (or autovacuum) sets the bits.

 Which index does PostgreSQL not create automatically?

Primary keys and unique constraints need an index to work. A foreign key only needs one on the referenced side, which already has it. The referencing column, the one you join and delete through, is up to you.

 A table gets four extra indexes. What happens to inserts?

In the lesson, four indexes roughly tripled the WAL records for the same 20,000 rows, and the indexes were larger than the table. Every index is paid for on every write.

 Why can indexing a column like last_seen_at, updated on every request, slow down updates more than you expect?

Heap-only tuple (HOT) updates keep the new row version on the same page and skip every index. Changing an indexed column rules that out, so each update now writes to every index on the table.

 Why do migrations on big tables use create index concurrently?

The trade is time for availability. It cannot run inside a transaction block, and if it fails it leaves an invalid index to drop and retry.

 In pg_stat_statements, what is the difference between sorting by total_exec_time and by mean_exec_time?

A 2 ms query called ten million times a day can cost more than a 3-second report run once. Look at both lists: one for capacity, one for user-facing latency.

 In pg_stat_statements, select * from order_lines where order_id = $1 is cheap per call but has 2,000,000 calls a day, 50 per page view of the order list. What is the fix?

This is the N+1 query problem: one query for the list, then one per row. Each call may already use an index; the cost is the round trips. One set-based query replaces fifty.

 A plan test runs against a test database with 12 orders, and it fails because the plan uses a Seq Scan although the index exists. What is wrong?

Reading one page is cheaper than reading an index page and then a heap page. The planner is right; the test data is unrealistic. Seed the test table with production-like volumes and distributions.

 Which index type fits "find products whose jsonb attributes contain {"colour": "black"}"?

GIN indexes the elements inside composite values (jsonb keys and values, array elements, words in a document), which is what containment queries (@>) need. B-tree is for ordered scalar values.
