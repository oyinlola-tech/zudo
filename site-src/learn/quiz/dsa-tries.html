A search box filters all n product names with startsWith on every keystroke. The customer has typed L characters. What does one keystroke cost?

Every name is checked, and each check compares up to L characters. Built-in methods still do that work. A trie makes finding the prefix O(L), independent of n.

 In a trie, what does the path from the root to a node represent?

Each edge is one character, so a path spells a string. Every word that starts with that string passes through the same node.

 Why does each trie node need an end flag?

"car" ends at a node that also has children (for "card", "care"). Without a flag you could not tell a stored word from a mere prefix, and has("ca") would wrongly say yes.

 A trie of 24,000 product names has 26,062 nodes for 400,880 characters. Why can it still use more memory than the plain array of names?

Node count is not memory. Per-node overhead dominates, so a trie is compact only relative to its number of nodes. Long keys with little sharing make it much worse.

 What does a radix tree (compressed trie) change?

"samsung " as eight single-child nodes becomes one edge. It saves the most for long keys with little branching, such as URL paths, which is why web routers use radix trees.

 What is the compact alternative to a trie for "first k names with this prefix"?

All names with a prefix sit next to each other in sorted order. A lower-bound binary search finds the first in O(L log n), and the next k are the answer. It uses far less memory than a trie, but inserting costs O(n).

 Why can't a Map or Set of product names answer "names starting with sam" efficiently?

A hash map is excellent for exact lookups but knows nothing about prefixes or order. Tries and sorted arrays keep strings with a common prefix together.

 A customer types "smasung". What does a plain trie of product names suggest?

Tries match exact prefixes. Typo tolerance needs fuzzy matching (edit distance), which search engines add on top; a trie is the fast first layer, not the whole search.

 Postcode zones "1", "10" and "100" have different rates. For postcode "105500", which zone applies, and how does the trie find it?

"100" does not match (the third digit is 5). Walking 1 → 0 → 5 passes rated nodes "1" and "10", and the path breaks at 5. The last rate seen belongs to the longest matching prefix. One pass, O(L).

 Your autocomplete API is called on every keystroke by every visitor. Which production measure matters most?

High-frequency endpoints need bounded work per call: a result limit, a maximum prefix length and a rate limit. The trie should be built once (or in the background) and read many times.

 A trie of 2 million products is rebuilt from the database every night. How should the service switch to the new one?

Building off to the side means requests always see a complete trie, old or new, never a half-filled one. The old trie is garbage-collected once nothing refers to it.
