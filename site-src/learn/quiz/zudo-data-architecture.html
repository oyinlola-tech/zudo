A dashboard loads 40 projects with one query, then runs one more query per project to count its open tasks. What is this called, and how many queries does one page view send?

One query for the list plus one per item is the N+1 problem. It grows with the data: 5,000 projects would mean 5,001 queries for one screen.

 The dashboard only needs, for each project, its name and how many open tasks it has. Which design sends the fewest queries and copies the least data into your process?

A grouped query lets the database do the counting and return only the numbers: one query, however many projects. Promise.all sends the same N+1 queries, just at the same time; loading every task copies rows you never show.

 When is "collect the ids, then load all related rows with one IN query" the right fix for an N+1, rather than a grouped SQL query?

Batch loading gives you the rows in 2 queries, which you then group in memory. When all you need is an aggregate, a GROUP BY query is cheaper still.

 Which repository method is the best design for the Task API?

Methods named after questions keep the query boundary in one place: nobody above the repository builds filters, and certainly not from request input. Repositories return entities; mapping to JSON happens at the edge.

 "Two live tasks in one project cannot have the same title." Where must this rule be enforced so that it holds even when two requests arrive at the same moment?

"Check, then insert" has a gap: both requests can pass the check before either inserts. Only a unique index makes the rule true. The repository then turns the violation into a 409.

A partial index only covers the rows that match its WHERE. Soft-deleted rows step aside, and restoring one whose title is now taken is refused with 409, which is right.

Equality columns first, then the sort columns in the same order and direction. PostgreSQL can then jump to the project and cursor position and read 21 rows in order, with no sort step.

Related writes must be all-or-nothing. withTransaction rolls back the insert if anything after it fails, and every repository joins with withTransaction(tx).

 How does optimistic concurrency with a version column stop a silent overwrite?

The check and the write are one statement, so there is no gap. The client that gets 409 reloads, sees the other change, and decides what to do.

A row lock makes the others wait, so it only suits work that takes milliseconds. You cannot hold a database lock while a person is typing; use a version for that.

Clients, proxies and users retry. Checking "already done" inside the transaction and returning early keeps the counter right however many times the request arrives.
