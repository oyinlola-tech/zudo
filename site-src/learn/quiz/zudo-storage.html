What is the main idea of @zudojs/storage?

Your app depends on what storage does (Database, ObjectStorage, LockManager…), not on what it is. To move files from disk to a cloud bucket, you write a new ObjectStorage, and nothing else changes.

 Which contract comes without a ready-made implementation, so you write a small adapter for your driver?

ObjectStorage has LocalObjectStorage, Serializer has JsonSerializer and LockManager has InMemoryLockManager. For Database you write an adapter, like the lesson's PgliteDatabase.

 In the Database contract, a query is an object: { text, parameters }. Why does that help security?

The contract has no method that takes one SQL string with values inside. Values always go in parameters as $1, $2…, so user input cannot become SQL.

 The PgliteDatabase adapter writes savepoint names straight into SQL: SAVEPOINT "${name}". What is the rule for those names?

A name is part of the SQL text, not a parameter. A name made by an attacker could close the quote and add their own SQL. Use fixed names written in your code.

 What should rowCount report for an UPDATE in the lesson's adapter?

A SELECT reports the rows it returned; INSERT, UPDATE and DELETE report the rows they changed. That is why the adapter uses affectedRows when there are no result fields.

Values become $1, $2 parameters, in order: first the new value, then the id. The column name done is written into the SQL, which is why it must be on the allow-list.

Limit and offset are values, so they are parameters. The sort column is a name, not a value, so it goes into the SQL text, after the allow-list check.

 A client puts SQL into the title. What does this print? import { BaseRepository } from "@zudojs/storage"; const db = { async query(q) { console.log(q.text, q.parameters); return { rows: [{ id: 1 }], rowCount: 1, fields: [], durationMs: 0 }; }, }; const tasks = new BaseRepository(db, { tableName: "tasks", columns: ["title", "done", "owner_id"] }); await tasks.update(1, { title: "x', owner_id = 'mallory" });

The value is a parameter, so PostgreSQL stores it as an odd title and nothing else changes. That is exactly right: values never need escaping by hand when they are parameters.

 A route passes the request body to tasks.update(id, body). The body is { "done": true, "owner_id": "mallory" }, and owner_id is on the repository's columns list. What happens?

This is mass assignment. owner_id must be on the list so your own code can set it. The allow-list is a safety net for SQL, not a permission system.

 What is the right fix for the mass-assignment bug?

The fix belongs at the edge of your app. A .strict() schema answers 400 for any unknown key such as owner_id, and the owner always comes from the session, never from the body.

Finish taskChanges(body), a plain-JavaScript version of a strict schema. A client may change only title and done. If the body has any other key, return { status: 400, unknown: [...] } listing those keys. Otherwise return { status: 200, changes } with only the allowed keys that are present.

 const ALLOWED = ["title", "done"]; function taskChanges(body) { // your code here } console.log(taskChanges({ done: true })); console.log(taskChanges({ done: true, owner_id: "mallory" })); console.log(taskChanges({ title: "Buy oat milk", is_admin: true, id: 9 })); const ALLOWED = ["title", "done"]; function taskChanges(body) { const unknown = Object.keys(body).filter((key) => !ALLOWED.includes(key)); if (unknown.length > 0) return { status: 400, unknown }; const changes = {}; for (const key of ALLOWED) { if (key in body) changes[key] = body[key]; } return { status: 200, changes }; } console.log(taskChanges({ done: true })); console.log(taskChanges({ done: true, owner_id: "mallory" })); console.log(taskChanges({ title: "Buy oat milk", is_admin: true, id: 9 })); { status: 200, changes: { done: true } } { status: 400, unknown: [ 'owner_id' ] } { status: 400, unknown: [ 'is_admin', 'id' ] }

Refuse unknown keys instead of silently dropping them: the client learns its request was wrong, and owner_id never gets near the database.

Finish newTaskRow(body, user). It builds the row to insert: title (trimmed) and done (default false) come from the body, but owner_id always comes from the logged-in user.id, whatever the body says.

 function newTaskRow(body, user) { // your code here } const ada = { id: "ada" }; console.log(newTaskRow({ title: " Buy milk " }, ada)); console.log(newTaskRow({ title: "Steal", done: true, owner_id: "mallory" }, ada)); function newTaskRow(body, user) { return { title: body.title.trim(), done: body.done ?? false, owner_id: user.id, }; } const ada = { id: "ada" }; console.log(newTaskRow({ title: " Buy milk " }, ada)); console.log(newTaskRow({ title: "Steal", done: true, owner_id: "mallory" }, ada)); { title: 'Buy milk', done: false, owner_id: 'ada' } { title: 'Steal', done: true, owner_id: 'ada' }

Pick each field on purpose instead of spreading the body ({ ...body }), which would copy owner_id from the client. The owner is the server's decision.

Parsed data can hold keys whose value is undefined, like { title: undefined, done: true }. BaseRepository skips such keys, but a query you build yourself might turn them into NULL. Finish definedOnly(data) so it returns a copy without those keys. Keep null and false: they are real values.

 function definedOnly(data) { // your code here } console.log(definedOnly({ title: undefined, done: true })); console.log(definedOnly({ title: "Buy milk", done: false, note: null, due: undefined })); function definedOnly(data) { return Object.fromEntries(Object.entries(data).filter(([, value]) => value !== undefined)); } console.log(definedOnly({ title: undefined, done: true })); console.log(definedOnly({ title: "Buy milk", done: false, note: null, due: undefined })); { done: true } { title: 'Buy milk', done: false, note: null }

Object.entries, a filter on value !== undefined, then Object.fromEntries. A check like if (value) would wrongly drop false and null.

 A client asks to sort by id. What does this print? import { BaseRepository } from "@zudojs/storage"; const db = { async query() { return { rows: [], rowCount: 0, fields: [], durationMs: 0 }; }, }; const tasks = new BaseRepository(db, { tableName: "tasks", columns: ["title", "done", "owner_id"] }); for (const orderBy of ["title; DROP TABLE tasks", "id", "title"]) { try { await tasks.findAll({ orderBy }); console.log(orderBy, "ok"); } catch (error) { console.log(orderBy, error.code); } }

A name with ; and spaces is not even a valid identifier. id is valid, but not on the columns list, so it is refused too. The allow-list is used for writes, filters and sorting alike.

 You want clients to sort by id, so you add id to columns. What else changes?

The same list controls writes, filters and sorting. With a strict schema at the edge that is harmless; without one, id is one more field a client could change.

 Where should a task's PDF attachment go?

Databases are for rows; files go into object storage. An object is the file plus a little metadata, stored under a key. Cloud services such as Amazon S3 work the same way.

 What does this print? import { mkdtemp, rm } from "node:fs/promises"; import { tmpdir } from "node:os"; import { join } from "node:path"; import { LocalObjectStorage } from "@zudojs/storage"; const folder = await mkdtemp(join(tmpdir(), "task-files-")); const files = new LocalObjectStorage(folder); const saved = await files.put("tasks/1/notes.txt", new TextEncoder().encode("Oat milk"), { contentType: "text/plain", }); console.log(saved.key, saved.size, saved.contentType); console.log("missing:", await files.get("tasks/9/nothing.txt")); await rm(folder, { recursive: true, force: true });

put returns the object's metadata: key, size in bytes (8 for "Oat milk") and content type. get returns null for a missing key, so your route can answer 404.

 What does this print? import { mkdtemp, rm } from "node:fs/promises"; import { tmpdir } from "node:os"; import { join } from "node:path"; import { LocalObjectStorage } from "@zudojs/storage"; const folder = await mkdtemp(join(tmpdir(), "task-files-")); const files = new LocalObjectStorage(folder); const bytes = new Uint8Array(3); await files.put("tasks/1/a.txt", bytes); await files.put("tasks/2/b.txt", bytes); await files.put("tasks/10/c.txt", bytes); console.log((await files.list("tasks/1/")).objects.map((o) => o.key)); console.log((await files.list("tasks/1")).objects.map((o) => o.key)); await rm(folder, { recursive: true, force: true });

list(prefix) finds every key that starts with the text. "tasks/10/c.txt" starts with "tasks/1", so end your prefix with / to list one task only.

 A task has 2500 attachments. files.list("tasks/1/") returns 1000 objects and isTruncated: true. What do you do?

list returns at most maxKeys objects (1000 by default). The continuationToken tells the next call where to go on, like a cursor.

 put also computes an etag, a SHA-256 hash of the content. What is it useful for?

A hash is a fingerprint of the bytes. Same content, same etag; change one byte and the etag changes. It is not encryption and says nothing about who uploaded it.

 What does this print? import { mkdtemp, rm } from "node:fs/promises"; import { tmpdir } from "node:os"; import { join } from "node:path"; import { LocalObjectStorage } from "@zudojs/storage"; const folder = await mkdtemp(join(tmpdir(), "task-files-")); const files = new LocalObjectStorage(folder, { maxObjectBytes: 1024 }); const attempts = [ ["tasks/1/../../../etc/passwd", new Uint8Array(1)], ["tasks/1/huge.bin", new Uint8Array(5000)], ["tasks/1/ok.txt", new Uint8Array(1)], ]; for (const [key, data] of attempts) { try { await files.put(key, data); console.log("stored"); } catch (error) { console.log(error.statusCode, error.code); } } await rm(folder, { recursive: true, force: true });

A key with .. would climb out of the storage folder (path traversal), so it is refused with 400. A file larger than maxObjectBytes gets 413 Payload Too Large.

 What can a path traversal attack do if keys are not checked?

On disk a key becomes a path, and .. climbs out of the folder. With enough ../, a key reaches anywhere your server process can write or read.

 A user uploads holiday photo.png to task 7. Which key is best?

Don't use a user's file name as the key: make the key yourself, so it is always safe and never collides. Keep the original name in the metadata for display. Also check that the user may touch task 7.

Finish attachmentKey(taskId, fileName, id). Throw RangeError("taskId must be a positive whole number") unless taskId is a safe integer of at least 1. Return { key, metadata } where key is tasks/<taskId>/<id> and metadata.fileName is the original name cut to 200 characters. (In the app, id comes from randomUUID().)

 function attachmentKey(taskId, fileName, id) { // your code here } console.log(attachmentKey(1, "../../secret.txt", "3f1c")); for (const bad of [-1, 1.5, "1"]) { try { attachmentKey(bad, "a.txt", "x"); } catch (error) { console.log(error.name, error.message); } } function attachmentKey(taskId, fileName, id) { if (!Number.isSafeInteger(taskId) || taskId < 1) { throw new RangeError("taskId must be a positive whole number"); } return { key: `tasks/${taskId}/${id}`, metadata: { fileName: fileName.slice(0, 200) } }; } console.log(attachmentKey(1, "../../secret.txt", "3f1c")); for (const bad of [-1, 1.5, "1"]) { try { attachmentKey(bad, "a.txt", "x"); } catch (error) { console.log(error.name, error.message); } } { key: 'tasks/1/3f1c', metadata: { fileName: '../../secret.txt' } } RangeError taskId must be a positive whole number RangeError taskId must be a positive whole number RangeError taskId must be a positive whole number

The dangerous name is kept only as metadata; the key is built from values you control. Number.isSafeInteger refuses 1.5 and the string "1".

 What does plain JSON do to these values? const snapshot = { due: new Date(0), tags: new Set(["home"]), views: 1 }; console.log(JSON.parse(JSON.stringify(snapshot)));

JSON.stringify turns a Date into a string and a Set into an empty object. After parsing you get a plain string and {} back, and the tags are gone.

 What does this print? import { JsonSerializer } from "@zudojs/storage"; const serializer = new JsonSerializer(); const bytes = serializer.serialize({ due: new Date(0), views: 12n }); console.log(bytes.constructor.name); console.log(new TextDecoder().decode(bytes));

The result is bytes (Uint8Array), ready for object storage or a cache. Each special value is tagged with $type, so deserialize knows what to rebuild.

 What does this print? import { JsonSerializer } from "@zudojs/storage"; const serializer = new JsonSerializer(); const back = serializer.deserialize( serializer.serialize({ due: new Date(0), tags: new Set(["home"]), counts: new Map([["a", 1]]) }), ); console.log(back.due instanceof Date, back.tags.has("home"), back.counts.get("a"));

JsonSerializer keeps Date, Set, Map and BigInt through the round trip to bytes, thanks to the $type tags.

 What does this print? import { JsonSerializer } from "@zudojs/storage"; try { new JsonSerializer().serialize({ id: 1 }, "msgpack"); console.log("serialized"); } catch (error) { console.log(error.name); }

JsonSerializer only speaks JSON. Asking for another format throws a StorageError that says so, instead of silently writing JSON.

 Two requests edit task 1 at the same moment: both read it, both change it, both save. What goes wrong without a lock?

This is the lost update. A lock lets only one request work on the task at a time, so the second one reads the first one's result before changing it.

 What does this print? import { InMemoryLockManager } from "@zudojs/storage"; const locks = new InMemoryLockManager(); const first = await locks.acquire("task:1", { ttl: 5_000 }); console.log(first.fence, await locks.tryAcquire("task:1", 5_000)); await first.release(); const second = await locks.tryAcquire("task:1", 5_000); console.log(second.fence, first.isHeld(), second.isHeld()); await second.release(); locks.clear();

tryAcquire gives up at once and returns null while the lock is held. After the release, the next lock gets a bigger fence (2). The old lock no longer holds it.

 The first holder is too slow and its lock's TTL runs out. What does this print? import { InMemoryLockManager } from "@zudojs/storage"; const locks = new InMemoryLockManager(); const slow = await locks.acquire("task:1", { ttl: 30 }); await new Promise((resolve) => setTimeout(resolve, 60)); const fast = await locks.acquire("task:1", { ttl: 5_000 }); console.log(slow.isHeld(), slow.fence, fast.fence); await fast.release(); locks.clear();

After 30 ms the slow holder's lock expired, so the fast one got it, with fence 2. The slow worker may not notice; that is why the protected store must refuse writes with an older fence.

 Why does every lock have a ttl (time to live)?

A crashed process never calls release(). The TTL makes sure the lock is freed anyway. The price is that a slow (not crashed) holder can lose its lock, which fencing handles.

Finish save(title, fence) in TaskStore. If fence is smaller than the highest fence seen so far, throw new Error(`stale fence ${fence}, current is ${this.highestFence}`). Otherwise remember the fence and save the title.

 class TaskStore { highestFence = 0; title = "Buy milk"; save(title, fence) { // your code here } } const store = new TaskStore(); store.save("Buy oat milk", 2); try { store.save("Buy cow milk", 1); } catch (error) { console.log(error.message); } store.save("Buy soy milk", 3); console.log("title:", store.title); class TaskStore { highestFence = 0; title = "Buy milk"; save(title, fence) { if (fence < this.highestFence) { throw new Error(`stale fence ${fence}, current is ${this.highestFence}`); } this.highestFence = fence; this.title = title; } } const store = new TaskStore(); store.save("Buy oat milk", 2); try { store.save("Buy cow milk", 1); } catch (error) { console.log(error.message); } store.save("Buy soy milk", 3); console.log("title:", store.title); stale fence 1, current is 2 title: Buy soy milk

Every new lock gets a bigger fence, so a write with an older fence comes from a holder that lost its lock. Refusing it keeps the newer work safe.

 You run three copies of your server behind a load balancer, each with an InMemoryLockManager. What do the locks protect?

An in-memory lock lives in one process. For several servers, use a lock they share, such as PostgreSQL advisory locks via createLockManager from @zudojs/database, or a LockManager over Redis.

Finish withLock(locks, key, work): acquire the lock, run work(lock.fence) and return its result, and always release the lock, even when work throws. The small locks object below prints when it acquires and releases.

 let nextFence = 1; const locks = { async acquire(key) { console.log("acquire", key); return { fence: nextFence++, release: async () => console.log("release", key) }; }, }; async function withLock(locks, key, work) { // your code here } console.log(await withLock(locks, "task:1", async (fence) => `saved with fence ${fence}`)); try { await withLock(locks, "task:2", async () => { throw new Error("work failed"); }); } catch (error) { console.log(error.message); } let nextFence = 1; const locks = { async acquire(key) { console.log("acquire", key); return { fence: nextFence++, release: async () => console.log("release", key) }; }, }; async function withLock(locks, key, work) { const lock = await locks.acquire(key); try { return await work(lock.fence); } finally { await lock.release(); } } console.log(await withLock(locks, "task:1", async (fence) => `saved with fence ${fence}`)); try { await withLock(locks, "task:2", async () => { throw new Error("work failed"); }); } catch (error) { console.log(error.message); } acquire task:1 release task:1 saved with fence 1 acquire task:2 release task:2 work failed

try { return await work(…) } finally { release } is the pattern. The await inside try matters: without it, finally would run before the work finishes.

 The pool has min: 1, max: 2. What does this print? import { ConnectionPool } from "@zudojs/storage"; let opened = 0; async function openConnection() { opened += 1; const id = `conn-${opened}`; return { id, state: "connected", query: async () => ({ rows: [], rowCount: 0, fields: [], durationMs: 0 }), execute: async () => ({ rowCount: 0 }), ping: async () => true, close: async () => {}, }; } const pool = new ConnectionPool(openConnection, { min: 1, max: 2, acquireTimeout: 200 }); await pool.initialize(); console.log(pool.getStats()); const a = await pool.acquire(); const b = await pool.acquire(); const waiting = pool.acquire(); console.log(pool.getStats()); await pool.release(a); console.log((await waiting).id); await pool.drain();

min: 1 opens one connection at start. The second is opened when needed, and never more than max: 2. The third acquire waits, and gets conn-1 as soon as it is released.

 Why should you prefer pool.use(fn) over acquire() and release()?

use acquires, runs your function and releases in a finally. With manual acquire, one missed release on an error path slowly drains the pool.

 All connections are busy, and a request has waited longer than acquireTimeout. Why is it good that it fails instead of waiting forever?

A request that waits forever holds memory and a client connection. Failing fast gives a quick error, and the server stays responsive for the rest.

 When do you call pool.drain()?

drain() lets running work finish and then closes every connection, which is what a clean shutdown needs.

 What does StorageLifecycleManager do?

Storage has to start before the server takes requests and stop after the last one. The manager runs those steps for every component that implements StorageLifecycle.

 One component is healthy and one is not.  Your app uses LocalObjectStorage. Next month you move files to a cloud bucket. If your code depends only on the ObjectStorage contract, what must change?

That is the point of contracts: code that calls put, get and list does not care where the bytes live. You swap the implementation in one place, as with the dependency container.
