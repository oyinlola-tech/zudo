What is the main reason teams merge through pull requests instead of pushing to main?

A PR is a checkpoint: review catches what the author missed, and CI proves the combination with main still works. Branch protection makes the checkpoint mandatory.

 Which bug report lets a developer start fixing immediately?

What happens, what should happen, how to reproduce it, and where: with those four parts nobody has to come back with questions.

 What does this print? const pattern = /\b(?:close[sd]?|fix(?:e[sd])?|resolve[sd]?)\s+#(\d+)/gi; const text = "Fixes #12 and resolves #7. See #3. Closed #20 last week? No: this closes #21."; console.log([...text.matchAll(pattern)].map((m) => Number(m[1])));

 Which commit subject follows the conventions from the lesson?

Imperative mood, a type, a specific description, short, no full stop. "Stuff" says nothing, and the last one is several commits' worth of changes in one.

 Which commit forces a new major version?

The ! (or a BREAKING CHANGE: line in the body) says existing users must change their code: every client reading amounts would now be off by a factor of 100.

 What is the key difference between merging main into your branch and rebasing your branch onto main?

After a rebase, bb6b965 became 586f4ea: same change, new commit. That is why a rebased branch must be force-pushed, and why shared branches should not be rebased.

 Which branch should you not rebase?

Never rebase commits others have based work on. Their copies still contain the old commits, and the next pull duplicates or loses work.

 After git rebase origin/main, git push is rejected with "non-fast-forward", and the hint says to run git pull. What should you do?

git pull would merge the old, pre-rebase commits back in and give you two copies of every change. After a deliberate rebase you replace the branch, safely, with --force-with-lease.

 Your editor runs git fetch automatically in the background. Why can that weaken --force-with-lease?

The lease compares with your remote-tracking branch, which a background fetch moves. --force-if-includes adds a check that your branch actually contains what you fetched.

 During git rebase origin/main, a conflict appears. What does git checkout --ours cart.js keep?

A rebase replays your commits on top of main, so HEAD ("ours") is main and your commit is "theirs": the opposite of a merge. Read the marker labels rather than trusting the words.

 What does the zdiff3 conflict style add to the markers?

With the original in view you can see what each side changed, and so what each person intended, which is what a correct resolution must keep.

 After a rebase you want your old commits back. They are on no branch any more. Where can you find them?

Git does not delete abandoned commits right away. The reflog lists them, and git reset --hard HEAD@{n} moves your branch back to one.

 Why is a 1,500-line pull request a problem even if the code is good?

Review quality drops quickly with size. Split big work into a series of smaller PRs that each make sense on their own.

 Which GitHub setting prevents "someone pushed straight to main on Friday"?

Protection rules make the process mandatory instead of a habit. They can also block force-pushes and deletion of the branch.

 A PR has 9 commits: 3 real steps and 6 "fix typo"/"wip". Which merge option gives main a clean history without asking the author to rewrite?

Squash turns the whole PR into one commit on main, titled after the PR. Rebase and merge would copy all nine commits, noise included.

The content is on main, but not those commits. After verifying, -D deletes the branch anyway.

 What should a reviewer look at first?

Correctness, tests and security matter most. Formatting is the formatter's job, and naming comes after the code is right.

 Which review comment is most useful?

It names the problem, gives a concrete case, suggests a fix, and says how important it is. It is about the code, not the person.

 A reviewer asks for a change you disagree with. What is the professional response?

Disagreement with reasons is healthy; either you learn something or they do. Silence and workarounds destroy the trust review depends on.

 Why should releases use annotated tags (git tag -a)?

A lightweight tag is only a name for a commit. An annotated tag is a real object that records who released what and when; npm version creates annotated tags.

Others may already have built, deployed or installed from v1.2.0. If the same name suddenly means different code, nobody can trust any version number.

 Who is a changelog written for?

That is why refactors and test changes are usually left out, and why generated entries should be edited into plain language.

 In a fork workflow, what are origin and upstream?

You push branches to your fork and open the pull request from there into upstream. New work starts from upstream/main, which may be ahead of your fork.

 You want to add a large new feature to an open-source library you use. What should you do first?

Maintainers must support every line for years. Agreeing on the approach first saves you from a large PR being closed.
