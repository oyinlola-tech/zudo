What is the fragile base class problem?

The parent's author refactors something that callers of the parent cannot notice, such as whether addItems calls addItem. A subclass that depended on that detail breaks without being touched.

 What does this print? class Cart { items = []; addItem(item) { this.items.push(item); } addItems(items) { for (const item of items) this.addItem(item); } } class PointsCart extends Cart { points = 0; addItem(item) { this.points += 1; super.addItem(item); } addItems(items) { this.points += items.length; super.addItems(items); } } const cart = new PointsCart(); cart.addItems(["rice", "oil", "salt"]); console.log(cart.items.length, cart.points);

PointsCart.addItems adds 3 points, then the parent's addItems calls this.addItem three times. this is the points cart, so the override runs and adds 3 more points.

 The subclass only overrides addItem. Then the parent is changed as shown. What does this print? class Cart { items = []; addItem(item) { this.items.push(item); } addItems(items) { this.items.push(...items); } } class PointsCart extends Cart { points = 0; addItem(item) { this.points += 1; super.addItem(item); } } const cart = new PointsCart(); cart.addItem("rice"); cart.addItems(["oil", "salt"]); console.log(cart.items.length, cart.points);

The new addItems pushes directly instead of calling addItem, so the override never runs for the bulk add. Only the single addItem("rice") earns a point.

 Which of these does a subclass not get from extends?

Private fields belong to the class body that declares them; even a subclass cannot read them. The other three are exactly what makes subclasses coupled to their parents.

 A ReadOnlyAccount extends Account overrides deposit() to throw. Why is this a poor use of inheritance?

The Liskov substitution principle: a subclass must keep the promises its parent makes to callers. Sounding like "a kind of account" in English is not enough.

 What does this print? class Cart { items = []; addItem(item) { this.items.push(item); } addItems(items) { for (const item of items) this.addItem(item); } } class PointsCart { #cart; points = 0; constructor(cart) { this.#cart = cart; } addItem(item) { this.points += 1; this.#cart.addItem(item); } addItems(items) { this.points += items.length; this.#cart.addItems(items); } get count() { return this.#cart.items.length; } } const cart = new PointsCart(new Cart()); cart.addItems(["rice", "oil", "salt"]); console.log(cart.count, cart.points);

The wrapper calls addItems on the cart it holds. Inside the cart, this.addItem is the cart's own method, never the wrapper's, so points are counted once.

 What is the main cost of a forwarding wrapper compared with a subclass?

Methods you do not forward do not exist on the wrapper. That is extra typing, and often a benefit: the wrapper chooses its own public interface.

 Two wrappers around the same gateway. What does this print? const base = { charge: (amount) => amount }; const withVat = (g) => ({ charge: (amount) => g.charge(amount * 2) }); const withFee = (g) => ({ charge: (amount) => g.charge(amount + 10) }); console.log(withVat(withFee(base)).charge(100)); console.log(withFee(withVat(base)).charge(100));

The outer wrapper runs first. withVat(withFee(base)): 100 × 2 = 200, then + 10 = 210. withFee(withVat(base)): 100 + 10 = 110, then × 2 = 220. The order of wrapping is a real decision.

 What makes a wrapper a decorator in the sense used in the lesson?

Same shape in, same shape out. That is why withRetry(withLogging(gateway)) works: each layer looks like a gateway to the next.

 A withRetry wrapper retries a payment after a network timeout. What must be true for this to be safe?

A timeout means "no answer", not "no payment". Without idempotency by reference, a retry can charge the customer twice.

 A checkout holds a delivery object and calls delivery.feeKobo(order). Which statement is correct?

This is delegation to a strategy. The checkout depends on an interface, "has feeKobo", not on any class. Relying on what an object can do is duck typing.

 What does this print? const strategies = { flat: { feeKobo: () => 250000 }, free: { feeKobo: (o) => (o.subtotalKobo >= 5000000 ? 0 : 250000) }, }; function total(order, delivery) { return (order.subtotalKobo + delivery.feeKobo(order)) / 100; } const order = { subtotalKobo: 4990000 }; console.log(total(order, strategies.flat), total(order, strategies.free));

₦49,900 is below the ₦50,000 threshold, so the "free" strategy still charges ₦2,500. Both totals are ₦52,400.

 Where should a checkout check that its gateway has a charge method?

A missing method is a bug in how the program was assembled. Failing at construction surfaces it before the first customer tries to pay.

 What does this print? class Product { describe() { return "product"; } } const Describable = { describe() { return "mixin"; } }; const Taggable = { tag() { return "tagged"; } }; Object.assign(Product.prototype, Taggable, Describable); const p = new Product(); console.log(p.describe(), p.tag());

Object.assign overwrites existing keys without a warning, so the mixin's describe replaces the class's own. That silent clash is the main risk of object mixins.

 After Object.assign(Order.prototype, Taggable), what does order instanceof Taggable do?

The right side of instanceof must be callable. Object mixins give you no identity to test; you can only check for the methods.

 A Describable mixin's method reads this.id. Which mixin risk is this?

Nothing states that users of the mixin must have an id. The mistake does not throw; it produces wrong output.

 What does this print? const Loud = (Base) => class extends Base { speak() { return super.speak().toUpperCase(); } }; const Polite = (Base) => class extends Base { speak() { return super.speak() + ", please"; } }; class Clerk { speak() { return "next customer"; } } class A extends Loud(Polite(Clerk)) {} class B extends Polite(Loud(Clerk)) {} console.log(new A().speak()); console.log(new B().speak());

The outermost mixin's method runs first and calls super. In A, Loud upper-cases what Polite returned, including ", please". In B, Polite adds ", please" after Loud has already upper-cased the clerk's text.

 Why does the lesson say class-expression mixins are "still inheritance"?

SoftDeletable(Timestamped(Record)) builds a chain of anonymous classes. Every coupling problem of extends applies to it.

 What does this print? let stock = 10; const capability = { get left() { return stock; }, }; const product = { sku: "RICE", ...capability }; stock = 3; console.log(product.left);

Spread reads each property's value once. The product gets a plain data property holding 10; the getter is gone. Copy descriptors, or use methods, to keep live values.

 What does this print? let stock = 10; const capability = { get left() { return stock; } }; const product = Object.defineProperties({}, Object.getOwnPropertyDescriptors(capability)); stock = 3; console.log(product.left, typeof Object.getOwnPropertyDescriptor(product, "left").get);

Copying descriptors copies the getter function itself, so reading left still runs it and sees the current stock.

 What does this print? function createWallet(startKobo) { let balance = startKobo; return Object.freeze({ pay(kobo) { if (kobo > balance) throw new Error("insufficient funds"); balance -= kobo; }, balance: () => balance, }); } const wallet = createWallet(500000); wallet.pay(120000); wallet.balance = () => 999999999; console.log(wallet.balance(), Object.keys(wallet).length);

balance is a variable in the closure, not a property. The frozen object ignores the attempt to replace the method (in a sloppy script; in a module it would throw), so the real balance, 380,000, comes back.

 When is a class a better choice than a factory function that returns an object full of closures?

Closures give each object its own functions. For a few thousand objects that is fine; for millions, sharing methods on a prototype saves memory.

 The coupon should come off before VAT. What does this print? const vat = (amount) => Math.round(amount * 1.075); const coupon = (amount) => amount - 100000; const apply = (rules, amount) => rules.reduce((current, rule) => rule(current), amount); console.log(apply([coupon, vat], 1000000)); console.log(apply([vat, coupon], 1000000));

Coupon first: (1,000,000 − 100,000) × 1.075 = 967,500. VAT first: 1,075,000 − 100,000 = 975,000. The order of the rule list is part of the business rule.

 In const coupon = (code, offKobo) => (amount, order) => …, what is coupon("WELCOME", 200000)?

A function that returns a function. The returned rule closes over code and offKobo, so one definition covers every coupon.

 What happens when a subclass method reads this.#items, where #items is declared only in the parent class?

Private names are checked when the code is parsed. A subclass cannot even mention the parent's private fields, so it has to use the public API.

 What does this print? class Invoice { #number; constructor(number) { this.#number = number; } static isInvoice(value) { return #number in value; } } const real = new Invoice("INV-7"); const forged = Object.create(Invoice.prototype); console.log(forged instanceof Invoice, Invoice.isInvoice(forged), Invoice.isInvoice(real));

instanceof only checks the prototype chain, which Object.create can fake. #number in value is a brand check: only objects built by the constructor have the private field.

 Why does wrapping a class instance with private fields in a Proxy often throw when you read a getter through it?

Private fields are attached to the real object, not to the proxy. An explicit forwarding wrapper calls methods on the real object, so it does not have this problem.

 What does this print? class Account { constructor(owner) { this.owner = owner; } static open(owner) { return new this(owner); } } class SavingsAccount extends Account {} const a = SavingsAccount.open("Ada"); console.log(a.constructor.name, a instanceof Account);

Static methods are inherited, and inside a static method this is the class it was called on. new this(owner) therefore builds a SavingsAccount.

 When does the code in a class's static { … } block run?

A static block is class-wide set-up, run once. It suits things like building one shared Intl.NumberFormat for all instances.

 A class has get totalKobo() and no setter. Code in an ES module runs cart.totalKobo = 0. What happens?

Modules and classes are strict mode, and assigning to an accessor with no setter throws in strict mode. The caller learns about the mistake immediately.

 What does this print? class Cart { #lines = [{ sku: "OIL", qty: 2 }]; get count() { return this.#lines.length; } } class Order { #id = "ORD-1"; get id() { return this.#id; } toJSON() { return { id: this.#id }; } } console.log(JSON.stringify(new Cart()), JSON.stringify(new Order()));

Private fields are invisible to JSON.stringify, and getters live on the prototype, so the cart serialises as {}. A toJSON method decides what the JSON looks like.

 Which of these belongs in a getter?

Reading a property should be cheap and change nothing. I/O and side effects belong in methods, preferably async ones, so callers can see them.

 A cart keeps its lines in #lines. Why does its lines() method return this.#lines.map((l) => ({ ...l })) rather than this.#lines?

A private field protects the variable, not the object it points to. Handing out copies keeps the cart the only code that can change its lines.

 A checkout reserves stock for each line, then charges the card. The charge fails. What should it do?

Keep a list of what you reserved and undo that list. If the second reservation fails, the first one must be released too.

 Why is new Checkout({ gateway }) easier to test than a Checkout whose constructor runs this.gateway = new CardGateway()?

Passing collaborators in (dependency injection) is what makes them replaceable. A class that creates its own gateway can only be tested against that gateway.

 Which is the best candidate for extends?

Error is designed to be extended, callers rely on instanceof and catch, and a declined-payment error really can stand in for an error everywhere. The others are better as wrappers, strategies or separate types.
