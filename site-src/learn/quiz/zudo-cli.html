An incomplete command line ends with 2 and the message Missing required argument "name". Code 1 is for a command that ran and failed, 3 for an unknown command.

 A CI script runs zudojs deploy. What happens?

The CLI has seven commands and deploy is not one of them. Deployment is your own pipeline's job, built from npm run build and npm start.

Only ✖ errors make doctor exit with 1; it even ends with "All checks passed!" after warnings. If warnings matter in your pipeline, you must check for them explicitly.

Layered schematics cascade: a controller needs a service, which needs a repository, which needs the DTO types. None of them wires anything in, so the controller is not reachable until you add a route.

 You already generated resource order-items. What does zudojs generate resource OrderItems do?

Names are normalized to kebab-case before anything else, so OrderItems, Order_Items and order-items are the same resource. Without --force, an existing resource is refused.

 Why does the CLI refuse zudojs generate resource records?

The singular of the name becomes the record type. Record, Promise, Map and other globals are refused because the generated code relies on them.

 Why is 2fa refused as a resource name, and what does the CLI suggest?

A TypeScript identifier cannot start with a digit. Refusing up front is better than generating files that do not compile, and the message says what to type instead.

 Someone deleted the // zudojs:routes:start and …:end comments from src/routes/index.ts. What does zudojs generate resource orders do?

Without markers the CLI refuses to guess where the line belongs. It still generates everything else and only warns, so the route answers 404 until you add the printed line yourself.

 Marker insertion is idempotent. What does that mean in practice?

Before inserting, the CLI checks whether the line is already between the markers and reports present if so. Regenerating is therefore safe for the wiring.

 What is the main risk of zudojs generate resource products --force on an existing resource?

--force rewrites the schematic's files. The wiring is safe because insertion is idempotent, but your edits to the DTO, service or controller are gone. Commit first and review with git diff.

 A refused generate ("already exists") leaves no new files behind. Which design makes that true?

Plan, check, then write. Checking file by file while writing would leave a half-generated resource when the third file clashes.

 In a modular monolith you run zudojs generate service refunds --module billing. What does the published CLI do?

In a modular monolith the CLI treats "service" as "module". To get a service inside billing, generate a resource or controller with --module billing and keep the layers you need.

 A modular monolith already has a top-level invoices resource. Why is zudojs generate resource invoices --module billing refused?

Source files go to src/modules/billing/…, but tests are not grouped by module. The only clash was tests/invoices.test.ts.

 In a microservice project, where does zudojs generate resource refunds (run from the project root, no --service) put the files?

Without --service the gateway is the target. --service payments targets apps/services/payments/, and an unknown service name is refused.

 Why is the file written by zudojs generate validator payment dangerous if left as it is?

The stub compiles and accepts everything, including "DROP TABLE". Replace its body with a real schema check and add a test with bad input before anything calls it.

 Your team wants its own zudojs generate webhook schematic. What does the published CLI offer?

The templates are built into the CLI and cannot be extended. The zudojs-cli package does export the CLI framework (createCLI), so project-specific commands are easy to write.

 A CI job runs npx zudojs@latest generate …. What problem can that cause?

Pin the version (npx zudojs@2.1.3) so every developer and every pipeline run uses the same templates, and upgrade on purpose.

The CLI changes templates for resources generated from then on, and says so. Existing resources keep their in-memory repository until you swap it in src/container.ts. The service does not change because it only knows the repository interface.

The folder heuristics say "src/modules means modular monolith", and a generated monolith has that folder too. That is why the recorded architecture must be kept.

dev hands the work to your dev script and passes the port as PORT, which src/configs/index.ts reads. No file is changed.

The option appears in the help, but it applies to frontends. For --type backend the CLI prints that JavaScript is not supported.
