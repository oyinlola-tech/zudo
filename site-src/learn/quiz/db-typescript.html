What does the type argument in db.query<Order>("select * from orders") guarantee?

The driver cannot know what a SQL string returns when TypeScript compiles. The type argument only tells the compiler what to assume; the lesson's first example compiled and then crashed.

 With the pg driver, what JavaScript value does a bigint column (or count(*)) arrive as?

64-bit integers can exceed JavaScript's safe integer range, so pg returns them as text by default. PGlite returns a number when it is safe and a bigint otherwise. The row type must match the driver you use.

 Why do both drivers return numeric columns as strings?

numeric exists for exact decimals, such as money. Converting to a float would undo that. Keep the string and parse it exactly, or use a decimal library.

 A server in Lagos reads a date column holding 2026-09-24 with the pg driver and calls toISOString(). It prints 2026-09-23T23:00:00.000Z. Why?

A calendar date has no time zone, but a JavaScript Date is a moment. Keep date columns as "YYYY-MM-DD" strings (a custom type parser) or run servers in UTC, and be deliberate about the conversion.

 A column note text allows nulls. How should the row type declare it?

Every column is present in every row; a missing value is null. ? means "the property may be absent" and says nothing about null, so it would let row.note.trim() compile on a null.

 What is the difference between a row type and an entity in the lesson?

Keeping them apart puts every awkward conversion (snake_case, bigint strings, money) in one mapper per table, and keeps the rest of the application free of driver details.

 Why does the lesson's toKobo throw instead of returning Number(value) for any input?

For money, a wrong number is worse than an error. The mapper is the boundary where database values become trusted application values, so that is where to refuse bad ones.

 Which type should a GET /customers/:id handler return?

A response DTO is the contract with the client. Building a new object is what actually removes secret fields; a type like Omit only hides them from the compiler.

 function toResponse(c: Customer): CustomerResponse { return c; } compiles although Customer has a passwordHash. Why?

Assignability asks "does it have at least these properties?". The returned object is still the full entity at runtime, so the hash leaks into the JSON.

 When does TypeScript's excess property check catch an extra property such as passwordHash?

The check applies to object literals only, and properties that come in through a spread are not checked as excess. That is why mappers list fields one by one.

 What does Partial<Pick<CreateCustomerInput, "fullName" | "phone">> express for an update endpoint?

Pick selects what may change at all; Partial makes each optional. email and password are not part of the type, so this path cannot change them.

 When is it worth validating rows from your own database at runtime?

Constraints guarantee some things, not your TypeScript types: a new status value, a column made nullable, or an old jsonb shape all pass the database's checks. Validate at the boundary where drift would hurt.

 Why does the validation example query with db.query<unknown>(…)?

With unknown, TypeScript refuses row.status until a check narrows the type. The schema's safeParse then returns typed data or a list of issues.

 What does type OrderRow = z.infer<typeof OrderRowSchema> give you?

Writing the shape once, as a schema, and deriving the type from it removes the risk of a type saying one thing while the validator checks another.

 Why does findById return Promise<Order | undefined> instead of Promise<Order>?

With strictNullChecks, (await findById(id)).status does not compile; the caller must check and answer 404 or similar. Failures (a lost connection) are still exceptions.

 What does a branded OrderId type cost at runtime?

Brand<number, "OrderId"> intersects number with a phantom property the compiler tracks. At runtime orderId(5) is just 5, but a CustomerId can no longer be passed where an OrderId is expected.

 Why does the repository map an OrderSort union to fixed SQL strings instead of accepting a column name?

The union makes invalid sorts a compile error, and the Record<OrderSort, string> makes a new sort option without SQL a compile error too. At runtime, input from a query string must still be checked against the same list.

 The repository's constructor takes a Queryable instead of a PGlite. What does that enable?

Depending on the smallest interface you need (dependency inversion) lets the caller decide the connection. Inside db.transaction(async (tx) => …), repositories built on tx all commit or roll back together.

 How does the lesson propose to stop generated row types from drifting from the schema?

A drift check turns "someone forgot to update the types" into a failing build, next to the migration that caused it.

 The generator typed orders.status as string, not "pending" | "paid" | …. Why?

A PostgreSQL enum type or a lookup table with a foreign key carries the allowed values in the schema itself, where tools can see them. With a check constraint, you narrow the type by hand.

 In the tiny query builder, what is the result type of selectFrom(db, "orders", ["id", "total_kobo"])?

The column list is inferred as the literal union "id" | "total_kobo", constrained to the table's keys, and Pick builds the result type from exactly those columns.

 Which risk is typical of ORMs and must still be watched for?

ORMs save a lot of code, but the database work still happens. Log or inspect the generated SQL, check pg_stat_statements, and drop to raw SQL where you need precise control.

 How should the login code get a customer's password_hash?

Data that is never loaded cannot leak. Keeping secrets out of the widely used entity reduces the places where a mistake could expose them.
