A file has a missing ) on line 3. Line 1 is console.log("Starting");. What happens when you run it with Node.js?

Node.js checks the whole file before it runs any of it. A syntax error stops everything, even the lines above the mistake.

 What is a runtime error?

A runtime error happens while the code runs. Everything before it has run; nothing after it runs unless the error is caught.

 Why does the lesson call a logic error the worst kind?

JavaScript cannot know what you meant, so a wrong + 1 gives a wrong answer silently. Logic errors are found by checking results against known answers: tests.

 What does this print? const tasks = [{ title: "Buy milk" }]; console.log("start"); try { console.log(tasks.lenght.toFixed(0)); console.log("after"); } catch (error) { console.log(error.name); }

The typo lenght gives undefined, and calling toFixed on undefined throws a TypeError. The line "after" never runs.

 This function should return the average priority. What does it print? function averagePriority(tasks) { let total = 0; for (const task of tasks) { total += task.priority; } return total / tasks.length + 1; } console.log(averagePriority([{ priority: 2 }, { priority: 4 }]));

The average of 2 and 4 is 3, but a stray + 1 makes it 4. No error, no warning: that is a logic error.

 What does throw do?

throw jumps to the nearest catch: in the same function if the throw is inside a try there, otherwise in its caller, its caller's caller, and so on. If nothing catches it, the program crashes.

 What does this print? function parseTask(text) { const data = JSON.parse(text); if (typeof data.title !== "string") { throw new Error("title must be a string"); } return data; } for (const input of ['{"title":"Buy milk"}', '{"title":42}', "{not json"]) { try { console.log("OK:", parseTask(input).title); } catch (error) { console.log(error.name); } }

The second input fails our own check, which throws a plain Error. The third is not JSON, so JSON.parse itself throws a SyntaxError. Each error is caught, so the loop carries on.

 A server handles requests in a loop. Why wrap each request in try/catch?

An uncaught error can stop the whole server. Catching it per request turns one failure into one error answer, and the next request is handled normally.

 What does this print? function run(fail) { try { if (fail) throw new Error("boom"); return "ok"; } catch (error) { return `caught ${error.message}`; } finally { console.log("finally"); } } console.log(run(false)); console.log(run(true));

finally runs whether try returned or threw, and it runs before the function's result reaches the caller. So "finally" prints before each result.

 What does this print? let openConnections = 0; function query(sql) { openConnections += 1; try { if (sql === "") throw new Error("empty query"); return `rows for: ${sql}`; } finally { openConnections -= 1; } } query("SELECT 1"); try { query(""); } catch (error) { console.log("failed:", error.message); } console.log("open:", openConnections);

finally gives the connection back in both cases: after the return and after the throw. Without it, every failed query would leak a connection.

 What belongs in a finally block?

finally always runs: after success, after an error, even after return. That makes it the right place for clean-up.

 Which built-in error do Node.js and Chrome throw when the call stack overflows?

RangeError is for values out of range, and for "Maximum call stack size exceeded". TypeError is for wrong types, ReferenceError for unknown names.

 Which error does JSON.parse("{oops") throw?

Invalid JSON is invalid syntax, so JSON.parse throws a SyntaxError. You did not write that throw: built-in functions throw too.

 What does this print? function checkPriority(priority) { if (priority < 1 || priority > 5) { throw new RangeError(`priority must be 1 to 5, got ${priority}`); } return priority; } try { checkPriority(9); } catch (error) { console.log(error instanceof RangeError, error instanceof Error); console.log(error.name); console.log(error.message); }

RangeError is a subclass of Error, so both checks are true. name is the class name and message is only the text you passed.

 What does this print? try { throw new TypeError("title must be a string"); } catch (error) { console.log(error.stack.split("\n")[0]); }

The first line of stack is the name and the message. The lines after it are the call stack, top first.

 Why should you never write throw "not found"?

JavaScript lets you throw anything, but a string carries no information about what or where. Always throw an Error or a subclass.

 What does this print? try { throw "not found"; } catch (error) { console.log(error instanceof Error, error.name, error.stack); }

What you catch is just the string. It is not an Error, and it has no name and no stack, so the code that catches it cannot tell what happened.

 What does this print? function loadSettings(text) { try { return JSON.parse(text); } catch (error) { throw new Error("Could not load settings", { cause: error }); } } try { loadSettings("{ theme: dark }"); } catch (error) { console.log(error.message); console.log(error.cause.name); }

The new error gives the caller a clear message at its own level. error.cause still holds the original SyntaxError from JSON.parse for debugging.

 Why pass { cause: error } when you wrap a low-level error in a new one?

Without cause, the original error disappears. With it, the caller reads "Could not load settings" and a developer can still see the real SyntaxError.

 Why give each kind of failure its own error class, like NotFoundError and ValidationError?

"Task not found" should give 404, "bad input" 400, "database down" 500. Separate classes let the catching code decide with instanceof.

 What does this print? class AppError extends Error { constructor(message, { status = 500 } = {}) { super(message); this.name = new.target.name; this.status = status; } } class NotFoundError extends AppError { constructor(message) { super(message, { status: 404 }); } } const error = new NotFoundError("Task 7 not found"); console.log(error.name, error.status, error instanceof AppError);

new.target is the class new was called with, here NotFoundError, even inside the parent's constructor. It extends AppError, so instanceof AppError is true.

 What does this print? class AppError extends Error { constructor(message, { status = 500, code = "INTERNAL" } = {}) { super(message); this.name = new.target.name; this.status = status; this.code = code; } } const error = new AppError("Something broke"); console.log(error.status, error.code, error.message);

The second parameter defaults to {}, and status and code have their own defaults. So calling it with only a message is safe.

 A catch handles NotFoundError and ValidationError. What should it do with any other error?

Only handle the errors you expect. A catch that swallows everything hides real bugs. Re-throwing lets a higher level deal with it.

 What does this print? class NotFoundError extends Error { constructor(message) { super(message); this.name = "NotFoundError"; } } function handle(fn) { try { return fn(); } catch (error) { if (error instanceof NotFoundError) return "404"; throw error; } } console.log(handle(() => { throw new NotFoundError("no task"); })); try { handle(() => null.title); } catch (error) { console.log("outer caught", error.name); }

The expected NotFoundError is handled. The TypeError from null.title is not expected, so handle re-throws it and the outer catch receives it.

 In a ZudoJS app you need a "not found" error with status 404. What should you do?

@zudojs/errors ships NotFoundError, ValidationError, ConflictError and many more, following the same pattern as this lesson. Use them instead of rewriting them.

The input is valid, so it is not 400. The calculator throws its own DivisionByZeroError with status 422: "I understood, but I cannot do it".

 Why does the calculator look up op in an OPERATIONS allow-list instead of using eval?

User input must never be run as code. An allow-list only accepts the operations you wrote, and everything else is refused with a ValidationError.

 Why does the calculator use Object.hasOwn? What does this print? const OPERATIONS = { add: (a, b) => a + b, }; const op = "constructor"; console.log(Boolean(OPERATIONS[op]), Object.hasOwn(OPERATIONS, op));

Every object inherits constructor from Object.prototype, so a plain lookup finds it. Object.hasOwn only accepts keys you wrote yourself, so op=constructor is refused.

What does this print? function toNumber(value, field) { if (typeof value !== "string" || value.trim() === "") { return `${field} is required`; } const number = Number(value); if (!Number.isFinite(number)) { return `${field} must be a number`; } return number; } console.log(toNumber("10", "a"), toNumber(" ", "a"), toNumber("ten", "b"), toNumber(undefined, "b"));

 The API catches an error that is not an AppError, such as an unexpected TypeError. What should it send the client?

An unexpected error's message and stack can reveal file paths, library versions, SQL or data, which attackers collect. Log them privately and answer with a generic message.

 Which error message is safe to send to the client as it is?

Errors you designed for users, like ValidationError, contain only what you chose to say. Everything unexpected gets the generic 500 message.

 In the calculator build, which part knows about HTTP status codes in responses?

The calculator only validates, calculates and throws typed errors. The API layer is the single place that maps them to a status and body. A new error type then fits in without changing the calculator's callers.
