A hash function returns a different number for the same key each time it is called (for example, it mixes in the current time). What breaks?

A hash function must be deterministic. Randomness is allowed only as a fixed seed chosen once when the table is created, so every call during the table's life agrees.

 A table has 16 buckets and a key's hash is 3,553,150,151. Which bucket does the key go into?

The modulo maps any hash onto the available buckets. When the table resizes to 32 buckets, the same hash maps to a different bucket, which is why every entry must be rehashed.

 What is a collision in a hash table?

With more possible keys than buckets, collisions are unavoidable. The table handles them by chaining (a list per bucket) or by probing for another slot.

 Why must get compare the full key with === after finding the bucket?

Returning the first entry in the bucket would hand one user's session to another user whose token happens to collide. Equal hashes never mean equal keys.

 A table holds 1,200 entries in 2,048 buckets. What is its load factor, and what does it tell you?

Load factor = entries / buckets. Keeping it under a constant (often 0.75 for chaining) keeps chains short, so lookups stay O(1) on average.

 A hash table never resizes and has 8 buckets. What is the average cost of a lookup after 80,000 inserts?

The O(1) average depends on the load factor staying bounded. Without resizing, the load factor grows with n and the table degrades into eight linked lists.

 Resizing rehashes every entry, which is O(n). Why is set still called O(1) amortized?

It is the same argument as for push on a growable array: doubling makes the expensive steps geometric, and a geometric sum is bounded by a constant times its largest term.

 What is the worst-case time of get in a chained hash table with n entries, and when does it happen?

The average is O(1) only if the hash spreads the keys. If every key collides, the table is one long chain. Attackers try to cause exactly this.

 Why is "add up the character codes" a poor hash function for voucher codes?

A good hash mixes each character into all bits of the result, so position matters and small changes scatter keys across buckets. FNV-1a does this with an XOR and a multiplication per character.

 A server parses JSON bodies into objects. What protects it against hash flooding?

If attackers can predict collisions, one request with thousands of colliding keys makes every insert O(n). A secret seed makes collisions unpredictable; size limits cap the damage of any single request.

 A support tool stores customers in a plain object keyed by username: customers[username]. A customer signs up with the username "constructor". What happens before they are added?

Plain objects inherit keys such as constructor, toString and __proto__. A Map (or Object.create(null)) has no inherited keys.

 What is the effect of stock[7] = 10; stock["7"] = 3; on a plain object?

Objects convert non-symbol keys to strings. A Map keeps 7 and "7" as different keys.

 Code stores the last login time per user with lastSeen[user] = time, where user is an object. What goes wrong?

Objects become strings when used as object keys. Use lastSeen[user.id], or a Map, which uses the object itself as the key.

 const m = new Map([[{ id: "USR-1" }, "admin"]]); Why does m.get({ id: "USR-1" }) return undefined?

Map compares keys with SameValueZero, which for objects means "the same object in memory". Key by a stable string such as user.id when content should decide equality.

 Which is the best fit for a Map rather than a plain object?

A dictionary whose keys come from data and change often is Map's job. Objects are records: a fixed set of known property names, easy to serialize as JSON.

 A webhook delivered the same order twice, as two separate objects with identical content. Why does new Set(orders) keep both?

new Map(orders.map((o) => [o.id, o])) keeps one entry per id. A Set dedupes primitives and identical references, not equal-looking objects.

 You store orders in a Map keyed by order ID. Which question does the map not make fast?

Hashing scatters keys on purpose, so range questions need a full scan: O(n). A sorted array or a tree keyed by time answers ranges efficiently.

 In the hash map two-sum, why does the loop check seen.has(target - price) before adding the current price?

With the check first, [5000] gives no pair, while [5000, 5000] pairs index 0 with index 1, which is correct.

 A Node.js service keeps sessions in a Map and never removes expired ones. What happens over weeks of traffic?

An entry in a Map is reachable, so the garbage collector keeps it. Expiry times, periodic cleanup or a bounded LRU cache prevent the leak.

 The lesson's delete moves the last entry of the chain into the removed entry's place and pops. Why is that allowed?

When order is irrelevant, swap-and-pop is O(1) instead of the O(chain length) shifting of splice.

 A price table uses naira amounts like 0.3 as Map keys. Why is prices.get(0.1 + 0.2) undefined?

Floating-point arithmetic is not exact, and a hash table needs exact equality. Integer minor units (kobo) avoid the problem.

 In an open-addressing (linear probing) table, why can delete not simply set the slot back to empty?

Probing searches until it finds the key or an empty slot. Real implementations leave a "deleted" marker (a tombstone) so searches continue past it.

 An app runs on three server processes behind a load balancer and keeps sessions in a Map in each process. What is the symptom?

Each process has its own memory. A shared store (such as Redis, a hash table on its own server) or sticky routing is needed so that every process sees every session.
