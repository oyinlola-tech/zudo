This class compiles in JavaScript. What does TypeScript (strict) say about it? class Task { id: number; constructor(id: number, title: string) { this.id = id; this.title = title; } }

TypeScript wants every property declared at the top of the class with its type. id is declared and set in the constructor, so it is fine. title was never declared, so this.title is error TS2339, the same error a typo like this.titel would give.

 Which property does TypeScript (strict) reject, and why? class Task { done = false; title: string; id: number; constructor(id: number) { this.id = id; } }

done = false gets a value and TypeScript infers boolean. id is set in the constructor. title is declared as a string but never set, so it would really be undefined: error TS2564, "has no initializer and is not definitely assigned".

 What does this print? class Task { done = false; constructor(public id: number, public title: string) {} complete(): this { this.done = true; return this; } describe(): string { return `${this.done ? "[x]" : "[ ]"} #${this.id} ${this.title}`; } } console.log(new Task(1, "Buy milk").complete().describe()); console.log(new Task(2, "Call Ada").describe());

complete() returns this, the task itself, so you can call describe() right after it. Each new Task is a separate object, so the second task is still not done.

 What does this print? class Task { done = false; tags: string[] = []; id: number; title: string; constructor(id: number, title: string) { this.id = id; this.title = title; } } console.log(new Task(1, "Buy milk"));

All four properties exist on the object, in the order they are declared. Node prints the class name in front of the object, so you can tell a Task from a plain object.

 Which constructor makes title a property of the object without any other line?

Putting public, private, protected or readonly in front of a constructor parameter makes it a parameter property: TypeScript declares the property and copies the argument into it. A plain parameter is only a local variable.

 What does this print? class Task { constructor( public readonly id: number, public title: string, public done = false, ) {} } const task = new Task(1, "Buy milk"); task.title = "Buy oat milk"; console.log(task);

All three parameters are parameter properties, so the object gets id, title and done. done uses its default false. title is not readonly, so it can be changed afterwards.

 Which line does TypeScript reject? class Book { constructor(public readonly isbn: string, public title: string) {} } const book = new Book("978-0", "Dune"); book.title = "Dune Messiah"; book.isbn = "978-1";

readonly means the value is set once, in the constructor, and never changes: error TS2540 "Cannot assign to 'isbn' because it is a read-only property". title is a normal public property, so changing it is fine.

 A property is readonly and holds an array. What does this print? class Recorder { readonly saved: string[] = []; save(text: string): void { this.saved.push(text); } } const recorder = new Recorder(); recorder.save("a"); recorder.save("b"); console.log(recorder.saved);

readonly stops you from pointing saved at a different array. The array itself can still change, just like a const variable holding an array. So push works.

 Why does Node's built-in type stripping refuse parameter properties like constructor(private repo: Repo) {}?

Type stripping works by removing the type parts and running what is left. A parameter property is not just a type: TypeScript has to write the assignment for you. tsx, tsc and the browser terminal do that, which is why the course runs code with tsx.

 Who may use a protected property?

public (the default) is for anyone, private is only for the class itself, and protected adds subclasses. Outside code may use neither private nor protected.

 Which line does TypeScript reject? class Account { protected balance = 0; private readonly history: number[] = []; deposit(amount: number): void { this.balance += amount; this.history.push(amount); } } class Savings extends Account { addInterest(rate: number): void { this.balance += this.balance * rate; } } const s = new Savings(); s.deposit(100); console.log(s.balance);

Account may use its own private history, and the subclass Savings may use the protected balance. deposit is public. But outside code reading s.balance is error TS2445: protected is for the class and its subclasses only.

 What does this print? class UserA { constructor(public email: string, private passwordHash: string) {} } class UserB { #passwordHash: string; constructor(public email: string, passwordHash: string) { this.#passwordHash = passwordHash; } } console.log(JSON.stringify(new UserA("ada@example.com", "h4sh"))); console.log(JSON.stringify(new UserB("ada@example.com", "h4sh")));

TypeScript's private is only a type, and types are erased: at runtime passwordHash is an ordinary property, so it goes into the JSON. A # field is private in JavaScript itself and never appears in JSON.stringify.

 What does this print? class A { constructor(public email: string, private token: string) {} } class B { #token: string; constructor(public email: string, token: string) { this.#token = token; } } console.log(Object.keys(new A("x@y.z", "t")), Object.keys(new B("x@y.z", "t")));

After compiling, private token is a normal property, so Object.keys lists it. A #token field is not a normal property at all: it is hidden from Object.keys, JSON.stringify and outside code.

 This file type-checks. What does it print? class User { constructor(public email: string, private passwordHash: string) {} } const user = new User("ada@example.com", "h4sh"); console.log(user["passwordHash"]);

TypeScript allows square-bracket access to a private property as a deliberate escape hatch, and at runtime the property is really there. private organises your code; it does not hide anything.

 A class holds an API key that must never leak into logs or responses. Which is the right choice?

private, protected and readonly are compile-time checks only: at runtime the key is a normal property that JSON.stringify and console.log show. #apiKey is enforced by JavaScript. Even better, build responses with only the fields you choose.

 A User object has id, email and a passwordHash. What is the safest way to send the user in an API response?

Listing the fields you send is the only way that stays safe when someone later adds a new secret property. Stringifying, spreading and Object.assign all copy every normal property, including a TypeScript-private hash.

 Which line does TypeScript reject? class User { #hash: string; constructor(public email: string, hash: string) { this.#hash = hash; } } const u = new User("a@b.c", "h"); console.log(u.email); console.log(u["#hash"]);

Inside the class, this.#hash is allowed. From outside there is no way to reach a # field: the string "#hash" is not a property name of User, so TypeScript reports an error (and at runtime it would just be undefined).

 What happens with new Shape() when Shape is an abstract class?

An abstract class is only a starting point for subclasses. TypeScript rejects new on it (TS2511). You create a subclass that fills in the abstract methods, and use that.

 abstract class Notifier has protected abstract send(to: string, text: string): Promise<void>. You write class EmailNotifier extends Notifier {}. What happens?

An abstract method is a name and a type with no body, and every (non-abstract) subclass must write it. The compiler reports the missing method on the subclass (TS2515), long before anything runs.

 What does this print? abstract class Notifier { constructor(protected readonly appName: string) {} protected abstract send(to: string, text: string): Promise; async taskDue(to: string, title: string): Promise { await this.send(to, `[${this.appName}] "${title}" is due today`); } } class ConsoleNotifier extends Notifier { protected async send(to: string, text: string): Promise { console.log(`to ${to}: ${text}`); } } await new ConsoleNotifier("Tasks").taskDue("ada@example.com", "File taxes");

Notifier decides what the message says (taskDue), and the subclass decides how it is delivered (send). Calling taskDue on a ConsoleNotifier runs the subclass's send.

 When should you choose an interface instead of an abstract class?

An abstract class shares code: finished methods plus abstract ones. An interface is only a contract: "anything that stores tasks must have these methods". Both are checked at compile time.

 What does TypeScript report for this code? interface Clock { now(): Date; } class TextClock implements Clock { now(): string { return "noon"; } }

implements Clock makes the compiler check the class itself against the interface. A missing method, or a method with the wrong type, is reported right there on the class (TS2416 here).

 What does this print? interface Named { name: string; } interface Aged { age: number; } class Person implements Named, Aged { constructor(public name: string, public age: number) {} } const p = new Person("Ada", 36); console.log(Object.keys(p), typeof p);

A class can implement several interfaces, and implements adds no code at all: it is only a check. At runtime the object has just its own properties, and typeof any object is "object".

 Why does TaskService take its repository and clock in the constructor, instead of writing new MemoryTaskRepository() and new Date() inside?

If the service creates its own dependencies, it is stuck with them forever. Asking for them in the constructor, typed as interfaces, is constructor injection: whoever creates the service decides which real or fake objects to use.

 With dependency injection by hand, where are the real objects (repository, clock, service) created?

Services only know interfaces. The entry file (for example main.ts) creates the real objects and passes them in. That one place is the composition root.

 interface Clock { now(): Date }. Is const systemClock: Clock = { now: () => new Date() } allowed?

TypeScript checks the shape, not the name. A plain object with the right method is a Clock. implements is only an extra check you can put on a class.

 What does this print? interface Clock { now(): Date; } class TaskService { readonly #titles: { title: string; dueDate: Date }[] = []; constructor(private readonly clock: Clock) {} add(title: string, daysUntilDue: number): void { const dueDate = new Date(this.clock.now().getTime() + daysUntilDue * 86_400_000); this.#titles.push({ title, dueDate }); } overdue(): string[] { const now = this.clock.now(); return this.#titles.filter((t) => t.dueDate < now).map((t) => t.title); } } const clock: Clock = { now: () => new Date("2026-03-01T09:00:00Z") }; const service = new TaskService(clock); service.add("File taxes", 3); service.add("Call Ada", -1); service.add("Pay rent", 0); console.log(service.overdue());

A fake implements the same interface, so the service cannot tell it from the real thing. It is simple on purpose: a clock that stands still, a repository that just records what was saved.

A dependency can be a function type, not just an interface. The reminder service only needs "give me the overdue titles", so a test can pass async () => ["File taxes"] without building a whole task service.

 Wiring services by hand in main.ts works for three classes. What helps when a backend has dozens of services?

A container creates the services in the right order and passes each one what it needs. It works with exactly the same constructor-injected classes; only the wiring moves out of your hands.
