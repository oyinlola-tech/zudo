What does JavaScript create each time a function is called?

Every call gets a fresh environment. That is why two calls of createAccount produce two separate balances, and why closures made in different calls never share local variables.

 A function runs. Where does JavaScript look for a name that is not in the function's own call environment?

A function stores the environment it was created in ([[Environment]]). Its call environment links to that one, not to the caller's. This is what "lexical scope" means.

 createAccount() returns { deposit, balance }, two functions created inside the same call. What is true?

Functions created in the same call point at the same environment. A deposit changes the variable that balance reads.

 Which description of a closure is the most accurate?

A closure keeps a reference to its environment, not a snapshot. It sees the current value of every variable it uses, and it keeps that environment alive as long as the function itself is reachable.

 A checkout shows a price using exchangeRate, a module variable that is updated every minute. The customer must be charged at the rate they saw. How do you lock it in a closure?

The factory call's parameter is a new variable that nothing assigns to again, so it keeps the value it was given. Reading the module variable would follow every later update.

 Why does for (let i = 0; i < 3; i++) fns.push(() => i) give functions that return 0, 1 and 2?

This per-turn copy is a special rule for let declared in the for head. With var there is only one i, and all arrows read its final value.

 This code still makes every handler report the last position. Which change fixes it? let n = 0; while (n < 3) { handlers.push(() => n); n += 1; }

There is only one n, declared outside the loop. A const inside the body lives in the body's block environment, which is new on every turn, and it never changes after the closure captures it. (const n would fail at n += 1.)

 Old code wraps a loop body in (function (position) { … })(i);. What problem did that solve?

An IIFE (Immediately Invoked Function Expression) is a function called right where it is written. Each call creates a new environment with a new position parameter. Today let, const and array methods do the job more clearly.

 An import job creates one million order-line objects, each with the same five methods. Why might a class be better here than a closure-based factory?

Every call of a factory creates new functions for the returned object. With a million objects that adds up. Class methods live on the prototype and are shared by all instances, and #private fields keep data just as private.

 A closure-based account returns { deposit, balance }, and the methods use variables, not this. What is the practical benefit?

Class methods lose this when taken off their object. Closure methods find their data through their environment, so amounts.forEach(account.deposit) works.

 createFeeCalculator({ percent: 0.5, minKobo: 1000, capKobo: 200000 }) returns feeFor(amountKobo). What is this technique called, and what does it buy you?

Supplying some inputs now and the rest later is partial application. The closure remembers the settings, so the rest of the program never passes them around again.

 const pay = once(chargeCard). The first call is pay("ORD-7", 5000). What does pay("ORD-8", 9000) do?

once runs the function the first time and returns the stored result forever after, ignoring new arguments. That is right for one-time setup, and wrong as general duplicate protection for payments, which must be keyed by order id.

 Which function is safe to memoize?

Memoization is only safe for pure functions: same arguments, same result, no side effects. The others read changing data or perform an action that the cache would silently skip.

 A memoized totalOf(cart) uses the cart object as the Map key. What goes wrong?

A Map key is matched by identity, not content. Memoize functions of simple values, or build an explicit key, and never cache results for data that can change.

 Why should a memoization cache in a long-running server have a size limit?

The cache lives in a closure that lives as long as the memoized function, often the whole process. Evicting the oldest entry (a Map keeps insertion order) keeps the size bounded.

 In const result = fn(key); cache.set(key, result);, what happens to the cache when fn throws?

A thrown error ends the function at that line. Not caching failures is usually what you want, because the next attempt might succeed.

 Every request handler calls priceUpdates.subscribe((e) => notify(request, e)) and never unsubscribes. What happens over days of traffic?

The hub is long-lived and reachable, so are the listeners in it, so are the environments they closed over. Return an unsubscribe function from subscribe and call it when the work is done.

 Why call unsubscribe() inside a finally block?

finally always runs when the try block ends, by return or by throw. Cleanup placed there cannot be skipped by an error.

 A long-lived label function is () => `${report.title}`, where report holds 50,000 rows. How do you stop it from keeping the rows alive?

A closure keeps alive what it uses. If it only uses a short string, the large object can be collected once nothing else refers to it (as long as no other closure from the same call still uses report).

 Why does createTransferLimit take a today function instead of calling new Date() itself?

Passing a dependency in makes the code testable: the limiter only needs "what day is it?", not a real clock. This is dependency injection with a function.

 How should you test a closure's private sentKobo variable?

Tests should check behaviour the same way callers see it. That also lets you change the private details later without rewriting the tests.

 The daily limiter keeps its totals in closures. The app now runs as two server processes behind a load balancer. What breaks?

Memory belongs to one process. Limits that must hold across processes and restarts live in a shared store such as Redis or the database; the closure design carries over, with the store passed in like the clock.
