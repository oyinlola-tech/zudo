Why does a backend use asynchronous code when it waits for a database?

A backend mostly waits. If it stopped everything while waiting, it could only serve one person at a time. Asynchronous code says "call me back when it is ready" and moves on.

 What does this print? console.log("1. Ask the database"); setTimeout(() => { console.log("3. The database answered"); }, 20); console.log("2. Carry on");

setTimeout registers the function and returns at once. JavaScript keeps going, and runs the function when the time is up, after line 2.

 The timer asks for 0 ms. What does this print? setTimeout(() => console.log("timer"), 0); for (let i = 0; i < 3; i++) { console.log("loop", i); }

JavaScript runs on one thread. The timer is due right away, but it has to wait until the synchronous code has finished and let go of the thread.

 JavaScript runs your code on a single thread. What does that mean for a long while loop that keeps the thread busy for 2 seconds on a server?

That is blocking code. While synchronous code runs, nothing else can, so a busy loop freezes the whole server, not just one request.

 A server reads a file for each request. Which should it use?

readFileSync blocks the thread until the file is read. The non-blocking version starts the work, gives the thread back and calls you later.

 Node.js callbacks are error-first. What does that mean?

The shape is (error, result) => { … }. You must check error every time, then use the result.

 What does this print? function getUser(id, callback) { setTimeout(() => { if (id !== 1) return callback(new Error(`user ${id} not found`)); callback(null, { id, name: "Ada" }); }, 10); } getUser(2, (error, user) => { if (error) { console.log("failed:", error.message); return; } console.log(user.name); });

For id 2 the function calls back with an error first and no result. The callback checks error and returns before touching user.

 Which is not one of the problems of "callback hell"?

Callbacks do pass data (the result argument). Their problems are deep nesting, repeated error checks that are easy to forget, no try/catch across steps, and double calls. Promises fix these.

 What is a Promise?

A function that works asynchronously returns a promise straight away. You attach what should happen once the value is there, with .then or await.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); function findTask(id) { return wait(20).then(() => ({ id, title: "Buy milk" })); } const promise = findTask(1); console.log(promise instanceof Promise); promise.then((task) => console.log("Found:", task.title)); console.log("waiting");

findTask returns a promise at once, so instanceof Promise is true and "waiting" prints next. The .then function runs later, when the value is ready.

 Which list shows the three states of a promise?

A promise starts pending, then becomes fulfilled with a value or rejected with a reason. Fulfilled and rejected together are called settled.

 What does this print? const p = new Promise((resolve, reject) => { reject(new Error("disk full")); resolve("too late"); reject(new Error("again")); }); p.then( (value) => console.log("fulfilled:", value), (error) => console.log("rejected:", error.message), );

A promise settles only once and never changes. The first call, reject(disk full), wins; the later calls are ignored. That rule removes the "callback called twice" bug.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const save = (report) => wait(10).then(() => { if (report.length > 10) throw new Error("report too long"); return report; }); save("Ada: Buy milk, Call Grace") .then((saved) => console.log("saved:", saved)) .catch((error) => console.log("failed:", error.message)) .finally(() => console.log("done"));

The report is longer than 10 characters, so save rejects. The .then step is skipped, .catch handles it, and .finally runs at the end either way.

 In a chain a().then(b).then(c).catch(handle), which failures does .catch(handle) receive?

A rejection skips the following .then steps until it reaches a .catch. One .catch at the end covers the whole chain.

 What does this print? async function getLimit() { return 10; } const result = getLimit(); console.log(result instanceof Promise); result.then((value) => console.log(value));

An async function always returns a promise, even when it returns a plain value. You get the value with await or .then.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); async function main() { console.log("A"); await wait(20); console.log("C"); } main(); console.log("B");

await pauses only main. The rest of the program keeps running, so "B" prints while main waits, and "C" comes after the 20 ms.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); async function saveTask(task) { await wait(10); if (task.title === "") throw new Error("title must not be empty"); return { ...task, id: 3 }; } async function main() { try { const saved = await saveTask({ title: "Call Ada" }); console.log("Saved:", saved.id); await saveTask({ title: "" }); console.log("This line never runs"); } catch (error) { console.log("Could not save:", error.message); } } main();

When an async function throws, its promise is rejected. await turns the rejection back into a thrown error, which jumps to catch and skips the next line.

 The await is missing. What does this print? (The last line catches the error so the program does not crash.) const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); async function saveTask(task) { await wait(10); if (task.title === "") throw new Error("title must not be empty"); return task; } let promise; try { promise = saveTask({ title: "" }); console.log("Saved, I think"); } catch (error) { console.log("Could not save:", error.message); } promise.catch((error) => console.log("later:", error.message));

Without await, the call returns a pending promise at once and try finishes happily. The error comes later, when the try block is long gone.

 What happens in Node.js when a rejected promise is never handled (no await in a try, no .catch)?

An error nobody saw is dangerous, so Node.js crashes on it. Whenever you call an async function, either await it or attach a .catch.

 You need the user count and the task count, and neither depends on the other. What is the better way?

Independent waits should run at the same time. Two 100 ms lookups then take about 100 ms, not 200. Use sequential awaits only when a step needs the previous result.

 The slow promise finishes last. What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const fetchTask = (id, ms) => wait(ms).then(() => id); Promise.all([fetchTask(1, 40), fetchTask(2, 10), fetchTask(3, 20)]).then((ids) => { console.log(ids); });

Promise.all keeps the results in the same order as the input, whatever order they finish in.

 You must load 10,000 records from a database. Why not start all 10,000 queries at once with Promise.all?

Parallel is not always right. Start a small number at a time (a batch), wait for them with Promise.all, then start the next batch.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const succeed = (value, ms) => wait(ms).then(() => value); const fail = (message, ms) => wait(ms).then(() => { throw new Error(message); }); Promise.all([succeed("tasks", 20), fail("users down", 10)]) .then((values) => console.log("all:", values)) .catch((error) => console.log("all failed:", error.message));

Promise.all rejects with the first error. The successful "tasks" value is lost. Use allSettled when partial results are useful.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const succeed = (value, ms) => wait(ms).then(() => value); const fail = (message, ms) => wait(ms).then(() => { throw new Error(message); }); Promise.allSettled([succeed("tasks", 20), fail("users down", 10)]).then((results) => { console.log(results.map((r) => r.status)); console.log(results.map((r) => (r.status === "fulfilled" ? r.value : r.reason.message))); });

allSettled never fails. It reports each promise in input order: status plus value when fulfilled, or reason when rejected.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const succeed = (value, ms) => wait(ms).then(() => value); const fail = (message, ms) => wait(ms).then(() => { throw new Error(message); }); Promise.race([succeed("slow", 40), fail("fast failure", 10)]) .then((value) => console.log("race:", value)) .catch((error) => console.log("race failed:", error.message));

Promise.race settles like whichever promise settles first, success or failure. The failure came first, so the race fails.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const succeed = (value, ms) => wait(ms).then(() => value); const fail = (message, ms) => wait(ms).then(() => { throw new Error(message); }); Promise.any([fail("mirror 1 down", 10), succeed("mirror 2", 30)]).then((value) => { console.log("any:", value); });

Promise.any waits for the first success and skips failures. It only fails if every promise fails.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); const fail = (message, ms) => wait(ms).then(() => { throw new Error(message); }); Promise.any([fail("a down", 10), fail("b down", 20)]).catch((error) => { console.log(error.name, error.errors.map((e) => e.message)); });

When every promise fails, Promise.any rejects with an AggregateError. Its errors array lists every reason.

 A page needs the user and may show tasks and notifications. You want every result that arrived, even if some services failed. Which should you use?

allSettled reports each promise separately and never fails, so you keep the partial results. all would throw away everything on the first failure.

 How does the lesson's withTimeout(promise, ms) put a time limit on a promise?

Promise.race([promise, timeout]) settles with whichever comes first. If the timer rejects first, the slow work counts as failed. finally then clears the timer.

 Why does withTimeout call clearTimeout(timer) in .finally?

When the real work wins, the timer is no longer needed. Clearing it stops it from running later and from keeping the process alive.

 What does this print? const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms)); function withTimeout(promise, ms, name) { let timer; const timeout = new Promise((resolve, reject) => { timer = setTimeout(() => reject(new Error(`${name} timed out`)), ms); }); return Promise.race([promise, timeout]).finally(() => clearTimeout(timer)); } const tasks = wait(10).then(() => "tasks"); const notes = wait(80).then(() => "notes"); Promise.allSettled([withTimeout(tasks, 40, "tasks"), withTimeout(notes, 40, "notes")]).then((results) => { console.log(results.map((r) => r.value ?? r.reason.message)); });

tasks answers in 10 ms, inside the 40 ms limit. notes needs 80 ms, so the timer rejects first and it counts as failed.

 In the dashboard loader, what happens when the user service fails, and when the notifications service fails?

The user is required, so the loader re-throws user.reason. Tasks and notifications are nice to have: the page shows the rest and reports what is missing.

 In retry, the lesson writes return await fn(attempt); inside try. Why not just return fn(attempt);?

This is the forgotten-await bug again. await makes the rejection happen inside the try, so catch can count the attempt and try again.
