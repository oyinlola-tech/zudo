A loan type has approved: boolean, rejected: boolean, approvedBy?: string and rejectionReason?: string. The business has three real states. What is the core problem?

2 × 2 × 2 × 2 = 16 shapes for 3 states. Every reader must guess which combinations are real. A discriminated union allows exactly the three real states.

 Thinking of types as sets of values, which statement is right?

A literal type is a set with one value; a union puts sets together. never is the empty set, and "in both" describes an intersection, A & B.

 Why does amount.toFixed(2) fail to compile when amount: number | string?

The value might be a string, so TypeScript refuses a number-only method until you narrow, for example with typeof amount === "number".

 Given type Status = "pending" | "approved", which assignment is an error?

A member fits the union, and a union fits any wider type. But a union does not fit one of its members: someStatus might be "pending". Narrow first.

 What makes a union of object types a discriminated union?

A shared property with distinct literal types (status: "pending", status: "approved", …) lets TypeScript narrow to exactly one member when you check it.

 Why does narrowing stop working if the discriminant is typed status: string in every member?

The discriminant must be a literal type in each member. With string, the check tells TypeScript nothing about which member it has.

 What does TypeScript report for this, where LoanRequest is the pending/approved/rejected union? const loan: LoanRequest = { id: 3, customer: "Chidi", amount: 20000, status: "pending", approvedBy: "Tunde" };

TypeScript uses the discriminant to pick the member you meant, PendingLoan, and then checks the object literal against it alone. The extra property is caught.

 Why is function approve(loan: PendingLoan, officer: string): ApprovedLoan better than function approve(loan: LoanRequest, officer: string): LoanRequest?

The parameter type encodes where the move may start, and the return type where it ends. Passing a rejected loan is a compile error, and the result has approvedBy without further checks.

 Why build a new object in approve instead of writing loan.status = "approved"?

A state change usually adds or removes fields. Building a complete new object of the target member keeps every value valid. Making the discriminant readonly stops the in-place change at compile time.

 What does an assertNever(loan) call in the default branch give you that a plain default: return "" does not?

When every member is handled, loan is never in the default branch and the call compiles. A forgotten member is not never, so the call fails to compile. At runtime, the throw turns silent wrong answers into visible errors.

 A switch over a union has no default, every case returns, and the function's return type is string. A new member is added. What happens?

It is exhaustive, but indirectly: the error points at the return type, not at the switch, and it only works while every case returns.

 How does const colour: Record<LoanStatus, string> = { … } act as an exhaustive check?

Record<K, V> requires a property for every key in K. It suits mappings from each member to a value, but has no runtime safety net: an unexpected key reads as undefined.

 Why is an if / else if / else chain over a status union risky when members are added later?

The code keeps compiling and treats the new member like whatever the else was written for. A switch with assertNever turns that into a compile error.

 What is the type "pending" | "approved" | string equal to?

A set united with a bigger set that contains it is just the bigger set. Misspellings like "aproved" then compile. Model open-ended values as their own member instead, for example { status: "other"; label: string }.

 Why does if (loan.approvedBy) fail to compile on the loan union?

Rule 1 again: only what every member supports. Check the discriminant, loan.status === "approved", and then approvedBy is available.

 Why return a TransferResult union instead of throwing when a transfer is declined for insufficient funds?

A thrown error is invisible in the function's type, and catch receives unknown. A result union lists every outcome. Keep exceptions for the unexpected: a crashed database, a bug.

 In TransferError, why does the "insufficient-funds" member carry balance and requested, while "account-frozen" carries nothing?

The same principle as the loan states: data belongs to the case it describes. The message function can then say "You have ₦30000, but tried to send ₦45000" without optional fields.

 For object types, what is Loan & Audit?

An intersection keeps values that belong to both sets. For objects that means having every property of both. If Loan is a union, the intersection applies to each member.

 Loan is Pending | Approved. What is Loan & Audit equivalent to?

Intersection spreads over union like multiplication over addition. Each member gains the audit fields, and the union stays discriminated.

 What is the type of id in { id: number } & { id: string }?

Intersections combine property by property, and number & string is empty. No object can satisfy the type. When you see an unexpected never, look for intersected types that disagree.

 What does TypeScript reduce { status: "pending" } & { status: "approved" } to?

When two object types disagree on a literal property that acts as a discriminant, TypeScript reduces the whole intersection to never.

 What does Extract<Loan, { status: "pending" }> give you?

Extract picks union members that are assignable to the second type. It avoids repeating the member's definition. Like every type, it is erased at runtime.

 A client sends { "status": "approved", "approvedBy": "me", "amount": 900000 } to your create-loan endpoint. The handler's parameter is typed LoanRequest. What protects you?

The body arrives at runtime, long after compiling. Validate the input, and never let a client set a field that staff should set: a new loan is always created as pending by your code.
