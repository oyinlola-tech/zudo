What does @zudojs/lifecycle manage, compared with @zudojs/runtime?

The ideas are the same (order, rollback, graceful shutdown), one level down. The lifecycle package also stands alone: it depends only on @zudojs/errors and @zudojs/constants.

 Three components depend on each other: http → queue → database. In what order do the hooks run on start()?

A phase runs for every component before the next phase begins, and within a phase dependencies go first. When http becomes ready, every component has at least started.

 Which work belongs in initialize rather than start?

initialize prepares; start connects; ready confirms. Keeping network work out of initialize means a configuration mistake fails before anything is opened.

 What is manager.state after await manager.shutdown(), and can you call start() again?

disposed has no outgoing transitions. To run again, create and register a new manager.

 According to LIFECYCLE_VALID_TRANSITIONS, where can a component go from failed?

A failed component is cleaned up, never "un-failed". Retrying happens inside a phase (the retry option), before the component is marked failed.

 cache and database do not depend on each other. How does the manager start them?

Independent components share a stage and run concurrently. Starting them one by one would add their times for nothing.

 metrics has priority: 100; database and cache have the default. What does that mean?

Priority is a barrier: all components of a higher priority finish the phase before a lower priority begins. Shutdown is the mirror image, so the highest priority stops last.

 database takes 200 ms, queue (depends on database) takes 50 ms, cache takes 100 ms, all starting at 0 ms. When is queue up?

The queue waits only for the database (200 ms), then needs 50 ms. The cache runs alongside and does not delay it.

 When does the manager report a dependency cycle between orders and payments?

The whole graph is validated first. No connection is opened for an application whose wiring is impossible.

 What happens if you call manager.register(...) after manager.start()?

Freezing the registry keeps the plan that is running consistent. Register everything before starting.

 A mailer registered with critical: false fails to start. What is the result?

Non-critical parts may fail without failing the application. Watch component:failed or the status so someone notices.

 The non-critical mailer failed to start. On shutdown, is its stop called?

The same is true for the component that fails during a rollback. Guard stop on the resource it closes.

 A component always fails and is registered with retry: { attempts: 3, delay: 100 }. How many times is start called?

attempts counts retries. Plan the total time with that in mind.

 With retry: { attempts: 3, delay: 100 } and no backoff, what are the waits between calls?

Backoff is exponential unless you write backoff: "fixed". maxDelay caps a single wait (10 seconds by default).

 Which startup failure is worth retrying?

Retry transient failures: a service still booting, a timeout, a 503. A wrong password or a missing table fails the same way every time, and retrying only delays the message the operator needs.

 A component has timeout: 100 and its start takes 500 ms. When does manager.start() reject in the published version?

Waiting prevents a stop from running alongside a start that is still going. The cost is that a timeout does not free startup by itself.

 A start hook returns a promise that never settles. It has timeout: 100. What happens?

Because the manager waits for timed-out hooks to settle, a hook that never settles hangs startup. Make the work itself cancellable, for example with AbortSignal.timeout.

 What does passing AbortSignal.timeout(100) to a connect call achieve inside a start hook?

Cancellation has to happen where the waiting happens. The manager's timeout then acts only as a safety net.

 A component times out during start. What is the error chain of the rejection?

Each layer adds what it knows: the start failed, this component and phase failed, and why. Walk error.cause to reach the original.

 The HTTP server fails to start after the database and queue started. What does the rollback do?

Rollback leaves nothing open. To try again, build a new manager.

 After a failed start you call manager.start() again. What happens?

start() and shutdown() are idempotent: they return the same promise every time. A retry of the whole start needs a new manager.

 During shutdown, the search component's stop throws. What happens to the others?

One broken part must not keep the others open. Because shutdown() still resolves, you must listen for the event to see the failure.

 shutdownTimeout: 200 expires while a worker's stop is still running. What happens?

Listening to context.signal lets the worker stop cleanly. The published version reports nothing when a hook is abandoned, so a shutdown that takes exactly the deadline is a warning sign.

 Kubernetes waits 30 seconds between SIGTERM and a hard kill. What is a sensible shutdownTimeout?

Your own deadline must fire first, so your clean-up (aborting work, closing connections) runs before the platform kills the process.

 What does the default handleSignals: true do?

Handlers are installed by start() and removed afterwards. The manager never calls process.exit() after a normal shutdown; the process ends when nothing is left open.

 A process has a @zudojs/runtime runtime with signal handling on, and a lifecycle manager inside one of its modules. What should the manager use?

One owner per process. Two handlers race, and the order between "stop the module" and "stop its components" is lost.

 In the shop example, why must the HTTP server stop before the queue, and the queue before the database?

Shutdown reverses the dependency chain: stop taking work, finish it, then release what it used. With the queue's dependsOn missing, orders stayed pending.
