Three entry points (an HTTP route, a CLI tool, a batch job) each run their own copy of the authentication, authorization and validation checks. What is the main risk?

Every copy compiles and passes its own tests. The bug is the line nobody wrote a second time. One pipeline shared by every entry point removes the copies.

 What does this print? import { compose } from "@zudojs/middleware"; import type { Middleware } from "@zudojs/middleware"; type Context = { log: string[] }; const a: Middleware = async (context, next) => { context.log.push("a in"); const result = await next(); context.log.push("a out"); return result.toUpperCase(); }; const b: Middleware = async (context, next) => { context.log.push("b in"); return next(); }; const run = compose([a, b], async (context) => { context.log.push("handler"); return "paid"; }); const context: Context = { log: [] }; console.log(await run(context), context.log.join(", "));

The first middleware starts first and finishes last, and it can change the result on the way out: a upper-cased what the handler returned.

 What does createPipeline's function return when a middleware throws, with the default options?

The default error mode is "capture": the chain stops and the failure is reported in the outcome, including executedMiddleware and errors.

 What does this print? import { createPipeline } from "@zudojs/middleware"; import type { NamedMiddleware } from "@zudojs/middleware"; type Context = { token?: string }; const step = (name: string, fail = false): NamedMiddleware => ({ name, handler: async (_context, next) => { if (fail) throw new Error(`${name} refused`); return next(); }, }); const run = createPipeline([step("log"), step("authenticate", true), step("validate")], async () => "done"); const outcome = await run({}); console.log(outcome.success, outcome.executedMiddleware, outcome.errors.length);

 Why can you write if (outcome.success) use(outcome.result) without TypeScript complaining that result may be undefined?

PipelineResult is PipelineSuccess | PipelineFailure, told apart by success: true or false. Narrowing on it is the TypeScript pattern from the unions lesson.

 What does this print? import { resolveNamedMiddleware } from "@zudojs/middleware"; import type { NamedMiddleware } from "@zudojs/middleware"; const m = (name: string, priority?: number, enabled?: boolean): NamedMiddleware => ({ name, priority, enabled, handler: async (_c, next) => next(), }); const order = resolveNamedMiddleware([m("validate"), m("authorize", 10), m("metrics", 0, false), m("authenticate", 10), m("log", 0)]); console.log(order.map((x) => x.name).join(" > "));

Lower priority runs first, the default is 100, disabled middleware is dropped, and equal priorities keep their list order. That last rule put authorize before authenticate: a real bug in a security chain.

 What priority does a named middleware get when you give none?

The default is 100 and lower numbers run earlier. errorMiddleware uses 0, so it runs before everything with the default.

 When one file builds the whole pipeline, why does this lesson prefer a plain list in the right order over priorities?

Priorities help when middleware comes from several places. Within one file, the list itself is the clearest statement of order.

 In the transfer context, token and body are readonly while user and transfer are optional and writable. Why?

Only authenticate sets user and only validate sets transfer. A handler that reads them knows they were checked; a handler reading body would skip validation.

 Which value should the transfer handler use for the amount?

The raw body is untrusted: it may be missing, a string or negative. The parsed transfer exists only if validation passed, which is the whole point of putting validation before the handler.

 What does this print? import { createPipeline } from "@zudojs/middleware"; import type { NamedMiddleware } from "@zudojs/middleware"; const audit: NamedMiddleware = { name: "audit", handler: async () => { throw new Error("audit store down"); }, }; for (const errorMode of ["capture", "continue"] as const) { const outcome = await createPipeline([audit], async () => "transfer done", { errorMode })({}); console.log(errorMode, outcome.success, outcome.success ? outcome.result : "-", outcome.errors.length); }

capture stops and reports. continue records the failure, skips the rest of that middleware and still runs the handler, so the outcome succeeds with one recorded error.

 Why must a pipeline that contains authenticate never use errorMode: "continue"?

continue is for truly optional steps such as an audit log. For a security check, "skip the failing middleware and carry on" means "let the attacker in".

 When is errorMode: "throw" the right choice?

"throw" stops the chain and lets the error propagate. The deprecated option is stopOnError, not errorMode.

 What does this print? import { createPipeline } from "@zudojs/middleware"; import type { NamedMiddleware } from "@zudojs/middleware"; let payments = 0; const again: NamedMiddleware = { name: "again", handler: async (_context, next) => { await next(); return next(); }, }; const outcome = await createPipeline([again], async () => { payments += 1; return "paid"; })({}); console.log(outcome.success, payments, !outcome.success && (outcome.error as Error).name);

A second next() would run the handler, and the payment, twice. The pipeline refuses it before the handler runs again. A retry belongs inside the handler, around the operation you know is safe to repeat.

 What does errorMiddleware(onError) do with an error thrown further down the pipeline?

It is a reporter, not a handler. With priority 0 it runs first, so it sees every error of the middleware after it.

 What does this print? import { createPipeline, timeoutMiddleware } from "@zudojs/middleware"; let bankDone = false; const run = createPipeline([timeoutMiddleware(20)], async () => { await new Promise((resolve) => setTimeout(resolve, 60)); bankDone = true; return "sent"; }); const outcome = await run({}); console.log(outcome.success, bankDone); await new Promise((resolve) => setTimeout(resolve, 80)); console.log(bankDone);

The timeout made the pipeline stop waiting, but the work it was waiting for kept running and finished later. A timeout means "I don't know", never "it did not happen".

 A payment call must really stop when the timeout fires. What do you need?

Nothing in the middleware contract can stop a promise that is already running. Only code that checks a signal can stop, which is why fetch and many clients accept one.

 What does this print? import { createPipeline } from "@zudojs/middleware"; const controller = new AbortController(); controller.abort(); const outcome = await createPipeline([], async () => "sent", { signal: controller.signal })({}); console.log(outcome.success, !outcome.success && (outcome.error as Error).name);

The pipeline checks its signal before each middleware and before the handler. An aborted signal fails the run with MiddlewareAbortedError without calling the handler.

 A request path is /transfers\n[INFO] admin logged in. Why does loggingMiddleware write the newline as the two characters \n?

Escaping control characters keeps every caller-supplied value inside its own line, while the original stays readable. sanitizeLogValue does the same for your own lines.

 Why does loggingMiddleware leave the error message out of its completion line by default?

A message like connection to postgres://bank:s3cret@db failed would put a password in the logs. Opt in with includeErrorMessage: true only when your messages are safe.

 What does this print? import { sanitizeLogValue } from "@zudojs/middleware"; console.log(sanitizeLogValue("Chiamaka\r\nERROR fake")); console.log(sanitizeLogValue("x".repeat(12), 5));

Control characters are escaped, not dropped, so the value stays visible without breaking out of its line. The second argument truncates long values and marks the cut with an ellipsis.

 Where does rateLimitMiddleware find the key it counts by?

It reads context.key. In the transfer pipeline, authenticate sets it to the user id, so each user has their own allowance.

Every request without a key lands in one shared bucket with an allowance of two, so the third unkeyed request is refused, while ada has her own bucket. rejectUnkeyed: true refuses unkeyed requests instead of pooling them.

 What goes wrong if the per-user rate limiter runs before authenticate?

The limiter can only count per user once the user is known. With rejectUnkeyed: true the wrong order fails loudly instead of quietly pooling everyone.

 A MiddlewareRateLimitError is thrown out of a route in @zudojs/http. What does the client get in the published packages?

The error carries retryAfterMs, but not an HTTP status the server honours. The adapter in this lesson checks instanceof MiddlewareRateLimitError and answers 429 with Retry-After.

 The lesson puts validation before the rate limit. What is the benefit, and what is the cost?

A client with a bug gets a clear 400 instead of a 429. The expensive handler is still protected, and the HTTP pipeline's per-IP limiter stops floods of junk.

 Why does authorization run before validation in the transfer pipeline?

Refusing early leaks less and costs less. Validation error messages describe your input format, which an unauthorised caller does not need to see.

 Why is a guard response branded with a symbol instead of being any object with a status field?

A middleware may legitimately return data that happens to have a status key. Only the brand, which request data cannot forge, turns an object into a response.

 In the transfer example, which part knows about HTTP status codes?

Keeping the pipeline transport-independent is what lets a CLI tool or a queue job run it too. The errors carry meaning (401, 403, 400); only the adapter decides how to present them.

 The Task API registers the import pipeline in the container as a singleton. What would go wrong if it created a new pipeline for every request?

The limiter's counts live inside the middleware instance. One shared pipeline means one shared set of counts for all requests in the process.

 Why does the import pipeline compare SHA-256 digests with timingSafeEqual instead of token === expected?

=== can stop at the first different character, which leaks timing. Equal-length digests compared in constant time avoid that, and storing only digests means a leaked configuration does not reveal tokens.
