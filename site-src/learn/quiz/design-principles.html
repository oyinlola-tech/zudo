You must refactor a 300-line checkout function that runs in production and has no tests. What should you do before moving any code?

A characterization test pins current behaviour, right or wrong. Every refactoring step can then be checked against it. Without it, a changed total or a missing e-mail goes unnoticed until a customer reports it.

 After extracting priceOrder, a characterization test fails: the old code returned 145125 kobo, the new function returns 145124. What does this tell you?

A refactoring must not change behaviour. One kobo on every order is real money and a real difference between the receipt and the charge. If the new rounding is actually better, that is a behaviour change to agree on and ship on its own, not a side effect of moving code.

 The tangled placeOrder validates, prices, charges, saves and e-mails. Which part is the safest and most useful to extract first?

Pure code can be moved and tested without fakes, databases or networks. Once it is out, the remaining function is mostly side effects in a clear order, which is easier to handle next.

 Which of these best describes a concern in "separation of concerns"?

Pricing, payment, storage and notification are concerns: each has its own experts and its own reasons to change. Separating them means a pricing change does not touch the payment code.

 Which module description signals low cohesion?

If you need "and" to describe a module, its parts serve different purposes and change for different reasons. Such modules become merge-conflict magnets and hide duplicates.

 VAT is computed in the checkout, the invoice and the receipt. The rate changes and only the receipt is updated, so receipts disagree with charges. What is the design problem?

High cohesion means one idea lives in one place. When the invoice and the receipt call priceOrder, they cannot disagree with the charge, whatever the rate becomes.

 Four modules import an exported array outbox and push to it or clear it. Which kind of coupling is this, and why does it hurt?

Shared mutable globals connect every user of them. Tests that run in the same process see each other's leftovers, and you cannot tell who emptied the array.

 notify(order, true) sends an SMS; notify(order, false) sends an e-mail. What is the better design?

A flag that picks the code path is control coupling: the caller must know how the callee is built inside. A string flag is the same coupling with a different type. Passing the behaviour itself (a notifier) lets new channels be added without editing notify.

 The e-mail function receives the whole order record, including the card number, although it only needs the address and the total. What is the risk?

Passing only what is needed (data coupling) keeps modules independent of each other's record shapes and limits where sensitive data can leak.

 A function does const client = new PaystackClient(KEY) inside itself before charging. Which problem does this cause first?

A function that builds its own collaborators has decided for every caller, tests included. Receiving the gateway as a parameter (dependency injection) moves that decision to the composition root.

 A developer makes status private and adds setStatus(value) that assigns any status. Is the order encapsulated now?

Encapsulation is about protecting invariants. Methods such as markPaid and markRefunded check the current state; a general setter checks nothing.

 Which of these is an invariant of an order?

An invariant is a rule that must be true of the object at every moment. Freezing the lines and computing the price inside Order.create makes this one impossible to break.

 Why does the lesson's Order have a private constructor and a static create method?

Controlling creation is part of encapsulation: every order that exists went through the one door that establishes the invariants.

 Which payment interface is a leaky abstraction?

Returning the provider's own field names forces the caller to understand one provider's format. A second provider with different fields silently breaks the caller, as the Flutterwave example showed.

 Who should decide the shape of the PaymentGateway interface?

The side that uses an abstraction knows what it needs: did it work, a reference for refunds, and whether a failure is retryable. Designing from the provider's side leaks the provider into the service.

 The card was charged, then saving the order fails because the database is down. What should the order service do?

The charge cannot be rolled back like a database transaction, so an explicit undo step (a compensation) is needed. Otherwise the customer has paid for an order the shop does not know about.

 The order is paid and saved, but the e-mail server is down. Where does the lesson put the decision "do not fail the order because of this"?

It is a policy about notifying, not about ordering. As a wrapper it can be applied to any notifier and changed without editing the service.

 Which of these most likely does not need an interface and injection?

Inject what talks to the outside world or must be replaced in tests. A pure function is already easy to test and replace; an interface around it adds names and hides nothing.

 What is the composition root?

Only the composition root knows every concrete choice: which gateway, which store, which notifiers. Tests have their own small composition roots that pick fakes.

 Which is the most practical everyday measure of whether a design is loosely coupled?

Coupling is about change. If a VAT change touches one file and a provider switch adds one file and edits the composition root, the design is doing its job.

 A developer splits a clear 15-line function into seven files of two lines each. Which principle suffers?

Separate by reason to change, not by line count. Over-splitting scatters one concern the same way the VAT rule was scattered.

 A PlaceOrderDto only carries values from an HTTP body into the service. Should it be a class with private fields and guarded methods?

Data that only crosses a boundary is checked once (by validation) and then read. The Order has rules about its lifecycle, so it gets the private state and guarded methods.
