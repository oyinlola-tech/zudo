Which statement describes @zudojs/core best?

The core defines Module/BaseModule and ContextStorage, and createApplication builds a container, configuration, logger and runtime for you. It depends only on @zudojs/errors and @zudojs/constants.

 A project made by zudojs create: which package runs its modules, and where does its BaseModule come from?

The generated src/app.ts calls createRuntime, and the generated modules extend the core's BaseModule. The module contract is shared; the orchestrator differs.

 Why should you check the package of an import like createRuntime or Container?

The names overlap but the APIs do not: @zudojs/runtime's createRuntime(services, options) is not the core's, and the core's Container uses register(token, { useValue }) rather than registerValue.

 What is the difference between a module and a module definition (defineModule)?

Definitions are frozen descriptions. Because the application builds modules from factories, a stopped application can start again with new instances instead of reusing half-stopped ones.

 What is app.state right after await createApplication({ … }) returns?

createApplication initializes the application (and its participants) before returning. It starts nothing unless you pass autoStart: true; you call start().

 Definitions are listed as payments (needs orders), orders (needs inventory), inventory. In which order do the onInitialize hooks run?

The order comes from the dependencies, not from the list. Each module initializes after the modules it depends on; stopping reverses it.

 The orders module declares only inventory. In its hook it calls context.getModuleContext("payments"), and payments is registered. What happens?

Only declared dependencies are reachable, so the declared graph is the real graph. hasModule("payments") answers false for the same reason.

 Why is reaching an undeclared module forbidden rather than allowed "because it is there anyway"?

Declaring a dependency does two jobs: it orders startup and it documents the coupling. Access without declaring would defeat both.

 What is the difference between context.getConfig("orders.maxItems") and context.requireConfig("orders.maxItems")?

Use requireConfig for settings the module cannot run without, so a missing value fails at startup instead of halfway through a request.

 What problem does the execution context solve?

Built on AsyncLocalStorage, it follows the async work started inside run(), so a deep log() call knows its correlation id.

 Inside storage.run(ctx, async () => { … }), which of these does not see ctx automatically?

Async propagation follows promises, timers and callbacks scheduled within the run. Your own data structures are not async resources, so a job stored and run later needs capture() and runSnapshot().

 What does storage.runDerived({ operation: "reserve-stock" }, fn) keep from the current context?

A derived context marks a stage of the same execution. It throws when no context is active, because there is nothing to derive from.

 When should code call storage.require() instead of storage.get()?

get() returns undefined outside a context, which is normal for start-up code. require() turns a missing context into an immediate error.

 const b = a.set(USER, user) where a is a ContextValues. What is true?

Immutable updates mean code that received a never sees it change underneath it, which matters when collections are shared across async work.

 During a request that has a current user in its ContextValues, an event listener starts a new execution with storage.run(newContext, …). Does the listener see the request's user?

Carrying values into new work must be a decision: use runDerived, runWithValues or a snapshot.

 Why is createContextKey<CurrentUser>("current-user") better than using the string "current-user" as a key?

Two libraries can both name a key "user"; two symbols are always different. And the type parameter makes the lookup type-safe.

 A cart provider is registered as "scoped" in the application's container. What do two concurrent requests get, and what happens outside any request?

createApplication's container uses the current execution context as the scope. Failing outside any scope prevents one cart being shared by every customer.

 A module fails during start(). The application is failed. How do you try again?

start() from failed throws InvalidStateError. stop() cleans up, including participants, and a stopped application can start again.

 In the published core, database fails to initialize, and orders (which depends on it) never initialized. Which onDestroy hooks run in the rollback?

That is how the published version behaves, so every onDestroy must be safe for a module that never initialized: check that a resource exists before releasing it.

 start() rejects with RuntimeInitializationError: Runtime module initializing failed. Where is the useful information?

The wrapper's message is generic. Log the cause chain, or you will read "initializing failed" without knowing that the database refused the connection.

 Why does a test pass signalTarget to createApplication?

With a fake target, the runtime registers its listeners there. The test calls them, checks the modules stopped, and the test runner keeps running.

 Why give each test application its own contextStorage: createContextStorage()?

getDefaultContextStorage() is shared on purpose, so all framework pieces agree in a normal app. Isolation is something you opt into.

 A handler logs logger.info("login", { email, password }) with the core's ConsoleLogger created with default options. What appears in the log?

Redaction is opt-in for the core logger. createLogRedactor() replaces values under sensitive names such as password, secret and token.

 What is the default startup deadline of the core's runtime, and what is the risk?

startup.timeoutMs defaults to 0. Set a limit so a stuck start fails with RuntimeTimeoutError and your process manager can react.
