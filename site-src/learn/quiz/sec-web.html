Why can a page on another site make Ada's browser send a transfer request that the wallet accepts?

This is ambient authority: the credential travels with the request automatically. The other site never sees the cookie and never reads the answer; it only needs the request to be sent.

 The session cookie is HttpOnly. What does that do against CSRF?

HttpOnly protects the cookie's value from page JavaScript (useful against XSS). CSRF does not need the value, only that the browser sends it. SameSite is the cookie attribute that controls sending.

 A session cookie has SameSite=Lax. On which request started by another site does the browser still send it?

Lax sends the cookie on top-level GET navigations so links from email still arrive logged in. That is why a GET handler must never change data.

 Which cookie is the best fit for SameSite=Strict?

Strict is never sent on requests from other sites, not even link clicks. That is the safest choice for high-value actions, at the cost of users following a link arriving without that cookie.

 Why is SameSite not enough on its own?

A request from blog.wallet.example is same-site for app.wallet.example. If a subdomain runs untrusted code or can be taken over, SameSite does not help. Add a token or an origin check as a second layer.

 Why does a CSRF token in a hidden form field stop the forged request?

The same-origin policy stops the other site from reading your form page. Without the per-session secret, the forged request fails the server's token check.

 A server issues one CSRF token per session but accepts any token it has ever issued. What can an attacker do?

A token proves something only if it is checked against this session. Otherwise the attacker's own token works in the victim's request.

 What makes Origin and Sec-Fetch-Site useful for CSRF checks?

They are controlled by the browser. A request with Sec-Fetch-Site: cross-site or a foreign Origin can be refused before the body is read. A non-browser client can send anything, but it also does not hold the victim's cookie.

 An API authenticates with Authorization: Bearer …, added by the app's own JavaScript. No cookies are used. Does it need CSRF tokens?

CSRF relies on credentials the browser adds automatically. A bearer token added by your own script is not sent by requests other sites start. The risk returns if the token moves into a cookie.

 The wallet test sends a request with the correct Origin but no token. Why test that, if the origin check already blocks real attacks?

With one test for the whole attack, a refactor could delete a whole layer and the test would still pass thanks to the other layer. One test per layer keeps every layer honest.

 A server copies the request's Origin into Access-Control-Allow-Origin and sends Access-Control-Allow-Credentials: true. What does this allow?

The browser's rule is "exact origin plus credentials true". Reflection satisfies it for every origin, so every site can read the user's data, and a token read from a response defeats the CSRF token too.

 Why should a server add Vary: Origin when its CORS headers depend on the origin?

Vary tells caches which request headers change the response. Without it, a cache could store the answer for a trusted origin and replay it for a different one.

 Which statement about CORS is true?

CORS is a browser rule for reading. Simple requests (like form posts) are still sent, and non-browser clients ignore CORS completely.

 Why should an allow-list never contain the origin null?

The null origin does not identify anyone. Any page can create a sandboxed frame whose requests carry Origin: null.

 A search page puts the q query parameter into its HTML without encoding. Which kind of XSS is that?

The data comes from the current request and goes straight back in the server's HTML, so whoever controls the link decides the markup. Stored XSS comes from saved data; DOM XSS happens in page JavaScript.

 The server sends a static page. Its script does el.innerHTML = location.hash.slice(1). Which kind of XSS is this, and where is it fixed?

The fragment is never even sent to the server. The page's own code moves a source (the URL) into a markup sink, so the fix is in that code.

 Why does an XSS bug defeat CSRF tokens and CORS?

The same-origin policy protects the attacker's script once it runs inside your origin. That is why output encoding and CSP matter so much.

 A profile shows <a href="${website}">. The value is HTML-escaped. What is still missing?

Escaping stops the value from leaving the attribute, but javascript:… contains no characters to escape and still runs when clicked. URL contexts need a scheme check.

 Product descriptions come from a rich-text editor and must keep bold text, lists and links. What should the server do?

Escaping would show the markup as text. Hand-written regex filters miss event attributes, odd nesting and parser quirks. A sanitizer parses the HTML and keeps only what the allow-list names.

 What is the role of a Content-Security-Policy against XSS?

Encoding is the fix; CSP limits the damage of the encoding bug you have not found yet.

 Which of these nonce setups protects the page?

The attacker must not be able to predict the nonce of the page the victim will load. A fixed or guessable nonce can simply be copied into the injected tag. 'unsafe-inline' would allow inline scripts anyway.

 What can a CSP in a <meta> tag not do that the header can?

Browsers ignore frame-ancestors, report-uri and sandbox in meta policies. Send the policy as a header.

 You are adding a strict CSP to an old app with many inline scripts. What is the safe rollout?

Report-Only makes the browser report violations without blocking, so you find your own inline scripts before users see broken pages.

 Which header stops the browser from treating an uploaded .txt file as HTML or script?

nosniff makes the browser trust the declared Content-Type instead of guessing from the content.

 What does naming the session cookie __Host-sid add?

The prefix is enforced by the browser. It locks the cookie to exactly your host, which blocks cookie injection from other subdomains.
