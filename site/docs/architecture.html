Architecture Overview

Five-layer architecture with clear dependency direction.

FIVE LAYERS DEPENDENCY DIRECTION MODULAR

Overview

Zudo is designed around a layered, modular architecture where each package owns a single concern and depends only on packages below it in the hierarchy. This prevents circular dependencies, enables tree-shaking, and makes it trivial to swap implementations.

The framework is built on four pillars: a DI Container for dependency resolution, a Lifecycle Manager for startup/shutdown orchestration, a Module System for composable application structure, and an Event Bus for decoupled communication.

KEY PILLARS

  • • Dependency Injection — Token-based container for all service resolution
  • • Lifecycle Management — State machine for startup, readiness, and shutdown
  • • Module System — Composable, dependency-aware application structure
  • • Event-Driven — Decoupled communication via middleware-pipeline events

Architecture Layers

Zudo's packages are organized into four layers. Dependencies flow strictly downward — a package may only depend on packages in the same layer or below it.

Key Principles

Interface-First Design

Every package defines its public API as TypeScript interfaces before implementing them. Consumers depend on interfaces, not concrete classes, making it easy to swap implementations or create test doubles.

Dependency Injection

All service resolution goes through the DI container. Services are registered with tokens (strings, symbols, or class tokens) and resolved at runtime. This eliminates global state and enables clean testing.

Configuration Layering

Configuration is resolved from multiple sources in priority order: environment variables, config files, defaults. Sensitive values are auto-redacted. No hardcoded configuration values in source code.

Event-Driven Communication

Packages communicate through events via a middleware-pipeline event bus. Handlers are registered on the emitter (not the registry). This decouples modules and enables cross-cutting concerns like logging and metrics.

Core Components

DI Container

Token-based registration and resolution. Supports singletons, factories, and value providers. Scoped containers for request isolation.
