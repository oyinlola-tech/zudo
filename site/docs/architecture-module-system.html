Module System

Modules as self-contained units of functionality with explicit boundaries.

MODULES BOUNDARIES ENCAPSULATION

Overview

Zudo's module system lets you organize your application into self-contained, composable units. Each module declares its dependencies, provides services to the DI container, and participates in the application lifecycle through well-defined hooks.

Modules are resolved in topological order based on their declared dependencies, ensuring that each module's dependencies are available before it initializes.

WHY MODULES?

  • • Encapsulation — Each module owns its services and internal state
  • • Reusability — Modules can be shared across applications
  • • Testability — Modules can be tested in isolation
  • • Lazy Loading — Modules can be loaded on demand

Module Definition

A module is defined by implementing the Module interface. Each module has a unique name, optional dependencies, and lifecycle hooks.

import { Module, ModuleContext } from "@zudojs/core"; const AuthModule: Module = { name: "auth", dependencies: ["database", "config"], async initialize(ctx: ModuleContext) { const config = ctx.resolve("config"); const db = ctx.resolve("database"); // Register services ctx.provide("authService", () => new AuthService(config, db)); ctx.provide("tokenService", () => new TokenService(config)); }, async start() { console.log("Auth module started"); }, async stop() { console.log("Auth module stopped"); } };

Module Interface

interface Module { name: string; dependencies?: string[]; initialize(ctx: ModuleContext): Promise<void>; start?(ctx: ModuleContext): Promise<void>; stop?(ctx: ModuleContext): Promise<void>; destroy?(ctx: ModuleContext): Promise<void>; }

Module Registration

Modules are registered with the application before initialization. The runtime resolves dependencies and initializes modules in the correct order.

import { createApp } from "@zudojs/core"; const app = createApp(); // Register modules app.module(DatabaseModule); app.module(ConfigModule); app.module(LoggerModule); app.module(AuthModule); app.module(HttpModule); // Initialize and start await app.initialize(); // Resolves deps, calls initialize() await app.start(); // Calls start() on all modules // Graceful shutdown process.on("SIGTERM", () => app.shutdown());

Dependency Resolution

The module system uses topological sorting to determine initialization order. If Module A depends on Module B, Module B is always initialized first. 

Given these dependencies:

ConfigModule     → (no deps)
DatabaseModule   → [config]
LoggerModule     → [config]
AuthModule       → [database, config]
HttpModule       → [auth, logger]

Initialization order:

1. ConfigModule        ← no dependencies
2. DatabaseModule       ← config ready
3. LoggerModule         ← config ready
4. AuthModule           ← database + config ready
5. HttpModule           ← auth + logger ready

CIRCULAR DEPENDENCIES

Circular module dependencies will cause an error at initialization time. If you detect a cycle, refactor by extracting shared logic into a separate module or using an event-driven approach.

Module Lifecycle Hooks

Each module can implement four lifecycle hooks that are called in order during the application lifecycle:

initialize()

Called during app initialization. Register services with the DI container, set up connections, validate configuration. Dependencies are already initialized.

start()

Called after all modules are initialized. Start background tasks, open connections, begin accepting work. The application is now ready.

stop()

Called during graceful shutdown. Stop accepting new work, finish in-flight operations, close connections. Called in reverse dependency order.

destroy()

Called after stop() completes. Release all resources, clear timers, disconnect from external systems. Final cleanup.

Module Context

The ModuleContext provides access to the DI container, other modules, and application-level utilities:

interface ModuleContext { // Resolve a service from the DI container resolve<T>(token: string): T; // Register a service with the DI container provide(token: string, factory: () => unknown): void; // Access another module's public API getModule(name: string): Module | undefined; // Application config readonly config: AppConfig; // Application logger readonly logger: Logger; }

Best Practices

1. Keep Modules Small and Focused

Each module should own a single concern. If a module grows beyond ~200 lines of initialization logic, consider splitting it into sub-modules.

2. Declare All Dependencies Explicitly

Never assume a module is initialized. Always declare dependencies in the dependencies array so the runtime can resolve the correct order.

3. Use Interface Tokens

Register services using string or symbol tokens, not class references. This allows swapping implementations without changing consumers.

4. Handle Errors in initialize()

If initialization fails, throw a descriptive error. The runtime will abort startup and log the failure with the module name.

5. Clean Up in stop() and destroy()

Always release resources in reverse order. Close database connections, clear intervals, remove event listeners. Use try/catch to prevent one module's cleanup from blocking others.
