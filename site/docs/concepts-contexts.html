Execution Contexts

AsyncLocalStorage-based context propagation across async boundaries.

CONTEXT ASYNCLOCALSTORAGE PROPAGATION

Overview

Zudo uses AsyncLocalStorage to propagate execution context across async call chains. This means request-scoped data (user identity, correlation IDs, tenant info) is available anywhere in the call stack without explicit parameter passing.

Architecture Position

Contexts are a runtime primitive used by @zudojs/core, @zudojs/tenancy, @zudojs/transactions, and @zudojs/observability.

What Is Execution Context

Execution context is a data envelope that travels with every request through your application. It carries metadata that services need without cluttering function signatures.

// Context carries request-scoped data interface ExecutionContext { requestId: RequestId; // Unique request identifier correlationId: CorrelationId; // Traces across services userId?: UserId; // Authenticated user tenantId?: TenantId; // Multi-tenant context timestamp: Timestamp; // Request start time }

AsyncLocalStorage Usage

Node.js AsyncLocalStorage creates a context that persists across all async operations within a single request. Zudo wraps this in a ContextProvider.

import { ContextProvider } from "@zudojs/core"; const ctx = new ContextProvider(); // Run code within a context await ctx.run({ requestId: "req-123" }, async () => { // Any code here can access the context const current = ctx.get(); console.log(current.requestId); // "req-123" // Even nested async calls await someService(); // ctx.get() still works here });

Context Providers & Consumers

Providers set context at request boundaries. Consumers read context anywhere in the call chain.

Providers
  • HTTP middleware
  • Message handlers
  • Event listeners
  • CLI command runners
Consumers
  • Services and repositories
  • Logger (auto-injects requestId)
  • Database clients (audit trails)
  • External API clients

Request-Scoped Data Patterns

Common patterns for using execution context in Zudo applications.

// Pattern 1: Auto-logging with context class UserService { constructor(private readonly logger: Logger) {} async getUser(id: UserId): Promise<User> { // Logger automatically includes requestId from context this.logger.info("Fetching user", { userId: id }); return this.repo.findById(id); } } // Pattern 2: Tenant isolation async getProjects() { const ctx = contextProvider.get(); // Repository automatically filters by tenantId return this.projectRepo.findAll({ tenantId: ctx.tenantId }); } // Pattern 3: Audit trail async updateUser(id: UserId, data: Partial<User>) { const ctx = contextProvider.get(); await this.repo.update(id, data); await this.auditLog.record({ action: "user.update", userId: ctx.userId, requestId: ctx.requestId, }); }

Why Contexts Matter

  • 01 No parameter drilling — context is available everywhere without passing it through 10 function layers.
  • 02 Request tracing — every log, metric, and database query carries the request ID automatically.
  • 03 Tenant isolation — multi-tenant apps get automatic data filtering without service-level boilerplate.
  • 04 Audit compliance — who did what, when, and from which request — all captured automatically.
